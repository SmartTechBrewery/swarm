### Toolchain & persistence

### SCM layer

**Verification clarification.** Bitbucket's and GitLab's runtime wiring is unit-verified against the real registered manifests, but no real Bitbucket Cloud repository or gitlab.com project has yet been driven through the pipeline end to end. Both commit→pull-request lookups are mocked, so production verification must confirm that Bitbucket accepts the normalized 12-character revision on `/commit/{revision}/pullrequests` and that gitlab.com answers `commits/:sha/merge_requests` for a branch pipeline's commit under the reviewer token's scope. GitHub checks skip that lookup only when a `check_suite` payload already names a pull request; unresolved branch and default-branch checks perform it.
- The SCM provider self-registers through a manifest + registry loaded from the same canonical entrypoint as the PM one (`src/integrations/entrypoint.ts`), behind the provider-neutral `SCMProvider` contract (`src/scm/types.ts`) that `GitHubSCMIntegration` implements — so a consumer can resolve the whole contract by id without importing the concrete class. **Inbound now runs on it (#385):** the webhook receiver mounts one route per registered manifest and delegates header interpretation, signature verification, event parsing, and comment loop prevention to the provider; the durable queue envelope carries a provider id plus a normalized, provider-neutral event (`ScmEvent`, `src/scm/events.ts`, which also reads pre-#385 rows so in-flight dispatches survive a deploy); and the worker resolves the provider once at its composition root and injects it into the trigger context. **Outbound now runs on it too (#386):** the delivery-provider default in the five delivery-owning phases, the worker's control-plane local delegate, its run-row PR-title read and its phase-failure/interrupted-job PR comments, the durable merge executor's default merge capability, and the router's server-side worker-delivery default all resolve through the registry — by the durable job's own `providerId` where one is carried, otherwise by project (`requireProjectSCMProvider`). **That project-scoped lookup now selects (#478):** a project states its provider in the optional `scm` config field — the SCM twin of `pm.type`, persisted as `projects.scm_type` — so two or more runtime-ready providers can be registered at once with each project's operations routed to its own; a project that states none resolves to the sole runtime-ready provider — a back-compat path that stopped resolving with #618, when Bitbucket became the second ready provider, so **every project must now state `scm` explicitly** (see the migration note below); and an unregistered id, an id that is registered but not runtime-ready, or no id at all with no single runtime-ready provider each throw loudly and name the project and what it asked for, rather than falling back onto another provider. **The DB-free federated worker joined too (#462),** closing the outbound migration: the contract gained `operatorDeliveryProvider(repo, credential)` — a delivery provider authenticated as the worker operator's *own* account rather than a per-project persona, which is what a worker holding no secret store needs (ADR-003 §2 / ADR-004 §3) — GitHub implements it over the existing `operator-delivery.ts`, and `src/transport/assignment-execution.ts` resolves it by project, with `src/transport/connect-entry.ts` importing the integrations entrypoint so the remote worker's registry is populated (it still opens no Postgres/Redis connection). Operator-credential *env* resolution (`SWARM_OPERATOR_GH_TOKEN`) deliberately stays on the worker entry, since that credential is the operator's rather than the project's. Two concrete provider-named reaches remain on purpose: the dashboard's pasted-secret validation route (`src/api/routers/scm.ts`), which runs before there is a project to resolve a provider from and therefore holds one `verify…` procedure per provider (GitHub's, plus Bitbucket's since #618), and the GitHub Projects PM provider's webhook verifier delegating to the GitHub SCM HMAC check (`src/integrations/pm/github-projects/webhook.ts`) — one webhook, one secret. Its other two reaches are gone as of issue #537: board authentication and the board's loop-prevention identity are now the PM provider's own declared credential (`src/integrations/pm/github-projects/credentials.ts`).
- **Bitbucket is implemented and runtime-reachable (#296's four phases, made reachable by #618).** `src/integrations/scm/bitbucket/` adds a credential-scoped Bitbucket **Cloud** client (`AsyncLocalStorage`, plain `fetch` — no new dependency), persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN`, reviewer from a project credential reference — the provider-neutral pair GitHub then shared, and Bitbucket's own `credentials.scm.bitbucket.reviewer` since issue #628), persona identity + loop-prevention helpers, and `BitbucketSCMIntegration implements SCMProvider` with **no method stubbed**. **Webhook ingress works (#455, phase 2 of 4):** `webhook.ts` verifies `X-Hub-Signature` as `sha256=<hex>` over the raw body through the shared timing-safe `verifyHmac` (failing closed, since Bitbucket omits the header for a secret-less hook), reads the event from `X-Event-Key` and the dedup identity from `X-Request-UUID`, and normalizes the eleven event keys SWARM acts on (PR lifecycle, approval / changes-requested, PR comment, commit status) into the neutral `ScmEvent` — everything else returns `null`. Two provider gaps are handled explicitly: Bitbucket has no review object, so `reviewId` is synthesized from PR + verdict + account `uuid` + head SHA (a format the issue-#235 verdict ledger keys on, so it must stay stable), and a `commit_status` payload carries no PR association at all, so `workItemId`/`prBranch` need a commit→PR lookup at whichever ingress layer serves the route. **The reads now work too (#456, phase 3 of 4):** `pull-requests.ts` implements PR details, title, merge state, participant approvals, the open-PRs-for-a-base conflict candidates (server-side `q=` filter, forks dropped), the aggregate commit build status (deduped by status `key`, newest `updated_on` wins, so a re-run's stale failure can't sink a green commit), and the commit→PR lookup — with `PullRequestDetails.mergeable` permanently `null`, since Bitbucket Cloud exposes no mergeability flag; the conflict handler reads that as "unknown" and exhausts its bounded rechecks rather than ever calling a PR cleanly mergeable. **The writes complete the contract (#457, phase 4 of 4):** `writes.ts` posts comments idempotently on the shared `<!-- swarm-delivery:… -->` marker (now `deliveryMarker` in `src/scm/swarm-origin.ts`, so the two providers cannot drift), maps a review verdict onto Bitbucket's `approve` / `request-changes` participant endpoints — applying the verdict *before* the marker comment, since the comment is the retry anchor and Bitbucket has no review object to key on, which also makes that comment's id the neutral review id — creates pull requests, and merges directly (repository-default strategy, source branch left alone). `deliveryProvider` supplies the delivery seam per persona: commit identity from the account `nickname` plus its confirmed primary email, falling back to `<nickname>@users.noreply.bitbucket.org` when the credential lacks the `email` scope (a commit then shows the right name but stays unattributed); PR find/create; and the same expected-SHA `git push` GitHub uses, with the credential in a `GIT_CONFIG_*` extraheader rather than argv. `mergePullRequest` never throws: because Bitbucket's merge endpoint takes no expected-head parameter, a re-read of current state *is* the protection (already merged → `merged`; moved head, draft, closed, changes-requested, or dismissed approval → `not-eligible`), and 409/555 → `not-ready`, 403 or a named merge-check refusal → `policy-blocked`, anything else → `provider-error`. A multi-provider conformance suite (`tests/unit/integrations/scm/scm-conformance.test.ts`) now runs over every registered manifest and asserts no method is a stub. **The wiring landed with #618**, the issue that took ownership of the step #457 left behind: the manifest declares `runtimeReady: true`, so the receiver mounts `/bitbucket/webhook` (GET ping + POST delivery) from the same loop that mounts GitHub's, and `requireProjectSCMProvider` routes a project that sets `"scm": "bitbucket"` there. So **a Bitbucket project now runs end to end**, with GitHub projects untouched. The `commit_status` gap closed there too, and neutrally: `SCMProvider` gained `listPullRequestsForCommit`, implemented by all three providers, and the receiver completes a `checks` event that names no pull request by adopting the first **open** candidate for its commit — skipped entirely for GitHub, whose `check_suite` payload already names its pull requests, and failing open (log + enqueue unresolved, where it matches no trigger) rather than 500'ing a delivery neither provider redelivers on its own.
- **GitLab is implemented and runtime-reachable (#295's four phases, made reachable by #619).** `src/integrations/scm/gitlab/` adds a credential-scoped GitLab**.com** REST v4 client (`AsyncLocalStorage`-bound token, plain `fetch` — no new dependency, `PRIVATE-TOKEN` auth with no credential-form branch since personal/group/project tokens all authenticate and resolve `GET /user` identically, a `GitLabApiError` carrying the same `status` field GitHub's and Bitbucket's merge classifiers read, and offset pagination that follows the `x-next-page` header under a `MAX_PAGES` bound, cycle detection, and a numeric-cursor check — GitLab's cursor is a page *number* appended to a constant base rather than a server-supplied URL, so there is no off-origin link to reject as Bitbucket's paginator must), persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_GITLAB_TOKEN`, reviewer from a project credential reference — the provider-neutral pair then shared, and GitLab's own `credentials.scm.gitlab.reviewer` since issue #628 — with `repo` doubling as GitLab's URL-encoded `namespace/project` path), persona identity + case-insensitive loop-prevention helpers on the GitLab `username` behind the same 60s per-project TTL cache, and `GitLabSCMIntegration implements SCMProvider` with **no method stubbed**. **Webhook ingress works (#483, phase 2 of 4):** `webhook.ts` reads the event from `X-Gitlab-Event`, the dedup identity from the per-delivery `X-Gitlab-Event-UUID` (never the per-*configuration* `X-Gitlab-Webhook-UUID`), and authenticates the delivery by comparing `X-Gitlab-Token` against the project's webhook secret (`credentials.scm.gitlab.webhookSecret` since issue #628) in constant time, failing closed on an absent, empty, or mismatched token — GitLab's own mechanism is a shared secret token, so unlike GitHub's and Bitbucket's HMAC this authenticates the *sender* and not the body; GitLab 19.0's Standard-Webhooks signing tokens would close that gap but need the `verifyWebhookSignature` contract widened (the signed message uses `webhook-id` / `webhook-timestamp` headers it never sees), so they are a recorded follow-up rather than this phase; their other prerequisite — a per-provider secret reference, since a GitLab-minted `whsec_…` key cannot be the operator-chosen secret the PM webhook shared — landed with issue #628. It normalizes merge-request lifecycle, approval/unapproval, merge-request notes, and pipelines into the neutral `ScmEvent`; everything else — issues, pushes, tags, wikis, system notes, notes on non-merge-request targets, and a body whose `object_kind` contradicts the header — returns `null`. Two provider gaps are handled explicitly: GitLab exposes no review object, so `reviewId` is synthesized as `<iid>:<verdict>:<user id>:<head SHA>` (a format the issue-#235 verdict ledger keys on, so it must stay stable), and it has **no "request changes" merge-request action** — verified against GitLab 19.1's webhook reference, whose action vocabulary is `open`/`close`/`reopen`/`update`/`approval`/`approved`/`unapproval`/`unapproved`/`merge` — so that verdict is derived from the *acting* reviewer's own `reviewers[].state === 'requested_changes'`; the limitation is that a later `update` by the same reviewer, while that state still stands, reads as the same verdict again (the ledger's two-verdict cap absorbs it while the head is unchanged). A branch pipeline carries no merge request at all, so `workItemId`/`prBranch` stay unset and phase 3's commit→merge-request lookup is what ties such an event back to one, and the pipeline status vocabulary lives in `pipelines.ts` so an event and an API read never spell one pipeline two ways (an *unrecognized* status is deliberately non-terminal, so the aggregate decision defers rather than judging a pipeline it doesn't understand). **The reads work (#484, phase 3 of 4):** `merge-requests.ts` implements the four contract reads over the phase-1 client with the same persona defaults the other two adapters use (merge request → reviewer, title → implementer, aggregate checks → reviewer, conflict candidates → implementer), and reuses `pipelines.ts` unchanged for commit statuses since GitLab spells them with the pipeline vocabulary. `PullRequestDetails.mergeable` carries GitLab's real tri-state — unlike Bitbucket's permanent `null`, so the conflict-resolution side-car actually decides here: `merge_status` is preferred because it is the *git-only* signal the contract's `mergeable` means (deprecated in 15.6, hence a documented `detailed_merge_status` fallback that also covers the undocumented `cannot_be_merged_recheck`), where `conflict`/`commits_status` → `false`, `checking`/`preparing`/`unchecked` → `null`, and every other blocker (`not_approved`, `ci_still_running`, `draft_status`, `need_rebase`, …) → `true`, because `mergeable` means "no merge conflict" and not "policy satisfied". `baseSha` is `diff_refs.base_sha`, the **merge base** rather than GitHub's target-branch tip, which is the stable value the conflict claim key needs; a missing `iid`, branch, `sha`, or base SHA throws rather than being replaced by a stand-in, since those are exact-match key material. Conflict candidates filter server-side, drop forks, then cost one single-merge-request read per survivor: GitLab's *list* response omits `diff_refs` and serves a cached `merge_status`, while reading a single merge request is itself what asks GitLab to recompute mergeability — which is also what makes the trigger's bounded recheck converge. Commit statuses dedupe by `name` keeping the newest `finished_at ?? created_at`, so a re-run's stale failure can't make a green commit look failed. Two reads exist for phase 4's merge-eligibility recheck rather than for a caller of their own (the merge state — which also derives `changesRequested` from `detailed_merge_status`, the only place one merge-request read exposes a reviewer's blocking verdict — and standing approvals mapped to GitHub's `APPROVED` spelling; GitLab pins an approval to no commit and its approvals entity carries no SHA, so each verdict carries the merge request's current head and is only exactly right when the project resets approvals on new commits; approvals are Free while approval *rules* are Premium, and a changes-requested verdict lives on `reviewers[].state`). **The writes complete the contract (#485, phase 4 of 4):** `writes.ts` posts merge-request notes idempotently on the same shared `<!-- swarm-delivery:… -->` marker (skipping `system: true` notes, since GitLab files its own activity entries into the same listing and one of them quotes the note it describes), and maps a review verdict onto `approve` — passing `sha` so GitLab refuses an approval against a moved head, the pinning Bitbucket cannot do — or, for `request-changes`, onto `unapprove` plus the findings note, because a reviewer's `requested_changes` state has no REST endpoint on GitLab 19.1's surface at all; the verdict goes out *before* the marker note, which is what makes the note the retry anchor, and the note's id is the neutral review id since GitLab has no review object either. GitLab refuses a *redundant* verdict rather than absorbing it (approve → 401 once the account has approved, unapprove → 404 with nothing to withdraw), so exactly those two statuses are tolerated — otherwise every retry after a landed verdict and a failed note POST would strand the reviewer's findings unposted. `deliveryProvider` supplies the delivery seam per persona: commit identity from a single `GET /user` (both `username` and `email` in one request, unlike Bitbucket's second call), falling back to `<username>@users.noreply.gitlab.com` when the token's scope withholds the address — a commit then shows the right name but stays unlinked, since GitLab matches a **verified** account email; merge-request find/create; and the same expected-SHA `git push` the other two use, with the token in a `GIT_CONFIG_*` extraheader rather than argv, framed as Basic under GitLab's reserved `oauth2` user. `mergePullRequest` never throws: the direct merge is pinned to the approved head with `sha`, the full pre-merge recheck runs on every attempt (already merged → `merged`; moved head, draft, closed, changes requested, or dismissed approval → `not-eligible`), and GitLab's own third status table maps 409 → `not-eligible` (the pinned head moved inside the recheck window, so a fresh review is required), 405/422/406 → `not-ready`, 401/403 → `policy-blocked` (GitLab documents 401, not 403, for the merge permission refusal), anything else → `provider-error`; nothing maps to `unsupported`, since merge trains refuse with 405 until the required pipeline is green and then accept the direct merge. `operator-delivery.ts` supplies the DB-free worker's operator-credential seam with `submitReview` throwing, since reviewer verdicts belong to the control plane. Registration lands here too: `gitlab/index.ts` registers with `runtimeReady: false` and `listSCMProviders()` now returns `['github', 'bitbucket', 'gitlab']` — deliberately not before, because the conformance suite asserts that no *registered* provider stubs a contract method (`ai/TESTING.md` frames that as the gate on the third provider), so passing that gate was this phase's job rather than something an earlier phase exempted itself from. **Reachable since #619:** the manifest declares `runtimeReady: true`, so `requireProjectSCMProvider` routes a project stating `"scm": "gitlab"` here and the receiver mounts `/gitlab/webhook` from the same per-manifest loop that mounts GitHub's and Bitbucket's — **a GitLab project runs end to end.** Nothing shared had to be built for it: `listPullRequestsForCommit` landed with #618, so a **branch** pipeline (which names no merge request at all) gets its `workItemId`/`prBranch` from the receiver's neutral commit→merge-request read, while a merge-request pipeline skips that read because the payload already names one. Still out of scope: the GitLab 19.0 signing-token upgrade (see the next bullet), self-managed GitLab hosts, GitLab subgroup paths, and GraphQL.
- **The webhook trade-off #619 accepted, not deferred again.** Serving `/gitlab/webhook` makes GitLab's *sender* authentication live: `X-Gitlab-Token` carries the operator-chosen secret echoed verbatim, so unlike GitHub's and Bitbucket's HMAC nothing covers the body's integrity in transit. Judged **acceptable as-is** rather than a prerequisite — it is GitLab's own long-standing mechanism, `verifyGitLabWebhookToken` fails closed on an absent, empty, or mismatched token and compares in constant time, and an attacker able to tamper with or replay a delivery has already broken the TLS the secret itself travels under. GitLab 19.0's Standard-Webhooks signing tokens stay the recorded follow-up: they need `SCMProvider.verifyWebhookSignature` widened for the `webhook-id`/`webhook-timestamp` headers it never sees **and** a per-provider secret reference, since a GitLab-minted `whsec_…` key cannot be the operator-chosen secret the same project's PM webhook shares. The decision is recorded at the flag itself (`src/integrations/scm/gitlab/index.ts`).
- **SCM credentials are per provider, storage through UI (#628 then #632).** A project used to hold one shared `credentials.reviewer` / `credentials.webhookSecret` pair, so storing GitLab's reviewer token overwrote GitHub's in place and the Source Control tab showed one provider's fields whatever its selector said. #628 moved storage and resolution to `credentials.scm[<providerId>][<role>]` — each provider's own conventional reference name declared on `SCMProviderManifest.credentialRoles`, resolution as `(project, providerId, role)` reading only the provider it was asked for, and a migration (SQL backfill + parse-time adoption) that files every existing project's reference names under the provider it runs on, verbatim, so nothing is renamed and no secret is re-entered. #632 rewired the API and the tab: `projects.credentials.list`/`set`/`delete` take `(providerId, role)` and resolve the store key **server-side** (the browser no longer names one, which is what the overwrite depended on), the tab queries per selected provider — pick GitLab and its own fields appear, unconfigured, under `GITLAB_*` reference names, while GitHub's stored secrets stay put and come back on switching back — and every field label is per-provider copy, since "Reviewer PAT" is GitHub's word for a Bitbucket app password and a GitLab access token. Each field names the key the project *resolves* the role through, not the manifest's conventional one: for any project created since #290 those genuinely differ, and naming the convention would point an operator at a variable nothing reads.
- **The worker operator's SCM credential lives in the DB, per worker per provider (#765, phase 1/3).** It used to be one process env var read unconditionally at worker startup (`SWARM_OPERATOR_GH_TOKEN` → `resolveOperatorGitHubToken`), which meant no validation, no rotation flow, nothing stopping a duplicate `.env` key from silently shadowing the intended value — production hit exactly that, with a revoked duplicate failing every Planning/Implementation run on one worker with no board-visible cause — and a hardcoded GitHub credential regardless of `project.scm`. It is now a `worker_scm_credentials` row keyed by `(workerId, scmProviderId)`, encrypted with the same AES-256-GCM primitive `project_credentials` uses and bound to **both** parts as AAD; resolved control-plane side at dispatch by the provider the project actually names (`requireProjectSCMProviderId`, never `project.scm ?? 'github'`) and carried on the assignment frame as `TaskAssignment.operatorCredential`, since the worker is DB-free. A missing credential fails the dispatch before anything is pushed, naming the worker and the provider; an invalid one is re-framed at the worker's own seam rather than surfacing as the provider's generic identity error. There is **no** env fallback left on that path — `resolveOperatorGitHubToken` is deleted, and `SWARM_OPERATOR_GH_TOKEN` is now router-only (three control-plane readers, listed in ai/ARCHITECTURE.md). Rotation takes effect on the next dispatch with no worker restart. Write surface is `swarm workers set-scm-credential`, joined by the dashboard form below (#766, phase 2/3). **Phase 3/3 (#767) closed the discoverability gap**: `swarm workers register` now says in its success output and its `--help` that a freshly registered machine has no SCM identity and cannot run a phase until this credential is set, and points at both write surfaces — the owner's dashboard card at `/workers/<worker-id>`, or `set-scm-credential` for someone else's machine. It deliberately gained no token flag or prompt: a worker's provider is a property of its enrollments and is unknown at registration time, so asking there would bake in the GitHub assumption the SCM layer avoids. **`swarm workers register-and-enroll` (#786) is the third write surface and the recommended onboarding path** — one command that registers, credentials and enrolls a new machine and prints the exact line that starts it, prompting for one provider's secret only because it resolves that provider from the target project.
- **Configuring a GitLab project from the dashboard (#619).** GitLab joins the Source Control tab's provider selector and the project-create dialog (`SCM_PROVIDERS`, `dashboard/src/lib/credentials.ts`), so a project goes onto GitLab without hand-editing `swarm.config.json`, and the tab's copy switches with it — including the webhook line, which names a *secret token* rather than an HMAC key because that is what GitLab actually configures. `scm.verifyGitLabToken` joins `verifyGithubToken`/`verifyBitbucketCredential` so a pasted token can be checked against the account it resolves to before saving. The per-provider credential-role UI this bullet deferred landed with #632 (above). Still deferred: any webhook-registration automation — the GitLab project hook is still created by hand, pointed at `/gitlab/webhook` with the project's secret token and its Merge request, Comment, and Pipeline events enabled.
- **GitLab phase-3 aggregate details:** conflict-candidate list reads request `with_merge_status_recheck=true` and bound their required per-merge-request refreshes to batches of ten, because the list response still omits `diff_refs.base_sha`. Commit statuses marked `allow_failure`, including optional manual jobs, map to completed/skipped regardless of their raw status: GitLab excludes them from its pipeline result, so SWARM must not let them fail or defer the aggregate. Keeping them visible as skipped means an all-advisory pipeline remains reviewable.
- **Migration — every project must now name its SCM provider (#618).** With GitHub, Bitbucket, and (since #619) GitLab all runtime-ready, the "no `scm` set → the sole runtime-ready provider" fallback no longer resolves: `requireProjectSCMProvider` throws, names the project, and lists the ids to choose from. The fix for an installation predating the field is one line per project — `"scm": "github"` in `swarm.config.json`, then `swarm config apply` (or the dashboard's Source Control tab). It is deliberately **not** defaulted to `github` in the schema: a default would silently route a Bitbucket or GitLab project's operations onto GitHub, which is precisely the failure that lookup exists to prevent. One pre-existing constraint becomes reachable alongside it: `projects.repo` is globally unique and `findProjectByRepo` is provider-blind, so one installation cannot hold a GitHub `owner/repo`, a Bitbucket `workspace/repo_slug`, and a GitLab `namespace/project` that spell the same string — a same-name collision across providers needs a repo-plus-provider lookup, which nothing has asked for yet.
- **Configuring a Bitbucket project from the dashboard (#618).** The Source Control tab's provider selector — UI-only since #200 — now writes `project.scm`, so an operator picks Bitbucket Cloud without hand-editing JSON, and the tab's copy (credential form, operator env var, ingress route) switches with it. `scm.verifyBitbucketCredential` joins `verifyGithubToken` so a pasted `username:app_password` can be checked against the account it resolves to before saving. **Deferred to a follow-up, explicitly:** a per-provider credential-role UI (delivered by #628/#632 — a Bitbucket project now holds its own references and the tab labels them an app password), a GitLab option (delivered by #619), and any webhook-registration automation — the Bitbucket repository hook is still created by hand, pointed at `/bitbucket/webhook` with the project's webhook secret.
- **Bitbucket delivery credentials:** source delivery requires a `username:app_password` credential because workspace/repository access tokens cannot resolve `GET /2.0/user` and fail identity resolution before the email lookup. An app password without the `email` scope still delivers with a noreply commit address; grant that scope for attributed commits.
- **GitLab delivery credentials:** any token form GitLab accepts in `PRIVATE-TOKEN` works — personal, group, or project access — but it needs the `api` scope, since delivery writes merge-request notes, verdicts, and merges, and it must be able to read `GET /user` for the commit identity. A token whose scope withholds the account email (and a project/group access token's bot user, which has none) still delivers, using a `<username>@users.noreply.gitlab.com` commit address that leaves the commit unlinked; use a token that exposes the email for attributed commits. Approving also requires the account to be an eligible approver on the project.
- Dual-persona (`implementer`/`reviewer`) credential scoping via `AsyncLocalStorage`, with per-persona token resolution from Postgres.
- The SCM receiver resolves the project (`findProjectByRepo`) and delegates loop prevention (`isSwarmGeneratedEvent`) to the provider adapter.
- The router serves the HTTP webhook receiver, now provider-neutral (issue #385): it mounts one POST route per registered, runtime-ready SCM manifest (`webhookRoute` — `POST /github/webhook` and, since #618, `POST /bitbucket/webhook`) and asks that provider to interpret its own headers, verify the HMAC-SHA256 signature, and normalize the body into an `ScmEvent`, then feeds it through an enqueue seam that shapes each verified event into a `SwarmJob` carrying the provider id, records it as a durable dispatch (dedup-keyed on the delivery id — ADR-002), and publishes its wake-up onto the `swarm-jobs` BullMQ queue (SWARM-35, issue #284).

### PM (GitHub Projects, Linear, Jira, Trello) integration
- The `projects_v2_item` board webhook is normalized at ingress into a provider-neutral `PmEvent` (`src/pm/events.ts`) behind `PMRouterAdapter` (`src/pm/router-adapter.ts`): the adapter resolves the project by its provider container id, filters Status-field edits, and shared code resolves a phase from `WorkItem.statusKey`. Its durable envelope is `{ type: 'pm', providerId, event }`, while still reading pre-#297 rows so in-flight dispatches survive deployment; project→provider resolution uses `requireProjectPMProvider` / `requireProjectPMAdapter` on `project.pm.type`. The card↔SCM-artifact mapping is provider-neutral too (issue #498): a card's task id comes off `WorkItem.taskRef`, which the provider resolves from its own linkage — together with `WorkItem.taskRepository`, the repository that number belongs to, read from the same linkage since issue #710 so a board-wide read keys each card against its own repository — and a pull request finds its card through SWARM's durable `runs.work_item_id` link resolved control-plane side — see ai/ARCHITECTURE.md "Task identity" for the decision and the one legacy GitHub-shaped fallback that remains.
- The PM provider self-registers through a manifest + registry loaded from a single canonical entrypoint (`src/integrations/entrypoint.ts`), so the receiver resolves its adapter by id rather than hardcoding it (SWARM-13).
- The concrete GitHub Projects `PMProvider` (`src/integrations/pm/github-projects/provider.ts` — GraphQL item read/move plus linked-Issue comments) backs the two board-driven phases.
- **Linear is the second implemented PM provider** (`src/integrations/pm/linear/`, issue #491's six phases, registered by #530): a container is a Linear **team** and a status is that team's **workflow state** (mapped by UUID), comments land natively on the issue, assignees and native `blocks`/`blockedBy` relations back both capability flags, and it authenticates with its own two declared credential roles (`LINEAR_API_KEY` + `LINEAR_WEBHOOK_SECRET`) — inheriting nothing from the SCM side, because a Linear board is a separate system from the repo. Its ingress is its **own** route: the receiver mounts `GET`/`POST /linear/webhook` (no SCM manifest owns that path) and authenticates each delivery with the manifest's own verifier — an unprefixed hex HMAC-SHA256 in `linear-signature`. It passes the PM conformance suite with **no exemption**, and a project with `pm.type: 'linear'` runs the board-driven pipeline. Since issue #531 its team + workflow-state mapping is also picked and saved from the dashboard's Project Management tab, so `swarm.config.json` is no longer the only way to configure one — and since issue #642 a project can be *moved onto* it there too.
- **Jira is the third implemented PM provider** (`src/integrations/pm/jira/`, issue #490's six phases, registered by #580): REST v3 over `fetch`, where a container is a Jira **project key** and a status is a workflow **status id**, `moveWorkItem` executes a **transition** (and fails loudly when the workflow offers none reaching the target — the one structural difference from every other provider), comments land natively in ADF, and assignees plus `is blocked by` issue links back both capability flags. It authenticates with its own three declared roles (`JIRA_EMAIL` + `JIRA_API_TOKEN`, the two halves of basic auth, and `JIRA_WEBHOOK_SECRET`), inheriting nothing from the SCM side. Its ingress is its **own** route: the receiver mounts `GET`/`POST /jira/webhook` and authenticates each delivery with the manifest's own verifier — `sha256=<hex>` in `x-hub-signature`, GitHub's framing against the *board's* secret. It too passes the conformance suite with **no exemption**, so `listPMProviders()` is now `['github-projects', 'linear', 'jira']` and a project with `pm.type: 'jira'` runs the board-driven pipeline. Its project + status mapping is edited from the dashboard's **Project Management** tab like the other two providers' (issue #581); only `baseUrl` stays a `swarm.config.json` field, preserved across a save rather than edited there — which is also why a *switch to* Jira from that tab (issue #642) is gated on the site URL already being set, with the same explanation the Save gate has always given.

- **Trello is the fourth implemented PM provider** (`src/integrations/pm/trello/`, issue #492's six phases, registered by #588): a container is a Trello **board** and a status is the **list** a card belongs to, with native comments and its own API-key/token/webhook-secret credentials. It passes PM conformance with a declared `supportsDependencies: false` opt-out, serves `GET`/`POST /trello/webhook`, and its board/list mapping is configured from the Project Management tab alongside the other registered providers.

- **A board card is routed to one of the project's repositories** (issue #686). Each provider answers `PMProvider.resolveItemRepository` from its own axis — GitHub Projects from the card's backing Issue/PR, Linear and Trello from a label id, Jira from a component id — against candidates the caller builds from the project record, since a provider is constructed from a repository-scoped config that carries no list. Ingress makes the call in `handlePmEvent` after authentication and loop prevention, records the answer on the `pm` job (`PmWebhookJob.repository`), and the worker's existing `repositoryForJob` seam scopes the project to it, so the worktree, branch, PR, `runs.repository` and the queue read model all name the routed repository with no phase or trigger change. A project owning one repository short-circuits to it and pays no board read; a card claiming **none** or **more than one** is refused rather than defaulted to the first entry — acknowledged with the reason plus a warning naming the project, the card, and the repositories it could have gone to. A pre-#686 `pm` row carries no repository and still means the default entry.

### Worker & pipeline phases
- The BullMQ job consumer (SWARM-17) claims each wake-up's durable dispatch record (refusing cancelled/completed/superseded ones — issue #284), resolves the job through a Cascade-style trigger registry (`src/triggers/`, SWARM-53) and dispatches the matched trigger to its pipeline phase; the consumer resolves the phase, hands off to the orchestrator, and settles both the dispatch record and the job outcome from its result.
- Shared building blocks (`src/pipeline/`): per-task worktree lifecycle (`GitWorktreeManager`, `src/worker/git-worktree-manager.ts`, SWARM-14 — provisions an isolated worktree under `.swarm-workspaces/task-<id>/`, with a detached-HEAD mode for read-only phases), environment grafting (`graftEnvironment`, `src/worktree/graft.ts`, SWARM-15 — symlinks `node_modules`/`.env`/caches into it), and the agent-CLI execution engine (`src/harness/agent-cli.ts`, SWARM-16 — spawns `claude`/`antigravity`/`codex` with the worktree as CWD).
- All six phases are wired into the trigger registry:
  - **Planning** (SWARM-18) — detached worktree → Claude Code writes `proposed_plan.md` → posted on the linked Issue → moves the item to "ToDo" itself only if `pipeline.planning.autoAdvance` is on (default off).
  - **Implementation** (SWARM-19) — task-branch worktree → the agent implements/verifies and writes a structured hand-off → SWARM validates, commits, pushes, opens/reuses the PR, links it on the item, and moves it to "In review" when Review is enabled (otherwise it remains "In progress"). Either phase's agent CLI/model can be overridden per project via `swarm.config.json`'s `agents` block (`src/harness/models.ts`).
  - **Review** (SWARM-20) — detached worktree at the PR's head SHA → the reviewer agent writes a structured hand-off of fields → SWARM **renders** the review body from them (issue #470) and submits the formal review under the reviewer persona. The agent writes no layout: severity (`blocker`/`major`/`minor`/`nit`) picks between a full Evidence/Failure-scenario/Impact/Fix-plan/Tests treatment and a one-paragraph compact form, the hand-off schema enforces each tier's slots, the verdict as a function of the severity histogram, and the re-review rule that an unresolved carried item must be re-reported as a finding under its original id (so an approval can never sit above a "not addressed" disposition row), and the rendered header names the pass (Review / First re-review / Second re-review — the last marked as the final permitted verdict). A hand-off that fails that validation gets one repair pass, re-running the agent against the validator's own complaint, before the run fails. The verdict vocabulary is `approve` or `request-changes`: `comment` was removed because it cleared no review gate, dispatched no follow-up, and still consumed a verdict slot, so a PR that received one was silently terminal — a reviewer that cannot reach a verdict now fails its run instead. (Inbound, SWARM still observes a human's `commented` review.) A durable, restart-safe ledger (`review_verdicts`, issue #235) caps every PR at three submitted verdicts total — an initial review plus at most two re-reviews (`REVIEW_VERDICT_CAP`); a same PR/head retry reuses its existing slot rather than charging a new one, and once the cap is reached a further reservation — and the Review dispatch that would need it — is rejected. An authorized operator can deliberately continue past that stop once (**Force re-review**, issue #511): the grant is recorded on the capped ledger record itself and buys exactly one extra slot, spent by the next reservation, so the forced pass runs at ordinal 4 and — still being at or past the cap — stops the automatic cycle again rather than reopening it. Both the ledger writes and that prior-review lookup key on the repository the **run** recorded, fed to the phase as a required input from the control plane rather than read off the project config (issue #692, the last phase of #683) — the same string as the project config's own `repo`, because both are resolved from the job's own repository (issue #699), not because a project holds only one. Issue #685 pins that: two PRs carrying the same number in two repositories of one project reserve, key and read distinct ledger slots and distinct delivery identities. Each permitted re-review is scoped, not a fresh full pass (issue #328): when a prior `request-changes` verdict already exists for the PR (`getPriorSubmittedReview`), the reviewer is told to verify only whether those requested changes were implemented correctly — approve when they were, otherwise request changes with a specific fix instruction — and not to surface pre-existing issues an earlier review missed. An opt-in approved review persists a durable merge dispatch that merges the PR directly under the implementer PAT, head-SHA-guarded (never GitHub's native auto-merge — issue #292), while any non-merged outcome remains non-fatal.
  - **Respond-to-review** (SWARM-21) — worktree on the existing task branch → the implementer addresses feedback and writes a structured response → SWARM commits/pushes any fix and posts the idempotent response. Stops automatically instead of dispatching once the reviewer persona's **last permitted** `changes_requested` verdict lands (the safety cap above) — that PR needs a human, and the run is recorded as `manual-intervention-required` rather than starting a further review cycle. The **Force re-review** action on that run's detail page (issue #511) is the supported way back in: it grants the extra review slot and enqueues the corrective run as a synthetic review event carrying `forcedReReview`, the one flag that stands the cap gate down, so the ordinary Respond-to-review → follow-up Review sequence resumes. Both writes are conditional (the grant fires only while none exists; the dispatch carries a deterministic per-(repo, PR, reviewed head) dedup key), so repeated clicks, concurrent requests, and refreshes resolve to one corrective cycle. A `fixed` outcome that actually pushed a new commit reliably enqueues exactly **one** follow-up Review for that new head SHA (issue #241) — through the same Review trigger, aggregate-check routing, reviewer persona, PR/head dedup, and review-verdict ledger a real webhook would use, so a follow-up approval can still trigger the same opt-in merge automation. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head enqueue nothing; the enqueue is part of this phase's own deterministic delivery (a deterministic per-(project, PR, head) job id, checkpointed after success) rather than a best-effort action, so queue retries, a worker restart mid-delivery, or a redelivered webhook can't duplicate the follow-up Review.
  - **Respond-to-CI** (SWARM-64) — worktree on that same task branch → the implementer fixes a failing check or reports no change → SWARM commits/pushes and posts the explanation.
  - **Resolve Conflicts** — worktree on a confirmed-conflicting PR branch → the implementer merges the current base, resolves conflicts, runs relevant checks, commits and pushes normally. Mergeability-null rechecks are coalesced and bounded; dispatch is deduplicated per PR/head/base state. Candidates are claimed by the work-item origin gate below rather than by the PR's author (issue #836) — the author gate skipped every federated PR, so on a project served by remote workers this trigger never fired at all and a conflicting approved PR sat in **In review** with no run attached.
- Dispatch: a single **status-change handler** (`src/triggers/handlers/pm-status.ts`) re-reads the board item authoritatively and starts Planning or Implementation by the card's Status; **PR-lifecycle handlers** start Review (on a non-draft, same-repo, SWARM-managed PR opening or its checks passing) and Respond-to-review (by default, only on the reviewer persona submitting `changes_requested`; `skipOnMinors: false` also dispatches approvals and an inbound comment-only review — SWARM's own Review stopped submitting that verdict in issue #470).
- A **work-item origin gate** (`src/triggers/swarm-managed-pr.ts`, issue #397) acts only on PRs SWARM manages: the PR's head branch must decode to a work item under the project's `branchPrefix` *and* SWARM must hold an `implementation` run row for that item. It replaced the former author-persona gate, which skipped every federated PR now that the implementer credential is the worker operator's own account (ADR-004 §3). Since issue #836 it covers **both** PR-ownership triggers — `pr-review` and `resolve-conflicts` — through one shared resolver that also classifies "could not decide", so neither the decision nor its failure handling can drift between them. On `pr-review` the gate runs once for both entry events, and still before the `checks` aggregate query so a PR we'd never review doesn't cost an Actions-API call; on `resolve-conflicts` it runs ahead of the mergeability check, so a PR that is not ours spends no recheck. A run-history lookup failure degrades to a bounded recheck on either trigger rather than dropping the PR — and in `resolve-conflicts`' fan-out an undecided candidate is kept rather than dropped, since that path can only schedule a per-PR check, never dispatch.
- On `checks` completion, the `pr-review` handler aggregates *every* check on the head SHA (via the Actions API) rather than trusting the single suite's own conclusion — reviewing, routing a failed suite to Respond-to-CI, or deferring with a coalesced recheck (`scheduleCoalescedDispatch`, #63) when the Actions API lags webhook delivery.
- **A closed pull request stops the chain before either budget is touched (issue #772).** The mergeability gate reads the SCM contract's neutral `PullRequestDetails.state` and skips a closed or merged pull request outright, since no provider ever reports a final `mergeable` for one. Before it, a recheck chain still in flight when the PR merged polled to its cap and then reported a `failed` run for work that had already finished — on PR #768 a stray `checks` chain kept polling for ~16 minutes after the PR was reviewed, approved and merged. This short circuit precedes both bullets below: it is a plain skip, with no durable trace and no pull-request comment.
- **A defer spends the budget its reason names (issue #720).** "The provider answered but not finally" (a check still running, no checks registered, `mergeable` still `null`) spends `recheckAttempt` — 20 attempts at a fixed ~30s. "The read never answered" (the provider threw, or the run-history lookup threw) spends its own `readFailureRecheckAttempt` — 15 attempts on a capped exponential backoff (30s doubling to a 5-minute ceiling, ~62 minutes of outage outlasted) — and carries the CI-lag count through untouched, while any defer that *did* get an answer clears the read-failure count. They used to share one counter, so a transient source-control outage drew down the CI-lag allowance and abandoned the review: on PR #694, 17 of 20 attempts went to a DNS failure and the synthetic follow-up Review (`src/pipeline/follow-up-review.ts`), which has no later webhook to fall back on, was dropped. Both budgets stay bounded, so a provider that never returns still winds down to one warn rather than rescheduling forever.
- **A terminal give-up leaves a durable trace (issue #742).** Whichever budget runs out, the handler records one `failed` Review run in SWARM's own Postgres naming the pull request, head SHA, exhausted budget, attempts spent and last read — so an operator asking why an item stopped finds it in the Runs list instead of the worker log, and can retry it from there (the row stores the event payload with both recheck counters reset). It is recorded rather than posted precisely because the give-up is usually caused by the source-control provider being unreachable: in the incident behind issue #720 the give-up comment failed against the same DNS failure, and the abandoned review settled as an ordinary `no-trigger` leaving no trace anywhere. The pull-request comment is now a best-effort extra on the mergeability path (the aggregate-check path posts none and relies on the record alone).
- A cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62) — a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, failing closed if Redis is down — ensures a PR that opens *and* then passes its checks is acted on once per commit, not once per event. The respond-to-ci path shares that slot and adds a per-PR fix-attempt cap (`src/triggers/respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- Revised from live end-to-end testing:
  - Planning no longer moves the item by default — a human reviews the plan and moves it to "ToDo" themselves, unless `autoAdvance` is enabled in the project settings.
  - Implementation triggers on "ToDo" rather than "In progress" — the phase itself moves the item to "In progress" as a status report once it picks up the task, not as the trigger (`src/pm/pipeline.ts`).
  - The Board view's drag-and-drop fires a `reordered` action with no field-value data, not `edited` as originally assumed — the router/trigger now accept `reordered` too, guarded by a Redis-backed dedup (`pm-status-dedup.ts`) against the harmless within-column reorders it also fires on.

### Worker resilience & queue
- **Agent session resume**: a rate-limited, response-stalled, or genuinely timed-out run — in **any** phase, on **any** CLI — is deferred with its worktree preserved and resumed on retry, continuing the same agent session instead of redoing its work (`claude --resume`, `agy --conversation <id>`, `codex exec resume <id>`). The session id is captured per CLI — all three report it in their own structured output, with Antigravity's `conversation_id` falling back to a diff of its conversation store (`src/harness/antigravity-session.ts`) when the stream carried none — and retention pins the checkout until the retry runs. A run whose session wasn't captured, or whose checkout was pruned, falls back to a fresh invocation.
- **Worktree preservation & recovery state**: when a run fails or is cancelled, its worktree and active CLI session can be preserved to prevent losing partial progress. If a recovery/resume is subsequently attempted, the worker executes a recovery gate to ensure the worktree is still valid (e.g. exists, has no conflicting live leases, or is clean if starting fresh). The dashboard surfaces the run's recovery state (`preserved`, `recovered`, or `blocked` with the specific reason: `dirty`, `unpushed`, `live-leased`, `resumable-owner`, `missing-validation`, or `checkpoint-divergent`), and the "Resume" action allows the operator to retry the run while continuing the prior agent session.
- **Checkpoint-seeded continuation (Tier 2)**: for the stops native session resume can't serve — no session id was captured, or a resume attempt itself failed (the expired/pruned session) — an implementer phase's preserved checkout is adopted on the strength of the checkpoint file the stopped run left in it, validated against the working tree actually on disk, run on a fresh session with no resume id, and seeded with the recorded remainder (so a continuation may even run on a different CLI than the stopped run did). **Tier 1 keeps absolute priority**: a run with a resumable session id behaves exactly as it did before. A selected fallback settles the run as `checkpointed` — a second retry-pending status, with a null `agent_session_id`, the parsed checkpoint on the row, and an incremented continuation count — and enqueues its continuation through the same durable dispatch that carries `resumeSession`, with `recoveryMode: 'checkpoint'`. Retention pins a `checkpointed` checkout by status rather than by session id, since it has none. The fallback is bounded by `pipeline.maxContinuations` (default 2, kept through a retry and cleared only by "Reset & restart"); exceeding it is a terminal failure that says the continuation budget was exhausted. A federated worker reports the same settle by attaching the checkpoint it parsed to its `deferred` frame — the control plane keeps the policy and the budget. A missing, malformed, or divergent checkpoint blocks (`missing-validation` / `checkpoint-divergent`) rather than silently continuing — and a divergence now says *where the missing work went* (issue #705): the phase prompt tells the agent never to leave the worktree's changes stashed (with the reason, since a single agent turn cannot infer that it may be continued by a fresh session in the same worktree), and the guard reports whether a `refs/stash` entry on the task's branch — or one holding the paths the tree stopped changing — has the work, naming the `git -C <worktree> stash apply '<ref>'` that restores it, or saying plainly that nothing matches. The probe only reports: it never applies, pops, or drops a stash, it is fail-soft (a failed git call degrades to "could not check" and cannot flip the verdict), and the refusal itself is unchanged. The dashboard renders and drives the state (see the Dashboard section below), which completes Tier 2 (`docs/CHECKPOINTS.md`).
- **A continuation runs on the machine that holds its work** (issue #567). A preserved checkout — a Tier 2 checkpoint, a resumable session, a delivery sidecar — is machine-local with no server-side copy, and worker selection had no notion of where the state was: a continuation re-dispatched to any other eligible machine found nothing to adopt, provisioned a fresh checkout, and re-ran the phase from scratch at full token cost with nothing in the run record saying so (seen live on task 549, where "Continue now" restarted a checkpointed Implementation on a second machine three seconds after it created its own empty checkout). The settle that preserves a checkout now records the machine on the run (`recovery.preservedWorkerId`, no migration — the column is free-form `jsonb`) and it survives every later re-bind; the dispatch gate offers a continuation (`recoveryMode` `resume`/`checkpoint`, `resumeSession`, or a delivery resume — never `fresh`) **only** to that machine, ahead of assignee affinity. When it is busy or offline the dispatch waits under its own verdict (`preserved-worker-unavailable`, dispatch wait reason `preserved-worker`), **without a budget**: failing would abandon work still on disk and a timed fallback is the same defect with a delay, so the wait is unbounded and the run names the machine it is waiting for — on the dispatch row and in a run-detail callout, which distinguishes "currently waiting for this machine" from "merely pinned to it" by reading the active dispatch's wait reason — for as long as it waits. Ending it is an operator decision: "Reset & restart" releases the pin, needs nothing from the pinned machine (so it works while that machine is unreachable), and converts the record into `abandonedWorkerId`, so a run that started over instead of continuing says so afterwards. The two token-free re-check deferrals also stopped re-deriving recovery intent, which had been dropping a `'checkpoint'` mode and re-minting a `'resume'` session id on the very wait that was meant to preserve them.
- **A deferred dispatch says which kind of wait it is in** (issue #607). Every refusal from the eligibility gate used to record the same wait reason, so a dispatch waiting because a machine was momentarily busy or offline was indistinguishable, on the row and in the Queue, from one waiting because a human had to grant sharing consent, approve an enrollment, or widen an allowed phase — the first clears by itself in seconds, the second never clears until somebody acts (seen live as two dispatches deferred `reason=worker-unavailable retryDelayMs=300000` while both workers were idle, recorded only as `worker-eligibility`). The gate's whole reason vocabulary is now partitioned by one exported predicate, `isAvailabilityRefusal` (`src/worker/eligibility-gate.ts`) — a `Record` over the union, so a reason added later fails to compile until it is classified rather than defaulting silently into a bucket: an availability refusal keeps the dispatch wait reason `worker-eligibility` (unchanged, so the rows the incident produced still read correctly), while `missing-enrollment` / `missing-consent` / `missing-cli-capability` / `missing-phase-capability` / `phase-not-permitted` record `worker-authorization`, and the preserved-checkout pin keeps its own `preserved-worker` ahead of both. **Nothing about the timing changed**: same 5-minute cadence, same `workerEligibilityRecheckAttempt` counter, same budget, no migration (`wait_reason` is plain `text`), no new dispatch state and no new configuration. The Queue read model and the dashboard label the two waits apart ("waiting for an available worker" vs "waiting for a worker to be authorized"). Rows written before the deploy carry `worker-eligibility` even where the refusal was structural; each is re-classified by its own next re-check, so they age out within one interval. Waking an availability wait early is what the distinction unlocked — issue #610, below.
- **An availability-blocked dispatch starts as soon as a worker becomes available** (issue #610). The gate's refusal was deferred on a fixed timer and nothing woke it early, so work refused a moment before a worker connected — or a moment before one finished its run — sat still next to an idle machine for up to the full `SWARM_DEPENDENCY_RECHECK_MS` interval (seen live: two board deliveries deferred at 07:24:20Z/07:24:25Z with `retryDelayMs=300000`, both workers reconnected and idle from 07:24:46Z, nothing dispatched until 07:29:21Z — ≈4.5 minutes of dead time reading from the dashboard as "two workers are online and nothing is being picked up"). The wait is now event-driven, the way concurrency waits have been since issue #262: a worker's authenticated socket opening, and a dispatch bound to it settling (success, failure, cancellation, or deferral alike — the capacity-freed signal for a federated transport worker too), each promote the dispatches that were only waiting for that. A `worker-eligibility` row is woken by any worker routably enrolled in its project; a `preserved-worker` row only by its own recorded machine, enrolled there or not (issue #567), and its wait stays unbounded. A **structural** wait (`worker-authorization`, issue #607) is never promoted — a machine connecting cannot grant consent — so it keeps the timed cadence and its budget. An early wake cannot start the same dispatch twice or skip the gate: the delayed wake-up is removed before its replacement is published (so exactly one exists per row at any moment), the re-date is conditional on the wake sequence that was read (so two workers waking concurrently promote once), and the woken job re-enters the full eligibility evaluation spending the attempt budget the previous settle persisted rather than a fresh one. The timed re-check remains the fallback, `SWARM_DEPENDENCY_RECHECK_MS` / `SWARM_DEPENDENCY_MAX_WAIT_MS` keep their meanings, and there is no migration, no new dispatch state, and no new configuration. Every promotion logs which worker, what made it available, and how many dispatches it woke; a promotion failure is swallowed rather than failing the settled run that triggered it.
- **A deferred prioritized continuation keeps — and reuses — its dispatch dedup claim** (issue #780). Review, Respond-to-CI and Resolve-conflicts claim a cross-process dedup slot in the trigger handler (`claimReviewDispatch` / `claimConflictResolution`) *before* the eligibility gate runs, and the handler already knows to reuse a held claim rather than re-claim it (`ctx.continuationDispatchClaimed`, issue #214) — but the eligibility deferral was the one pre-run wait that never set that flag. The woken retry therefore re-entered its handler from scratch, collided with the claim it was itself still holding, was dropped as a duplicate, and the job settled `"matched no trigger"` — leaving a dispatch row `state: completed` with `run_id: NULL` and no `runs` row at all, which reads in the dispatches table as a normal, uneventful success. Nothing else showed it either: the board card moves to **In review** off the PR-opened webhook, independently of whether the Review dispatch ran. Seen live on PR #779 (task 778): Review deferred `worker-unavailable` at 11:19:33 because the only capable worker was still finishing Implementation for the same task, Implementation freed it 973 ms later, the fast availability wake (issue #610) promoted the dispatch immediately, and it completed as a silent no-op. The fast path is what made the collision certain rather than merely likely — it fires seconds into a 5-minute claim TTL, where the timed re-check had been landing just *after* the TTL lapsed and usually re-claiming cleanly by luck; Resolve-conflicts had no such luck at all, since its claim TTL is 24 hours. The deferral now holds the claim open for the length of its own wait and records `continuationDispatchClaimed` on the dispatch's persisted payload, which is the single payload **both** wake paths republish, so the timed re-check and the fast promotion resume identically. The two pre-run waits and the eligibility wait retain the claim through one shared helper rather than each re-deriving half of it. **The guard is not weakened** — the claim is *held*, not skipped, so two independent events for the same PR+SHA still produce exactly one dispatch, and a fresh event still re-claims normally. Planning and Implementation hold no claim of this shape and are untouched, `src/dispatch/dispatcher.ts` is unchanged so issue #610's promotion behaves exactly as before, and there is no migration and no new configuration.
- **The gate refuses a worker holding another repository, and names that refusal for what it is** (issue #714). A worker declares which repository its one local checkout is at handshake (#687) and refuses a mismatched assignment when it arrives (#688) — but worker *selection* had no repository signal at all, so a mismatch cost a full selection, claim and terminal refusal instead of being skipped, and the wait reason named something other than the real cause. `evaluateWorkerEligibility` now takes the **task's** repository (the scoped project's own `repo`, which #684 pins to the job's repository rather than the project's default entry) and refuses a candidate whose declaration is a different one, with its own `repository-mismatch` reason — never by reusing `worker-unavailable` or `missing-enrollment`. The comparison is the shared `repoSlugsMatch` (`src/scm/repo-slug.ts`), which normalises the config side too, and the check sits ahead of every capability (a machine holding the wrong tree can run no phase of this task at all) but behind connection and capacity (a machine that *does* hold the repository and is merely busy or offline still reports `worker-unavailable`, the wait that clears by itself). A worker that declared **no** repository is not refused — an unidentifiable checkout must not become unroutable, and the provision-time `origin` verification plus #688's assignment refusal stay its guards, exactly as #690 decided for enrollment. The refusal is classified as one only a human can clear, so a deferred dispatch records `worker-authorization` rather than `worker-eligibility` (issue #607's split — a checkout is re-declared only at handshake, so waking the wait when a machine connects would only spend its budget faster), and the message names the task's repository and the action that ends the wait. Pool-aware scheduling narrows each *contender* by its own repository too, so contention is only counted between dispatches that could share a machine; a contender whose stored payload names none is judged against every machine rather than by a guessed default entry, a third approximation in the same widening direction as the two already recorded in `src/worker/pool-demand.ts`. No migration, no new configuration, and no dashboard change — the Queue surfaces label the two wait *buckets*, not individual reasons. **Known limitation:** because #690 compares a declaration against the project's *default* entry, a worker holding a non-default repository cannot yet enroll in that project at all, so the full "one worker per repository, several per project" roster still needs that enrollment check widened; the refusal is reachable and useful today for the common case — a worker holding the default entry must not take a task for another repository.
- **A task's next phase waits for its previous one instead of being dropped as a duplicate** (issue #759). The in-flight collision guard keyed on `taskId` alone, and the two board-driven phases share a task id *on purpose* — Planning and Implementation work in the same `task-<id>` checkout on the same `issue-<n>` branch (issue #498) — so the ordinary progression "Planning finished, the operator moves the card to ToDo" was indistinguishable from a repeated webhook, and both were completed `skipped-duplicate`. That outcome is terminal and phases fire on status *transitions*, so a card already sitting in ToDo produced no further event: nothing re-dispatched (seen live on issue #754 — the Implementation dispatch was discarded at 09:53:50, **71 seconds before** Planning finished at 09:55:01, and the card sat in ToDo with both workers idle until a transition was made by hand at 12:31). Two details made the window wider than it looked: it is queue time *plus* execution time (of #754's twelve minutes, the first 6.5 were spent waiting for a worker), and the guard's own scope was "already running in *this* worker", so whether a dispatch was dropped depended on where it was routed. The guard now keys on `(taskId, phase)`: a **different** phase is deferred as a `pending` dispatch with wait reason `task-in-flight` and woken by the holding phase settling — every settle path, success or not — while the **same** phase arriving twice is still dropped as `skipped-duplicate`, so the dispatch record keeps telling the two apart. The worktree protection is unweakened: a deferred dispatch holds no checkout and starts only once nothing is executing for the task, and the collision is read from the dispatch table as well as from the worker's own memory, so the outcome no longer depends on routing. Nothing is silently terminal either — the wait is a `pending` dispatch plus a `deferred` run row, both operator-visible with their own Queue copy ("waiting for the task's earlier phase to finish") and the usual Retry now / Put back / Terminate controls — and a duplicate that carries a run row now finalizes it with a stated reason instead of leaving it `deferred`. It reuses the deferral vocabulary the capacity wait already had (no attempt spent, event-woken, reconciler republish underneath) rather than inventing a mechanism, so there is no migration (`wait_reason` is plain `text`), no new dispatch state, and no new configuration.
- **Implementation no longer overtakes a Planning dispatch that has not started** (issue #761). The guard above admits one phase to `task-<id>` at a time, but it chose nothing between two deliveries that had *both* not started: whichever claimed first ran first, so an Implementation could run without the plan it was dispatched to consume — the plan then landing after the implementation that needed it. The window is queue time *plus* execution time, which is what makes it reachable: on issue #754 a Planning dispatch created at 09:42:47 did not start running until 09:49:15, 6.5 minutes queued behind busy workers with nothing executing, and the board gives an operator no sign that execution has not begun — so moving the card to ToDo in that window, a natural thing to do after reading a plan, produced two pending dispatches racing to claim. **The fix is an asymmetric yield: Implementation defers while a non-terminal Planning dispatch exists for the same task, and Planning never defers to Implementation.** That one-directional relationship has no mirror case by construction, which is precisely what three passes of symmetric claim-time ordering could not achieve (PR #760, reverted): a yielding Implementation returns to `pending`, which the executing read does not count, so no pair of dispatches can defer to each other and no total order over the pair is derived from the dispatch table. **A task with no Planning dispatch is untouched** — the ordinary Backlog → ToDo path finds no hold, starts immediately, and gains no gate; the rule is "do not overtake a Planning that exists", never "Implementation requires a plan", which would block the common case. The signal is the dispatch record's own `(task_id, phase, state)`, **not the `planned` label**: that label's write is deliberately best-effort (`markSplitChildPlanned` swallows a failed `addLabel` so a refused label cannot abort a split mid-loop, issue #737), so gating a second thing on it would let one swallowed failure both un-gate Planning and mis-order a phase — and "a plan exists" is the wrong question anyway. Those are columns the dispatch row already normalises when a claim resolves the trigger, so no provider-shaped payload path enters shared code (`ai/RULES.md` §2) and the verdict does not depend on which worker or process the dispatch was routed to. Nothing is silently dropped: the wait reuses #759's own vocabulary — the same `task-in-flight` reason, the same `pending` dispatch plus `deferred` run row with its reason stated ("has its planning phase queued — waiting for it to settle", distinct from the executing case's wording), woken by Planning settling on every settle path, with the reconciler's republish underneath so a cancelled Planning self-heals too — hence no migration, no new dispatch state, no new wait reason, and no new configuration. **One window stays open, deliberately:** a Planning dispatch that has *never* been claimed still carries a null `task_id`/`phase` and is invisible to this check. That is a queue hop rather than a wait, and closing it would need either a provider-shaped payload path or a new normalized column — while matching unresolved rows on `phase IS NULL` would make two duplicate Implementation deliveries defer to each other, the mirror case this shape exists to avoid.
- **Two phases of one pull request no longer act on it at once** (issue #850). The in-flight guard above is keyed on the worktree task id, and the four PR-driven phases carry deliberately distinct suffixed ids (`<pr>`, `<pr>-respond`, `<pr>-conflicts`, `<pr>-ci`) *on purpose* — they need separate checkouts so they can run alongside one another — so nothing held the artifact they actually share. Three of them (Respond-to-review, Respond-to-CI, Resolve-conflicts) commit and push to the PR's head branch, and a Review reads a head SHA one of them is about to replace. Both halves were seen live on `SmartTechBrewery/rover#101` on 2026-08-31: two writing phases held one head branch at once, so the second one's push could not fast-forward and its whole ~18-minute agent run was thrown away; and a Review started mid-flight, reviewed the head about to be replaced, announced itself as a re-review, and spent one of the three permitted verdict slots (issue #235) on it — the verdict ledger had been masking how often this happened, since a second Review for the same head is refused a reservation while the first is `pending`, which hid the collision without preventing it. The dispatch row now records the pull request it acts on (normalized `repository` + `pr_number`, written when the trigger resolves — never read out of the job payload), and the claim point holds *that*, beside the task hold: a writing phase waits as `pr-in-flight` and is woken when the holder settles (every settle path, success or not), while a Review is **dropped** — completed `skipped-pr-in-flight`, with its PR+SHA dedup claim released and its verdict reservation abandoned, so no ledger slot is spent and the re-review of the head the writer actually pushes arrives through the writer's own follow-up. Dropping rather than deferring is the point for a Review: it is pinned to a head SHA, so a deferred one would wake and review the wrong commit. It cannot deadlock — only *executing* writers hold, a deferred one is back in `pending` where the read does not count it, and a Review neither holds nor waits — and both new reads fail open, because a DB hiccup must never turn into a dropped or stalled dispatch. Reporting a branch that moved under a phase *anyway* (a fail-open read, a human pushing mid-run) is the residual net, and is phase 2/2 of the same issue.
- **A branch that moved under a writing phase is reported as what it is** (issue #850, phase 2/2). The PR-scoped hold above prevents the concurrency; this is the report for what a hold cannot cover — its own two reads fail open on a database hiccup, a human can push to a PR branch mid-run, and neither a hold nor a queue has any say over a force-push. Respond-to-review and Respond-to-CI committed and pushed with no check that the branch was still where the dispatch found it, so both failure modes surfaced only as the rejected push `pushDeliveredBranch` classifies (issue #558) — after a whole agent run and a push round-trip, and with no signal at all when the branch had already moved before the agent started. Both phases now ask the question twice, in the two places an answer is still worth something. **Before the agent runs**, `assertCheckoutHoldsHead` compares the fresh checkout's HEAD with the head the dispatch was pinned to: equal is silent and unchanged, a HEAD that *contains* it logs one warning naming both SHAs and carries on — that is the hold's own wake-up, a Resolve-conflicts merge landing while this dispatch waited, and the response belongs on the newer tip — and a HEAD that does not contain it fails terminally as an `UnretryableDeliveryError` before a single model token is spent, naming the branch, the commit that is gone and what is there instead. Presence of that commit is probed on its own (`cat-file -e`) rather than inferred from ancestry, because `merge-base --is-ancestor` exits 128 for a commit the object store no longer has — indistinguishable from the git blip the fail-open rule is for, and a force-pushed branch is precisely where that object is gone, so without the split the case this exists to catch would be swallowed. That probe answers "absent" only when git *resolved* the name and found nothing (`cat-file -e` exit 1, asked unpeeled so a missing object reports 1 rather than the 128 peeling to `^{commit}` would give it): a dispatched ref git cannot resolve as an object name at all is no evidence the branch was rewritten, so it fails open with the rest. **Before anything is committed**, `assertRemoteFastForwardable` asks `divergedRemoteHead`'s existing question — is `origin/<branch>` still an ancestor of what we are about to commit on top of? — so the honest `DeliveryDivergedError` replaces the doomed commit instead of following it, in one wording shared with the push's own report (`divergedBranchMessage`) so an operator reads the same sentence whichever side catches it. Both asserts fail **open** on a git or network error: a blip must never fail a phase that would otherwise have succeeded, and the push stays the backstop. A resumed delivery re-runs no agent and skips the pre-agent check, as Resolve-conflicts skips its own fresh-merge gates on that path. Resolve-conflicts is untouched — its delivery-time `assertRemoteHead` is the model this copies — and there is no migration, no new configuration, and no change to how the failure reaches the PR or the board.
- **A rate-limit retry no longer mislabels an already-succeeded run as failed** (issue #815). A Review that rate-limits *after* submitting its verdict is deferred, and its retry re-evaluates the original webhook event through the trigger registry — where the Review trigger correctly declines, because the `review_verdicts` slot for that PR and head is already `submitted`. That decline landed on `processJob`'s shared no-trigger branch, which wrote `failed` with one generic message for every `runId`-bearing job, having no way to tell "this run's work already completed successfully" from "there was genuinely nothing to do". Two things followed: the run read as an errored no-op indistinguishable from a review that never ran, and — because the Review success path never executed — `requestMergeAutomationIfEligible` never persisted the merge dispatch the approval had earned, so an approved and mergeable PR was silently left unmerged on a project with `pipeline.respondToReview.autoMerge` on (seen live on PR #809, merged by hand after the fact). The branch now reads the ledger back for a redelivery whose run row is a Review for the same PR, finalizes it `completed` with the ledger's own verdict, ordinal and automation outcome (clearing the deferral's message and next-retry time), and re-requests the merge for a submitted `approve` — idempotent on `merge:<reviewRunId>`, so a further redelivery creates no second dispatch. The dedup claim is deliberately **not** handed back on that path (the review really was posted, so releasing it would let a sibling event post a duplicate — a failed run's claim is left to its TTL for the same reason), the *dispatch* still completes as `no-trigger` since that delivery genuinely matched nothing, and a run with no submitted slot behind it settles exactly as before, message unchanged. Review is the only phase answered, being the only one with a durable record of its own completion; the findings for the other four are recorded in the branch's own comment — Respond-to-review, Respond-to-CI and the two PM continuations cannot reach this failure, while **Resolve-conflicts has the same class of bug** (a run that rate-limits after pushing its resolution is declined on retry once the PR is mergeable) and needs a ledger of its own before it can be fixed the same way. No migration and no new configuration.
- **A Review dropped as `no-trigger` no longer leaves the pull request unreviewable** (issue #856). The Review trigger takes two claims in the router *before* any run row exists — the cross-process PR+SHA dedup slot, and a durable `review_verdicts` reservation — while every hand-back path was worker-side and keyed on `job.runId`. A dispatch deferred for worker capacity has no run row, so when its retry re-evaluated to `no-trigger` (GitHub answered `mergeable: null`, the trigger scheduled a recheck and declined) neither claim came back: the recheck it had just scheduled bounced off the still-held dedup slot until the TTL lapsed, and because `reserveReviewVerdict` permits exactly **one** `pending` slot per pull request, the leaked row made every later Review of that PR — at any head, including the one Resolve-conflicts pushed — answer `blocked`. The PR sat green, mergeable and silently unreviewable until the row was cleared by hand (`rover#116`). The `no-trigger` settle now hands both back, keyed on the dispatch row's own recorded phase rather than on a run row, so it works on the deferred-before-a-run path — and only for the dispatch that actually took them: a Respond-to-CI shares the dedup slot but reserves nothing, and a delivery that resolved another phase (or nothing at all, like a sibling event the dedup claim dropped) hands back nothing, since releasing a live Review's claim is the same bug mirrored. Issue #815's exception is untouched: a redelivery whose ledger slot is already `submitted` still keeps both, or a sibling event would post a duplicate review.
- **A pending review-verdict reservation no longer outlives the dispatch it was taken for** (issue #857, phase 2/2). #856 fixed one missed hand-back; this is the class behind it. A `pending` row in `review_verdicts` recorded no owner and no expiry, and it is created trigger-side before any run row exists while every hand-back is worker-side — so nothing could tell "a Review is in flight" from "the dispatch that reserved this died five weeks ago", and since `reserveReviewVerdict` permits exactly one `pending` slot per pull request, a single forgotten hand-back made a PR unreviewable for life. Five leaked rows were sitting in the production ledger, the oldest reserved on 2026-07-24, and the first one to land on a PR that still needed its Review orphaned it outright (`rover#116`, green and mergeable and silently unreviewable until the row was cleared by hand). The reservation now names its dispatch (`review_verdicts.dispatch_id`, written in the same advisory-locked transaction that inserts the row and re-pointed when a fresh dispatch reuses a `pending` slot), and the rule lives in `reserveReviewVerdict` itself rather than in a new writer on every terminal settle path: a blocking `pending` row is honoured only while its dispatch is still queued, deferred, leased, running or inside its retry budget, and is otherwise abandoned so the reservation proceeds. No future drop path can forget it, and no operator has to touch Postgres — a missed hand-back is now a delay, not a permanent block. A live Review is never cleared out from under itself, a `submitted` slot is never touched, and the safety cap (issue #235) is unchanged, because a recovered ordinal was never a spent verdict and #511's operator override is evaluated afterwards, neither spending it nor being spent by it. The migration adds the column, adopts the reservations whose Review is in flight across the deploy, and settles the five relics; there is no age-based expiry in the running system (a deferred Review can legitimately wait hours, so "old" and "abandoned" are different questions) and recovery stays lazy — a PR that receives no further event keeps its relic, visibly, in the dashboard's Stalled section (issues #840/#847). No new configuration.
- A usage/session-limit hit from the agent CLI (`classifyAgentFailure`, `src/harness/agent-failure.ts`) doesn't fail the job outright — it's deferred and re-enqueued once the CLI's own reported reset time passes (SWARM-91).
- A transient provider-capacity hit (e.g., Anthropic's `529 Overloaded` or Codex's `at capacity`) is similarly deferred and re-enqueued fresh on its own capped backoff budget (issue #229).
- Not every classified failure is a retry signal: an **authentication/login** failure (an expired-and-unrefreshable OAuth session, `Not logged in · Please run /login`, or `Invalid API key · Please run /login`) is classified as its own `auth` kind and surfaced in the run headline as `… exited with code 1 (authentication failed) …` for every phase, so the operator sees the cause without opening the raw run output (issue #343). It stays **terminal** — waiting cannot restore a login, so it is never deferred or re-enqueued and consumes no rate-limit/capacity retry budget — while still triggering the recovery CLI/quota discovery that refreshes the dashboard's CLI status. The terminal-window scan recognises only CLI-owned `/login`, OAuth-session, and `authentication_error` markers, so CI logs or reviewed code that merely discuss authentication stay a plain `error`.
- That same defer-and-retry path also covers a run the *worker itself* killed (a dev `--watch` restart, a deploy, a graceful shutdown mid-phase) — previously indistinguishable from an unexplained agent crash, since an aborted `claude`/`agy` process can exit with empty output and no OS-reported signal. Both cases share one capped retry budget, with the retry delay floored above the review-dispatch-dedup TTL so it can't collide with a claim the interrupted run may have already taken.
- A genuinely-interrupted wall-clock timeout and an agent response stall (`stalled` kind, e.g. "timeout waiting for response") are deferred and resumed on the same shared retry budget (see the "Agent session resume" bullet above); only a timeout that still exited 0 (worktree already gone) is a terminal failure. For those terminal cases on PM-driven phases (planning/implementation), `reportPhaseFailureToBoard` appends a splitting suggestion to the failure comment, advising that the task's scope may be too large and should be split by hand.
- PM retries preserve their original phase dispatch separately from branch reuse: Implementation records an explicit checkpoint only after its task worktree is acquired, so an early failed/manual retry can re-enter the phase without falsely trying to check out a branch that was never created.
- Job-priority split: SCM jobs (`kind !== 'work-item'`) always dequeue ahead of PM-driven jobs (`kind === 'work-item'`), via `src/queue/producer.ts`'s `priorityFor`.
- Concurrency is governed by the per-project `maxConcurrentJobs` and the per-enrollment `concurrencyAllocation`, both enforced at claim time; the former process-wide env cap is gone (issue #811).
- Jobs older than 24 hours are discarded at worker pickup (`SWARM_MAX_JOB_AGE_MS` overrides this), so restarting a worker after an extended offline period cannot replay stale board activity.

### Cross-cutting
- One shared structured logger (`src/lib/logger.ts`, SWARM-23) emits JSON log lines (level, ISO timestamp, message, context) for machine parsing, with a `pretty` mode for local dev and a `SWARM_LOG_LEVEL` filter; the router and worker each tag their lines with a `component`.
- Antigravity's actual binary is `agy`, and its `-p`/`--print` flag — unlike Claude's, which is a bare boolean — takes the prompt as its own value: it must be the last flag before the prompt, or it silently swallows whatever comes next as the "prompt" instead (confirmed live: a real Implementation run answered a question about `--dangerously-skip-permissions` instead of doing the task). See the `SUBCOMMAND_ARGS`/`PRINT_FLAG` comment in `src/harness/agent-cli.ts` and `ai/RULES.md` §6.
- **An operator can authenticate the CLI over the network** (issue #798). Until now the only identity this installation recognised was a dashboard session *cookie*, resolved from a browser request by the loopback-bound API server — there was no API key, no personal-access-token, and no `swarm login` anywhere in the repo, so an operator on a machine holding only `SWARM_CONTROL_PLANE_URL` reachability had no identity at all. Three routes under `/operator/session` on the **router** (`src/router/operator-session.ts`) close that: `POST` to log in, `GET` to resolve a bearer, `DELETE` to revoke. They live on the router rather than the API server because that is the process `SWARM_CONTROL_PLANE_URL` points at and the only tunnel-exposed one. They reuse `verifyCredentials`/`createSession`/`resolveSession`/`revokeSession` verbatim — no new table, hashing, or dependency — so a `swarm login` is an ordinary `user_sessions` row under `SWARM_SESSION_TTL_HOURS`. `swarm login` (`--status`, `--logout`) is the client: it holds no `DATABASE_URL`, reads the password without echo or from a pipe (never argv), caches the opaque token at `~/.swarm/operator-sessions/<sha256 of the normalised control-plane URL>/session.json` (`700`/`600`), and prints neither secret. **`SWARM_SINGLE_USER_MODE` is deliberately not honoured** by those routes: the branch that is safe on a loopback-only API server would be an open door on an internet-reachable router, so a single-user installation sets a password once and logs in like anyone else. What the token buys is the operator API below.
- **That token now reaches an API: the router hosts the `swarm workers` operations** (issue #799). `/operator/trpc/*` (`src/router/operator-api.ts`) is a tRPC endpoint whose context resolves `ctx.user` from `Authorization: Bearer <operator token>` via the same `resolveSession`, so no bearer — or an unknown, expired or revoked one — is `UNAUTHORIZED` and no procedure on it is public. It serves a **strict subset** of the dashboard's router, `router({ workers: workersRouter })` (`src/api/operator-router.ts`) and never `appRouter`: this process is the internet-exposed one, so projects, credentials, settings, users and runs stay on the loopback-bound API server. **No procedure's authorization is relaxed** for being reached over the network — the unscoped installation roster is still `instanceAdmin`, `remove`/`rename`/`setConsent`/`scmCredentials.*` still strictly-owner-only, the project roster still `assertProjectAccess` — and `SWARM_SINGLE_USER_MODE` is deliberately not honoured here either. Two procedures were added for it, since a DB-free CLI can do neither itself: `workers.register`, the network equivalent of `swarm workers register` (nothing wrapped `registerWorker` before) and the one procedure in the tree that returns a secret — the one-time worker credential, stored only as a SHA-256 and never re-readable; and `workers.projectScmProvider`, a `contributor` read returning the provider id `requireProjectSCMProviderId(project)` resolves rather than `project.scm ?? 'github'`, so a `register-and-enroll` holding no `DATABASE_URL` can name the provider it files the operator credential under.
- **And `swarm workers` now calls it, so the command group is DB-free** (issue #800). Every subcommand — `register`, `register-and-enroll`, `enroll`, `set-scm-credential`, `set-cli`, `remove`, `approve`, `consent`, `update-enrollment`, `list` — goes through `src/cli/_shared/operator-client.ts`, one module owning the wire details each call shares (base-URL join, the bearer header, an injectable `fetch`, and an error contract where a non-2xx throws the server's own message). It speaks tRPC's HTTP protocol directly with `fetch` rather than adding `@trpc/client`, which is only valid because `src/api/trpc.ts` configures **no data transformer**; a mutation POST must carry an explicit `content-type: application/json` or `@hono/trpc-server` refuses the body, and `tests/unit/router/operator-api.test.ts` round-trips the real client through the real mount so that assumption cannot rot. `src/cli/commands/workers.ts` imports nothing from `db/` or `identity/*-service.js` and calls no `closeDb()`; the CLI's `(worker-id, project-id)` arguments reach the enrollment-id-keyed mutations through `workers.getById`, and `register-and-enroll` keeps its load-bearing plan-then-act ordering (project, provider and secret all resolved before `workers.register`) so a typo still never leaves an orphaned worker. **Three deliberate narrowings**, because the tRPC layer enforces ownership the direct-DB CLI never did: `set-scm-credential` and `remove` are strictly owner-only (an admin can no longer credential somebody else's machine from the control-plane host — its own issue if wanted), `remove` refuses a machine that is running a job, and an unfiltered `list` is `instanceAdmin`-only, with `list <your own handle>` served by `workers.listMine`. One thing moved rather than narrowed: `register-and-enroll` now validates the owner identifier *after* prompting for the secret, since it is `workers.register` that resolves it. The onboarding flow this closes is three commands on the machine being onboarded, from inside its own checkout, with no Postgres credentials anywhere near it: `swarm login`, `swarm workers register-and-enroll <owner> <project> --name <name> --cli <clis>`, `swarm run:worker`.
- **Not yet:** rate limiting or lockout on that login route. `POST /auth/login` has none either and `verifyCredentials` already spends constant scrypt time on an unknown identifier, so this is a recorded follow-up rather than an omission.

- Runs record per-phase token usage where the agent CLI reports it (issue #138). All three CLIs now do: `claude` and `antigravity` on their own `--output-format stream-json` streams, `codex` on `--json` (issue #465). An `agy` predating `--output-format` still degrades gracefully to usage-unavailable.
- A running or deferred run can be terminated from its detail page (issue #166). Terminating a running run stops its agent; terminating a deferred run cancels its scheduled retry. Both settle as a failed run with the neutral `Run cancelled after a cancellation request.` outcome, and a terminated deferred run cannot be automatically resumed. The dashboard's `terminate` action additionally records a structured cancellation origin (`source: 'dashboard'`, plus `actor` only when identity is available) alongside that neutral outcome (issue #308); the run detail page shows it beneath the neutral message only when one was actually recorded — a marker-only (external/unknown) cancellation and every legacy row show no source/actor, never an inferred one.
- **Terminate** and **Reset & restart** stay disabled and say what they are waiting for from the moment a request is accepted until the run resolves (issue #561). Both mutations return long before anything visible happens, so the pending state is read from a durable, run-scoped fact the request already wrote — the Redis cancellation marker for a `running` run, the run's waiting `manual-retry` dispatch otherwise — surfaced by `runs.getById` as an additive `pendingRequest`, never from the local mutation's lifetime: it therefore survives a reload, shows to every viewer of the run rather than only the operator who clicked, and blocks the repeat click that used to record the same intent again. The label changes from the action to the wait (`Waiting to stop…` / `Waiting to restart…`) and a callout says what has to happen next plus the bound the run records (the agent timeout, or the `swarm run reset <runId>` escape when there is none). A run that settles — or a restart a worker claims — clears the state on its own, since it is derived rather than stored.
- An **errored run exposes one Recover action** instead of competing recovery buttons (issue #593). Retry and **Reset & restart** are two ways to recover the *same* `failed` run, and side by side both could be submitted while the first was still unresolved — two conflicting requests, with nothing saying which was in progress. The failure callout now renders a single **Recover** trigger whose popup carries whichever choices are currently eligible: the retry-family action under its own server-derived label (`Retry now` / `Resume` / `Recheck and retry`) plus the agent-CLI/model/reasoning override fields, and `Reset & restart` with its unchanged confirmation modal, discard opt-in, and per-step report. Choosing one closes the popup and submits only that action; the trigger then becomes a disabled status label naming it (`Retrying…`, `Resetting…`) until it resolves, and every submit inside a popup left open across a background refetch is disabled with it, so no alternate action can be issued during the wait. The disabled state is the **durable** one issue #561 already derives: both choices open a `manual-retry` dispatch, so `runs.getById` reports either as the run's outstanding `restart` request and the trigger reads `Waiting to restart…` for a second viewer and after a reload, not just for the operator who clicked — the local mutation adds only *which* choice is in flight, which the derived fact can't say. A rejected action returns the control to an enabled `Recover` with the server's message (a refused reset keeps its modal open, as before), and a run with no eligible choice renders nothing. Deliberately scoped to error recovery: a `deferred` or `checkpointed` run has not ended in an error and keeps its side-by-side **Retry now**/**Continue now**, **Terminate**, and **Reset & restart** controls unchanged. No server change — the mutations, guards, and `pendingRequest` derivation are exactly as they were.
- A **checkpointed run** is a first-class state on the runs screens (issue #504), never folded into `Deferred`: its own `Checkpointed` badge in the documented `sky` hue — with a tooltip saying it waits on a continuation rather than on quota — on the Runs table, its cards, and the detail page, plus a `Checkpointed` value in the Status filter. The run detail page adds a **Checkpoint hand-off** panel rendering the persisted `checkpoint` column: the remaining work numbered in the order a continuation works through it, the already-completed steps, the decisions carried over, and the working tree the checkpoint recorded — so a federated worker's run reads the same as a local one, no filesystem access involved. The panel is gated on the checkpoint's *presence* rather than on the status, because the column survives an ordinary retry as the record of what the current attempt was seeded from; its spent `continuation_count` reads against the project's ceiling, which `runs.getById` resolves server-side as an additive `maxContinuations` (from `pipeline.maxContinuations`) so that default is never re-declared in the web bundle and can't go stale. A sky callout carries the state — why it stopped, when the continuation is scheduled — and the three operator actions: **Continue now**, which fires the existing `runs.retryNow` mutation (the server sends a `checkpointed` row through `recoveryMode: 'checkpoint'` unconditionally, so a CLI/model override composes with the continuation instead of turning it into a fresh start), **Terminate**, which settles it down the same branch a deferred run takes with a confirmation naming the recorded remainder it abandons, and **Reset & restart**, whose copy adds that it discards the checkpoint and returns the spent continuation budget. It is read-only: naming, sharing consent, and execution constraints stay on the worker detail screen, where the server declares per value who may change it. It polls on the shared 5s worker cadence (`WORKERS_REFETCH_MS`), and an owner who operates no machines gets an empty state naming `swarm workers register`. Two states are named rather than hidden: a machine enrolled nowhere says so in place of its availability lines, and — the standing limitation — such a machine still opens to `NOT_FOUND` on the detail route, since `workers.getById` remains scoped by project membership, which is issue #647's deliberate choice and not widened here. The tab deliberately does **not** show connection/last-seen state: the owner-scoped read model does not carry it, and adding it would be a server read-model change rather than a presentation one, so the idle badge says explicitly that connectivity is on the machine's own screen. The **My Projects** tab (issue #661) is the personal counterpart to the `/projects` screen: a two-column table of the projects the viewer can open — the name linking to the existing `/projects/$projectId` screen over its id in mono — and, per row, the role they hold on it as a badge with a line saying what that role grants (**Project administrator** / **Member** / **Contributor**, a `Record` over `ProjectRole` so a fourth role is a compile error rather than an unlabelled badge). Unlike the other two profile tabs it does add one read model, `projects.listMine` — deliberately a new query rather than a `role` field on `projects.list`, for the reason `viewerAccess` was kept out of `getById`: that query's cache is rewritten by `projects.update`'s result, which carries no viewer-scoped field. **Visibility is not a new rule**: it is the same `filterAccessibleProjects` scoping `projects.list` runs on, so a project the viewer may not discover is absent here for exactly the reason it is absent there, and a `discoverable` project they have not joined is not listed either — asking to join one stays `listDiscoverable`/`requestMembership`. The projection is id + name + role only, so no repo path, board mapping, or credential reference travels to a personal overview. A `role` of `null` — reachable only by an `instanceAdmin`, who accesses a project with no membership row of their own — is reported as the *absence* of a membership and reads as **Installation-wide** rather than as a synthesized `projectAdmin`, since inventing a membership would misdescribe access that removing an installation role would take away; an admin who *is* a member sees that real membership role, with a line above the table stating that they administer every project whatever role is shown. Membership stays read-only here: joining, leaving, and role changes remain with a project's administrators — on the project's own Members tab since issue #806, or with the `swarm members` CLI — so the tab offers no control and invents no authorization. Its entry point is **pinned** (issue #665): the sidebar's footer is now a single compact account row — the profile link, Sign out, and the connection state — sitting outside the only part of the sidebar that scrolls, so neither control scrolls away behind a long project list. It drops the textual "Connected"/"Disconnected" label the footer used to carry beside the dot; the dot states the same thing in a row that is an account area rather than a status bar. The pinning is desktop-only, since below `md` the sidebar stacks full-width above the content, where a full-height column would fill a phone screen. The **Security** tab (issue #662) is where the profile stops being read-only: a signed-in user changes their own **display name** (draft-and-save, the same shape as the worker rename, invalidating `auth.me` so the sidebar and the Account tab pick the new name up) and their own **password**, over the first two mutations the `auth` router has carried — `auth.updateDisplayName` and `auth.changePassword`. Both resolve their subject from the session and take **no user id**, so no request addresses another account, and the login identifier, the installation role, and project membership roles stay read-only and operator-managed (`swarm users` / `swarm members`) — the tab says so in place of offering a control. The password change requires the **current** password, verified server-side against the stored scrypt hash (`changeOwnPassword`, `src/identity/auth.ts`, composed from the existing `hashPassword`/`verifyPassword`); it **fails closed** for an account with no password set — the passwordless single-user `localhost-admin` included — rather than treating a null hash as "any current password matches", and a wrong current password writes nothing. **No password value is returned, displayed after submission, or logged**: the mutation answers `{ ok: true }` and nothing else, all three form fields are cleared once it settles (success *or* failure, so a wrong-password retry retypes), and the expected outcomes map to distinct statuses (`FORBIDDEN` / `PRECONDITION_FAILED` / `NOT_FOUND`) whose copy names no value. No schema change and no migration: it adds `usersRepository.setDisplayName` + `findUserCredentialById` over the existing `users` table. The password policy is deliberately only "not empty, and different from the current one" — the rule `swarm users set-password` already applies; a strength/rotation policy, rate limiting, and revoking the caller's *other* sessions on a change are all out of scope and are follow-up work (the tRPC context carries the user, not the raw session token, so session revocation is an auth-lifecycle change rather than a screen). One backend consequence beyond the screen: in `SWARM_SINGLE_USER_MODE` the API's tRPC context used to memoize the whole bootstrapped admin for the process's lifetime, so a rename would have kept reporting the old name until a restart — the bootstrap still happens once, but the row is now re-read per request, the same per-request user read the cookie path already does. Signing out is unchanged and stays in the sidebar. Finally, the account row's **leading icon is the profile's own** (issue #680): the connection state sat in front of the name, where a `CircleCheck` read as a checkmark labelling the account rather than as a way into it, so the profile link now leads with a plain outlined `User` bust — decorative (`aria-hidden`), with the visible display name still naming the link — and the connection state keeps its per-state shape, `role="status"`, and accessible name at the trailing end of the row instead of being dropped.
- The **Project Management** tab (issue #201, renamed and widened by #537) is a provider-ready project-detail screen that edits the configured provider's `pm` board mapping through board/status pickers instead of raw node-ID text entry, below a **provider** section (issue #630 — display-only until issue #642 made it the switch control) and a **credentials** section rendering whatever credential roles the project's PM provider declares (`projects.credentials.listPm`/`setPm`/`deletePm` — masked previews, encrypted at rest, no plaintext ever returned; a role that inherits a shared SCM credential stays read-only and points at the Source Control tab). It discovers the configured PM provider's boards and, for the selected board, its Status options through a new `pm` tRPC router (`pm.listProviders`/`discoverContainers`/`discoverStates`), which dispatches through the registered `PMProviderManifest` and the provider's new optional `discover()` capability — run under the project's own PM credential rather than any worker's SCM token (the browser never handles a credential). Discovery is `projectAdmin`-gated (a privileged read of the provider account's board catalogue), hides project existence from non-members, and turns an unconfigured PM credential into an actionable `PRECONDITION_FAILED` naming the role to set here. Persisted config is still the opaque node IDs; a saved board/status that can't be rediscovered is preserved behind neutral "configured value unavailable" copy until the operator deliberately changes it. The manifest supplies credential roles, their labels/descriptions, and the server-side discovery dispatch; the board/status picker catalogue supplies the correct GitHub Projects or Linear vocabulary. Issue #531 made the screen's projection helpers provider-aware, so it saves any registered provider's mapping — a GitHub Projects board + Status options, a Linear team + workflow states, a Jira project + statuses, or a Trello board + lists — and issue #642 made the provider itself switchable there. **A provider switch is a client-held draft, not a sequence of writes:** picking another registered provider scopes the credential and discovery calls to it (issue #641's provider parameter), and only Save writes — one `projects.update` carrying the whole new `pm` union member, so the project never names a provider whose mapping is absent or still the previous provider's, and abandoning the draft changes nothing. The outgoing provider's credentials are retained in their own `credentials.pm` block (issue #631) rather than destroyed, the existing Save gates (at least one canonical status mapped, a Jira base URL present) are unchanged, and `projects.update` refuses a `pm.type` change to an unregistered provider or one whose required credential references are absent — the backstop the parse-time schema check cannot provide on a path that does not re-parse. A switch is deliberately **not refused** while runs are active; instead the review step and `docs/configuration.md` state that in-flight runs and their `runs.work_item_id` links keep pointing at the outgoing provider's board and will not resolve on the new one.
- The **installation-wide screens are restricted to instance administrators** (issue #647; the global `/runs` **list** was one of them until issue #821 — see the next bullet). The global `/runs` and `/workers` routes read across every project on the instance — an operator's view of the installation, not a member's view of their own work — so the *unscoped* `runs.list`, `runs.queued`, and `workers.list` reads are gated server-side by `assertInstanceAdmin` (`src/api/authz.ts`) on the installation role alone, returning `FORBIDDEN` rather than the project helpers' `NOT_FOUND` (the caller named no project id, so there is no existence to hide). Those branches no longer derive a membership scope at all: the previously membership-filtered unscoped variants are gone rather than unreachable. The dashboard mirrors the same boundary instead of defining it — one `InstanceAdminOnly` gate *is* the component both routes mount, so direct navigation, a filtered deep link, and an in-app link hit the identical frame and a denied screen never mounts (its cross-project queries are never issued); the two sidebar links are hidden for a non-admin; and `/` now forwards by role, an administrator to `/runs` and anyone else to `/projects`, which is also where a non-admin lands after signing in. **A worker owner keeps every project-scoped view they had**: their projects' runs on the project detail page's Runs tab and their projects' workers on its Workers tab (`runs.list`/`queued` and `workers.list` with a `projectId`, plus `workers.roster`, all still `contributor`-gated), and the run and worker detail routes, `/runs/$runId` and `/workers/$workerId`, are unchanged — the latter deliberately still scoped by membership, since that is the page a roster row click opens. Local single-user installs are unaffected: `SWARM_SINGLE_USER_MODE` resolves the reserved `localhost-admin` as an instance administrator, so both global screens stay available there.
- **The global runs list is open to every signed-in user, scoped to their projects** (issue #821). Run *history* is the one of #647's three unscoped reads that membership can answer, and gating it on the installation role meant a member could only ever see runs one project at a time. The unscoped `runs.list` now resolves `accessibleProjectScope(ctx.user)` instead of asserting the installation role: an `instanceAdmin` still queries every project unfiltered, anyone else is bounded to the projects they are a member of (through the repository's existing `projectIds` authorization filter), and a user who belongs to no project gets an empty page without a query rather than a `FORBIDDEN`. The `/runs` route mounts with no gate and the sidebar link is offered to everyone; the per-project Runs tab (`projectId` present) is unchanged, as is `landingRouteFor` — an admin still lands on `/runs`, everyone else on `/projects`. **`runs.queued` and `workers.list` deliberately did not move**: the queue is an operator's dispatch view and the roster spans machines enrolled in no project, so both stay `assertInstanceAdmin`-gated, and the Queued section on `/runs` renders (and issues its query) only for an administrator or once a project is picked in the filters. Scoping the queue the same way is a possible follow-up, not part of this change.
- The project page's **configuration tabs are restricted to project administrators** (issue #655) — the same boundary as above, one level down. Settings, Agent Configuration, Pipeline, Project Management, and Source Control were `projectAdmin`-gated server-side but still openable by a `contributor`/`member`, who then met a `FORBIDDEN` on every read and write — a dead-end, read-only credential-management screen. **Runs and Workers stay visible to every enrolled non-administrator**, so the project-scoped views that support their work are untouched. The dashboard learns the boundary rather than guessing it: a new `projects.viewerAccess` query reports `{ canAdminister }` from `mayAccessProject(…, 'projectAdmin')` (the pattern `workers.getById`'s per-enrollment `viewerCanAdminister` already uses), under `getById`'s own `contributor` gate and existence-hiding `NOT_FOUND`; it is a separate query because `projects.update`'s result overwrites the `getById` cache on every config save and carries no viewer capability. One `ProjectAdminOnly` gate is the frame the whole configuration half renders through, so a typed URL, a bookmarked `?tab=` deep link, and an in-app tab click hit the identical boundary and a denied tab's panels never mount — their credential, PM-provider, and board-discovery queries are never issued — with the tab bar simply omitting the tabs on top of that. An unresolved access read fails closed, and the screen waits for it alongside the project so the tabs never flash in and back out. **No capability widened and nothing server-side changed**: `projects.update`, the credential procedures, and the `pm` router each still assert `projectAdmin` for themselves, and an `instanceAdmin` keeps every tab on every project — so local single-user installs, where `SWARM_SINGLE_USER_MODE` resolves the reserved `localhost-admin` as an instance administrator, are unaffected.
- A **Members** tab on the project detail screen (issue #806) — the dashboard half of the membership API issue #805 landed, so a project administrator manages the roster with no CLI and no database access. It lists the project's members (display name, login identifier in mono, and a role `<select>` per row), adds one by identifier in a chosen role, re-roles an existing member, and removes one behind a confirmation dialog naming who is being removed and what they lose. It **adds no API surface**: its four operations are exactly `members.list`/`add`/`setRole`/`remove` as phase 1 defined them, and the panel owns its own query and mutations in the shape of `WorkersRoster`, so the route passes it nothing but the project id. It is **not polled** — membership is configuration rather than liveness, so the list refreshes by invalidating its own query key after each write. **No authorization is invented client-side**: the tab is last in `PROJECT_TABS` and listed in `PROJECT_ADMIN_TABS`, so it renders inside the existing `ProjectAdminOnly` frame — a non-administrator is not offered it and a typed `?tab=members` URL meets the same denial the other configuration tabs give, while every `members` procedure re-asserts `projectAdmin` server-side regardless. Server rejections are rendered **verbatim** beside the control that caused them (a duplicate on the add form, a stale row on that row's select), since phase 1's copy already names the fix; a failed role change or removal never silently rewrites the roster. The three role labels now live in `dashboard/src/lib/project-roles.ts`, extracted from the profile's My Projects panel so the two screens cannot word a role differently, and both `<select>`s render `ProjectRoleSchema.options` rather than a hand-written list. Out of scope and unchanged: any server-side change, a roster for non-administrators (`members.list` stays `projectAdmin`-gated), a membership-request approval UI, and creating or inviting SWARM users from the dashboard — `swarm users add` stays the only path, which is what the empty and unknown-identifier copy points at.
