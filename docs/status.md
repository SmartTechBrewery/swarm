### SCM layer

**Verification clarification.** Bitbucket's and GitLab's runtime wiring is unit-verified against the real registered manifests, but no real Bitbucket Cloud repository or gitlab.com project has yet been driven through the pipeline end to end. Both commit→pull-request lookups are mocked, so production verification must confirm that Bitbucket accepts the normalized 12-character revision on `/commit/{revision}/pullrequests` and that gitlab.com answers `commits/:sha/merge_requests` for a branch pipeline's commit under the reviewer token's scope. GitHub checks skip that lookup only when a `check_suite` payload already names a pull request; unresolved branch and default-branch checks perform it.
- The SCM provider self-registers through a manifest + registry loaded from the same canonical entrypoint as the PM one (`src/integrations/entrypoint.ts`), behind the provider-neutral `SCMProvider` contract (`src/scm/types.ts`) that `GitHubSCMIntegration` implements — so a consumer can resolve the whole contract by id without importing the concrete class. **Inbound now runs on it (#385):** the webhook receiver mounts one route per registered manifest and delegates header interpretation, signature verification, event parsing, and comment loop prevention to the provider; the durable queue envelope carries a provider id plus a normalized, provider-neutral event (`ScmEvent`, `src/scm/events.ts`, which also reads pre-#385 rows so in-flight dispatches survive a deploy); and the worker resolves the provider once at its composition root and injects it into the trigger context. **Outbound now runs on it too (#386):** the delivery-provider default in the five delivery-owning phases, the worker's control-plane local delegate, its run-row PR-title read and its phase-failure/interrupted-job PR comments, the durable merge executor's default merge capability, and the router's server-side worker-delivery default all resolve through the registry — by the durable job's own `providerId` where one is carried, otherwise by project (`requireProjectSCMProvider`). **That project-scoped lookup now selects (#478):** a project states its provider in the optional `scm` config field — the SCM twin of `pm.type`, persisted as `projects.scm_type` — so two or more runtime-ready providers can be registered at once with each project's operations routed to its own; a project that states none resolves to the sole runtime-ready provider — a back-compat path that stopped resolving with #618, when Bitbucket became the second ready provider, so **every project must now state `scm` explicitly** (see the migration note below); and an unregistered id, an id that is registered but not runtime-ready, or no id at all with no single runtime-ready provider each throw loudly and name the project and what it asked for, rather than falling back onto another provider. **The DB-free federated worker joined too (#462),** closing the outbound migration: the contract gained `operatorDeliveryProvider(repo, credential)` — a delivery provider authenticated as the worker operator's *own* account rather than a per-project persona, which is what a worker holding no secret store needs (ADR-003 §2 / ADR-004 §3) — GitHub implements it over the existing `operator-delivery.ts`, and `src/transport/assignment-execution.ts` resolves it by project, with `src/transport/connect-entry.ts` importing the integrations entrypoint so the remote worker's registry is populated (it still opens no Postgres/Redis connection). Operator-credential *env* resolution (`SWARM_OPERATOR_GH_TOKEN`) deliberately stays on the worker entry, since that credential is the operator's rather than the project's. Two concrete provider-named reaches remain on purpose: the dashboard's pasted-secret validation route (`src/api/routers/scm.ts`), which runs before there is a project to resolve a provider from and therefore holds one `verify…` procedure per provider (GitHub's, plus Bitbucket's since #618), and the GitHub Projects PM provider's webhook verifier delegating to the GitHub SCM HMAC check (`src/integrations/pm/github-projects/webhook.ts`) — one webhook, one secret. Its other two reaches are gone as of issue #537: board authentication and the board's loop-prevention identity are now the PM provider's own declared credential (`src/integrations/pm/github-projects/credentials.ts`).
- **Bitbucket is implemented and runtime-reachable (#296's four phases, made reachable by #618).** `src/integrations/scm/bitbucket/` adds a credential-scoped Bitbucket **Cloud** client (`AsyncLocalStorage`, plain `fetch` — no new dependency), persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN`, reviewer from the same provider-neutral `credentials.reviewer` reference GitHub uses, so no config field was added), persona identity + loop-prevention helpers, and `BitbucketSCMIntegration implements SCMProvider` with **no method stubbed**. **Webhook ingress works (#455, phase 2 of 4):** `webhook.ts` verifies `X-Hub-Signature` as `sha256=<hex>` over the raw body through the shared timing-safe `verifyHmac` (failing closed, since Bitbucket omits the header for a secret-less hook), reads the event from `X-Event-Key` and the dedup identity from `X-Request-UUID`, and normalizes the eleven event keys SWARM acts on (PR lifecycle, approval / changes-requested, PR comment, commit status) into the neutral `ScmEvent` — everything else returns `null`. Two provider gaps are handled explicitly: Bitbucket has no review object, so `reviewId` is synthesized from PR + verdict + account `uuid` + head SHA (a format the issue-#235 verdict ledger keys on, so it must stay stable), and a `commit_status` payload carries no PR association at all, so `workItemId`/`prBranch` need a commit→PR lookup at whichever ingress layer serves the route. **The reads now work too (#456, phase 3 of 4):** `pull-requests.ts` implements PR details, title, merge state, participant approvals, the open-PRs-for-a-base conflict candidates (server-side `q=` filter, forks dropped), the aggregate commit build status (deduped by status `key`, newest `updated_on` wins, so a re-run's stale failure can't sink a green commit), and the commit→PR lookup — with `PullRequestDetails.mergeable` permanently `null`, since Bitbucket Cloud exposes no mergeability flag; the conflict handler reads that as "unknown" and exhausts its bounded rechecks rather than ever calling a PR cleanly mergeable. **The writes complete the contract (#457, phase 4 of 4):** `writes.ts` posts comments idempotently on the shared `<!-- swarm-delivery:… -->` marker (now `deliveryMarker` in `src/scm/swarm-origin.ts`, so the two providers cannot drift), maps a review verdict onto Bitbucket's `approve` / `request-changes` participant endpoints — applying the verdict *before* the marker comment, since the comment is the retry anchor and Bitbucket has no review object to key on, which also makes that comment's id the neutral review id — creates pull requests, and merges directly (repository-default strategy, source branch left alone). `deliveryProvider` supplies the delivery seam per persona: commit identity from the account `nickname` plus its confirmed primary email, falling back to `<nickname>@users.noreply.bitbucket.org` when the credential lacks the `email` scope (a commit then shows the right name but stays unattributed); PR find/create; and the same expected-SHA `git push` GitHub uses, with the credential in a `GIT_CONFIG_*` extraheader rather than argv. `mergePullRequest` never throws: because Bitbucket's merge endpoint takes no expected-head parameter, a re-read of current state *is* the protection (already merged → `merged`; moved head, draft, closed, changes-requested, or dismissed approval → `not-eligible`), and 409/555 → `not-ready`, 403 or a named merge-check refusal → `policy-blocked`, anything else → `provider-error`. A multi-provider conformance suite (`tests/unit/integrations/scm/scm-conformance.test.ts`) now runs over every registered manifest and asserts no method is a stub. **The wiring landed with #618**, the issue that took ownership of the step #457 left behind: the manifest declares `runtimeReady: true`, so the receiver mounts `/bitbucket/webhook` (GET ping + POST delivery) from the same loop that mounts GitHub's, and `requireProjectSCMProvider` routes a project that sets `"scm": "bitbucket"` there. So **a Bitbucket project now runs end to end**, with GitHub projects untouched. The `commit_status` gap closed there too, and neutrally: `SCMProvider` gained `listPullRequestsForCommit`, implemented by all three providers, and the receiver completes a `checks` event that names no pull request by adopting the first **open** candidate for its commit — skipped entirely for GitHub, whose `check_suite` payload already names its pull requests, and failing open (log + enqueue unresolved, where it matches no trigger) rather than 500'ing a delivery neither provider redelivers on its own.
- **GitLab is implemented and runtime-reachable (#295's four phases, made reachable by #619).** `src/integrations/scm/gitlab/` adds a credential-scoped GitLab**.com** REST v4 client (`AsyncLocalStorage`-bound token, plain `fetch` — no new dependency, `PRIVATE-TOKEN` auth with no credential-form branch since personal/group/project tokens all authenticate and resolve `GET /user` identically, a `GitLabApiError` carrying the same `status` field GitHub's and Bitbucket's merge classifiers read, and offset pagination that follows the `x-next-page` header under a `MAX_PAGES` bound, cycle detection, and a numeric-cursor check — GitLab's cursor is a page *number* appended to a constant base rather than a server-supplied URL, so there is no off-origin link to reject as Bitbucket's paginator must), persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_GITLAB_TOKEN`, reviewer from the same provider-neutral `credentials.reviewer` reference, so again no config field was added — `repo` doubles as GitLab's URL-encoded `namespace/project` path), persona identity + case-insensitive loop-prevention helpers on the GitLab `username` behind the same 60s per-project TTL cache, and `GitLabSCMIntegration implements SCMProvider` with **no method stubbed**. **Webhook ingress works (#483, phase 2 of 4):** `webhook.ts` reads the event from `X-Gitlab-Event`, the dedup identity from the per-delivery `X-Gitlab-Event-UUID` (never the per-*configuration* `X-Gitlab-Webhook-UUID`), and authenticates the delivery by comparing `X-Gitlab-Token` against the project's `credentials.webhookSecret` in constant time, failing closed on an absent, empty, or mismatched token — GitLab's own mechanism is a shared secret token, so unlike GitHub's and Bitbucket's HMAC this authenticates the *sender* and not the body; GitLab 19.0's Standard-Webhooks signing tokens would close that gap but need the `verifyWebhookSignature` contract widened (the signed message uses `webhook-id` / `webhook-timestamp` headers it never sees) **and** a per-provider secret reference (a GitLab-minted `whsec_…` key cannot be the operator-chosen secret the PM webhook shares), so they are a recorded follow-up rather than this phase. It normalizes merge-request lifecycle, approval/unapproval, merge-request notes, and pipelines into the neutral `ScmEvent`; everything else — issues, pushes, tags, wikis, system notes, notes on non-merge-request targets, and a body whose `object_kind` contradicts the header — returns `null`. Two provider gaps are handled explicitly: GitLab exposes no review object, so `reviewId` is synthesized as `<iid>:<verdict>:<user id>:<head SHA>` (a format the issue-#235 verdict ledger keys on, so it must stay stable), and it has **no "request changes" merge-request action** — verified against GitLab 19.1's webhook reference, whose action vocabulary is `open`/`close`/`reopen`/`update`/`approval`/`approved`/`unapproval`/`unapproved`/`merge` — so that verdict is derived from the *acting* reviewer's own `reviewers[].state === 'requested_changes'`; the limitation is that a later `update` by the same reviewer, while that state still stands, reads as the same verdict again (the ledger's two-verdict cap absorbs it while the head is unchanged). A branch pipeline carries no merge request at all, so `workItemId`/`prBranch` stay unset and phase 3's commit→merge-request lookup is what ties such an event back to one, and the pipeline status vocabulary lives in `pipelines.ts` so an event and an API read never spell one pipeline two ways (an *unrecognized* status is deliberately non-terminal, so the aggregate decision defers rather than judging a pipeline it doesn't understand). **The reads work (#484, phase 3 of 4):** `merge-requests.ts` implements the four contract reads over the phase-1 client with the same persona defaults the other two adapters use (merge request → reviewer, title → implementer, aggregate checks → reviewer, conflict candidates → implementer), and reuses `pipelines.ts` unchanged for commit statuses since GitLab spells them with the pipeline vocabulary. `PullRequestDetails.mergeable` carries GitLab's real tri-state — unlike Bitbucket's permanent `null`, so the conflict-resolution side-car actually decides here: `merge_status` is preferred because it is the *git-only* signal the contract's `mergeable` means (deprecated in 15.6, hence a documented `detailed_merge_status` fallback that also covers the undocumented `cannot_be_merged_recheck`), where `conflict`/`commits_status` → `false`, `checking`/`preparing`/`unchecked` → `null`, and every other blocker (`not_approved`, `ci_still_running`, `draft_status`, `need_rebase`, …) → `true`, because `mergeable` means "no merge conflict" and not "policy satisfied". `baseSha` is `diff_refs.base_sha`, the **merge base** rather than GitHub's target-branch tip, which is the stable value the conflict claim key needs; a missing `iid`, branch, `sha`, or base SHA throws rather than being replaced by a stand-in, since those are exact-match key material. Conflict candidates filter server-side, drop forks, then cost one single-merge-request read per survivor: GitLab's *list* response omits `diff_refs` and serves a cached `merge_status`, while reading a single merge request is itself what asks GitLab to recompute mergeability — which is also what makes the trigger's bounded recheck converge. Commit statuses dedupe by `name` keeping the newest `finished_at ?? created_at`, so a re-run's stale failure can't make a green commit look failed. Two reads exist for phase 4's merge-eligibility recheck rather than for a caller of their own (the merge state — which also derives `changesRequested` from `detailed_merge_status`, the only place one merge-request read exposes a reviewer's blocking verdict — and standing approvals mapped to GitHub's `APPROVED` spelling; GitLab pins an approval to no commit and its approvals entity carries no SHA, so each verdict carries the merge request's current head and is only exactly right when the project resets approvals on new commits; approvals are Free while approval *rules* are Premium, and a changes-requested verdict lives on `reviewers[].state`). **The writes complete the contract (#485, phase 4 of 4):** `writes.ts` posts merge-request notes idempotently on the same shared `<!-- swarm-delivery:… -->` marker (skipping `system: true` notes, since GitLab files its own activity entries into the same listing and one of them quotes the note it describes), and maps a review verdict onto `approve` — passing `sha` so GitLab refuses an approval against a moved head, the pinning Bitbucket cannot do — or, for `request-changes`, onto `unapprove` plus the findings note, because a reviewer's `requested_changes` state has no REST endpoint on GitLab 19.1's surface at all; the verdict goes out *before* the marker note, which is what makes the note the retry anchor, and the note's id is the neutral review id since GitLab has no review object either. GitLab refuses a *redundant* verdict rather than absorbing it (approve → 401 once the account has approved, unapprove → 404 with nothing to withdraw), so exactly those two statuses are tolerated — otherwise every retry after a landed verdict and a failed note POST would strand the reviewer's findings unposted. `deliveryProvider` supplies the delivery seam per persona: commit identity from a single `GET /user` (both `username` and `email` in one request, unlike Bitbucket's second call), falling back to `<username>@users.noreply.gitlab.com` when the token's scope withholds the address — a commit then shows the right name but stays unlinked, since GitLab matches a **verified** account email; merge-request find/create; and the same expected-SHA `git push` the other two use, with the token in a `GIT_CONFIG_*` extraheader rather than argv, framed as Basic under GitLab's reserved `oauth2` user. `mergePullRequest` never throws: the direct merge is pinned to the approved head with `sha`, the full pre-merge recheck runs on every attempt (already merged → `merged`; moved head, draft, closed, changes requested, or dismissed approval → `not-eligible`), and GitLab's own third status table maps 409 → `not-eligible` (the pinned head moved inside the recheck window, so a fresh review is required), 405/422/406 → `not-ready`, 401/403 → `policy-blocked` (GitLab documents 401, not 403, for the merge permission refusal), anything else → `provider-error`; nothing maps to `unsupported`, since merge trains refuse with 405 until the required pipeline is green and then accept the direct merge. `operator-delivery.ts` supplies the DB-free worker's operator-credential seam with `submitReview` throwing, since reviewer verdicts belong to the control plane. Registration lands here too: `gitlab/index.ts` registers with `runtimeReady: false` and `listSCMProviders()` now returns `['github', 'bitbucket', 'gitlab']` — deliberately not before, because the conformance suite asserts that no *registered* provider stubs a contract method (`ai/TESTING.md` frames that as the gate on the third provider), so passing that gate was this phase's job rather than something an earlier phase exempted itself from. **Reachable since #619:** the manifest declares `runtimeReady: true`, so `requireProjectSCMProvider` routes a project stating `"scm": "gitlab"` here and the receiver mounts `/gitlab/webhook` from the same per-manifest loop that mounts GitHub's and Bitbucket's — **a GitLab project runs end to end.** Nothing shared had to be built for it: `listPullRequestsForCommit` landed with #618, so a **branch** pipeline (which names no merge request at all) gets its `workItemId`/`prBranch` from the receiver's neutral commit→merge-request read, while a merge-request pipeline skips that read because the payload already names one. Still out of scope: the GitLab 19.0 signing-token upgrade (see the next bullet), self-managed GitLab hosts, GitLab subgroup paths, and GraphQL.
- **The webhook trade-off #619 accepted, not deferred again.** Serving `/gitlab/webhook` makes GitLab's *sender* authentication live: `X-Gitlab-Token` carries the operator-chosen secret echoed verbatim, so unlike GitHub's and Bitbucket's HMAC nothing covers the body's integrity in transit. Judged **acceptable as-is** rather than a prerequisite — it is GitLab's own long-standing mechanism, `verifyGitLabWebhookToken` fails closed on an absent, empty, or mismatched token and compares in constant time, and an attacker able to tamper with or replay a delivery has already broken the TLS the secret itself travels under. GitLab 19.0's Standard-Webhooks signing tokens stay the recorded follow-up: they need `SCMProvider.verifyWebhookSignature` widened for the `webhook-id`/`webhook-timestamp` headers it never sees **and** a per-provider secret reference, since a GitLab-minted `whsec_…` key cannot be the operator-chosen secret the same project's PM webhook shares. The decision is recorded at the flag itself (`src/integrations/scm/gitlab/index.ts`).

Commit statuses marked `allow_failure`, including optional manual jobs, map to completed/skipped regardless of their raw status: GitLab excludes them from its pipeline result, so SWARM must not let them fail or defer the aggregate. Keeping them visible as skipped means an all-advisory pipeline remains reviewable.

### Worker & pipeline phases
- The BullMQ job consumer (SWARM-17) claims each wake-up's durable dispatch record (refusing cancelled/completed/superseded ones — issue #284), resolves the job through a Cascade-style trigger registry (`src/triggers/`, SWARM-53) and dispatches the matched trigger to its pipeline phase; the consumer resolves the phase, hands off to the orchestrator, and settles both the dispatch record and the job outcome from its result.
- Shared building blocks (`src/pipeline/`): per-task worktree lifecycle (`GitWorktreeManager`, `src/worker/git-worktree-manager.ts`, SWARM-14 — provisions an isolated worktree under `.swarm-workspaces/task-<id>/`, with a detached-HEAD mode for read-only phases), environment grafting (`graftEnvironment`, `src/worktree/graft.ts`, SWARM-15 — symlinks `node_modules`/`.env`/caches into it), and the agent-CLI execution engine (`src/harness/agent-cli.ts`, SWARM-16 — spawns `claude`/`antigravity`/`codex` with the worktree as CWD).
- All six phases are wired into the trigger registry:
  - **Planning** (SWARM-18) — detached worktree → Claude Code writes `proposed_plan.md` → posted on the linked Issue → moves the item to "ToDo" itself only if `pipeline.planning.autoAdvance` is on (default off).
  - **Implementation** (SWARM-19) — task-branch worktree → the agent implements/verifies and writes a structured hand-off → SWARM validates, commits, pushes, opens/reuses the PR, links it on the item, and moves it to "In review" when Review is enabled (otherwise it remains "In progress"). Either phase's agent CLI/model can be overridden per project via `swarm.config.json`'s `agents` block (`src/harness/models.ts`).
  - **Review** (SWARM-20) — detached worktree at the PR's head SHA → the reviewer agent writes a structured hand-off of fields → SWARM **renders** the review body from them (issue #470) and submits the formal review under the reviewer persona. The agent writes no layout: severity (`blocker`/`major`/`minor`/`nit`) picks between a full Evidence/Failure-scenario/Impact/Fix-plan/Tests treatment and a one-paragraph compact form, the hand-off schema enforces each tier's slots, the verdict as a function of the severity histogram, and the re-review rule that an unresolved carried item must be re-reported as a finding under its original id (so an approval can never sit above a "not addressed" disposition row), and the rendered header names the pass (Review / First re-review / Second re-review — the last marked as the final permitted verdict). A hand-off that fails that validation gets one repair pass, re-running the agent against the validator's own complaint, before the run fails. The verdict vocabulary is `approve` or `request-changes`: `comment` was removed because it cleared no review gate, dispatched no follow-up, and still consumed a verdict slot, so a PR that received one was silently terminal — a reviewer that cannot reach a verdict now fails its run instead. (Inbound, SWARM still observes a human's `commented` review.) A durable, restart-safe ledger (`review_verdicts`, issue #235) caps every PR at three submitted verdicts total — an initial review plus at most two re-reviews (`REVIEW_VERDICT_CAP`); a same PR/head retry reuses its existing slot rather than charging a new one, and once the cap is reached a further reservation — and the Review dispatch that would need it — is rejected. An authorized operator can deliberately continue past that stop once (**Force re-review**, issue #511): the grant is recorded on the capped ledger record itself and buys exactly one extra slot, spent by the next reservation, so the forced pass runs at ordinal 4 and — still being at or past the cap — stops the automatic cycle again rather than reopening it. Each permitted re-review is scoped, not a fresh full pass (issue #328): when a prior `request-changes` verdict already exists for the PR (`getPriorSubmittedReview`), the reviewer is told to verify only whether those requested changes were implemented correctly — approve when they were, otherwise request changes with a specific fix instruction — and not to surface pre-existing issues an earlier review missed. An opt-in approved review persists a durable merge dispatch that merges the PR directly under the implementer PAT, head-SHA-guarded (never GitHub's native auto-merge — issue #292), while any non-merged outcome remains non-fatal.
  - **Respond-to-review** (SWARM-21) — worktree on the existing task branch → the implementer addresses feedback and writes a structured response → SWARM commits/pushes any fix and posts the idempotent response. Stops automatically instead of dispatching once the reviewer persona's **last permitted** `changes_requested` verdict lands (the safety cap above) — that PR needs a human, and the run is recorded as `manual-intervention-required` rather than starting a further review cycle. The **Force re-review** action on that run's detail page (issue #511) is the supported way back in: it grants the extra review slot and enqueues the corrective run as a synthetic review event carrying `forcedReReview`, the one flag that stands the cap gate down, so the ordinary Respond-to-review → follow-up Review sequence resumes. Both writes are conditional (the grant fires only while none exists; the dispatch carries a deterministic per-(repo, PR, reviewed head) dedup key), so repeated clicks, concurrent requests, and refreshes resolve to one corrective cycle. A `fixed` outcome that actually pushed a new commit reliably enqueues exactly **one** follow-up Review for that new head SHA (issue #241) — through the same Review trigger, aggregate-check routing, reviewer persona, PR/head dedup, and review-verdict ledger a real webhook would use, so a follow-up approval can still trigger the same opt-in merge automation. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head enqueue nothing; the enqueue is part of this phase's own deterministic delivery (a deterministic per-(project, PR, head) job id, checkpointed after success) rather than a best-effort action, so queue retries, a worker restart mid-delivery, or a redelivered webhook can't duplicate the follow-up Review.
  - **Respond-to-CI** (SWARM-64) — worktree on that same task branch → the implementer fixes a failing check or reports no change → SWARM commits/pushes and posts the explanation.
  - **Resolve Conflicts** — worktree on a confirmed-conflicting PR branch → the implementer merges the current base, resolves conflicts, runs relevant checks, commits and pushes normally. Mergeability-null rechecks are coalesced and bounded; dispatch is deduplicated per PR/head/base state.
- Dispatch: a single **status-change handler** (`src/triggers/handlers/pm-status.ts`) re-reads the board item authoritatively and starts Planning or Implementation by the card's Status; **PR-lifecycle handlers** start Review (on a non-draft, same-repo, SWARM-managed PR opening or its checks passing) and Respond-to-review (by default, only on the reviewer persona submitting `changes_requested`; `skipOnMinors: false` also dispatches approvals and an inbound comment-only review — SWARM's own Review stopped submitting that verdict in issue #470).
- A **work-item origin gate** (`src/triggers/swarm-managed-pr.ts`, issue #397) reviews only PRs SWARM manages: the PR's head branch must decode to a work item under the project's `branchPrefix` *and* SWARM must hold an `implementation` run row for that item. It replaced the former author-persona gate, which skipped every federated PR now that the implementer credential is the worker operator's own account (ADR-004 §3). The gate runs once for both entry events, and still before the `checks` aggregate query so a PR we'd never review doesn't cost an Actions-API call; a run-history lookup failure degrades to the same bounded recheck as a failed mergeability fetch rather than dropping the review.
- On `checks` completion, the `pr-review` handler aggregates *every* check on the head SHA (via the Actions API) rather than trusting the single suite's own conclusion — reviewing, routing a failed suite to Respond-to-CI, or deferring with a coalesced ~30s recheck (`scheduleCoalescedDispatch`, #63) when the Actions API lags webhook delivery.
- A cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62) — a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, failing closed if Redis is down — ensures a PR that opens *and* then passes its checks is acted on once per commit, not once per event. The respond-to-ci path shares that slot and adds a per-PR fix-attempt cap (`src/triggers/respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- Revised from live end-to-end testing:
  - Planning no longer moves the item by default — a human reviews the plan and moves it to "ToDo" themselves, unless `autoAdvance` is enabled in the project settings.
  - Implementation triggers on "ToDo" rather than "In progress" — the phase itself moves the item to "In progress" as a status report once it picks up the task, not as the trigger (`src/pm/pipeline.ts`).
  - The Board view's drag-and-drop fires a `reordered` action with no field-value data, not `edited` as originally assumed — the router/trigger now accept `reordered` too, guarded by a Redis-backed dedup (`pm-status-dedup.ts`) against the harmless within-column reorders it also fires on.

### Worker resilience & queue
- **Agent session resume**: a rate-limited, response-stalled, or genuinely timed-out run — in **any** phase, on **any** CLI — is deferred with its worktree preserved and resumed on retry, continuing the same agent session instead of redoing its work (`claude --resume`, `agy --conversation <id>`, `codex exec resume <id>`). The session id is captured per CLI — all three report it in their own structured output, with Antigravity's `conversation_id` falling back to a diff of its conversation store (`src/harness/antigravity-session.ts`) when the stream carried none — and retention pins the checkout until the retry runs. A run whose session wasn't captured, or whose checkout was pruned, falls back to a fresh invocation.
- **Worktree preservation & recovery state**: when a run fails or is cancelled, its worktree and active CLI session can be preserved to prevent losing partial progress. If a recovery/resume is subsequently attempted, the worker executes a recovery gate to ensure the worktree is still valid (e.g. exists, has no conflicting live leases, or is clean if starting fresh). The dashboard surfaces the run's recovery state (`preserved`, `recovered`, or `blocked` with the specific reason: `dirty`, `unpushed`, `live-leased`, `resumable-owner`, `missing-validation`, or `checkpoint-divergent`), and the "Resume" action allows the operator to retry the run while continuing the prior agent session.
- **Checkpoint-seeded continuation (Tier 2)**: for the stops native session resume can't serve — no session id was captured, or a resume attempt itself failed (the expired/pruned session) — an implementer phase's preserved checkout is adopted on the strength of the checkpoint file the stopped run left in it, validated against the working tree actually on disk, run on a fresh session with no resume id, and seeded with the recorded remainder (so a continuation may even run on a different CLI than the stopped run did). **Tier 1 keeps absolute priority**: a run with a resumable session id behaves exactly as it did before. A selected fallback settles the run as `checkpointed` — a second retry-pending status, with a null `agent_session_id`, the parsed checkpoint on the row, and an incremented continuation count — and enqueues its continuation through the same durable dispatch that carries `resumeSession`, with `recoveryMode: 'checkpoint'`. Retention pins a `checkpointed` checkout by status rather than by session id, since it has none. The fallback is bounded by `pipeline.maxContinuations` (default 2, kept through a retry and cleared only by "Reset & restart"); exceeding it is a terminal failure that says the continuation budget was exhausted. A federated worker reports the same settle by attaching the checkpoint it parsed to its `deferred` frame — the control plane keeps the policy and the budget. A missing, malformed, or divergent checkpoint blocks (`missing-validation` / `checkpoint-divergent`) rather than silently continuing. The dashboard renders and drives the state (see the Dashboard section below), which completes Tier 2 (`docs/CHECKPOINTS.md`).
- **A continuation runs on the machine that holds its work** (issue #567). A preserved checkout — a Tier 2 checkpoint, a resumable session, a delivery sidecar — is machine-local with no server-side copy, and worker selection had no notion of where the state was: a continuation re-dispatched to any other eligible machine found nothing to adopt, provisioned a fresh checkout, and re-ran the phase from scratch at full token cost with nothing in the run record saying so (seen live on task 549, where "Continue now" restarted a checkpointed Implementation on a second machine three seconds after it created its own empty checkout). The settle that preserves a checkout now records the machine on the run (`recovery.preservedWorkerId`, no migration — the column is free-form `jsonb`) and it survives every later re-bind; the dispatch gate offers a continuation (`recoveryMode` `resume`/`checkpoint`, `resumeSession`, or a delivery resume — never `fresh`) **only** to that machine, ahead of assignee affinity. When it is busy or offline the dispatch waits under its own verdict (`preserved-worker-unavailable`, dispatch wait reason `preserved-worker`), **without a budget**: failing would abandon work still on disk and a timed fallback is the same defect with a delay, so the wait is unbounded and the run names the machine it is waiting for — on the dispatch row and in a run-detail callout, which distinguishes "currently waiting for this machine" from "merely pinned to it" by reading the active dispatch's wait reason — for as long as it waits. Ending it is an operator decision: "Reset & restart" releases the pin, needs nothing from the pinned machine (so it works while that machine is unreachable), and converts the record into `abandonedWorkerId`, so a run that started over instead of continuing says so afterwards. The two token-free re-check deferrals also stopped re-deriving recovery intent, which had been dropping a `'checkpoint'` mode and re-minting a `'resume'` session id on the very wait that was meant to preserve them.
- **A deferred dispatch says which kind of wait it is in** (issue #607). Every refusal from the eligibility gate used to record the same wait reason, so a dispatch waiting because a machine was momentarily busy or offline was indistinguishable, on the row and in the Queue, from one waiting because a human had to grant sharing consent, approve an enrollment, or widen an allowed phase — the first clears by itself in seconds, the second never clears until somebody acts (seen live as two dispatches deferred `reason=worker-unavailable retryDelayMs=300000` while both workers were idle, recorded only as `worker-eligibility`). The gate's whole reason vocabulary is now partitioned by one exported predicate, `isAvailabilityRefusal` (`src/worker/eligibility-gate.ts`) — a `Record` over the union, so a reason added later fails to compile until it is classified rather than defaulting silently into a bucket: an availability refusal keeps the dispatch wait reason `worker-eligibility` (unchanged, so the rows the incident produced still read correctly), while `missing-enrollment` / `missing-consent` / `missing-cli-capability` / `missing-phase-capability` / `phase-not-permitted` record `worker-authorization`, and the preserved-checkout pin keeps its own `preserved-worker` ahead of both. **Nothing about the timing changed**: same 5-minute cadence, same `workerEligibilityRecheckAttempt` counter, same budget, no migration (`wait_reason` is plain `text`), no new dispatch state and no new configuration. The Queue read model and the dashboard label the two waits apart ("waiting for an available worker" vs "waiting for a worker to be authorized"). Rows written before the deploy carry `worker-eligibility` even where the refusal was structural; each is re-classified by its own next re-check, so they age out within one interval. Waking an availability wait early is what the distinction unlocked — issue #610, below.
- **An availability-blocked dispatch starts as soon as a worker becomes available** (issue #610). The gate's refusal was deferred on a fixed timer and nothing woke it early, so work refused a moment before a worker connected — or a moment before one finished its run — sat still next to an idle machine for up to the full `SWARM_DEPENDENCY_RECHECK_MS` interval (seen live: two board deliveries deferred at 07:24:20Z/07:24:25Z with `retryDelayMs=300000`, both workers reconnected and idle from 07:24:46Z, nothing dispatched until 07:29:21Z — ≈4.5 minutes of dead time reading from the dashboard as "two workers are online and nothing is being picked up"). The wait is now event-driven, the way concurrency waits have been since issue #262: a worker's authenticated socket opening, and a dispatch bound to it settling (success, failure, cancellation, or deferral alike — the capacity-freed signal for a federated transport worker too), each promote the dispatches that were only waiting for that. A `worker-eligibility` row is woken by any worker routably enrolled in its project; a `preserved-worker` row only by its own recorded machine, enrolled there or not (issue #567), and its wait stays unbounded. A **structural** wait (`worker-authorization`, issue #607) is never promoted — a machine connecting cannot grant consent — so it keeps the timed cadence and its budget. An early wake cannot start the same dispatch twice or skip the gate: the delayed wake-up is removed before its replacement is published (so exactly one exists per row at any moment), the re-date is conditional on the wake sequence that was read (so two workers waking concurrently promote once), and the woken job re-enters the full eligibility evaluation spending the attempt budget the previous settle persisted rather than a fresh one. The timed re-check remains the fallback, `SWARM_DEPENDENCY_RECHECK_MS` / `SWARM_DEPENDENCY_MAX_WAIT_MS` keep their meanings, and there is no migration, no new dispatch state, and no new configuration. Every promotion logs which worker, what made it available, and how many dispatches it woke; a promotion failure is swallowed rather than failing the settled run that triggered it.
- A usage/session-limit hit from the agent CLI (`classifyAgentFailure`, `src/harness/agent-failure.ts`) doesn't fail the job outright — it's deferred and re-enqueued once the CLI's own reported reset time passes (SWARM-91).
- A transient provider-capacity hit (e.g., Anthropic's `529 Overloaded` or Codex's `at capacity`) is similarly deferred and re-enqueued fresh on its own capped backoff budget (issue #229).
- Not every classified failure is a retry signal: an **authentication/login** failure (an expired-and-unrefreshable OAuth session, `Not logged in · Please run /login`, or `Invalid API key · Please run /login`) is classified as its own `auth` kind and surfaced in the run headline as `… exited with code 1 (authentication failed) …` for every phase, so the operator sees the cause without opening the raw run output (issue #343). It stays **terminal** — waiting cannot restore a login, so it is never deferred or re-enqueued and consumes no rate-limit/capacity retry budget — while still triggering the recovery CLI/quota discovery that refreshes the dashboard's CLI status. The terminal-window scan recognises only CLI-owned `/login`, OAuth-session, and `authentication_error` markers, so CI logs or reviewed code that merely discuss authentication stay a plain `error`.
- That same defer-and-retry path also covers a run the *worker itself* killed (a dev `--watch` restart, a deploy, a graceful shutdown mid-phase) — previously indistinguishable from an unexplained agent crash, since an aborted `claude`/`agy` process can exit with empty output and no OS-reported signal. Both cases share one capped retry budget, with the retry delay floored above the review-dispatch-dedup TTL so it can't collide with a claim the interrupted run may have already taken.
- A genuinely-interrupted wall-clock timeout and an agent response stall (`stalled` kind, e.g. "timeout waiting for response") are deferred and resumed on the same shared retry budget (see the "Agent session resume" bullet above); only a timeout that still exited 0 (worktree already gone) is a terminal failure. For those terminal cases on PM-driven phases (planning/implementation), `reportPhaseFailureToBoard` appends a splitting suggestion to the failure comment, advising that the task's scope may be too large and should be split by hand.
- PM retries preserve their original phase dispatch separately from branch reuse: Implementation records an explicit checkpoint only after its task worktree is acquired, so an early failed/manual retry can re-enter the phase without falsely trying to check out a branch that was never created.
- Job-priority split: SCM jobs (`kind !== 'work-item'`) always dequeue ahead of PM-driven jobs (`kind === 'work-item'`), via `src/queue/producer.ts`'s `priorityFor`.
- Worker-global concurrency is configurable (`SWARM_WORKER_CONCURRENCY`, default 1), with an enforced per-project `maxConcurrentJobs` cap layered on top.
- Jobs older than 24 hours are discarded at worker pickup (`SWARM_MAX_JOB_AGE_MS` overrides this), so restarting a worker after an extended offline period cannot replay stale board activity.

### Cross-cutting
- One shared structured logger (`src/lib/logger.ts`, SWARM-23) emits JSON log lines (level, ISO timestamp, message, context) for machine parsing, with a `pretty` mode for local dev and a `SWARM_LOG_LEVEL` filter; the router and worker each tag their lines with a `component`.

  - **The queue lists work that is going to happen** (issue #570). A run with no recorded worker (unfederated, and every row predating the columns) gets `attribution: null` and renders the same neutral `—` the other optional fields use — never a raw UUID and never a fabricated owner; a *recorded* worker or user whose row no longer resolves degrades to its id in the muted style rather than losing the record, and a failed lookup degrades to ids-without-names instead of erroring the page. A historical row carrying `worker_id` but no `worker_user_id` attributes through the worker row's current `owner_user_id`. **GitHub References** additionally links `produced_pr_url` as **PR opened by this run**, labelled apart from the `PR #n` a Review / Respond-to-review run *acted on*, and a run whose only reference is that produced PR no longer reads as empty. Read-only and additive: the Runs table, the Queue section, and the phase-1 write paths are untouched.
- The **run list** names the machine too (issue #523): the Runs table's **Phase** column carries the executing worker's display name on a second, visually subordinate line beneath the phase (smaller, muted, mono, truncated with the full name on hover so a long name can't stretch the fixed-width column), and the below-`md` run cards carry it in the same lighter metadata line the phase already reads from. It is fed by an additive `workerName` on every `runs.list` row, resolved server-side — after the same project-access check the list already applies — by one *batched* `getWorkers` read over the page's distinct `worker_id`s, so a 50-row page costs one identity query rather than fifty. A run with no recorded worker, a worker whose row no longer resolves, and a failed lookup all yield `null` and render **no second line at all** rather than a dash, a UUID, or a stale machine — the list never implies a machine it can't name. The run detail page already names the machine in its **Execution Environment** grid (issue #446, above), so it is unchanged; the Queue section, filters, pagination, and every write path are untouched.

- A **Workers** screen (issues #133, #282, #473) at `/workers` lists the registered machines the viewer may see, backed by the `workers.list` query: machine display name, owner, online/offline (derived from the existing heartbeat TTL, with a relative last-seen time for offline machines and `Never connected` for one that never has), declared CLI capabilities, the **Active job** it is executing, and — per visible project — whether it is **Available** for automatic dispatch. The Capabilities cell lists the effective CLIs and **no phase at all** (issue #542): it used to lead with an amber `planning` badge when the daemon declared that phase, on the argument that a DB-free remote daemon declared every CLI and still refused Planning — issue #536 made every daemon run every phase, so the badge distinguished nothing while still reading as though Planning were a special, differently-trusted capability. The declared repertoire (`supportedPhases`, issue #467) is on the worker detail view instead, in full and with no phase promoted over another; the dispatch gate remains the authority either way (`missing-phase-capability`, `src/identity/worker-eligibility.ts`). It polls every 5s (no realtime transport). An instance administrator sees every worker, including un-enrolled machines; anyone else sees only workers enrolled in projects they can access, with inaccessible enrollments and any in-flight run from an inaccessible project withheld. **Active job** describes the run the way the Runs table's Task column does, over three lines: the executing phase (a leading line of its own, since this table has no Phase column), the resolved Issue/PR title, then its `Issue: #n` / `PR #n` reference — rendered by the same shared `WorkItemCell` component, with the title linking to the run detail page — rather than printing the run's UUID (issue #473); `workers.list` therefore returns a `currentRun` summary (run id, project, phase, work-item/PR title, URL and number) in place of the bare `currentRunId`, still exposed only while that run is `running` and its project is in the viewer's scope, and still assembled field-by-field so no job payload, error, or usage rides along. The **Available** column carries the owner-only sharing-consent switch (#282) and nothing else: it is actionable only for an enrollment the signed-in operator owns (established by its presence in `workers.listMine`, never inferred client-side) and calls `workers.setConsent`, which re-checks ownership server-side. Enabling applies directly; disabling first opens a confirmation making clear it blocks future automatic dispatch immediately but never kills a run already in progress. A worker the viewer does not own shows the same switch **disabled** — so a project administrator can still see that an enrolled worker is unavailable because its owner revoked sharing, with no machine path, token, or credential exposed and no control over it — and a project whose roster query is loading or failed shows an explained em dash rather than an implied `off`. Approval state, effective allowed CLIs and per-project busy/idle are deliberately **not** in the table (issue #473: they crowded the old Enrollment cell, and busy already reads off Active job) — they live on the detail view below, which is what that issue deferred them to. The table itself stays read-only apart from the consent switch: no machine paths, credentials, tokens, start/stop, or force-disconnect. The same roster is also a **Workers tab on the project detail page** (issue #574), directly after Runs and ahead of the configuration tabs: one shared `WorkersRoster` component renders both, so the scoped view *is* the `/workers` experience — status/capabilities, Active job, the owner consent switch, the 5s poll, row navigation to `/workers/$workerId`, and the loading/error/empty states — rather than a second panel that can drift. Scoping is the server's: `workers.list` takes an optional `projectId`, authorized by the project roster's own rule (a `contributor` reads it, a non-member gets `NOT_FOUND` so the roster and the project's existence stay hidden), and passes that single project as the read model's scope — so an enrollment in another project, an in-flight run outside it, and the un-enrolled machines an `instanceAdmin` otherwise sees never reach the browser, and the tab's Available column shows exactly one switch. The global `/workers` screen, the worker detail route, and every other project tab are unchanged. Both lists put **the signed-in operator's own machines first** (issue #657): `workers.list` orders the rows viewer-first before serializing them, so an operator scanning either view finds their own machines at the top. It is presentation order only — it runs after scoping has decided what is visible, so nothing about visibility, project scoping, ownership, or authorization moves — and the sort is stable, so machines keep their existing relative order within the viewer's own group and within everyone else's, and a viewer who owns no visible worker sees exactly the order they saw before.
- A **worker detail view** (issue #477) at `/workers/$workerId` opens on a row click and is where one machine is understood and administered; the table stays the scannable index. The selection is a route param rather than list state, so the URL deep-links and browser Back returns to the index (the shape `PhaseSettingsDetail` established for Agent Configuration), and it keeps the index's 5s polling so connectivity and the active job stay current while it is open. Its one source is a new `workers.getById` query — the same secret-free row `workers.list` returns, widened with the **full** enrollment detail per visible project (`getDashboardWorkerDetail`, `src/identity/worker-enrollment-service.ts`) and with two server-declared capability flags — so nothing is filtered client-side and no machine path, worker credential, credential hash, or project PAT exists on the surface to leak. Visibility is the same `accessibleProjectScope` rule as the list, and a worker the viewer may not see is the same `NOT_FOUND` as a missing one. It is grouped into sections: identity and owner (including the worker id the table drops), connectivity with last-seen, **both** declared capability axes in full — the agent CLIs and the whole `supportedPhases` repertoire, which is the only screen that states it (issue #542) — the active job (the same `WorkItemCell` description `/runs` gives it), and one block per project the machine is enrolled in. Each enrollment block states its approval status, effective allowed CLIs, effective allowed pipeline phases, concurrency allocation, sharing consent and derived routability, and — when it isn't routable — names the unmet conditions and whose they are, which is the "why is this machine not taking work here?" answer the table can't give. **Editing follows the authorization the server already enforces, with no new model invented**: sharing consent and the execution constraints (allowed CLIs, **allowed pipeline phases** — issue #509 — and concurrency allocation) are the worker owner's, over `workers.setConsent` / `workers.updateConstraints`; approval and suspend/reactivate are the project administrator's, over `workers.approveEnrollment` / `workers.setStatus`. `workers.getById` reports both capabilities per enrollment (`viewerIsOwner`, `viewerCanAdminister`) from the *same* ownership and `projectAdmin` checks those mutations re-run, so a viewer who may not change a value sees its state without a control that would fail (#473's pattern), and the mutations remain the enforcement point. Self-declared facts stay read-only — a daemon states its `capabilities`/`supportedPhases` at handshake, so the view reports them and never offers to edit them. Every mutation reports its outcome beside its own control (pending / saved / the server's message verbatim, e.g. the `BAD_REQUEST` for allowed CLIs exceeding the machine's capabilities), the two reduce-availability actions (revoking consent, suspending) confirm first and say they block only *future* dispatch, and a client-side guard keeps the last allowed CLI checked rather than sending a set the server must reject. **Allowed pipeline phases** (issue #509) is that same checkbox group for the second routing axis, and it is per *enrollment*, not per worker: the same machine may be eligible for `implementation` in one project and for everything in another, and the dispatch gate ANDs the selection with the daemon-declared `supportedPhases` (a candidate the enrollment does not permit is refused as `phase-not-permitted`, distinct from `missing-phase-capability` because the fix belongs to the worker's owner rather than to whoever operates the machine). It offers **every** phase rather than only the selectable ones and names what blocks the rest — a phase the machine's daemon does not declare, or one the project has switched off in `pipeline.<phase>.enabled` — since "not offered here" and "does not exist" are exactly what an operator needs to tell apart; those two conditions are the whole list, and `planning` is offered on exactly the same terms as the other five now that the instance-admin gate on it is gone (issue #542); such a phase cannot be *selected*, but an already-selected one can always be given up (a daemon re-declares its repertoire on reconnect and an administrator can flip a phase off, so an owner must never be stuck holding a phase they can't use). The daemon-declared repertoire stays read-only and keeps being refreshed on reconnect — it never overwrites the enrollment's selection — and a changed selection affects future dispatches only, exactly as revoking consent does. Enrollments that predate the field permit every phase, so dispatch behaviour is unchanged until an owner narrows one. Enrolling a machine into a *new* project is deliberately not here — offering a worker to a project is a different act from administering an existing enrollment, and stays with `swarm workers enroll`.
- The **Project Management** tab (issue #201, renamed and widened by #537) is a provider-ready project-detail screen that edits the configured provider's `pm` board mapping through board/status pickers instead of raw node-ID text entry, above a **credentials** section rendering whatever credential roles the project's PM provider declares (`projects.credentials.listPm`/`setPm`/`deletePm` — masked previews, encrypted at rest, no plaintext ever returned; a role that inherits a shared SCM credential stays read-only and points at the Source Control tab). It discovers the configured PM provider's boards and, for the selected board, its Status options through a new `pm` tRPC router (`pm.listProviders`/`discoverContainers`/`discoverStates`), which dispatches through the registered `PMProviderManifest` and the provider's new optional `discover()` capability — run under the project's own PM credential rather than any worker's SCM token (the browser never handles a credential). Discovery is `projectAdmin`-gated (a privileged read of the provider account's board catalogue), hides project existence from non-members, and turns an unconfigured PM credential into an actionable `PRECONDITION_FAILED` naming the role to set here. Persisted config is still the opaque node IDs; a saved board/status that can't be rediscovered is preserved behind neutral "configured value unavailable" copy until the operator deliberately changes it. The manifest supplies credential roles, their labels/descriptions, and the server-side discovery dispatch; the board/status picker catalogue supplies the correct GitHub Projects or Linear vocabulary. Issue #531 made the screen's projection helpers provider-aware, so it saves either provider's mapping — a GitHub Projects board + Status options, or a Linear team + workflow states — while provider changes stay in `swarm.config.json`, preventing ids from crossing config members.
