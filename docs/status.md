# Status

This is a snapshot of the implemented MVP. The [live GitHub Projects board](https://github.com/orgs/SmartTechBrewery/projects/6/views/1)
is the authoritative backlog and execution status.

Early implementation. Summary by area:

### Toolchain & persistence
- Node.js/TypeScript toolchain scaffolded: strict TS + ESM, `@/*` alias, Biome, Vitest, Lefthook, commitlint; `npm run verify` runs lint + typecheck + tests.
- Postgres persistence layer in place: Drizzle schema + migrations for project config, encrypted-at-rest credentials, and agent-run history.

### SCM layer
- The SCM provider self-registers through a manifest + registry loaded from the same canonical entrypoint as the PM one (`src/integrations/entrypoint.ts`), behind the provider-neutral `SCMProvider` contract (`src/scm/types.ts`) that `GitHubSCMIntegration` implements — so a consumer can resolve the whole contract by id without importing the concrete class. **Inbound now runs on it (#385):** the webhook receiver mounts one route per registered manifest and delegates header interpretation, signature verification, event parsing, and comment loop prevention to the provider; the durable queue envelope carries a provider id plus a normalized, provider-neutral event (`ScmEvent`, `src/scm/events.ts`, which also reads pre-#385 rows so in-flight dispatches survive a deploy); and the worker resolves the provider once at its composition root and injects it into the trigger context. **Outbound now runs on it too (#386):** the delivery-provider default in the five delivery-owning phases, the worker's control-plane local delegate, its run-row PR-title read and its phase-failure/interrupted-job PR comments, the durable merge executor's default merge capability, and the router's server-side worker-delivery default all resolve through the registry — by the durable job's own `providerId` where one is carried, otherwise by project (`requireProjectSCMProvider`, which asserts a single *runtime-ready* registered provider and throws rather than silently picking, so project→provider selection gets designed with the second provider that claims runtime readiness). Still concrete: the DB-free worker's operator-token delivery (`src/transport/assignment-execution.ts`), which awaits an operator-credential producer on the contract — Phase 2/2 of #386.
- **Bitbucket is registered but not usable (#296, phases 1–3 of 4).** `src/integrations/scm/bitbucket/` adds a credential-scoped Bitbucket **Cloud** client (`AsyncLocalStorage`, plain `fetch` — no new dependency), persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN`, reviewer from the same provider-neutral `credentials.reviewer` reference GitHub uses, so no config field was added), persona identity + loop-prevention helpers, and `BitbucketSCMIntegration implements SCMProvider` whose not-yet-built methods throw a message naming the method and the phase that fills it in. **Webhook ingress works (#455, phase 2 of 4):** `webhook.ts` verifies `X-Hub-Signature` as `sha256=<hex>` over the raw body through the shared timing-safe `verifyHmac` (failing closed, since Bitbucket omits the header for a secret-less hook), reads the event from `X-Event-Key` and the dedup identity from `X-Request-UUID`, and normalizes the eleven event keys SWARM acts on (PR lifecycle, approval / changes-requested, PR comment, commit status) into the neutral `ScmEvent` — everything else returns `null`. Two provider gaps are handled explicitly: Bitbucket has no review object, so `reviewId` is synthesized from PR + verdict + account `uuid` + head SHA (a format the issue-#235 verdict ledger keys on, so it must stay stable), and a `commit_status` payload carries no PR association at all, so `workItemId`/`prBranch` need a commit→PR lookup at whichever ingress layer serves the route. **The reads now work too (#456, phase 3 of 4):** `pull-requests.ts` implements PR details, title, merge state, participant approvals, the open-PRs-for-a-base conflict candidates (server-side `q=` filter, forks dropped), the aggregate commit build status (deduped by status `key`, newest `updated_on` wins, so a re-run's stale failure can't sink a green commit), and the commit→PR lookup — with `PullRequestDetails.mergeable` permanently `null`, since Bitbucket Cloud exposes no mergeability flag; the conflict handler reads that as "unknown" and exhausts its bounded rechecks rather than ever calling a PR cleanly mergeable. Its manifest still registers with `runtimeReady: false`, which is what makes the registration a no-op for GitHub: the project-scoped lookup counts only runtime-ready manifests, and the receiver mounts no `/bitbucket/webhook` route, so none of this code is reachable yet. Comments/delivery/merge are phase 4; **even after that, a Bitbucket project cannot run end to end** — nothing selects a project's SCM provider, which needs project→provider selection plus a served ingress route in a separate follow-up.
- Dual-persona (`implementer`/`reviewer`) credential scoping via `AsyncLocalStorage`, with per-persona token resolution from Postgres.
- The SCM receiver resolves the project (`findProjectByRepo`) and delegates loop prevention (`isSwarmGeneratedEvent`) to the provider adapter.
- The router serves the HTTP webhook receiver, now provider-neutral (issue #385): it mounts one POST route per registered, runtime-ready SCM manifest (`webhookRoute` — still only `POST /github/webhook`) and asks that provider to interpret its own headers, verify the HMAC-SHA256 signature, and normalize the body into an `ScmEvent`, then feeds it through an enqueue seam that shapes each verified event into a `SwarmJob` carrying the provider id, records it as a durable dispatch (dedup-keyed on the delivery id — ADR-002), and publishes its wake-up onto the `swarm-jobs` BullMQ queue (SWARM-35, issue #284).

### PM (GitHub Projects) integration
- The `projects_v2_item` board webhook is routed (SWARM's `pm:status-changed` ingress): a PM router adapter resolves the SWARM project by board node ID, filters to Status-field edits, and maps Status options to pipeline phases in a provider-agnostic way.
- The PM provider self-registers through a manifest + registry loaded from a single canonical entrypoint (`src/integrations/entrypoint.ts`), so the receiver resolves its adapter by id rather than hardcoding it (SWARM-13).
- The concrete GitHub Projects `PMProvider` (`src/integrations/pm/github-projects/provider.ts` — GraphQL item read/move plus linked-Issue comments) backs the two board-driven phases.

### Worker & pipeline phases
- The BullMQ job consumer (SWARM-17) claims each wake-up's durable dispatch record (refusing cancelled/completed/superseded ones — issue #284), resolves the job through a Cascade-style trigger registry (`src/triggers/`, SWARM-53) and dispatches the matched trigger to its pipeline phase; the consumer resolves the phase, hands off to the orchestrator, and settles both the dispatch record and the job outcome from its result.
- Shared building blocks (`src/pipeline/`): per-task worktree lifecycle (`GitWorktreeManager`, `src/worker/git-worktree-manager.ts`, SWARM-14 — provisions an isolated worktree under `.swarm-workspaces/task-<id>/`, with a detached-HEAD mode for read-only phases), environment grafting (`graftEnvironment`, `src/worktree/graft.ts`, SWARM-15 — symlinks `node_modules`/`.env`/caches into it), and the agent-CLI execution engine (`src/harness/agent-cli.ts`, SWARM-16 — spawns `claude`/`antigravity`/`codex` with the worktree as CWD).
- All six phases are wired into the trigger registry:
  - **Planning** (SWARM-18) — detached worktree → Claude Code writes `proposed_plan.md` → posted on the linked Issue → moves the item to "ToDo" itself only if `pipeline.planning.autoAdvance` is on (default off).
  - **Implementation** (SWARM-19) — task-branch worktree → the agent implements/verifies and writes a structured hand-off → SWARM validates, commits, pushes, opens/reuses the PR, links it on the item, and moves it to "In review" when Review is enabled (otherwise it remains "In progress"). Either phase's agent CLI/model can be overridden per project via `swarm.config.json`'s `agents` block (`src/harness/models.ts`).
  - **Review** (SWARM-20) — detached worktree at the PR's head SHA → the reviewer agent writes a structured hand-off of fields → SWARM **renders** the review body from them (issue #470) and submits the formal review under the reviewer persona. The agent writes no layout: severity (`blocker`/`major`/`minor`/`nit`) picks between a full Evidence/Failure-scenario/Impact/Fix-plan/Tests treatment and a one-paragraph compact form, the hand-off schema enforces each tier's slots, the verdict as a function of the severity histogram, and the re-review rule that an unresolved carried item must be re-reported as a finding under its original id (so an approval can never sit above a "not addressed" disposition row), and the rendered header names the pass (Review / First re-review / Second re-review — the last marked as the final permitted verdict). A hand-off that fails that validation gets one repair pass, re-running the agent against the validator's own complaint, before the run fails. The verdict vocabulary is `approve` or `request-changes`: `comment` was removed because it cleared no review gate, dispatched no follow-up, and still consumed a verdict slot, so a PR that received one was silently terminal — a reviewer that cannot reach a verdict now fails its run instead. (Inbound, SWARM still observes a human's `commented` review.) A durable, restart-safe ledger (`review_verdicts`, issue #235) caps every PR at three submitted verdicts total — an initial review plus at most two re-reviews (`REVIEW_VERDICT_CAP`); a same PR/head retry reuses its existing slot rather than charging a new one, and once the cap is reached a further reservation — and the Review dispatch that would need it — is rejected. Each permitted re-review is scoped, not a fresh full pass (issue #328): when a prior `request-changes` verdict already exists for the PR (`getPriorSubmittedReview`), the reviewer is told to verify only whether those requested changes were implemented correctly — approve when they were, otherwise request changes with a specific fix instruction — and not to surface pre-existing issues an earlier review missed. An opt-in approved review persists a durable merge dispatch that merges the PR directly under the implementer PAT, head-SHA-guarded (never GitHub's native auto-merge — issue #292), while any non-merged outcome remains non-fatal.
  - **Respond-to-review** (SWARM-21) — worktree on the existing task branch → the implementer addresses feedback and writes a structured response → SWARM commits/pushes any fix and posts the idempotent response. Stops automatically instead of dispatching once the reviewer persona's **last permitted** `changes_requested` verdict lands (the safety cap above) — that PR needs a human, and the run is recorded as `manual-intervention-required` rather than starting a further review cycle. A `fixed` outcome that actually pushed a new commit reliably enqueues exactly **one** follow-up Review for that new head SHA (issue #241) — through the same Review trigger, aggregate-check routing, reviewer persona, PR/head dedup, and review-verdict ledger a real webhook would use, so a follow-up approval can still trigger the same opt-in merge automation. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head enqueue nothing; the enqueue is part of this phase's own deterministic delivery (a deterministic per-(project, PR, head) job id, checkpointed after success) rather than a best-effort action, so queue retries, a worker restart mid-delivery, or a redelivered webhook can't duplicate the follow-up Review.
  - **Respond-to-CI** (SWARM-64) — worktree on that same task branch → the implementer fixes a failing check or reports no change → SWARM commits/pushes and posts the explanation.
  - **Resolve Conflicts** — worktree on a confirmed-conflicting PR branch → the implementer merges the current base, resolves conflicts, runs relevant checks, commits and pushes normally. Mergeability-null rechecks are coalesced and bounded; dispatch is deduplicated per PR/head/base state.
- Dispatch: a single **status-change handler** (`src/triggers/handlers/pm-status.ts`) re-reads the board item authoritatively and starts Planning or Implementation by the card's Status; **PR-lifecycle handlers** start Review (on a non-draft, same-repo, SWARM-managed PR opening or its checks passing) and Respond-to-review (by default, only on the reviewer persona submitting `changes_requested`; `skipOnMinors: false` also dispatches approvals and an inbound comment-only review — SWARM's own Review stopped submitting that verdict in issue #470).
- A **work-item origin gate** (`src/triggers/swarm-managed-pr.ts`, issue #397) reviews only PRs SWARM manages: the PR's head branch must decode to a work item under the project's `branchPrefix` *and* SWARM must hold an `implementation` run row for that item. It replaced the former author-persona gate, which skipped every federated PR now that the implementer credential is the worker operator's own account (ADR-004 §3). The gate runs once for both entry events, and still before the `checks` aggregate query so a PR we'd never review doesn't cost an Actions-API call; a run-history lookup failure degrades to the same bounded recheck as a failed mergeability fetch rather than dropping the review.
- On `checks` completion, the `pr-review` handler aggregates *every* check on the head SHA (via the Actions API) rather than trusting the single suite's own conclusion — reviewing, routing a failed suite to Respond-to-CI, or deferring with a coalesced ~30s recheck (`scheduleCoalescedDispatch`, #63) when the Actions API lags webhook delivery.
- A cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62) — a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, failing closed if Redis is down — ensures a PR that opens *and* then passes its checks is acted on once per commit, not once per event. The respond-to-ci path shares that slot and adds a per-PR fix-attempt cap (`src/triggers/respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- Revised from live end-to-end testing:
  - Planning no longer moves the item by default — a human reviews the plan and moves it to "ToDo" themselves, unless `autoAdvance` is enabled in the project settings.
  - Implementation triggers on "ToDo" rather than "In progress" — the phase itself moves the item to "In progress" as a status report once it picks up the task, not as the trigger (`src/pm/pipeline.ts`).
  - The Board view's drag-and-drop fires a `reordered` action with no field-value data, not `edited` as originally assumed — the router/trigger now accept `reordered` too, guarded by a Redis-backed dedup (`pm-status-dedup.ts`) against the harmless within-column reorders it also fires on.

### Worker resilience & queue
- **Agent session resume**: a rate-limited, response-stalled, or genuinely timed-out run — in **any** phase, on **any** CLI — is deferred with its worktree preserved and resumed on retry, continuing the same agent session instead of redoing its work (`claude --resume`, `agy --conversation <id>`, `codex exec resume <id>`). The session id is captured per CLI (claude/codex report it in their output; Antigravity's is recovered from its conversation store, `src/harness/antigravity-session.ts`), and retention pins the checkout until the retry runs. A run whose session wasn't captured, or whose checkout was pruned, falls back to a fresh invocation.
- **Worktree preservation & recovery state**: when a run fails or is cancelled, its worktree and active CLI session can be preserved to prevent losing partial progress. If a recovery/resume is subsequently attempted, the worker executes a recovery gate to ensure the worktree is still valid (e.g. exists, has no conflicting live leases, or is clean if starting fresh). The dashboard surfaces the run's recovery state (`preserved`, `recovered`, or `blocked` with the specific reason: `dirty`, `unpushed`, `live-leased`, or `missing-validation`), and the "Resume" action allows the operator to retry the run while continuing the prior agent session.
- A usage/session-limit hit from the agent CLI (`classifyAgentFailure`, `src/harness/agent-failure.ts`) doesn't fail the job outright — it's deferred and re-enqueued once the CLI's own reported reset time passes (SWARM-91).
- A transient provider-capacity hit (e.g., Anthropic's `529 Overloaded` or Codex's `at capacity`) is similarly deferred and re-enqueued fresh on its own capped backoff budget (issue #229).
- That same defer-and-retry path also covers a run the *worker itself* killed (a dev `--watch` restart, a deploy, a graceful shutdown mid-phase) — previously indistinguishable from an unexplained agent crash, since an aborted `claude`/`agy` process can exit with empty output and no OS-reported signal. Both cases share one capped retry budget, with the retry delay floored above the review-dispatch-dedup TTL so it can't collide with a claim the interrupted run may have already taken.
- A genuinely-interrupted wall-clock timeout and an agent response stall (`stalled` kind, e.g. "timeout waiting for response") are deferred and resumed on the same shared retry budget (see the "Agent session resume" bullet above); only a timeout that still exited 0 (worktree already gone) is a terminal failure. For those terminal cases on PM-driven phases (planning/implementation), `reportPhaseFailureToBoard` appends a splitting suggestion to the failure comment, advising that the task's scope may be too large and should be split by hand.
- PM retries preserve their original phase dispatch separately from branch reuse: Implementation records an explicit checkpoint only after its task worktree is acquired, so an early failed/manual retry can re-enter the phase without falsely trying to check out a branch that was never created.
- Job-priority split: SCM jobs (`kind !== 'work-item'`) always dequeue ahead of PM-driven jobs (`kind === 'work-item'`), via `src/queue/producer.ts`'s `priorityFor`.
- Worker-global concurrency is configurable (`SWARM_WORKER_CONCURRENCY`, default 1), with an enforced per-project `maxConcurrentJobs` cap layered on top.
- Jobs older than 24 hours are discarded at worker pickup (`SWARM_MAX_JOB_AGE_MS` overrides this), so restarting a worker after an extended offline period cannot replay stale board activity.

### Cross-cutting
- One shared structured logger (`src/lib/logger.ts`, SWARM-23) emits JSON log lines (level, ISO timestamp, message, context) for machine parsing, with a `pretty` mode for local dev and a `SWARM_LOG_LEVEL` filter; the router and worker each tag their lines with a `component`.
- Antigravity's actual binary is `agy`, and its `-p`/`--print` flag — unlike Claude's, which is a bare boolean — takes the prompt as its own value: it must be the last flag before the prompt, or it silently swallows whatever comes next as the "prompt" instead (confirmed live: a real Implementation run answered a question about `--dangerously-skip-permissions` instead of doing the task). See the `DEFAULT_ARGS`/`PRINT_FLAG` comment in `src/harness/agent-cli.ts` and `ai/RULES.md` §6.

### Dashboard (phase-6 backlog)
- Host-run, same model as the worker. API scaffold in place: Hono + tRPC entrypoint (`src/api/server.ts`, SWARM-75) and its localhost-bound bearer-token auth guard (SWARM-76).
- `projectsRepository` has full CRUD primitives (SWARM-77); a `projects` tRPC router (list/getById/create/update/delete, SWARM-78) is implemented and up for review, not yet merged into `appRouter`.
- `runsRepository` has full CRUD, upsert, and pagination primitives for agent-run history (SWARM-102), ready for future dashboard API/UI integration.
- Runs record per-phase token usage where the agent CLI reports it (issue #138). Antigravity has no structured-output flag, so its run usage remains gracefully unavailable.
- A running or deferred run can be terminated from its detail page (issue #166). Terminating a running run stops its agent; terminating a deferred run cancels its scheduled retry. Both settle as a failed run with the neutral `Run cancelled after a cancellation request.` outcome, and a terminated deferred run cannot be automatically resumed. The dashboard's `terminate` action additionally records a structured cancellation origin (`source: 'dashboard'`, plus `actor` only when identity is available) alongside that neutral outcome (issue #308); the run detail page shows it beneath the neutral message only when one was actually recorded — a marker-only (external/unknown) cancellation and every legacy row show no source/actor, never an inferred one.
- `runs.queued` (issues #234, #284) surfaces every canonical waiting dispatch — `waiting`/`prioritized` (eligible now), `blocked` (waiting on a free project slot), and `delayed` (scheduled retries/rechecks) — read from the durable dispatch table, never a BullMQ snapshot, so nothing pending can be invisible; each item carries its wait reason, attempt count, and linked run id where one exists. Supports a "Put back" action (issue #251) that cancels the canonical dispatch (nothing can resurrect it) and returns its linked board card to the backlog, with a best-effort (non-authoritative) phase hint that upgrades to the worker-resolved phase once known. Every pending `pull_request`/`check_suite` job whose hint is `review` also carries `reviewGate` diagnostic metadata (source event/action, head SHA, recheck attempt) distinguishing a raw lifecycle event/recheck from an authoritative phase-dispatch decision (issue #275); the web layer groups pending review-gate rows sharing the same project, repo, PR number, and head SHA into one logical row (e.g. a Respond-to-review push's synthetic follow-up alongside GitHub's own `pull_request:synchronize` webhook), so it reads as "waiting for a review decision/checks" with a source-event count and diagnostics rather than as several queued Review agents — different PRs/SHAs are never grouped, and every other row still renders one-to-one. The web layer likewise folds *fresh* board (`github-projects`) dispatches sharing the same project and board-item node id into one row reporting how many queued events for that card were collapsed (issue #366) — one card drag fires both a `reordered` and an `edited` `projects_v2_item` delivery, whose differing delivery ids can never share a dedup key — while a dispatch that already owns a run or whose phase already resolved to `planning`/`implementation` always keeps its own row, and the dispatch flow itself is untouched (the redundant dispatches re-read authoritative board state at claim time and no-op). A compact **Queued** section (issue #238) renders this above the Runs table on both the global `/runs` route and the project-scoped Runs tab: each item shows its project (global view only), the same **Task** work-item labels as the Runs table, a phase hint, a neutral non-pulsing **Queued** badge, and enqueue/scheduled timing. GitHub Projects cards resolve their backing Issue/PR title and URL on the API side; lookup failures fall back safely. The section is hidden entirely when nothing is queued, preserves the server's dispatch order (no client re-sort), polls so items appear/disappear as work is enqueued/picked up, and never touches the existing runs table, filters, or pagination.
- The run detail page (`/runs/$runId`) surfaces the worker→PR attribution the run row records (ADR-004 §4, issue #446 — the read half of issue #398). Its **Execution Environment** grid gains **Worker** and **Worker owner** fields, resolved server-side by `runs.getById` into an additive `attribution` object (`{ workerId, workerName, userId, userDisplayName }`) from the row's `worker_id`/`worker_user_id` — via the same `getWorker` + `getUserById` pair the Workers screen uses, after the procedure's project-access check, so no identity read happens for a caller who may not see the run. A run with no recorded worker (unfederated / single-user, and every row predating the columns) gets `attribution: null` and renders the same neutral `—` the other optional fields use — never a raw UUID and never a fabricated owner; a *recorded* worker or user whose row no longer resolves degrades to its id in the muted style rather than losing the record, and a failed lookup degrades to ids-without-names instead of erroring the page. A historical row carrying `worker_id` but no `worker_user_id` attributes through the worker row's current `owner_user_id`. **GitHub References** additionally links `produced_pr_url` as **PR opened by this run**, labelled apart from the `PR #n` a Review / Respond-to-review run *acted on*, and a run whose only reference is that produced PR no longer reads as empty. Read-only and additive: the Runs table, the Queue section, and the phase-1 write paths are untouched.
- A `dashboard/` scaffold (Vite + React, TanStack Router/Query, a tRPC client, Tailwind and the `ai/DESIGN_SYSTEM.md` tokens, SWARM-81) is merged; the first real screen (projects list + create dialog, SWARM-82) is implemented.
- The `credentials` tRPC sub-router (list/set/delete, SWARM-79) is implemented under `projectsRouter`, exposing `credentialsRepository` database primitives over the dashboard API; `scm.verifyGithubToken` (SWARM-80) validates a pasted PAT against the GitHub API without storing it.
- The SCM/credentials screen (SWARM-85) is a project-detail tab that manages the three credential references (implementer/reviewer PAT, webhook secret) over `projects.credentials.*`, verifies each PAT via `scm.verifyGithubToken` before saving, and warns — without blocking — when both PATs resolve to the same GitHub login.
- A **Workers** screen (issues #133, #282, #473) at `/workers` lists the registered machines the viewer may see, backed by the `workers.list` query: machine display name, owner, online/offline (derived from the existing heartbeat TTL, with a relative last-seen time for offline machines and `Never connected` for one that never has), declared CLI capabilities, the **Active job** it is executing, and — per visible project — whether it is **Available** for automatic dispatch. It polls every 5s (no realtime transport). An instance administrator sees every worker, including un-enrolled machines; anyone else sees only workers enrolled in projects they can access, with inaccessible enrollments and any in-flight run from an inaccessible project withheld. **Active job** describes the run the way the Runs table's Task column does — the resolved Issue/PR title over its `Issue: #n` / `PR #n` reference, rendered by the same shared `WorkItemCell` component, with the title linking to the run detail page — rather than printing the run's UUID (issue #473); `workers.list` therefore returns a `currentRun` summary (run id, project, phase, work-item/PR title, URL and number) in place of the bare `currentRunId`, still exposed only while that run is `running` and its project is in the viewer's scope, and still assembled field-by-field so no job payload, error, or usage rides along. The **Available** column carries the owner-only sharing-consent switch (#282) and nothing else: it is actionable only for an enrollment the signed-in operator owns (established by its presence in `workers.listMine`, never inferred client-side) and calls `workers.setConsent`, which re-checks ownership server-side. Enabling applies directly; disabling first opens a confirmation making clear it blocks future automatic dispatch immediately but never kills a run already in progress. A worker the viewer does not own shows the same switch **disabled** — so a project administrator can still see that an enrolled worker is unavailable because its owner revoked sharing, with no machine path, token, or credential exposed and no control over it — and a project whose roster query is loading or failed shows an explained em dash rather than an implied `off`. Approval state, effective allowed CLIs and per-project busy/idle are deliberately **not** on this screen (issue #473: they crowded the old Enrollment cell, and busy already reads off Active job); they remain on `workers.roster` for a later surface. Everything else stays read-only — no machine paths, credentials, tokens, start/stop, force-disconnect, approval, or routing controls.
- The **Board Mapping** tab (issue #201) is a provider-ready project-detail screen that edits the `githubProjects` mapping through provider/board/status pickers instead of raw node-ID text entry. It discovers the configured PM provider's boards and, for the selected board, its Status options through a new `pm` tRPC router (`pm.listProviders`/`discoverContainers`/`discoverStates`), which dispatches through the registered `PMProviderManifest` and the provider's new optional `discover()` capability — GitHub Projects runs the reads under the project's implementer token (the browser never handles a credential). Discovery is `projectAdmin`-gated (a privileged read of the provider account's board catalogue), hides project existence from non-members, and points a missing implementer token at the Source Control tab. Persisted config is still the opaque node IDs; a saved board/status that can't be rediscovered is preserved behind neutral "configured value unavailable" copy until the operator deliberately changes it. GitHub Projects remains the sole PM provider — the panel and API are provider-agnostic so Jira/Linear/Trello can slot in behind the same pickers, but none is implemented.
- Still backlog: the remaining per-project settings screens (SWARM-86–87).
