GitLab 19.0's Standard-Webhooks signing tokens would close that gap but need the `verifyWebhookSignature` contract widened (the signed message uses `webhook-id` / `webhook-timestamp` headers it never sees) **and** a per-provider secret reference (a GitLab-minted `whsec_…` key cannot be the operator-chosen secret the PM webhook shares), so they are a recorded follow-up rather than this phase. It normalizes merge-request lifecycle, approval/unapproval, merge-request notes, and pipelines into the neutral `ScmEvent`; everything else — issues, pushes, tags, wikis, system notes, notes on non-merge-request targets, and a body whose `object_kind` contradicts the header — returns `null`. Two provider gaps are handled explicitly: GitLab exposes no review object, so `reviewId` is synthesized as `<iid>:<verdict>:<user id>:<head SHA>` (a format the issue-#235 verdict ledger keys on, so it must stay stable), and it has **no "request changes" merge-request action** — verified against GitLab 19.1's webhook reference, whose action vocabulary is `open`/`close`/`reopen`/`update`/`approval`/`approved`/`unapproval`/`unapproved`/`merge` — so that verdict is derived from the *acting* reviewer's own `reviewers[].state === 'requested_changes'`; the limitation is that a later `update` by the same reviewer, while that state still stands, reads as the same verdict again (the ledger's two-verdict cap absorbs it while the head is unchanged). A branch pipeline carries no merge request at all, so `workItemId`/`prBranch` stay unset and phase 3's commit→merge-request lookup is what ties such an event back to one, and the pipeline status vocabulary lives in `pipelines.ts` so an event and an API read never spell one pipeline two ways (an *unrecognized* status is deliberately non-terminal, so the aggregate decision defers rather than judging a pipeline it doesn't understand). **The reads work (#484, phase 3 of 4):** `merge-requests.ts` implements the four contract reads over the phase-1 client with the same persona defaults the other two adapters use (merge request → reviewer, title → implementer, aggregate checks → reviewer, conflict candidates → implementer), and reuses `pipelines.ts` unchanged for commit statuses since GitLab spells them with the pipeline vocabulary. `PullRequestDetails.mergeable` carries GitLab's real tri-state — unlike Bitbucket's permanent `null`, so the conflict-resolution side-car actually decides here: `merge_status` is preferred because it is the *git-only* signal the contract's `mergeable` means (deprecated in 15.6, hence a documented `detailed_merge_status` fallback that also covers the undocumented `cannot_be_merged_recheck`), where `conflict`/`commits_status` → `false`, `checking`/`preparing`/`unchecked` → `null`, and every other blocker (`not_approved`, `ci_still_running`, `draft_status`, `need_rebase`, …) → `true`, because `mergeable` means "no merge conflict" and not "policy satisfied". `baseSha` is `diff_refs.base_sha`, the **merge base** rather than GitHub's target-branch tip, which is the stable value the conflict claim key needs; a missing `iid`, branch, `sha`, or base SHA throws rather than being replaced by a stand-in, since those are exact-match key material. Conflict candidates filter server-side, drop forks, then cost one single-merge-request read per survivor: GitLab's *list* response omits `diff_refs` and serves a cached `merge_status`, while reading a single merge request is itself what asks GitLab to recompute mergeability — which is also what makes the trigger's bounded recheck converge. Commit statuses dedupe by `name` keeping the newest `finished_at ?? created_at`, so a re-run's stale failure can't make a green commit look failed. Two reads exist for phase 4's merge-eligibility recheck rather than for a caller of their own (the merge state — which also derives `changesRequested` from `detailed_merge_status`, the only place one merge-request read exposes a reviewer's blocking verdict — and standing approvals mapped to GitHub's `APPROVED` spelling; GitLab pins an approval to no commit and its approvals entity carries no SHA, so each verdict carries the merge request's current head and is only exactly right when the project resets approvals on new commits; approvals are Free while approval *rules* are Premium, and a changes-requested verdict lives on `reviewers[].state`). **The writes complete the contract (#485, phase 4 of 4):** `writes.ts` posts merge-request notes idempotently on the same shared `<!-- swarm-delivery:… -->` marker (skipping `system: true` notes, since GitLab files its own activity entries into the same listing and one of them quotes the note it describes), and maps a review verdict onto `approve` — passing `sha` so GitLab refuses an approval against a moved head, the pinning Bitbucket cannot do — or, for `request-changes`, onto `unapprove` plus the findings note, because a reviewer's `requested_changes` state has no REST endpoint on GitLab 19.1's surface at all; the verdict goes out *before* the marker note, which is what makes the note the retry anchor, and the note's id is the neutral review id since GitLab has no review object either. GitLab refuses a *redundant* verdict rather than absorbing it (approve → 401 once the account has approved, unapprove → 404 with nothing to withdraw), so exactly those two statuses are tolerated — otherwise every retry after a landed verdict and a failed note POST would strand the reviewer's findings unposted. `deliveryProvider` supplies the delivery seam per persona: commit identity from a single `GET /user` (both `username` and `email` in one request, unlike Bitbucket's second call), falling back to `<username>@users.noreply.gitlab.com` when the token's scope withholds the address — a commit then shows the right name but stays unlinked, since GitLab matches a **verified** account email; merge-request find/create; and the same expected-SHA `git push` the other two use, with the token in a `GIT_CONFIG_*` extraheader rather than argv, framed as Basic under GitLab's reserved `oauth2` user. `mergePullRequest` never throws: the direct merge is pinned to the approved head with `sha`, the full pre-merge recheck runs on every attempt (already merged → `merged`; moved head, draft, closed, changes requested, or dismissed approval → `not-eligible`), and GitLab's own third status table maps 409 → `not-eligible` (the pinned head moved inside the recheck window, so a fresh review is required), 405/422/406 → `not-ready`, 401/403 → `policy-blocked` (GitLab documents 401, not 403, for the merge permission refusal), anything else → `provider-error`; nothing maps to `unsupported`, since merge trains refuse with 405 until the required pipeline is green and then accept the direct merge. `operator-delivery.ts` supplies the DB-free worker's operator-credential seam with `submitReview` throwing, since reviewer verdicts belong to the control plane. Registration lands here too: `gitlab/index.ts` registers with `runtimeReady: false` and `listSCMProviders()` now returns `['github', 'bitbucket', 'gitlab']` — deliberately not before, because the conformance suite asserts that no *registered* provider stubs a contract method (`ai/TESTING.md` frames that as the gate on the third provider), so passing that gate was this phase's job rather than something an earlier phase exempted itself from. So **a GitLab project still cannot run end to end** — nothing selects a project's SCM provider and no `/gitlab/webhook` route is served, which needs project→provider selection plus a served ingress route in the same separate follow-up Bitbucket waits on. ### Worker & pipeline phases
- The BullMQ job consumer (SWARM-17) claims each wake-up's durable dispatch record (refusing cancelled/completed/superseded ones — issue #284), resolves the job through a Cascade-style trigger registry (`src/triggers/`, SWARM-53) and dispatches the matched trigger to its pipeline phase; the consumer resolves the phase, hands off to the orchestrator, and settles both the dispatch record and the job outcome from its result.
- Shared building blocks (`src/pipeline/`): per-task worktree lifecycle (`GitWorktreeManager`, `src/worker/git-worktree-manager.ts`, SWARM-14 — provisions an isolated worktree under `.swarm-workspaces/task-<id>/`, with a detached-HEAD mode for read-only phases), environment grafting (`graftEnvironment`, `src/worktree/graft.ts`, SWARM-15 — symlinks `node_modules`/`.env`/caches into it), and the agent-CLI execution engine (`src/harness/agent-cli.ts`, SWARM-16 — spawns `claude`/`antigravity`/`codex` with the worktree as CWD).
- All six phases are wired into the trigger registry:
  - **Planning** (SWARM-18) — detached worktree → Claude Code writes `proposed_plan.md` → posted on the linked Issue → moves the item to "ToDo" itself only if `pipeline.planning.autoAdvance` is on (default off).
  - **Implementation** (SWARM-19) — task-branch worktree → the agent implements/verifies and writes a structured hand-off → SWARM validates, commits, pushes, opens/reuses the PR, links it on the item, and moves it to "In review" when Review is enabled (otherwise it remains "In progress"). Either phase's agent CLI/model can be overridden per project via `swarm.config.json`'s `agents` block (`src/harness/models.ts`).
  - **Review** (SWARM-20) — detached worktree at the PR's head SHA → the reviewer agent writes a structured hand-off of fields → SWARM **renders** the review body from them (issue #470) and submits the formal review under the reviewer persona. The agent writes no layout: severity (`blocker`/`major`/`minor`/`nit`) picks between a full Evidence/Failure-scenario/Impact/Fix-plan/Tests treatment and a one-paragraph compact form, the hand-off schema enforces each tier's slots, the verdict as a function of the severity histogram, and the re-review rule that an unresolved carried item must be re-reported as a finding under its original id (so an approval can never sit above a "not addressed" disposition row), and the rendered header names the pass (Review / First re-review / Second re-review — the last marked as the final permitted verdict). A hand-off that fails that validation gets one repair pass, re-running the agent against the validator's own complaint, before the run fails. The verdict vocabulary is `approve` or `request-changes`: `comment` was removed because it cleared no review gate, dispatched no follow-up, and still consumed a verdict slot, so a PR that received one was silently terminal — a reviewer that cannot reach a verdict now fails its run instead. (Inbound, SWARM still observes a human's `commented` review.) A durable, restart-safe ledger (`review_verdicts`, issue #235) caps every PR at three submitted verdicts total — an initial review plus at most two re-reviews (`REVIEW_VERDICT_CAP`); a same PR/head retry reuses its existing slot rather than charging a new one, and once the cap is reached a further reservation — and the Review dispatch that would need it — is rejected. Each permitted re-review is scoped, not a fresh full pass (issue #328): when a prior `request-changes` verdict already exists for the PR (`getPriorSubmittedReview`), the reviewer is told to verify only whether those requested changes were implemented correctly — approve when they were, otherwise request changes with a specific fix instruction — and not to surface pre-existing issues an earlier review missed. An opt-in approved review persists a durable merge dispatch that merges the PR directly under the implementer PAT, head-SHA-guarded (never GitHub's native auto-merge — issue #292), while any non-merged outcome remains non-fatal.
  - **Respond-to-review** (SWARM-21) — worktree on the existing task branch → the implementer addresses feedback and writes a structured response → SWARM commits/pushes any fix and posts the idempotent response. Stops automatically instead of dispatching once the reviewer persona's **last permitted** `changes_requested` verdict lands (the safety cap above) — that PR needs a human, and the run is recorded as `manual-intervention-required` rather than starting a further review cycle. A `fixed` outcome that actually pushed a new commit reliably enqueues exactly **one** follow-up Review for that new head SHA (issue #241) — through the same Review trigger, aggregate-check routing, reviewer persona, PR/head dedup, and review-verdict ledger a real webhook would use, so a follow-up approval can still trigger the same opt-in merge automation. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head enqueue nothing; the enqueue is part of this phase's own deterministic delivery (a deterministic per-(project, PR, head) job id, checkpointed after success) rather than a best-effort action, so queue retries, a worker restart mid-delivery, or a redelivered webhook can't duplicate the follow-up Review.
  - **Respond-to-CI** (SWARM-64) — worktree on that same task branch → the implementer fixes a failing check or reports no change → SWARM commits/pushes and posts the explanation.
  - **Resolve Conflicts** — worktree on a confirmed-conflicting PR branch → the implementer merges the current base, resolves conflicts, runs relevant checks, commits and pushes normally. Mergeability-null rechecks are coalesced and bounded; dispatch is deduplicated per PR/head/base state.
- Dispatch: a single **status-change handler** (`src/triggers/handlers/pm-status.ts`) re-reads the board item authoritatively and starts Planning or Implementation by the card's Status; **PR-lifecycle handlers** start Review (on a non-draft, same-repo, SWARM-managed PR opening or its checks passing) and Respond-to-review (by default, only on the reviewer persona submitting `changes_requested`; `skipOnMinors: false` also dispatches approvals and an inbound comment-only review — SWARM's own Review stopped submitting that verdict in issue #470).
- A **work-item origin gate** (`src/triggers/swarm-managed-pr.ts`, issue #397) reviews only PRs SWARM manages: the PR's head branch must decode to a work item under the project's `branchPrefix` *and* SWARM must hold an `implementation` run row for that item. It replaced the former author-persona gate, which skipped every federated PR now that the implementer credential is the worker operator's own account (ADR-004 §3). The gate runs once for both entry events, and still before the `checks` aggregate query so a PR we'd never review doesn't cost an Actions-API call; a run-history lookup failure degrades to the same bounded recheck as a failed mergeability fetch rather than dropping the review.
- On `checks` completion, the `pr-review` handler aggregates *every* check on the head SHA (via the Actions API) rather than trusting the single suite's own conclusion — reviewing, routing a failed suite to Respond-to-CI, or deferring with a coalesced ~30s recheck (`scheduleCoalescedDispatch`, #63) when the Actions API lags webhook delivery.
- A cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62) — a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, failing closed if Redis is down — ensures a PR that opens *and* then passes its checks is acted on once per commit, not once per event. The respond-to-ci path shares that slot and adds a per-PR fix-attempt cap (`src/triggers/respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- Revised from live end-to-end testing:
  - Planning no longer moves the item by default — a human reviews the plan and moves it to "ToDo" themselves, unless `autoAdvance` is enabled in the project settings.
  - Implementation triggers on "ToDo" rather than "In progress" — the phase itself moves the item to "In progress" as a status report once it picks up the task, not as the trigger (`src/pm/pipeline.ts`).
  - The Board view's drag-and-drop fires a `reordered` action with no field-value data, not `edited` as originally assumed — the router/trigger now accept `reordered` too, guarded by a Redis-backed dedup (`pm-status-dedup.ts`) against the harmless within-column reorders it also fires on.

### Worker resilience & queue
- **Agent session resume**: a rate-limited, response-stalled, or genuinely timed-out run — in **any** phase, on **any** CLI — is deferred with its worktree preserved and resumed on retry, continuing the same agent session instead of redoing its work (`claude --resume`, `agy --conversation <id>`, `codex exec resume <id>`). The session id is captured per CLI — all three report it in their own structured output, with Antigravity's `conversation_id` falling back to a diff of its conversation store (`src/harness/antigravity-session.ts`) when the stream carried none — and retention pins the checkout until the retry runs. A run whose session wasn't captured, or whose checkout was pruned, falls back to a fresh invocation.
- **Worktree preservation & recovery state**: when a run fails or is cancelled, its worktree and active CLI session can be preserved to prevent losing partial progress. If a recovery/resume is subsequently attempted, the worker executes a recovery gate to ensure the worktree is still valid (e.g. exists, has no conflicting live leases, or is clean if starting fresh). The dashboard surfaces the run's recovery state (`preserved`, `recovered`, or `blocked` with the specific reason: `dirty`, `unpushed`, `live-leased`, `resumable-owner`, `missing-validation`, or `checkpoint-divergent`), and the "Resume" action allows the operator to retry the run while continuing the prior agent session.
- **Checkpoint-seeded continuation (Tier 2) — mechanism only, not yet reachable**: for the stops native session resume can't serve (an expired/pruned session, a surviving worktree whose session is gone, a continuation that has to run on a different CLI), the gate has a third mode that adopts a preserved checkout on the strength of the checkpoint file the stopped run left in it — validated against the working tree actually on disk, run on a fresh session with no resume id, and seeded with the recorded remainder. Nothing selects that mode in production yet; the policy that will is still to build (`docs/CHECKPOINTS.md`).
- A usage/session-limit hit from the agent CLI (`classifyAgentFailure`, `src/harness/agent-failure.ts`) doesn't fail the job outright — it's deferred and re-enqueued once the CLI's own reported reset time passes (SWARM-91).
- A transient provider-capacity hit (e.g., Anthropic's `529 Overloaded` or Codex's `at capacity`) is similarly deferred and re-enqueued fresh on its own capped backoff budget (issue #229).
- Not every classified failure is a retry signal: an **authentication/login** failure (an expired-and-unrefreshable OAuth session, `Not logged in · Please run /login`, or `Invalid API key · Please run /login`) is classified as its own `auth` kind and surfaced in the run headline as `… exited with code 1 (authentication failed) …` for every phase, so the operator sees the cause without opening the raw run output (issue #343). It stays **terminal** — waiting cannot restore a login, so it is never deferred or re-enqueued and consumes no rate-limit/capacity retry budget — while still triggering the recovery CLI/quota discovery that refreshes the dashboard's CLI status. The terminal-window scan recognises only CLI-owned `/login`, OAuth-session, and `authentication_error` markers, so CI logs or reviewed code that merely discuss authentication stay a plain `error`.
- That same defer-and-retry path also covers a run the *worker itself* killed (a dev `--watch` restart, a deploy, a graceful shutdown mid-phase) — previously indistinguishable from an unexplained agent crash, since an aborted `claude`/`agy` process can exit with empty output and no OS-reported signal. Both cases share one capped retry budget, with the retry delay floored above the review-dispatch-dedup TTL so it can't collide with a claim the interrupted run may have already taken.
- A genuinely-interrupted wall-clock timeout and an agent response stall (`stalled` kind, e.g. "timeout waiting for response") are deferred and resumed on the same shared retry budget (see the "Agent session resume" bullet above); only a timeout that still exited 0 (worktree already gone) is a terminal failure. For those terminal cases on PM-driven phases (planning/implementation), `reportPhaseFailureToBoard` appends a splitting suggestion to the failure comment, advising that the task's scope may be too large and should be split by hand.
- PM retries preserve their original phase dispatch separately from branch reuse: Implementation records an explicit checkpoint only after its task worktree is acquired, so an early failed/manual retry can re-enter the phase without falsely trying to check out a branch that was never created.
- Job-priority split: SCM jobs (`kind !== 'work-item'`) always dequeue ahead of PM-driven jobs (`kind === 'work-item'`), via `src/queue/producer.ts`'s `priorityFor`.
- Worker-global concurrency is configurable (`SWARM_WORKER_CONCURRENCY`, default 1), with an enforced per-project `maxConcurrentJobs` cap layered on top.
- Jobs older than 24 hours are discarded at worker pickup (`SWARM_MAX_JOB_AGE_MS` overrides this), so restarting a worker after an extended offline period cannot replay stale board activity.

### Cross-cutting
- One shared structured logger (`src/lib/logger.ts`, SWARM-23) emits JSON log lines (level, ISO timestamp, message, context) for machine parsing, with a `pretty` mode for local dev and a `SWARM_LOG_LEVEL` filter; the router and worker each tag their lines with a `component`.
- Antigravity's actual binary is `agy`, and its `-p`/`--print` flag — unlike Claude's, which is a bare boolean — takes the prompt as its own value: it must be the last flag before the prompt, or it silently swallows whatever comes next as the "prompt" instead (confirmed live: a real Implementation run answered a question about `--dangerously-skip-permissions` instead of doing the task). See the `DEFAULT_ARGS`/`PRINT_FLAG` comment in `src/harness/agent-cli.ts` and `ai/RULES.md` §6.

Every pending `pull_request`/`check_suite` job whose hint is `review` also carries `reviewGate` diagnostic metadata (source event/action, head SHA, recheck attempt) distinguishing a raw lifecycle event/recheck from an authoritative phase-dispatch decision (issue #275); the web layer groups pending review-gate rows sharing the same project, repo, PR number, and head SHA into one logical row (e.g. a Respond-to-review push's synthetic follow-up alongside GitHub's own `pull_request:synchronize` webhook), so it reads as "waiting for a review decision/checks" with a source-event count and diagnostics rather than as several queued Review agents — different PRs/SHAs are never grouped, and every other row still renders one-to-one. The web layer likewise folds *fresh* board (`pm`) dispatches sharing the same project and board-item node id into one row reporting how many queued events for that card were collapsed (issue #366) — one card drag fires both a `reordered` and an `edited` `projects_v2_item` delivery, whose differing delivery ids can never share a dedup key — while a dispatch that already owns a run or whose phase already resolved to `planning`/`implementation` always keeps its own row, and the dispatch flow itself is untouched (the redundant dispatches re-read authoritative board state at claim time and no-op). A compact **Queued** section (issue #238) renders this above the Runs table on both the global `/runs` route and the project-scoped Runs tab: each item shows its project (global view only), the same **Task** work-item labels as the Runs table, a phase hint, a neutral non-pulsing **Queued** badge, and enqueue/scheduled timing. GitHub Projects cards resolve their backing Issue/PR title and URL on the API side; lookup failures fall back safely. The section is hidden entirely when nothing is queued, preserves the server's dispatch order (no client re-sort), polls so items appear/disappear as work is enqueued/picked up, and never touches the existing runs table, filters, or pagination.

A run with no recorded worker (unfederated / single-user, and every row predating the columns) gets `attribution: null` and renders the same neutral `—` the other optional fields use — never a raw UUID and never a fabricated owner; a *recorded* worker or user whose row no longer resolves degrades to its id in the muted style rather than losing the record, and a failed lookup degrades to ids-without-names instead of erroring the page. A historical row carrying `worker_id` but no `worker_user_id` attributes through the worker row's current `owner_user_id`. **GitHub References** additionally links `produced_pr_url` as **PR opened by this run**, labelled apart from the `PR #n` a Review / Respond-to-review run *acted on*, and a run whose only reference is that produced PR no longer reads as empty. Read-only and additive: the Runs table, the Queue section, and the phase-1 write paths are untouched.

- A **Workers** screen (issues #133, #282, #473) at `/workers` lists the registered machines the viewer may see, backed by the `workers.list` query: machine display name, owner, online/offline (derived from the existing heartbeat TTL, with a relative last-seen time for offline machines and `Never connected` for one that never has), declared CLI capabilities, the **Active job** it is executing, and — per visible project — whether it is **Available** for automatic dispatch. The Capabilities cell leads with a violet `planning` badge when the machine's daemon declared that phase (`supportedPhases`, issue #467, now carried on the dashboard read model): it is the one capability an operator cannot infer from the machine's tooling — a DB-free remote daemon declares every CLI and still refuses Planning (`SUPPORTED_DB_FREE_PHASES`) — and it decides whether board work can start there at all. The other declared phases stay off the cell; the dispatch gate remains the authority either way (`missing-phase-capability`, `src/identity/worker-eligibility.ts`). It polls every 5s (no realtime transport). An instance administrator sees every worker, including un-enrolled machines; anyone else sees only workers enrolled in projects they can access, with inaccessible enrollments and any in-flight run from an inaccessible project withheld. **Active job** describes the run the way the Runs table's Task column does, over three lines: the executing phase (a leading line of its own, since this table has no Phase column), the resolved Issue/PR title, then its `Issue: #n` / `PR #n` reference — rendered by the same shared `WorkItemCell` component, with the title linking to the run detail page — rather than printing the run's UUID (issue #473); `workers.list` therefore returns a `currentRun` summary (run id, project, phase, work-item/PR title, URL and number) in place of the bare `currentRunId`, still exposed only while that run is `running` and its project is in the viewer's scope, and still assembled field-by-field so no job payload, error, or usage rides along. The **Available** column carries the owner-only sharing-consent switch (#282) and nothing else: it is actionable only for an enrollment the signed-in operator owns (established by its presence in `workers.listMine`, never inferred client-side) and calls `workers.setConsent`, which re-checks ownership server-side. Enabling applies directly; disabling first opens a confirmation making clear it blocks future automatic dispatch immediately but never kills a run already in progress. A worker the viewer does not own shows the same switch **disabled** — so a project administrator can still see that an enrolled worker is unavailable because its owner revoked sharing, with no machine path, token, or credential exposed and no control over it — and a project whose roster query is loading or failed shows an explained em dash rather than an implied `off`. Approval state, effective allowed CLIs and per-project busy/idle are deliberately **not** in the table (issue #473: they crowded the old Enrollment cell, and busy already reads off Active job) — they live on the detail view below, which is what that issue deferred them to. The table itself stays read-only apart from the consent switch: no machine paths, credentials, tokens, start/stop, or force-disconnect.
- A **worker detail view** (issue #477) at `/workers/$workerId` opens on a row click and is where one machine is understood and administered; the table stays the scannable index. The selection is a route param rather than list state, so the URL deep-links and browser Back returns to the index (the shape `PhaseSettingsDetail` established for Agent Configuration), and it keeps the index's 5s polling so connectivity and the active job stay current while it is open. Its one source is a new `workers.getById` query — the same secret-free row `workers.list` returns, widened with the **full** enrollment detail per visible project (`getDashboardWorkerDetail`, `src/identity/worker-enrollment-service.ts`) and with two server-declared capability flags — so nothing is filtered client-side and no machine path, worker credential, credential hash, or project PAT exists on the surface to leak. Visibility is the same `accessibleProjectScope` rule as the list, and a worker the viewer may not see is the same `NOT_FOUND` as a missing one. It is grouped into sections: identity and owner (including the worker id the table drops), connectivity with last-seen, **both** declared capability axes in full — the agent CLIs and the whole `supportedPhases` repertoire, not just the `planning` badge — the active job (the same `WorkItemCell` description `/runs` gives it), and one block per project the machine is enrolled in. Each enrollment block states its approval status, effective allowed CLIs, effective allowed pipeline phases, concurrency allocation, sharing consent and derived routability, and — when it isn't routable — names the unmet conditions and whose they are, which is the "why is this machine not taking work here?" answer the table can't give. **Editing follows the authorization the server already enforces, with no new model invented**: sharing consent and the execution constraints (allowed CLIs, **allowed pipeline phases** — issue #509 — and concurrency allocation) are the worker owner's, over `workers.setConsent` / `workers.updateConstraints`; approval and suspend/reactivate are the project administrator's, over `workers.approveEnrollment` / `workers.setStatus`. `workers.getById` reports both capabilities per enrollment (`viewerIsOwner`, `viewerCanAdminister`) from the *same* ownership and `projectAdmin` checks those mutations re-run, so a viewer who may not change a value sees its state without a control that would fail (#473's pattern), and the mutations remain the enforcement point. Self-declared facts stay read-only — a daemon states its `capabilities`/`supportedPhases` at handshake, so the view reports them and never offers to edit them. Every mutation reports its outcome beside its own control (pending / saved / the server's message verbatim, e.g. the `BAD_REQUEST` for allowed CLIs exceeding the machine's capabilities), the two reduce-availability actions (revoking consent, suspending) confirm first and say they block only *future* dispatch, and a client-side guard keeps the last allowed CLI checked rather than sending a set the server must reject. **Allowed pipeline phases** (issue #509) is that same checkbox group for the second routing axis, and it is per *enrollment*, not per worker: the same machine may be eligible for `implementation` in one project and for everything in another, and the dispatch gate ANDs the selection with the daemon-declared `supportedPhases` (a candidate the enrollment does not permit is refused as `phase-not-permitted`, distinct from `missing-phase-capability` because the fix belongs to the worker's owner rather than to whoever operates the machine). It offers **every** phase rather than only the selectable ones and names what blocks the rest — a phase the machine's daemon does not declare, or one the project has switched off in `pipeline.<phase>.enabled` — since "not offered here" and "does not exist" are exactly what an operator needs to tell apart; such a phase cannot be *selected*, but an already-selected one can always be given up (a daemon re-declares its repertoire on reconnect and an administrator can flip a phase off, so an owner must never be stuck holding a phase they can't use). The daemon-declared repertoire stays read-only and keeps being refreshed on reconnect — it never overwrites the enrollment's selection — and a changed selection affects future dispatches only, exactly as revoking consent does. Enrollments that predate the field permit every phase, so dispatch behaviour is unchanged until an owner narrows one. Enrolling a machine into a *new* project is deliberately not here — offering a worker to a project is a different act from administering an existing enrollment, and stays with `swarm workers enroll`.
- The **Board Mapping** tab (issue #201) is a provider-ready project-detail screen that edits the `pm` board mapping through provider/board/status pickers instead of raw node-ID text entry. It discovers the configured PM provider's boards and, for the selected board, its Status options through a new `pm` tRPC router (`pm.listProviders`/`discoverContainers`/`discoverStates`), which dispatches through the registered `PMProviderManifest` and the provider's new optional `discover()` capability — GitHub Projects runs the reads under the project's implementer token (the browser never handles a credential). Discovery is `projectAdmin`-gated (a privileged read of the provider account's board catalogue), hides project existence from non-members, and points a missing implementer token at the Source Control tab. Persisted config is still the opaque node IDs; a saved board/status that can't be rediscovered is preserved behind neutral "configured value unavailable" copy until the operator deliberately changes it. GitHub Projects remains the sole PM provider — the panel and API are provider-agnostic so Jira/Linear/Trello can slot in behind the same pickers, but none is implemented.
