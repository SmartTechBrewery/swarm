# Operations

This guide covers local setup, dashboard access, operator commands, ports,
database migrations, and webhook exposure. The short setup path remains in the
root [README](../README.md); this is the detailed operational reference.

## Running the stack (local)

Postgres, Redis, and the router run in Docker Compose; the **worker runs on the host**:

```bash
cp .env.docker.example .env   # adjust POSTGRES_PASSWORD / ports if needed
docker compose up -d --build  # postgres, redis, router (NOT the worker) — detached
npm run db:migrate            # apply the Postgres schema (uses DATABASE_URL from .env)
npm run db:seed               # load swarm.config.json into Postgres (projects + credentials)
npm run swarm -- users add you@example.com --admin   # create the first user, then:
npm run swarm -- users set-password you@example.com   # set their dashboard login password (prompts, no echo)
cd dashboard && npm install && cd .. # install dashboard (frontend) dependencies
npm run dev:api               # start the API server on the host (default port 3101)
npm run dev:dashboard         # start the Vite dev server (default port 5173)
npm run dev:worker            # start the worker on the host (or: npm run build && npm run start:worker) — the same program a remote worker runs, pointed at the router over loopback
```
`swarm start`, `npm run dev:api`, and their production start variants apply pending
committed migrations before serving requests. `npm run dev:worker` does **not** — it
holds no `DATABASE_URL` (the router and the API server own migrations; see "Process
responsibilities" in `ai/ARCHITECTURE.md`). The worker is intentionally stable: source
edits do not restart it and abort a live agent. Use `npm run dev:worker:watch` only
while developing the worker itself and when no real pipeline run is active. The
explicit `npm run db:migrate` step remains useful for setup and maintenance, and is safe
to run repeatedly.

The dashboard can be run in two modes:

- **Development Mode (with Hot-Reloading)**:
  Run the backend API and the Vite development server side-by-side:
  ```bash
  npm run dev:api               # Starts the API server on port 3101
  npm run dev:dashboard         # Starts the Vite dev server on port 5173
  ```
  Open `http://localhost:5173` in your browser. Code changes will hot-reload automatically.

- **Self-Hosted Mode (Production Build)**:
  Because the compiled assets under `dashboard/dist` are ignored in git, you must compile the frontend assets if you want the API server to serve the SPA statically. You can run both steps with a single command:
  ```bash
  npm run start:api             # Compiles the dashboard SPA and starts the API server on port 3101
  ```
  Open `http://localhost:3101` in your browser. The API server will serve the compiled files as a fallback for any non-API/non-health routes.

The dashboard uses **per-user session auth** (issue #281 task 2). It binds to `127.0.0.1` and every dashboard API request except `/health` and the `ping` liveness probe is authorized by a session cookie, not a shared secret. A user signs in at `/login` (username/email + password); the server verifies the password, mints an opaque session, and returns it as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost). Log out to revoke it. Set a user up first with `swarm users add` + `swarm users set-password` (below). There is no `DASHBOARD_TOKEN` anymore. Once signed in, a user changes their own display name and password themselves at `/profile?tab=security` (issue #662) — the password change requires their current password, and other devices they are signed in on stay signed in.

You can verify the dashboard API is running using `curl`:
```bash
# /health check requires no authentication
curl http://localhost:3101/health

# Log in — the session cookie lands in cookies.txt; the raw token is never in the body
curl -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"identifier":"you@example.com","password":"…"}' \
  http://localhost:3101/auth/login

# Authenticated tRPC request, reusing the session cookie
curl -b cookies.txt http://localhost:3101/trpc/auth.me
```

The `swarm` operator CLI (`src/cli/`, SWARM-22) wraps the config + stack steps above:

- `swarm init` — scaffolds `.env` (from `.env.docker.example`) and a `swarm.config.json` project-config template, validating it if one already exists.
- `swarm config apply` (a.k.a. `npm run db:seed`, SWARM-56) — loads that file's projects and their referenced credentials into Postgres, which is where the router and worker actually resolve config from (`swarm.config.json` is otherwise scaffold/documentation only). `npm run db:seed` runs with `--env-file=.env`, so it sees `DATABASE_URL` and credential secrets automatically; standalone `swarm config apply` reads only the ambient environment — export those vars first, or just use `npm run db:seed` (a reference whose env var is unset is silently skipped).
- `swarm start [--build]` / `swarm stop [-v]` — bring the Compose stack up/down.
- `swarm status` — shows the container states and probes the router's `/health`.
- `swarm logs [service] [-f]` — tails the logs.
- `swarm queue clear` (a.k.a. `npm run queue:clear`) — cancels every waiting dispatch (pending, capacity-blocked, and retry-scheduled — the canonical durable queue, issue #284) and drains their queued wake-ups plus any legacy jobs from Redis. Cancelled dispatches can never be resurrected by a retry, slot release, or reconciliation. It deliberately does not cancel an active run; stop the worker first when clearing work before restarting it. Requires both `DATABASE_URL` and `REDIS_URL`.
- `swarm worktrees prune [--project <id>] [--dry-run]` (a.k.a. `npm run worktrees:prune`) — reclaims stale `task-<id>` worktrees under `.swarm-workspaces/` that are safe to discard: no longer leased (in-flight), not pinned by a resumable deferred/failed run, with no uncommitted changes **and** no unpushed local commits. Anything protected is skipped and left in place. On a worker's host-local lease store (`src/worktree/host-local-runtime.ts`) "still leased" is a bounded answer: every liveness check there consults the lease's 4h expiry **first** (issue #717), so a marker left behind by a crashed or leaked owner stops counting as in-flight once it lapses, rather than making the sweep skip that checkout indefinitely. The same sweep also **reaps** those lapsed host-local coordination markers themselves under `.swarm-workspaces/.swarm-state` (issue #721) — an expired lock directory, preservation pin or takeover guard, plus a preservation staging file (`*.tmp`) stranded by a crash mid-write. Nothing else does: every one of those TTLs is otherwise only ever evaluated by the next provisioner for that same task, so a task never dispatched again kept its debris forever. Each artifact is judged by its own TTL (4h lease, 24h pin, 5min guard), one still inside it is never touched, an unrecognised entry there is left entirely alone, and `--dry-run` names what it would remove without removing it. Every path swept is printed and logged, because the artifact names are opaque `<sha256>` hashes — the log line is where an operator can connect one back to a task.
- `swarm run reset <runId>` (issue #429) — the per-run **last-resort recovery** for a *wedged* run: one whose dispatch, cancellation flag, worktree lease, and recovery record disagree badly enough that neither "Retry now" nor "Terminate" can move it. In one sequence it cancels the run's active dispatch, clears its Redis cancellation flag, settles its checkout and worktree lease, clears its recovery record, and re-dispatches the phase from scratch — printing one line per step (including the new dispatch id) so you can tell a reset that actually freed the checkout from one that left it for the worker holding it to clear. A reset — this command or the dashboard's identical "Reset & restart" button, both over the same service — is the only **immediate** path that can release a stale `live-leased` lease — a lease marker no live run owns, which `swarm worktrees prune` honours and therefore skips — and the only one that also clears the run's dispatch, cancellation and recovery state. It is no longer the only path at all: a DB-free worker's **host-local** lease (a `.swarm-state` file on that worker's own filesystem, which no control-plane action reaches) lapses by itself once it outlives its 4h expiry, and the next run for the task takes it over (issue #717). That backstop matters precisely *because* a reset cannot touch a file on another host — before it existed, a lease whose owner had leaked out of the daemon's in-flight set wedged a task for hours until that daemon was restarted. It settles a checkout on *this* host's local disk directly, not only Postgres and Redis; a checkout on another worker is settled by that worker when it provisions the restart, following the recovery intent the restart carries (issue #592) — so it can be run from anywhere. **The restart is composed as a first attempt** (issue #741): no resumed agent session, no adopted delivery progress, no already-provisioned task branch, and no recovery mode an earlier attempt chose — only the reset's own `'discard'`. The run row's stored payload is sanitised the same way, so a second reset, or a later "Retry now", cannot replay a latch either. This is not cosmetic: a run whose payload recorded a provisioned branch used to re-provision *without creating it* on every reset and die on `fatal: invalid reference: <branch>`, while an ordinary fresh dispatch of the same task ran fine. **It always discards and never refuses** (issue #744): there is no `--force` to remember, so one command cancels a dispatch a worker claimed a moment ago, removes the checkout with any uncommitted changes and unpushed commits **on whichever worker holds it**, and resets a run still marked `running` without it being terminated first. **It stops that run's agent itself** (issue #745), which is what ended the two-step "Terminate, then Reset" dance: before anything is torn down it records the same run-id-keyed cancellation Terminate records — which the router turns into a pushed `task-cancel` frame to the worker actually executing the run, the only channel a DB-free worker has — and then waits, bounded, for the row to leave `running`, so the dying attempt settles the *old* dispatch instead of landing on top of the restart. That attempt's uncommitted work goes with the checkout. A stop that is never confirmed within the wait is reported (`agent: … had not confirmed within the wait`) and the restart happens anyway — reset still never refuses. A local teardown that throws is reported and stepped over rather than blocking the restart. A run that cannot be re-dispatched at all — no stored job payload, or a project that no longer exists — has its dispatch, flag and recovery record cleared just the same and is then settled as `failed` with the stated reason, reported as `not restarted` on a normal exit 0 rather than refused. Only an unknown run id and a reset already under way exit non-zero, and neither leaves a run un-reset. Requires both `DATABASE_URL` and `REDIS_URL`, and works with the worker and the API stopped — it is the terminal equivalent of the dashboard's "Reset & restart" button on the run-detail page.
- `swarm users <add|list|grant-admin|revoke-admin|set-password>` — manages SWARM users and their dashboard credentials (the multi-user foundation, issue #281): `add <identifier> [--name <displayName>] [--admin]` creates a user by login handle (username/email) and optionally makes them the installation admin; `list` lists them; `grant-admin`/`revoke-admin <identifier>` toggle the installation-admin role; `set-password <identifier>` sets the user's dashboard login password (prompts without echo on a TTY, or reads it from stdin for scripting — never logged). Requires `DATABASE_URL`. A user needs a password set before they can sign in to the dashboard. `set-password` stays how an operator sets that *first* password or recovers a forgotten one; changing a password you can already sign in with is self-service on the dashboard's Security tab (issue #662), which requires the current one.
- `swarm members <add|list|set-role|remove>` — manages project membership (the multi-user foundation, issue #281): `add <project-id> <user-identifier> [--role <role>]` adds a user (by login handle) to a project with a per-project role (`projectAdmin | member | contributor`, default `member`); `list <project-id>` lists a project's members; `set-role <project-id> <user-identifier> --role <role>` changes an existing member's role; `remove <project-id> <user-identifier>` removes them. Roles rank `projectAdmin` (administer) > `member` (write) > `contributor` (read). Requires `DATABASE_URL`. Membership is enforced by every project-keyed tRPC procedure (`src/api/authz.ts`), and since issue #805 the same four operations are also reachable over the API as the `members` router (each gated at `projectAdmin`) — this CLI remains the `DATABASE_URL`-side path, unchanged.
- `swarm identities <link|unlink|list>` — links a SWARM user to the handles they own on a provider (assignee resolution, issue #130): `link --user <identifier> --provider <provider> --handle <handle>` links a provider handle (e.g. a GitHub login) to a user looked up by login handle; `unlink --provider <p> --handle <h>` removes the link; `list [--user <identifier>]` lists every link, or one user's. `<provider>` is a provider-neutral source key (`github-projects` for the GitHub Projects board); provider and handle are matched case-insensitively, and a handle maps to at most one user — re-linking the same pair is a no-op, pointing it at a second user is refused. Requires `DATABASE_URL`. Links are read by assignee resolution (`src/identity/assignee-resolver.ts`); nothing routes on them yet.

It manages only the containerized stack — the worker still runs on the host (`npm run dev:worker`). Run it from source with `npm run swarm -- <command>`, or `npm run build` and invoke the `swarm` bin directly. The `npm run swarm` wrapper loads `.env` automatically (via `--env-file-if-exists=.env`, so `swarm init` still works before `.env` exists), so DB-backed subcommands like `users` and `members` see `DATABASE_URL`/`DATABASE_SSL` without exporting them first. The bare `swarm` bin reads only the ambient environment — export those vars (or use the `npm run swarm --` wrapper) when running it directly.

The worker isn't containerized because it provisions Git worktrees and spawns the `claude` / `antigravity` CLIs — those need the developer's own PATH, authentication, and config, which a container wouldn't have. Running it on the host is the local-first fit. It connects to the Compose Redis/Postgres over their published host ports (`REDIS_URL` / `DATABASE_URL` in `.env`), so **`git` and the `claude` / `antigravity` CLIs must be installed and authenticated on your machine** for the worker to get past provision/spawn.

The Postgres schema (project config + credentials at rest) is defined with **Drizzle** in `src/db/` — `npm run db:generate` regenerates migrations from the schema, `npm run db:migrate` applies them. Credentials are encrypted with AES-256-GCM before storage when `CREDENTIAL_MASTER_KEY` is set (plaintext otherwise, for local dev).

SWARM's host ports are offset from Cascade's defaults (router `3100` vs `3000`, API server `3101` vs Cascade's dashboard `3001`, Postgres `5433` vs `5432`, Redis `6380` vs `6379`) so both stacks can run in parallel without a host-port clash — the compose project name is fixed to `swarm`, giving it its own network and volumes. Override any of them via `ROUTER_PORT` / `API_PORT` / `POSTGRES_PORT` / `REDIS_PORT` in `.env`.

The router exposes a health check at `http://localhost:${ROUTER_PORT:-3100}/health`; the API server exposes one at `http://localhost:${API_PORT:-3101}/health` plus a tRPC endpoint at `/trpc`. The router's webhook receiver mounts one route per registered provider manifest and verifies each delivery with that provider's own scheme, resolves the project, and applies a loop-prevention drop gate (SWARM-9), then hands off to the job queue: `POST /github/webhook` carries both repo-scoped SCM events and the GitHub Projects board event (one webhook, one secret), `POST /bitbucket/webhook` carries Bitbucket Cloud repo-scoped SCM events and verifies `X-Hub-Signature` as `sha256=<hex>`, `POST /gitlab/webhook` carries gitlab.com repo-scoped SCM events and authenticates the *sender* by comparing `X-Gitlab-Token` against the project's secret in constant time (GitLab's own mechanism — it does not sign the body; issue #619), `POST /linear/webhook` carries a Linear board's events under its own signing secret (issue #530), `POST /jira/webhook` carries a Jira project's issue events under its own (issue #580), and `POST /trello/webhook` carries a Trello board's card actions, verified against the raw body **plus that callback URL** (issue #588) — which is the one webhook SWARM creates itself rather than having a human configure it in the provider's UI: `swarm pm webhook create --project <id>` (issue #589, see the [command reference](./cli.md#swarm-pm)). Each also answers a `GET` ping, which is what a provider sends when its webhook is (re)configured — and Trello's answers the `HEAD` probe it confirms a new subscription with. From there, a trigger registry dispatches each event to the pipeline phase it names — see the [pipeline guide](./pipeline.md) and [status snapshot](./status.md) for implementation details.

To let GitHub reach this local router with webhooks, expose it over a public HTTPS URL with a Cloudflare Tunnel — see **[`cloudflare-tunnel.md`](./cloudflare-tunnel.md)** for the setup (a quick ephemeral tunnel for dev, a CLI-managed named tunnel for a stable URL, or a dashboard-created tunnel run as an opt-in `cloudflared` service in `docker-compose.yml` so it starts with the rest of the stack) and the GitHub webhook configuration.
