# Configuration

SWARM's configuration splits into three layers:

- **General settings** — process/host-level knobs, set as **environment variables** (usually in `.env`, sourced from `.env.docker.example`). No schema; read directly where needed. These configure the router, worker, dashboard, database, Redis, credential encryption, and logging.
- **Project config** — the **per-project** shape (`swarm.config.json`, one entry per project), validated by a Zod schema (`src/config/schema.ts` — the single source of truth) and loaded into Postgres via `swarm config apply` / `npm run db:seed`. This is where a project's repo, worktree layout, board mapping, credential references, and per-phase agent/pipeline behaviour live.
- **Global settings** — **app-wide** knobs that apply across every project, validated by a Zod schema (`src/config/app-settings.ts` — the single source of truth) and stored **DB-first** in the single-row `app_settings` table. Unlike project config these are *not* file-sourced; they're edited through the dashboard API (the `settings` tRPC router), and when nothing is stored the coded defaults apply. Today the global settings are `agents.defaults` (the global per-CLI default model) and `appearance.theme` (the dashboard's theme choice). One installation-wide *secret* sits beside them rather than inside them — the **instance-level default SCM credential** (issue #769), which is DB-first the same way but in its own table, since the `app_settings` blob is readable by any authenticated caller; see [Instance-level default credentials](#instance-level-default-credentials-instance_scm_credentials).

Beyond those three, one secret is none of them: the **per-worker operator SCM credential** (issue #765) is stored server-side per `(worker, SCM provider)`, encrypted at rest, and set with a CLI command rather than a file or an environment variable — see [Per-worker operator SCM credential](#per-worker-operator-scm-credential).

> **This document is the canonical, human-editable catalogue of every configuration option.** It is meant to be kept in lock-step with the code (see [`ai/RULES.md` §7](../ai/RULES.md)): when an option is added, removed, renamed, or its default changes, update the matching row here in the same change. When you'd rather not click through the dashboard UI, point an agent at this document and ask it to change a setting — everything editable is listed here with the exact key, default, and file it lives in.

### General settings (environment variables)

Grouped by concern. "Required" means startup throws if it's unset; everything else has a default or a safe fallback. Docker-side ports (`POSTGRES_PORT`, `REDIS_PORT`, `ROUTER_PORT`, …) are the **host-published** ports; inside the Compose network the services use their own fixed container ports.

**Database (Postgres)** — `src/db/client.ts`
| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | _(unset)_ | Full Postgres connection string. If set, used verbatim and the `SWARM_POSTGRES_*` fallbacks are ignored. If neither this nor `SWARM_POSTGRES_HOST` is set, startup throws. |
| `SWARM_POSTGRES_HOST` | _(unset)_ | Host used to assemble a connection string when `DATABASE_URL` is absent. |
| `SWARM_POSTGRES_PORT` | `5432` | Port for the assembled connection string (container-internal; the host port is `POSTGRES_PORT`). |
| `SWARM_POSTGRES_USER` | `swarm` | DB user for the assembled connection string. |
| `SWARM_POSTGRES_PASSWORD` | `` (empty) | DB password for the assembled connection string. |
| `SWARM_POSTGRES_DB` | `swarm` | Database name for the assembled connection string. |

**Queue & worker (Redis / BullMQ)**
| Variable | Default | Purpose |
| --- | --- | --- |
| `REDIS_URL` | **required** | Redis connection URL for the BullMQ queue and all Redis-backed dedup (`src/lib/redis.ts`). Parsed for host, port (default `6379`), and password. |
| `SWARM_WORKER_CREDENTIAL` | **required on every worker** | Raw registered-worker credential printed once by `swarm workers register` (and, since issue #788, also written by both registration paths to a per-checkout cache on the machine that ran them — `~/.swarm/worker-credentials/<sha256 of the checkout's realpath>/credential.json`, `700`/`600`, from which `swarm run:worker` supplies it so it never has to be pasted; the printed line stays for a remote machine or a process supervisor), read by the worker (`npm run dev:worker`, `src/transport/connect-entry.ts`, ADR-003 §1) — the only project-side secret it holds. The worker presents it at handshake; the control plane authenticates it, acquires and heartbeats that worker's fenced session, and dispatches to it only work atomically selected/capacity-claimed for it. An invalid credential or an already-live session makes startup fail. **Every deployment needs one, single-user installs included** (issue #552): `SWARM_SINGLE_USER_MODE` does not bypass the dispatch gate, so a host with no credential has nothing an enrolled project can dispatch to — `swarm start` and `swarm status` warn when this value is unset or matches no registered worker. Since issues #551/#553 there is one worker program, so the control-plane host's own worker needs a registered credential exactly like a remote one. Never commit this value. |
| `SWARM_WORKER_REPO_ROOT` | Current working directory | Absolute path to the assigned repository checkout on the worker's own host (remote, or the control-plane host's own). This is host-local execution state: the control plane's `project.repoRoot` is omitted from `TaskAssignment`, and the daemon reconstructs the project with this path instead. Set it when launching `npm run dev:worker` from anywhere other than the repository checkout. On the control-plane host, leaving it unset resolves to that host's own checkout. Provisioning verifies the checkout's `origin` remote resolves to the assigned project's repository and fails the run if it does not, so a mistyped path (or a second enrolled project) cannot be worked on silently; a checkout with no `origin` cannot be identified and is accepted. Since issue #687 that same `origin` is also read **once at daemon startup** and declared at handshake as the worker's `repository` (persisted on the worker row), so the control plane knows which repository this host holds — it adds no setting of its own, and a checkout with no identifiable `origin` declares nothing rather than failing to start. Since issue #688 that declaration is also checked **before the run starts**: an assignment for a different repository is refused up front with a message naming both it and this checkout's, and the dispatch fails terminally rather than deferring (no retry here could make them match), so a worker enrolled in two projects with different repositories no longer works on the wrong one. A daemon that declared nothing refuses nothing and keeps the provision-time check alone. Since issue #714 the same declaration is read one step earlier still — by worker **selection**: the dispatch gate skips a machine whose declared checkout is not the task's repository (`repository-mismatch`) instead of selecting it, claiming it, and then having the worker refuse the assignment, and the deferred dispatch records `worker-authorization` because only a human pointing a worker at that repository can clear it. Again, a daemon that declared nothing is skipped by nothing. Since issue #689 the daemon also **locks** this checkout for the life of the process, so two separately registered workers cannot be pointed at one working tree and collide on the same repository's `index.lock`: a host-local `~/.swarm/checkout-locks/<sha256 of the checkout's realpath>/owner.json`, refreshed while the daemon runs, kept in the operator's home directory rather than in the checkout (a daemon has no project config at startup, so it knows no `worktreeRoot`). It adds no setting of its own. A second daemon on the same path exits at startup naming the worker that holds it; to run two workers on one machine, give each its own checkout. Since issue #788 a **sibling** of that lock directory is keyed identically — `~/.swarm/worker-credentials/<the same hash>/credential.json` — and `swarm run:worker` is what reads it: run from inside a checkout, it supplies this variable (the current directory) and `SWARM_WORKER_CREDENTIAL` (from that file) itself, so neither has to be set by hand on the machine that registered the worker. It is an additional launcher, not a setting: the daemon's env contract is exactly as described here. The lock is reclaimable on liveness grounds — a dead pid, or a refresh lapsed for 15 minutes — so a crashed worker never permanently blocks its own checkout, and a graceful stop releases it at once. |
| `SWARM_OPERATOR_GH_TOKEN` | _(unset)_ | **Router-only since issue #765 — no worker reads it any more.** It used to be the worker-local operator GitHub token every implementer commit, push, PR and comment was authored as; that identity now lives in the DB, per worker per SCM provider (see **Per-worker operator SCM credential** below), and is resolved at dispatch and carried on the assignment. `src/lib/env.ts`'s `resolveOperatorGitHubToken` is gone and there is deliberately **no** env fallback left on that path, so a worker `.env` that still sets this changes nothing — delete it once the router and the worker are both upgraded (rollout order in [onboarding-worker.md](./onboarding-worker.md)). What still reads it is `src/config/operator-token.ts` on the **router**, for three things this phase did not move: `resolvePersonaIdentities` → `getPersonaTokenOrNull(project, 'implementer')`, used by `respond-to-review`'s author gate and `resolve-conflicts`' candidate filter; the Review trigger's `getPullRequest` fallback when a project configures no reviewer credential (`src/triggers/handlers/review.ts`); and `POST /worker/delivery/pr-comment` with `persona: 'implementer'` (issue #444). All three run on the router, which holds one value for every worker it serves — deciding *whose* operator identity a multi-worker installation should use there is its own design question. **Not needed by the API server**, which runs no implementer phase and resolves no persona. Also not needed to map a board or gate board events: since issue #537 the API server discovers boards with the project's own `credentials.pm.github-projects.apiToken`, and the board-side `isSelfAuthored` gate resolves that same PM credential's identity. When unset on the router, it logs a startup warning and answers `503 persona credential unavailable` on `/worker/delivery/pr-comment` for the implementer persona rather than a reason-less 500. Never commit this value. |
| `SWARM_OPERATOR_BITBUCKET_TOKEN` | _(unset)_ | Control-plane **operator Bitbucket credential** — the implementer persona's credential for the Bitbucket SCM provider (issue #296), the exact mirror of `SWARM_OPERATOR_GH_TOKEN` above and subject to the same invariants: **never persisted** to `project_credentials` and **never in project config**. Source delivery requires a `username:app_password` pair: it is the only form that can resolve `GET /2.0/user`; a workspace/repository access token fails identity resolution before delivery reaches the email lookup. An app password without the `email` scope still delivers using an unattributed noreply commit address; grant that scope for attributed commits. Only relevant to a host that runs Bitbucket implementer work, which is a real configuration since issue #618: a project setting `"scm": "bitbucket"` routes to the Bitbucket provider, and the worker running its implementer phases needs this set. Leaving it unset still changes nothing for a GitHub project. When unset, Bitbucket implementer operations fail with an actionable error naming it and persona identity resolution fails closed. **Never read by a worker** — like `SWARM_OPERATOR_GH_TOKEN` since issue #765, and unlike it, never was: a worker's operator identity for `bitbucket` comes from the per-worker store below. This variable backs the provider-local persona resolver on the **control plane** only. Never commit this value. |
| `SWARM_OPERATOR_GITLAB_TOKEN` | _(unset)_ | Control-plane **operator GitLab token** — the implementer persona's token for the GitLab SCM provider (issue #295), the exact mirror of `SWARM_OPERATOR_GH_TOKEN` above and subject to the same invariants: **never persisted** to `project_credentials` and **never in project config**. Any token form GitLab accepts in its `PRIVATE-TOKEN` header works — personal, group, or project access — since all of them resolve `GET /user` for persona identity (there is no credential-form branch as there is for Bitbucket). It needs the **`api` scope**: delivery writes merge-request notes, review verdicts, and merges, and `read_api`/`read_user` cannot perform those. Two consequences worth knowing before granting it: commit **attribution** follows the account email GitLab returns from `GET /user`, so a token whose scope withholds it — and a project/group access token's bot user, which has no address at all — still delivers, but under a `<username>@users.noreply.gitlab.com` author that keeps the right name and leaves the commit unlinked (GitLab links a commit only by a **verified** account email); and approving requires the account to be an **eligible approver** on the project, so a project that forbids self-approval leaves the merge request unapproved and merge automation reports the missing approval rather than merging. GitLab**.com** only; a self-managed host would need a base-URL setting that does not exist yet. Only relevant to a host that runs GitLab implementer work, which is a real configuration since issue #619: a project setting `"scm": "gitlab"` routes to the GitLab provider, and the worker running its implementer phases needs this set. Leaving it unset still changes nothing for a GitHub or Bitbucket project. When unset, GitLab implementer operations fail with an actionable error naming it and persona identity resolution fails closed. **Never read by a worker** — like `SWARM_OPERATOR_GH_TOKEN` since issue #765, and unlike it, never was: a worker's operator identity for `gitlab` comes from the per-worker store below. This variable backs the provider-local persona resolver on the **control plane** only. Never commit this value. |
| `SWARM_CONTROL_PLANE_URL` | **required on every worker** | Control-plane base URL, shared by two features that both point a worker at the router over the network. (1) **SCM + PM metadata delivery** (ADR-004 §2, `src/lib/env.ts`): together with `SWARM_WORKER_CREDENTIAL` it is what lets a worker perform **control-plane delivery** — the metadata-only delivery calls travel up the transport to the router's `POST /worker/delivery/*` routes, which perform the write under the per-project credential so that credential stays on the server and never reaches a worker. On the **SCM** side, submit-review runs under the per-project **reviewer PAT**, and post-PR-comment runs under the **persona the requesting phase named** — the reviewer for a Review's comment, the **implementer** for a Respond-to-review reply, which must not be authored by the reviewer it answers (issue #444) — defaulting to the reviewer when a client sends no persona (only the verdict + comment body + PR number + that persona cross the wire); on the **PM** side the two board writes (move a card, comment on the backing Issue/PR) run under the per-project **PM credential** (only the canonical status key / comment body crosses — never a board option ID). The repository tree never crosses in either case. Source-carrying / attribution ops (commit, push, create PR) and all PM **reads** stay worker-side under the operator's own token. (2) **Worker transport** (ADR-003 §1): the base URL the worker transport client (`npm run dev:worker`) connects to. From a remote machine that is typically the same Cloudflare-tunnel base URL GitHub's webhooks use (e.g. `https://swarm.example.com`); **on the control-plane host itself it is the loopback URL, `http://localhost:<ROUTER_PORT>`**, and that is precisely what makes the host worker identical to a remote one rather than a second program (issues #551/#553). Only worker-side code reads this variable — the router publishes its own address as `WEBHOOK_CALLBACK_BASE_URL` — so pointing it at loopback affects nothing but the worker. The client derives the transport endpoints from it: `POST <url>/worker/session` for the HTTP handshake and a WebSocket at the matching `ws(s)://<url>/worker/stream` for heartbeats (`src/transport/worker-client.ts`). The client holds **only** this URL and `SWARM_WORKER_CREDENTIAL` — no `DATABASE_URL`/`REDIS_URL`, even on a host that has them, and since issue #765 no operator SCM credential either (it arrives per assignment). That client also executes pushed assignments **DB-free** (ADR-003 §2) and reuses the delivery routes from (1) for everything its own token and its missing database cannot serve: Implementation's two board writes plus its `listBlockers` dependency lookup (`POST /worker/delivery/pm/blockers`), Respond-to-review's board-card lookup (`POST /worker/delivery/pm/find-item`) and its two status-report moves, Review's submitted verdict, Review's three review-verdict ledger calls (`POST /worker/delivery/review-ledger/prior|mark|abandon`, which front the `review_verdicts` table rather than a credential), the follow-up Review a pushed fix enqueues (`POST /worker/delivery/follow-up-review`, which fronts the dispatch store and queue), and Planning's board surface — its `findComment` replay guard plus the four writes a task split needs (`POST /worker/delivery/pm/find-comment|create-item|update-item|label|blocked-by`). **All six phases** run this way since issue #536 (`respond-to-ci`, `resolve-conflicts`, `implementation`, `review`, `respond-to-review`, `planning`), so no phase is refused for want of a database; a daemon built before #536 declares only the first five, and the eligibility gate routes around it rather than failing the dispatch. Required by `dev:worker`, which throws at startup if it is unset — and since there is one worker program (issues #551/#553), that means every host running a worker. Must be an `http(s)` URL. (3) **The operator CLI's login and the operator API it authorises** (issues #798, #799): `swarm login` reads the same variable to reach the router's `/operator/session` routes, and the bearer it caches is then spent against `/operator/trpc/*` on the same host — the `swarm workers` operations, served as a strict subset of the dashboard's tRPC router — the same reasoning that puts the worker transport on the router puts a *human's* login there too, since it is the only tunnel-exposed process and the API server binds `127.0.0.1`. That is the one reader of this variable that is not worker-side, and it needs no `DATABASE_URL` either; the session it caches is keyed on this URL (`~/.swarm/operator-sessions/<sha256 of the normalised URL>/session.json`, `700`/`600`), so one machine can hold a session per installation. Since issue #800 that bearer is actually spent: **every `swarm workers` subcommand** goes through `/operator/trpc/*`, so this variable plus a `swarm login` session is what that command group requires and `DATABASE_URL` no longer is — which is what lets a machine be onboarded from itself. |
| `SWARM_WORKER_TRANSPORT_CLIS` | _(auto-detect)_ | Optional comma-separated override of the agent CLIs the worker declares at handshake — any of `claude`, `antigravity`, `codex`. When unset, the client probes the host's PATH for each CLI's binary (`claude`, `agy`, `codex`) and declares those it finds (`src/transport/cli-discovery.ts`); this DB-free probe is why the client needs no `runs`-table quota lookup. An unknown value fails startup loudly. The declared set must still include every CLI the worker's enrollments require, or the handshake is rejected (HTTP 409) — so discovery drops a CLI only on proof it is absent (`ENOENT`): a probe that times out is retried once with a wider budget and then declared anyway, and a rejected *discovered* set is re-probed before the daemon gives up (issue #559). Setting this override opts out of that recovery, since an explicit declaration is not something a re-probe should talk over. Every worker reads it, the control-plane host's own included. It sets the **probe** on the machine itself, which is a different thing from the control-plane-side declaration `swarm workers set-cli` writes (issue #783): that one is durable — it survives the machine's next reconnect, where it used to be overwritten — and the set a worker is actually routable on is the intersection of the two. So this variable is how you widen what a machine offers, and `set-cli` is how you narrow it; `swarm workers set-cli <worker-id> --auto` clears the declaration and returns the worker to plain auto-discovery. |
| `SWARM_MAX_JOB_AGE_MS` | `86400000` (24h) | Maximum age of a BullMQ job when the router's dispatch consumer begins processing it (`src/worker/job-freshness.ts`). Older webhook or retry jobs are acknowledged as stale (and their durable dispatch cancelled) without dispatching an agent, preventing an offline installation from replaying board work completed manually. Must be a positive integer or startup throws. |
| `SWARM_WORKER_LOCK_DURATION_MS` | `900000` (15m) | BullMQ job-lock duration (`src/worker/runtime-options.ts`). Locks are renewed at least every 30s (or half the duration for a shorter override), while the longer expiry tolerates a sleeping laptop, event-loop starvation, or a transient Redis interruption without falsely reclaiming a still-running agent as stalled. Must be a positive integer or startup throws. |
| `SWARM_WORKER_HEARTBEAT_TTL_MS` | `60000` (60s) | How long a worker session lease stays live after its last heartbeat (`src/identity/worker-session-service.ts`). Every worker session is established over the router's worker transport (`POST /worker/session` + `GET /worker/stream`, ADR-003 §1), and the returned `heartbeatTtlMs` tells the daemon how often to heartbeat over the WebSocket to keep the lease live — it refreshes at one third of this interval. An older session is expired and may be re-acquired with a bumped fencing token; dispatch execution atomically validates that token and session before reserving capacity, so a stale/replaced host is rejected. A lease's **own holder** can also reclaim it early on a reconnect, by presenting the `sessionId`/`fencingToken` it already holds (issue #608), so this TTL no longer bounds the outage a control-plane restart causes — a second daemon, which has no such proof, is still refused. Must be a positive integer or the operation throws. |
| `SWARM_WORKTREE_SWEEP_INTERVAL_MS` | `3600000` (1h) | How often the background worktree retention sweep runs on the control-plane host. Owned by the **API server** (`src/api/maintenance.ts`, issue #550) — the one process there holding `DATABASE_URL`, the operator's PATH, and the checkout; the worker is DB-free and executes phases only. Must be a positive integer or the API server's startup throws. |
| `SWARM_AGENT_TIMEOUT_MS` | `1800000` (30m) | Default wall-clock timeout applied to **every** phase/agent run when the project sets no per-phase `agents.<phase>.timeoutMs` (`src/worker/consumer.ts`). The harness kills a run that exceeds it (SIGTERM, then SIGKILL after a 5s grace) so a hung agent can't hold a worker slot indefinitely. A genuinely-interrupted timeout is then **deferred and resumed** (the agent continues its prior CLI session in the preserved worktree — see the [pipeline guide](./pipeline.md#pipeline-phases)), bounded by the same retry cap as a rate-limit; only a run that trapped SIGTERM and still exited 0 is finalized `failed`. A per-phase `timeoutMs` in `swarm.config.json` overrides it. Must be a positive integer or startup throws. |
| `SWARM_STALE_RUN_SWEEP_INTERVAL_MS` | `300000` (5m) | How often the **router**'s dispatch consumer sweeps for stale `running` run-history rows while it keeps dispatching — a phase whose worker died without reporting a result (`src/router/dispatcher.ts`). A row still `running` past `max(configured timeout) + 10m` grace is reconciled to `failed`. Must be a positive integer or startup throws. |
| `SWARM_DEPENDENCY_RECHECK_MS` | `300000` (5m) | How often the dispatcher re-checks the prerequisites of an Implementation deferred because its work item is `blocked by` an unfinished issue — a **recorded** relationship, the only kind that defers a run since issue #643; a prerequisite named only in an item's prose is surfaced on the item and never deferred (`src/worker/dependency-recheck.ts`). The re-check is **token-free** — the dependency gate runs before any worktree or agent, so it costs one PMProvider read and zero model tokens (the same agent-less pattern as merge-automation). The federated dispatch gate (issue #339) deliberately shares this cadence for its own token-free wait (a dispatch with no eligible worker), tracked on a separate attempt budget. That wait records **which kind** it is on the dispatch row (issue #607): `worker-eligibility` when a machine is merely busy or offline, `worker-authorization` when only a human can clear the refusal (approve an enrollment, grant sharing consent, permit the phase, enroll a worker that runs the configured CLI). Both use this cadence and that one budget — the distinction is what an operator reads, not a different timing. For the **availability** half this cadence is now the *fallback* rather than the only way out (issue #610): a worker connecting, or freeing capacity by settling a dispatch, wakes those dispatches immediately, and only a wait no worker turns up for actually runs out this interval. A `worker-authorization` wait is never woken early and keeps this cadence exactly. Must be a positive integer or startup throws. |
| `SWARM_DEPENDENCY_MAX_WAIT_MS` | `604800000` (7d) | Total time a dependency-blocked Implementation keeps re-checking before it gives up and settles `failed` with an actionable "must be done first" comment on the item (`src/worker/dependency-recheck.ts`), rather than waiting forever on an abandoned prerequisite. Divided by `SWARM_DEPENDENCY_RECHECK_MS` to get the re-check budget — also the budget the federated dispatch gate's wait uses, under **either** of its two reasons (`worker-eligibility` / `worker-authorization`, issue #607), before it settles `failed` with the actionable reason (grant sharing consent, approve the enrollment, enroll a worker that can run the configured CLI). **One gate wait deliberately ignores this budget**: a continuation waiting for the machine that holds its preserved checkout (wait reason `preserved-worker`, issue #567) waits without limit, because giving up would abandon work still sitting on that machine's disk — an operator ends it with "Reset & restart". The two *pre-run* waits never reach this budget at all, since they defer before the gate runs and are woken by an event rather than a re-check: `project-capacity` (a freed project slot) and `task-in-flight` (the task's own earlier phase settling — one executing against the shared checkout, issue #759, or a Planning dispatch an Implementation must not overtake even while it is merely queued, issue #761). Must be a positive integer or startup throws. |
| `SWARM_AGENT_CONTAINMENT` | `bypass` | How far outside its task worktree an agent CLI run may reach (`src/harness/containment.ts`, issue #614). `bypass` — today's behavior: every CLI launches with its permission bypass (`--dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`), so the agent holds the worker user's whole filesystem and network. `worktree` — the CLI's **own OS-level sandbox**, scoped to the run's worktree: writes outside it fail, network is restricted to the allowlist below, and no permission prompt is needed because bash is auto-allowed *because* it is sandboxed. Codex additionally grants its linked worktree's shared `.git` directory so the required `git pull` can write refs and objects; phase prompts still forbid commits and pushes. Achievable for `codex` (a SWARM-owned permission profile passed as `-c` overrides, so `~/.codex/config.toml` is never written) and `claude` (a `--settings '<json>'` sandbox blob plus `--permission-mode acceptEdits`); **not** achievable for `antigravity` — `agy` exposes no per-invocation permission allow-rule and its `--sandbox` denies reads of a linked worktree's gitdir, so an `agy` run stays on the bypass and logs `agent run is not contained` saying so. A worker-host setting, not project config: containment is a property of the machine the agent runs on. An unrecognised value throws rather than silently downgrading. It stays `bypass` by default deliberately — containment must be proven on a host's own runs before it becomes what that host gets — so verify with `npm run check:containment -- /path/to/.swarm-workspaces/task-123` and read [`docs/agent-containment.md`](./agent-containment.md) before setting it. |
| `SWARM_AGENT_CONTAINMENT_DOMAINS` | `api.github.com,github.com` | Comma-separated network allowlist for a **contained** run (ignored under `bypass`). All three sandboxes deny network by default, and every phase prompt performs `gh` reads and most a `git pull --ff-only origin`, so these two are what keeps a contained pipeline working. Widen it for a project whose tests fetch — wildcards such as `*.npmjs.org` are accepted — since anything unlisted fails inside the sandbox. **Applies to `claude` only**: codex's `-c` dotted-path parser cannot express a domain key, so a contained codex run gets all-or-nothing egress (see [`docs/agent-containment.md`](./agent-containment.md)). An empty or separators-only value falls back to the default rather than denying all network. |
| `SWARM_ANTIGRAVITY_CONVERSATIONS_DIR` | `~/.gemini/antigravity-cli/conversations` | Where the harness looks for Antigravity's per-conversation `.db` files, used as the **fallback** way to capture the id of the session an `agy` run created so a deferred run can be resumed with `agy --conversation <id>` (`src/harness/antigravity-session.ts`). All three CLIs normally report their session id directly — Antigravity's arrives as the `conversation_id` on its `--output-format stream-json` stream (issue #465) — so this store diff only matters for an `agy` too old to support that flag, or a run killed before its opening event was captured. Override for a non-default `agy` install or in tests. |

| Variable | Default | Purpose |
| --- | --- | --- |
| `SWARM_SINGLE_USER_MODE` | `false` (coded default; **`true`** in `.env.docker.example`) | Local single-user **API authentication** policy (issue #298). Only the literal `true` enables it; unset/empty/any other value keeps the coded default. When enabled, the API atomically bootstraps a passwordless reserved `localhost-admin` `instanceAdmin` and resolves every `/trpc/*` request to that user **with no session cookie**, so a local install needs no `swarm users`, no password, and no `/login`; `/login` itself detects the resolved identity and enters the dashboard directly. Unless `SWARM_SINGLE_USER_MODE` (above) is enabled, the dashboard uses **per-user session auth** (issue #281 task 2), not a shared secret: a user set up with `swarm users add` + `swarm users set-password` signs in at `/login`, and the server issues an opaque session delivered as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost). Every `/trpc/*` request except `ping` is authorized by that cookie; `/health` stays public. No API token is configured — `DASHBOARD_TOKEN` and its browser copy `VITE_DASHBOARD_TOKEN` have been **retired**. Only a hash of the session token is stored (`user_sessions`), never the raw token. In single-user mode the cookie is not required at all: the API resolves the bootstrapped `localhost-admin` for every request directly.

The **operator CLI** authenticates against the same model without a browser (issue #798): `swarm login` posts the same identifier/password to the router's `POST /operator/session`, gets back the opaque session token itself rather than a cookie, and caches it under `~/.swarm/operator-sessions/` at `700`/`600`. It is the same `user_sessions` row with the same `SWARM_SESSION_TTL_HOURS` lifetime — no API key, no separate personal-access-token credential — and `SWARM_SINGLE_USER_MODE` is deliberately not honoured on that route (see its row above). The router container receives the setting through `docker-compose.yml`. See [`cli.md`](./cli.md#swarm-login).

That bearer is spent against the router's **operator API** at `/operator/trpc/*` (issue #799), which resolves the caller from it through the same `resolveSession` and answers `UNAUTHORIZED` without one. It carries the `workers` namespace of the dashboard's tRPC router and nothing else — never `appRouter` — because the router is the internet-exposed process, so projects, credentials, settings, users and runs stay on the loopback-bound API server. Every procedure keeps the authorization it has in the dashboard, and this mount ignores `SWARM_SINGLE_USER_MODE` for the same reason the login routes do. Since issue #800 it is the **only** way `swarm workers` reaches the installation: that command group needs `SWARM_CONTROL_PLANE_URL` plus a `swarm login` session and no `DATABASE_URL`, and it inherits the dashboard's rules unchanged — `set-scm-credential` and `remove` strictly owner-only, `remove` refused on a busy machine, an unfiltered `workers list` reserved to an `instanceAdmin` (`workers list <your handle>` needs nothing but a session). See [`cli.md`](./cli.md#swarm-workers).

For the recommended **same-origin** deploy (the API server serves the built dashboard SPA and the API from one process), no CORS config is needed. The separate-origin setup — running the SPA on the Vite dev server against the API on `API_PORT`, or `VITE_API_URL` pointing at a different host — is credentialed and therefore pre-flighted by the browser; the API allows it via `CORS_ORIGIN` (default `http://localhost:5173`, which matches `dashboard/vite.config.ts`). `SameSite=Strict` still delivers the cookie for the localhost dev case (ports don't change the *site*); a genuine cross-*site* production origin would additionally need different cookie attributes and is out of scope for SWARM's local-first model.

A project created since issue #290 therefore keeps resolving through the neutral `SCM_TOKEN_REVIEWER` / `SCM_WEBHOOK_SECRET`, and one predating #290 keeps its `GITHUB_TOKEN_REVIEWER` / `GITHUB_WEBHOOK_SECRET` — so `swarm config apply` keeps working against the environment you already export. Renaming a reference without moving its `project_credentials` row would break resolution, which is exactly why the migration does not do it. See [`credentials.scm`](#credentialsscm).

**Issue #631 did the same for the PM side, and it needs no manual step either.** `credentials.pm` went from one flat `role → reference` map to a `credentials.pm[<providerId>]` map, and a config written before that is migrated by copying the names it already stores under the provider `pm.type` names — a SQL backfill (`0046_pm_credentials_per_provider`) for persisted rows, a parse-time adoption for `swarm.config.json`. Nothing is renamed to the manifest's conventional key, so a project whose board token is stored as `MY_BOARD_TOKEN` keeps resolving through `MY_BOARD_TOKEN`. Re-running `swarm config apply` after upgrading is enough; the block moves under the provider it was always for. See [`credentials.pm`](#credentialspm).

The **implementer** persona is no longer a project credential (issue #396), and since issue #765 it is no longer an env var either: on the worker path it is the operator's own credential stored per `(worker, scmProvider)` (see [Per-worker operator SCM credential](#per-worker-operator-scm-credential) below), and on the router it is still `SWARM_OPERATOR_GH_TOKEN` for the three call sites listed in that variable's row. ### Per-worker operator SCM credential

**Not an environment variable and not project config** — a server-side, encrypted-at-rest secret keyed by `(workerId, scmProviderId)` in the `worker_scm_credentials` table (issue #765). It is the **worker operator's own** account credential: the identity every commit, push, pull request and implementer-side comment a phase makes is authored as. It is never a project credential, so it does not reintroduce the retired `credentials.implementer` persona (issue #396).

- **One credential per SCM provider per worker.** A worker enrolled across projects on different providers holds one for each; resolution reads only the provider the dispatched project names (`project.scm`), never another's.
- **Resolved at dispatch, on the control plane, and carried on the assignment.** The worker is DB-free (ADR-003 §2) and cannot read the store, so the router resolves the pair and puts the credential on the `TaskAssignment` frame — over TLS, on a socket already authenticated by that worker's own `SWARM_WORKER_CREDENTIAL`. A rotation therefore takes effect on the **next dispatch**, with no worker restart.
- **Encrypted with the same primitive `project_credentials` uses** (`src/db/crypto.ts`, AES-256-GCM under `CREDENTIAL_MASTER_KEY`), with `<workerId>:<scmProviderId>` as the AAD — so a ciphertext copied onto another worker's row, or onto the same worker's row for a different provider, fails authentication instead of resolving.
- **A missing or invalid credential fails the dispatch immediately and attributably**, naming the worker and the provider, before anything is pushed — rather than a few seconds into a run under the provider's own generic identity error.
- **Two write surfaces, one store**: the CLI command below, and the worker owner's own dashboard form (issue #766, see after the command).

Set or rotate it with:

```bash
swarm workers set-scm-credential <worker-id> <github|bitbucket|gitlab>
```

It prompts without echo on a TTY and otherwise reads the secret from stdin; it never takes the value as an argument and never prints it back. `swarm workers list` shows the worker ids.

Since issue #766 the worker's **owner** can also set and rotate it from the dashboard, at `/workers/<worker-id>` → **Operator source-control credential**, one field per provider that machine's enrollments actually resolve to. The dashboard verifies the value against the provider before storing it, so an invalid one is refused with nothing written rather than failing at the next dispatch; the stored value is never shown again, only that it is set and when. That form is strictly the owner's — an instance administrator managing someone else's machine uses the command above.

**An entry states no SCM provider** (issue #727). It did between issues #684 and #727 (surfaced in the dashboard by #700), and the field was removed because it was incoherent rather than merely unimplemented: a project's SCM credentials are project-wide and single-provider, so the provider a repository overrode to had nowhere for its `reviewer` / `webhookSecret` references to be entered and every operation scoped to that repository failed in `requireScmCredential`. **An unmigrated config still loads**: a stored `scm` on an entry is accepted and **stripped on parse** — never an error — so `validateConfig` / `swarm config apply` and the dashboard's repository editor (on the **Source Control** tab since issue #729) treat it identically, and the repository resolves the project's provider even where the two differed. A persisted `repositories` row may keep the dead key until the list is next saved; nothing reads it.

**Which repository a piece of work runs against** (issue #684 phase 2). The repository is decided once, from the work itself, and every phase downstream reads it — the worktree, the task branch, the agent prompts, the delivery ids, the review-verdict ledger key and the assignment pushed to a federated worker all name it:

- An **SCM webhook** (a pull request, a review, a check run) runs against the repository the delivery came from — any entry in the list, not just the first. That repository is recorded on the run (`runs.repository`), so every later control-plane action that starts from that run — Force re-review, Reset & restart, startup reconciliation, the runs API — rescopes to it rather than to the project's default.
- A **merge dispatch** runs against the repository the approving Review run acted on, carried on the dispatch itself.
- **Board-driven Planning and Implementation** run against the repository the card is **routed** to (issue #686). A project owning one repository routes to it with no board read at all — unchanged, and no token to declare. A project owning several routes on the `pmRoutingToken` field below: the delivery is refused, and says so, when the card claims **no** repository or **more than one**, rather than falling back to the first. The decision is made once, at ingress, and recorded on the job, so a redelivery or a "Retry now" routes identically.
- A job naming a repository the project **no longer owns** fails loudly — the dispatch fails with a message naming the project and the repositories it does own — rather than silently falling back to the default and pushing branches into the wrong repository.

> **A second repository is not yet fully usable, by design.** `repoRoot` above is a single checkout per project, and a worker host declares the one repository its checkout actually is (`SWARM_WORKER_REPO_ROOT`, issues #687–#689). A run for a non-default repository therefore never works in the wrong tree: since issue #714 the dispatch gate **skips** a machine whose checkout is a different repository and the dispatch waits (`repository-mismatch`, recorded as a `worker-authorization` wait) until a worker holding that repository is enrolled; a machine that declared no repository is still selectable and is caught later, by the assignment check or the provision-time `origin` verification. Per-repository checkout roots are host-local execution state and are a follow-up; until they land, keep one repository per project in production.

A repository entry's own `repo` doubles as that provider's project coordinates too: Bitbucket's `workspace/repo_slug`, GitLab's `namespace/project` path.
| Field | Purpose |
| --- | --- |

**`credentials.scm`** — the two credentials every SCM provider needs, held **per provider** so a project can carry GitHub's and GitLab's at the same time instead of one overwriting the other (issue #628). Each provider declares its own conventional reference name on its manifest (`SCMProviderManifest.credentialRoles`, `src/integrations/scm/manifest.ts`), and shared code resolves a `(provider, role)` pair — never a reference or an env var — through `resolveScmCredentialOrNull(project, providerId, role)` / `requireScmCredential(...)` (`src/config/provider.ts`).

| Role | `github` | `bitbucket` | `gitlab` |
| --- | --- | --- | --- |
| `reviewer` | `GITHUB_TOKEN_REVIEWER` | `BITBUCKET_TOKEN_REVIEWER` | `GITLAB_TOKEN_REVIEWER` |
| `webhookSecret` | `GITHUB_WEBHOOK_SECRET` | `BITBUCKET_WEBHOOK_SECRET` | `GITLAB_WEBHOOK_SECRET` |

`reviewer` is the reviewer-persona token. `webhookSecret` is what inbound deliveries are authenticated with, and what the provider does with it differs: GitHub and Bitbucket HMAC-sign the raw body with it, while GitLab echoes it verbatim in `X-Gitlab-Token` and the adapter compares the two (issue #295) — so for a GitLab project this value is a *token*, not an HMAC key, and it authenticates the sender rather than the body. Because the secret is now per provider, a GitLab project's webhook token is no longer shared with the GitHub Projects board webhook of the same project.

Three rules follow from the map being per provider, and they are deliberate:

- **Only the provider `scm` names is resolved.** Credentials retained for another provider — what you get when you switch the dashboard's provider selector, so switching back restores the earlier state — are *stored but never read*. This is not a fallback chain.
- **The dashboard edits one provider's block at a time.** The **Source Control** tab reads and writes `credentials.scm[<the provider its selector names>]` (issue #632): it names a `(provider, role)` pair and the server resolves which store key that writes to, so saving under one provider cannot land on another's row. Nothing in the browser chooses a reference name.
- **A missing credential fails with its own error.** Asking for a provider the project has no reference for throws naming the project, the provider, the role, and that provider's conventional key ("set `credentials.scm.gitlab.reviewer` to a stored reference; `GITLAB_TOKEN_REVIEWER` is its conventional config-apply key") rather than quietly resolving another provider's secret.
- **Presence is checked when the credential is used, not when the config is read.** The Source Control tab persists a provider switch on its own, so "provider selected, credentials not yet entered" is a state one click creates; a config in that state parses and `swarm config apply` accepts it. What *is* validated at load time is structure: every key must name a real provider id, and every role must be one that provider declares.

The table above lists what a **newly created** project is seeded with. An existing project keeps the reference names it already stores — see [Credential secret values](#general-settings-environment-variables) for why nothing is renamed and nothing has to be re-entered.

**`credentials.pm`** — the PM side needs credentials the two shared SCM references cannot express (Linear an API key, Jira an email plus an API token, Trello a key + token + secret), so **each PM provider declares its own roles on its manifest** (`PMProviderManifest.credentialRoles`, `src/integrations/pm/manifest.ts`) and this map supplies one reference per role, in **one block per provider id** (issue #631). A role spec is `{ role, label, envVarKey, optional?, inheritsSharedCredential? }` (`PmCredentialRoleSpec`), and shared code resolves a role — never a reference or an env var — through `resolvePmCredential(project, role)` / `requirePmCredential(project, role)` (`src/config/provider.ts`).

**One block per provider, because the role names collide.** `apiToken` is GitHub Projects' *and* Jira's, `apiKey` both Linear's and Trello's, `webhookSecret` all four's — so on the single flat map this used to be, storing one provider's reference overwrote the other's in place. A project can now hold two providers' references at once, and switching between them is a config change rather than a re-entry of every credential. Like [`credentials.scm`](#credentialsscm), **only the block for the provider the project names is ever resolved** (`pm.type`): a retained block is stored and never read, deliberately not a fallback chain, since resolving it would hand a newly selected Jira the GitHub Projects token.

Resolution order for one role: the reference configured under `credentials.pm[<pm.type>][<role>]` → the SCM-side reference the role declares it inherits (since issue #628 the *per-provider* one, `credentials.scm[<the provider `scm` names>][<role>]`) → the role's `envVarKey` in the host environment **only when the current provider's block explicitly names that role** → nothing. That final fallback supports an opted-in PM role whose store row is absent; it never widens an inherited role with no `credentials.pm` entry. The references named here are applied exactly like the SCM ones: `swarm config apply` reads each from the environment by that name and stores the value encrypted in Postgres — **every** block's, so a retained provider's secrets are applied too.

Validation, against the *registered* manifests: every key must name a real PM provider id, and within each block every role must be one that provider declares. Additionally — and unlike `credentials.scm`, which has no presence rule — every non-optional, non-inherited role of `pm.type` must be configured, so a half-switched config is rejected rather than loaded; an omitted role fails with the role, the path, and its env var named. A *retained* provider's block is only checked structurally, so it may be incomplete. The whole block is optional only when every one of the current provider's roles is optional or inherits a shared credential.

**GitHub Projects declares two roles, and one of them is required here** (issue #537):

| Role | Env-var key | Purpose |
| --- | --- | --- |
| `apiToken` | `PM_GITHUB_PROJECTS_TOKEN` | **Required.** The GitHub token every board read, board write, and board/state discovery authenticates as. A project credential, resolved only on the control plane — never a worker's token. |
| `webhookSecret` | `GITHUB_WEBHOOK_SECRET` | Inherits the repo side's webhook-secret reference for the SCM provider the project runs on (`credentials.scm[<`scm`>].webhookSecret` since issue #628), because the board and the repo are literally the same GitHub webhook — one URL, one secret. Needs no entry of its own, and is configured on the dashboard's **Source Control** tab. |

**Required token permissions for `apiToken`:** a classic PAT needs `repo` (the board's cards are Issues/PRs — SWARM comments on them, labels them, reads their dependencies), `project` (read **and write**: it moves cards between Status options), and `read:org` (enumerating organization-owned boards for the board picker — a token without it fails discovery with an error naming the missing scope; a failure GitHub does *not* attribute to permissions, such as an outage or a rate limit, surfaces as itself rather than as a scope diagnosis). A fine-grained token needs the equivalent: repository **Issues** and **Pull requests** read/write, plus organization **Projects** read/write for an org-owned board. This token's account is also the identity the board's loop-prevention gate recognizes as SWARM's own, so a card *it* moves does not re-trigger the pipeline — do not point it at the account a human moves cards from.

**Migrating a project written before #537.** Board access used to be borrowed from the SCM implementer persona — the worker-local `SWARM_OPERATOR_GH_TOKEN` — which is why `credentials.pm` could be omitted entirely. **Create the board webhook with `swarm pm webhook create --project <id>`** (issue #589 — see [`cli.md`](./cli.md#swarm-pm)). This is the step that replaces "configure the webhook in the provider's UI" for Trello, and it has no UI alternative: a GitHub repo/org hook, Linear's Settings → API screen, and Jira's WebHooks screen are all configured by a human, whereas a Trello webhook is a **resource SWARM has to create** — a REST object bound to one board and one callback URL, owned by the token that created it. The command registers `<WEBHOOK_CALLBACK_BASE_URL>/trello/webhook` against this project's `pm.boardId`, is idempotent (an identical subscription is reported and left alone rather than duplicated, which would double every delivery), and `swarm pm webhook list` / `swarm pm webhook delete --id <webhook-id>` show and remove them.

[`WEBHOOK_CALLBACK_BASE_URL`](#general-settings-environment-variables) must be set before you run it, and the command **refuses** without it: Trello probes the callback URL with a `HEAD` request before it will create the webhook (which the receiver's mounted route answers `200`) and then signs every delivery over that exact URL, so a webhook registered against a request-derived URL would `401` on every delivery. Changing that base URL later means `swarm pm webhook delete` then `swarm pm webhook create` — SWARM never rewrites a subscription in place. It is deliberately **not** part of `swarm config apply`: that command is a local-file → Postgres loader with no outbound provider calls, and giving every seed run a network dependency and a partial-failure mode is a bigger decision than webhook creation needs.

A board webhook delivers every card action, and SWARM reacts only to a card *created* on the board and a card *moved between lists* (Trello marks the move with `data.listAfter`); every other card edit is ignored. Trello signs each delivery with an HMAC-**SHA1**, base64-encoded, in `x-trello-webhook` — and, uniquely among SWARM's providers, over the raw body **plus SWARM's own callback URL**, so [`WEBHOOK_CALLBACK_BASE_URL`](#general-settings-environment-variables) must be set to SWARM's public base URL for a Trello project: without it the receiver falls back to the request's own `Host`, which a proxy can rewrite, and every delivery 401s. The **Project Management** tab discovers this provider's boards and their lists with the project's own `credentials.pm.trello.apiKey` + `credentials.pm.trello.token`, so the ids above are picked by name rather than typed, and saved from that screen too. See [Editable via the dashboard UI](#editable-via-the-dashboard-ui).

Issue #643 — which stopped prose from deferring a run anywhere — takes nothing further away here: the gate short-circuits on that flag before it asks for blockers, so a Trello project never had an automated gate to lose.

Must be a level the chosen `(cli, model)` supports per the hand-maintained catalog in `src/harness/models.ts` (`reasoningChoices`), which encodes each model's cap — e.g. Codex `gpt-5.4-mini` tops out at `high`, GPT-5.5/5.4 at `xhigh`, the GPT-5.6 family at `max`; Claude Fable/Opus/Sonnet expose the full range (default `high`). A model with **no** reasoning control has an empty list and rejects any level: **Claude Haiku** (no `--effort` support — budget-based thinking only) and Antigravity single-variant models (e.g. `claude-sonnet-4.6` "Thinking", `gpt-oss-120b`). The dashboard shows the selector disabled ("N/A" for a no-reasoning model, "Fixed" for a single fixed variant). **Omit to keep the CLI/model's own default reasoning** (nothing is passed for Claude/Codex; Antigravity uses the model's default variant). Reasoning has **no per-CLI defaults tier** — a level valid for one model can be invalid for another, so it is resolved against the effective model (per-phase/per-run override → the model's own default), never as a free-standing per-CLI value. |
  | `timeoutMs` | Per-phase wall-clock run timeout in **milliseconds**, from 5 to 45 minutes inclusive. The dashboard displays and edits it in whole minutes, defaulting each phase to 30 minutes. Omit it in file config to fall back to `SWARM_AGENT_TIMEOUT_MS`. A run that exceeds it is killed and recorded with `timedOut: true` and its real duration; it settles `deferred`/`checkpointed` when the run is resumable (the usual case — see `SWARM_AGENT_TIMEOUT_MS` above) rather than always `failed`. |
  | `prompt` | Optional project-owned custom prompt for this phase, appended to SWARM's built-in phase instructions as a clearly delimited "Project instructions" section (after the static instructions, before the task context). It **supplements** — never overrides or weakens — the phase guard, identity/auth guidance, hand-off contract, or phase scope. Trimmed on load; a whitespace-only value is treated as unset (adds nothing, so the effective prompt is exactly the default). Bounded to 10,000 characters (checked against the trimmed value). Edited per phase in the dashboard's **Agent Configuration → phase details** screen. Omit for the default behavior. |

  `cli`/`model`/`reasoning` are a **derived mirror of the highest-priority target**, not settings independent of `targets`: a phase that sets only those three — every config written before the list existed, including one storing a legacy antigravity combined string — is read as a one-element `targets` list, and when `targets` *is* given the three are rewritten from `targets[0]`. So a single-target config behaves exactly as it always has, and every reader that understands only one selection keeps resolving the top target. `timeoutMs` and `prompt` stay phase-level — they apply whichever target runs. The dashboard edits the list directly (**Agent Configuration → phase details**: add/remove/reorder targets, one per CLI) and saves only `targets`, leaving the mirror to be re-derived; a phase written as a single selection is shown as its one target and stays one unless you add another.

  **Target routing (issue #346).** Routing happens where the machine that will run the phase is chosen: the eligibility gate walks the list in order against each enrolled worker's allowed CLIs, selects a worker and a target together, and the selected host atomically revalidates both before execution. A target with no `cli` runs on the phase's coded default CLI and is always eligible. A dispatch that resolves **no** worker resolves no CLI set either — nothing is yet known about a host that will run it — so the highest-priority target is kept, and the run fails visibly on spawn if that CLI is genuinely missing wherever it ends up running, instead of being silently skipped. Nothing routes against the control-plane host's own CLI status (the `cli_quotas` snapshot capability discovery writes, the same signal the dashboard's CLI status shows): that host dispatches phases but never executes them, so its installed CLIs say nothing about where a run will go (issue #703). A per-run override from the **Retry now** dialog pins one exact CLI/model/reasoning and bypasses routing. The chosen target is logged (at `info` when a preferred CLI was skipped, `warn` when nothing was available), and the run row records the target that actually ran.

**`pipeline`** — controls which work items SWARM is allowed to start on at all (`automationLabel`), Planning board movement/splitting, whether SCM-event-driven phases run, and opt-in merging after a successful review response or approved review. Every field is optional. Review, Respond-to-review, and Respond-to-CI default to enabled when their setting or the whole `pipeline` block is omitted. Respond-to-review cannot be enabled unless Review is enabled. After successful delivery, Implementation moves the item to "In review" exactly when Review is enabled; this status report does not dispatch Review, which starts from PR lifecycle events:

### Global settings (`app_settings`)

App-wide settings that apply across **every** project, as opposed to the per-project `swarm.config.json`. Source of truth: `src/config/app-settings.ts` (`AppSettingsSchema`). Stored **DB-first** as one jsonb blob in the single-row `app_settings` table (id `global`) and edited through the dashboard API (the `settings` tRPC router — `get`/`update`), **not** a config file — so there is nothing to `swarm config apply`. When no row exists the coded defaults apply, so no seeding is required for correct default behaviour. The blob is extensible: future global settings (host URL, worker concurrency, …) are added as sibling keys without a migration.

**`agents.defaults`** — the **global** per-CLI default model: a map of `cli` (`claude` / `antigravity` / `codex`) → default `model`, each validated for that CLI per `src/harness/models.ts` (same rules as the project-level `agents.defaults`).

**`appearance.theme`** — the dashboard's theme choice (issue #250): `dark` (default), `light`, or `system` (follows the OS/browser `prefers-color-scheme` and updates live when it changes). Unlike `agents.defaults`, this key always materializes — `AppSettingsSchema` defaults it to `dark` even when parsing `{}` — so every `settings.get` response carries an effective theme rather than requiring callers to fall back manually. Applied dashboard-wide by `dashboard/src/components/theme/theme-provider.tsx`, which sets a `data-theme` attribute the whole palette (`dashboard/src/index.css`) responds to.

Before the four-tier chain runs, Implementation selects `agents.implementationUnplanned` for work items with no prior *completed* Planning run-history row (a failed or deferred attempt does not count), otherwise `agents.implementation`; an unset unplanned variant falls back to `implementation`. The worker then resolves the model for the selected config through a four-tier fallback chain, most specific first (`resolveModel`, `src/worker/consumer.ts`):

1. the phase's own `model` (project `agents.<phase>.model`);
2. the **project** default — project `agents.defaults[cli]`;
3. the **global** default — `agents.defaults[cli]` from these settings;
4. the coded default — `DEFAULT_MODEL_PER_CLI[cli]` (`src/harness/models.ts`: Claude `sonnet`, Antigravity `gemini-3.5-flash`, Codex `gpt-5.6-terra`).

Reasoning (issue #180) is **not** part of this model chain: it is resolved separately from the per-phase/per-run reasoning override and otherwise inherits the effective model's own default (see the per-phase `reasoning` field above). The run row records the requested reasoning (or `Default` when omitted) alongside the model, and the manual "Retry now" dialog can override it — an override incompatible with a changed CLI/model is dropped rather than launched.

### Instance-level default credentials (`instance_scm_credentials`)

**Not an environment variable, not project config, and not part of the `app_settings` blob** — a server-side, encrypted-at-rest secret keyed by `(providerId, role)` in the `instance_scm_credentials` table (issue #769). It is the *installation's default* for a source-control role one account normally serves across every project, recorded once by an instance administrator on the **Settings → Credentials** tab. DB-first exactly like `app_settings`, so there is nothing in `swarm.config.json` and nothing to `swarm config apply`.

- **Its own table, not an `app_settings` key.** `settings.get` returns the whole `AppSettings` object to any authenticated caller, so a secret stored there would be echoed back verbatim. The separate table also lets the read path select the *key columns only* and never decrypt anything just to mask it.
- **Keyed by `(provider, role)`, with no reference indirection.** The `env_var_key` indirection in `project_credentials` exists because a *project* names its own reference key; an instance default has no project and therefore no reference to honour — it is the value for one `(provider, role)` slot. The unique index on the pair is the upsert target, so rotating a default is a plain re-save.
- **Eligibility is declared by the provider, as data.** `SCMProviderManifest.credentialRoles[].instanceDefault` (`src/integrations/scm/manifest.ts`) says whether one value for a role may legitimately be shared installation-wide. Since issue #778 every runtime-ready provider's `reviewer` role opts in — GitHub's, Bitbucket's and GitLab's — because the reviewer identity is an installation-wide requirement rather than a per-provider convenience; the conformance suite asserts that rule rather than an enumeration, so a fourth provider inherits it. A `webhookSecret` may **never** opt in — it is tied to each project's own webhook endpoint — which the same suite asserts structurally, and only *runtime-ready* providers are offered at all.
- **Encrypted with the same primitive `project_credentials` uses** (`src/db/crypto.ts`, AES-256-GCM under `CREDENTIAL_MASTER_KEY`), with `instance:scm:<providerId>:<role>` as the AAD — so a ciphertext copied into another slot's row fails authentication instead of resolving as that provider's secret.
- **It is required to create a project, and copied into it — not resolved through at run time.** `projects.create` (`src/api/routers/projects.ts`) resolves the stored default for the new project's **own** SCM provider — for each `(provider, role)` pair that provider declares `instanceDefault` for — and since issue #778 **refuses creation** when one is not recorded, before any row is written: the error names the provider, the role and where to fix it (General Settings → Credentials), because a project on that provider would otherwise have no way to run Review and nothing would say so until Review failed days later. A lookup failure fails closed the same way, creating nothing. Once resolved, the value is copied into that project's `project_credentials` row under the key the project resolves the role through, so a project created from the dashboard is immediately routable for Review with no reviewer PAT pasted by hand. Only that *write* stays best-effort and post-commit: the value demonstrably exists by then, so a failure is logged, leaves creation successful, and the credential is still settable on the Source Control tab. A provider declaring no eligible role at all is not checked and creates exactly as before. This requirement is the dashboard's alone — `swarm config apply` (`src/config/apply.ts`) deliberately keeps warn-and-skip for a missing referenced secret, since applying a config file before every secret is exported is a legitimate partial state there — and nothing changes for an **existing** project.
- **It is not a resolution fallback.** Nothing reads this table at credential-resolution time: `resolveScmCredentialOrNull` / `requireScmCredential` (`src/config/provider.ts`) keep their no-fallback-chain rule, so a project with no credential of its own still fails naming the project, provider and role. Setting or clearing a default has **no** effect on any existing project, whose own value stays authoritative and stays editable on its Source Control tab — the copy above is made once, at creation, and nothing re-seeds afterwards. A project that later switches provider therefore cannot resolve a stale secret, and the copied value is re-encrypted under the project's own AAD, so clearing the instance default cannot reach it. Bulk-applying a default to already-created projects is deliberately not offered.
- **Administrator-only in the API, not just on the screen.** Every `settings.credentials` procedure — `list` included — answers `FORBIDDEN` for anyone who is not an `instanceAdmin` (`src/api/routers/instanceCredentials.ts`). No procedure returns plaintext, and `list` returns no masked echo either: only configured/not-configured state.

### Editable via the dashboard UI

Today the dashboard exposes a **subset** of settings:

**Who sees these screens.** Every project-scoped editing surface below — the **Settings**, **Agent Configuration**, **Pipeline**, **Project Management**, and **Source Control** tabs — is visible only to that project's administrators (`projectAdmin`, or an `instanceAdmin`, who administers every project) since issue #655. That is the boundary the underlying writes have always enforced; the tabs now match it instead of opening onto reads and writes that come back `FORBIDDEN`. An enrolled non-administrator keeps the project's **Runs** and **Workers** tabs. A project may have more than one administrator, and the creator of a project is written one.

- **Projects** — create a project (`id`, `name`, its one `repositories` entry's `repo`, `repoRoot`) and delete one, plus per-project **Settings** (`name`, `repoRoot`, `worktreeRoot`, `maxConcurrentJobs` — project identity and **host** layout, and nothing else). The project's **repository list** is edited on the **Source Control** tab, not here (issue #729): `repo` is an `owner/repo` slug, `baseBranch` is what pull requests target and worktrees are cut from, and `branchPrefix` names task branches, so the list is source-control vocabulary end to end and belongs beside the provider it runs on rather than a tab away. That tab now reads top-to-bottom as **provider → credentials → repositories** — the shape issue #630 gave Project Management — so one screen answers "which provider, authenticated how, operating on what". `repoRoot`/`worktreeRoot` deliberately stayed on Settings: they are one local checkout path per project on whichever machine runs the work, which is host layout rather than repository configuration (and the same reason a second repository is still refused at provisioning). Since issue #684 phase 3 the list is a real editor for `repositories` rather than three single inputs bound to the first entry, so a second repository no longer needs `swarm.config.json` plus `swarm config apply`. Each row holds that entry's `repo`, `baseBranch` and `branchPrefix` — and, since issue #727, no per-row source-control provider: the project has one, now selected in the card directly above the list, and the section says so. Rows can be added, edited, removed and reordered, and **order is meaningful** — the first row is the project's default repository, what board-driven Planning and Implementation run against, and the screen labels it as such. **The two screens save independently.** `projects.update` is a partial patch, so the repository card sends `repositories` alone under its own Save/Reset and the Settings form sends its four fields alone — the same one-slice-per-tab shape Agent Configuration, Pipeline and Project Management already use, which is what keeps either tab's Save from carrying the other's unsaved edits. Each tab's dirty state, Save/Reset enablement and success/error banner cover only its own fields, and both writes — together with the SCM provider selector's own `scm` write directly above the list (issue #734) — still pass through the one serialization gate that keeps a single config write in flight (issue #369): the selector reports its own write into that gate and is disabled back by it, so it cannot land between the list's read and its upsert, or the reverse. A save still replaces `repositories` wholesale, so the whole list goes every time. Two rules are enforced client-side because the server has no equivalent: at least one entry (Remove is disabled on the last row) and no repository twice within the project. A repository **another** project already owns stays a server-side `CONFLICT` and is rendered in the repository card's own error banner. Listing more than one repository also surfaces the caveat under [`repositories`](#repositories) above, since `repoRoot` is still one checkout per project. **Deep links are unchanged and neither tab can land blank:** `?tab=general` still resolves to Settings, which keeps every field it had bar the list, and `?tab=credentials` to Source Control — so a bookmark to the list's old location opens a populated Settings tab rather than an empty panel, and no alias is needed. Both remain administrator-only configuration tabs (issue #655). The **Project Management** tab stays project-wide and single-entry — the board mapping and the PM credentials are shared by the whole project — and so do Source Control's own provider and credential cards; nothing on either becomes per-repository. So does the New Project dialog — it creates a one-entry list, and further repositories are added on the Source Control tab afterwards. Plus **Agent Configuration** (a per-phase summary table where each row opens a phase-details screen for that phase's ordered `targets` list — add/remove/reorder `cli`/`model`/`reasoning` rows, at most one per CLI — plus its timeout, enable toggle, an optional custom `prompt`, and Planning's auto-advance and verify-plan toggles — plus the project-level `agents.defaults`), a **Pipeline** tab for the Respond-to-review merge-automation/minor-review controls and the Review check policy (`pipeline.review.checks`, a **Require CI checks** / **Review when no checks exist** choice defaulting to **Require CI checks**), and a **Project Management** tab (issue #201, renamed and widened by #537) with four sections, ordered so the tab names the provider before the settings it scopes (issue #630): the **provider** — a live selector naming which PM provider this project is on, and the place a project is **moved** to another one (issue #642) — then that provider's **credentials** — one masked-secret field per credential role it declares (`credentials.pm`), stored encrypted and never returned to the browser — then the **board** picker and the **status mapping**, which edit the configured provider's `pm` member through board/status pickers: it discovers that provider's containers and, for the selected one, its workflow states — using that project's own PM credential, resolved server-side — so you map by real names instead of typing opaque ids (which stay the persisted representation). Four PM providers are implemented — GitHub Projects, Linear (issue #530), Jira (issue #580), and Trello (issue #588) — and the screen reads *and* saves any of the four's mapping (issues #531, #581, and #588): a GitHub Projects **board** + **Status** options, a Linear **team** + **workflow states**, a Jira **project** + **workflow statuses**, or a Trello **board** + **lists** (a Trello card's status is the list it sits in). A Jira project's `pm.baseUrl` is the one mapping field the screen does not edit: it is board identity set in `swarm.config.json`, so a save carries the stored value through unchanged, and Save stays disabled — with copy naming that field — for a Jira mapping with no base URL rather than writing a member `jiraConfigSchema` would reject. The manifest supplies the credential roles, their labels/descriptions, and server-side discovery dispatch; the board/status picker catalogue supplies the correct provider vocabulary for each. **Changing the PM provider is done here** (issue #642), no longer only in `swarm.config.json` plus `swarm config apply`. Picking another registered provider does not change anything on its own: it puts the tab into a client-held draft that walks the order the circular dependency between "which provider" and "which board" requires — supply the new provider's manifest-declared credential roles, discover its containers and states, map SWARM's six canonical status keys, then Save. Only that Save writes, and it writes the whole new `pm` union member in one `projects.update` call, so the project never names a provider whose mapping is absent, incomplete, or still the previous provider's; abandoning the draft, or selecting the persisted provider again, leaves the stored configuration intact and running. The offered list is confirmed against the registry, so a provider the installation registers nothing for is not selectable. The **outgoing provider's credentials are retained**, not destroyed — they live in their own `credentials.pm[<providerId>]` block (issue #631), so switching back needs no secret re-entered. The existing Save gates are unchanged: a mapping with no canonical status key mapped, or a Jira mapping with no `pm.baseUrl`, still fails with the same explanation rather than saving a broken mapping. `projects.update` enforces the same completeness server-side — a `pm.type` change is refused unless the incoming provider is registered and every non-optional, non-inherited credential role it declares has a reference in its own block — because that write does not re-parse the config and so cannot rely on the schema's own presence rule. **A switch does not migrate work in flight, and is deliberately not refused while runs are active**: runs already queued or executing, and the durable `runs.work_item_id` links behind them, refer to the outgoing provider's board and will not resolve against the new one, so finish or cancel them first if that matters. The review step before the save states all three consequences. A role that inherits an SCM-side credential — GitHub Projects' webhook secret, which since issue #628 is the repo side's *per-provider* secret for the provider the project runs on — is shown read-only here and edited on the Source Control tab, so one secret never has two homes; Linear, Jira, and Trello inherit nothing, so all of their roles are edited here.
- **Settings** — a top-level, app-wide **Settings** screen (sidebar → *Settings*) for [global settings](#global-settings-app_settings), with three tabs: **Agent Defaults** — the global per-CLI default model for Claude / Antigravity / Codex (writes `agents.defaults` via the `settings` tRPC router); leaving a CLI on its default option clears the global default so the coded default applies. **Credentials** (issues #769, #778) — one write-only masked-secret field per `(SCM provider, role)` pair a provider declares eligible for an [instance-level default](#instance-level-default-credentials-instance_scm_credentials): since #778 that is each of GitHub's, Bitbucket's and GitLab's reviewer roles, one field per provider, rendered generically from the registry with no dashboard change. A saved value is stored encrypted and never returned to the browser, not even as a masked preview. A stored default is **copied into every project created from the dashboard afterwards** — matched to that project's own SCM provider — so a new project is routable for Review with nothing pasted by hand; **a project cannot be created at all for a provider whose default is unset**, with the refusal naming the provider and this tab. Setting or clearing one changes nothing for an existing project. **Appearance** — a Dark / Light / System default radio group (writes `appearance.theme`); selecting an option repaints the dashboard immediately and persists without a separate Save action. **Agent Defaults and Credentials are shown only to an `instanceAdmin`** (issues #666, #769): both are installation-wide configuration, so neither tab is offered to anyone else and a direct `?tab=agents` / `?tab=credentials` link lands on **Appearance** instead. For Agent Defaults that is a visibility boundary on the screen alone — the `settings.get`/`update` procedures' own authorization is unchanged. For **Credentials it is not**: every `settings.credentials` procedure, reads included, enforces `instanceAdmin` in the router, because a secret must not be writable (or its configured state readable) by any authenticated user just because a tab is hidden.

The pipeline controls other than the board mapping, the PM provider, Planning auto-advance and plan verification, Respond-to-review merge-automation/minor-review handling, and the Review check policy — plus all general/env settings — are **not** yet editable in the UI; change those in `swarm.config.json` / `.env` and re-apply. Board mapping and PM credentials (**Project Management** tab, issues #201/#537) and the SCM provider, its credentials and the project's repository list (**Source Control** tab, issues #200/#632/#729) are now editable in the dashboard — the Source Control tab edits [`scm`](#project-config-swarmconfigjson), [`credentials.scm[<the selected provider>]`](#credentialsscm) — the two references of whichever provider its selector currently names (issue #632: pick GitLab and you see and edit GitLab's pair, under GitLab's own field labels and reference names, with GitHub's stored secrets left untouched and shown again when you switch back) — and [`repositories`](#repositories) beneath them (issue #729), the Project Management tab the PM provider's own `credentials.pm` roles. Each field names the store key the project *resolves* that role through, not the provider's conventional `envVarKey` — the two commonly differ (see [Credential secret values](#general-settings-environment-variables)), and only the resolved one is what a saved value lands on. Either surface is authoritative for what it wrote: the dashboard writes straight to the encrypted store (and records the reference), while `swarm config apply` re-applies whatever `swarm.config.json` names.
