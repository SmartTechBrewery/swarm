# Configuration

SWARM's configuration splits into three layers:

- **General settings** — process/host-level knobs, set as **environment variables** (usually in `.env`, sourced from `.env.docker.example`). No schema; read directly where needed. These configure the router, worker, dashboard, database, Redis, credential encryption, and logging.
- **Project config** — the **per-project** shape (`swarm.config.json`, one entry per project), validated by a Zod schema (`src/config/schema.ts` — the single source of truth) and loaded into Postgres via `swarm config apply` / `npm run db:seed`. This is where a project's repo, worktree layout, board mapping, credential references, and per-phase agent/pipeline behaviour live.
- **Global settings** — **app-wide** knobs that apply across every project, validated by a Zod schema (`src/config/app-settings.ts` — the single source of truth) and stored **DB-first** in the single-row `app_settings` table. Unlike project config these are *not* file-sourced; they're edited through the dashboard API (the `settings` tRPC router), and when nothing is stored the coded defaults apply. Today the global settings are `agents.defaults` (the global per-CLI default model) and `appearance.theme` (the dashboard's theme choice).

> **This document is the canonical, human-editable catalogue of every configuration option.** It is meant to be kept in lock-step with the code (see [`ai/RULES.md` §7](../ai/RULES.md)): when an option is added, removed, renamed, or its default changes, update the matching row here in the same change. When you'd rather not click through the dashboard UI, point an agent at this document and ask it to change a setting — everything editable is listed here with the exact key, default, and file it lives in.

### General settings (environment variables)

Grouped by concern. "Required" means startup throws if it's unset; everything else has a default or a safe fallback. Docker-side ports (`POSTGRES_PORT`, `REDIS_PORT`, `ROUTER_PORT`, …) are the **host-published** ports; inside the Compose network the services use their own fixed container ports.

**Queue & worker (Redis / BullMQ)**
| Variable | Default | Purpose |
| --- | --- | --- |
| `REDIS_URL` | **required** | Redis connection URL for the BullMQ queue and all Redis-backed dedup (`src/lib/redis.ts`). Parsed for host, port (default `6379`), and password. |
| `SWARM_WORKER_CONCURRENCY` | `1` | Maximum number of jobs one dispatcher process runs concurrently. In `in-process` mode this is the host worker's process-wide cap across every project it serves (`src/worker/index.ts`); override it per launch with `--concurrency <n>` (`npm run dev:worker -- --concurrency 2`), which takes precedence over the env var. In `transport` mode the router owns the consumer, and `docker-compose.yml` passes this setting to it so it can dispatch simultaneously to separate eligible workers. Must be a positive integer or startup throws. A project's `maxConcurrentJobs` additionally caps that project's in-flight jobs, and in a federated setup each enrollment's `concurrencyAllocation` caps one worker's share of one project. |
| `SWARM_WORKER_CREDENTIAL` | _(unset)_ | Raw registered-worker credential printed once by `swarm workers register`. When set, the host worker authenticates, acquires and heartbeats that worker's fenced session, and may execute only dispatches atomically selected/capacity-claimed for that worker. When `SWARM_SINGLE_USER_MODE` is disabled (multi-user mode), an unset credential may serve projects with no enrollments (unfederated mode) but defers every federated dispatch; an invalid credential or already-live session makes startup fail. When `SWARM_SINGLE_USER_MODE` is enabled, the federated dispatch gate is completely bypassed, so worker credentials and rosters are ignored and all phases execute locally on the host worker. The **remote** worker transport client (`npm run dev:worker:connect`, `src/transport/connect-entry.ts`, ADR-003 §1) reads the same credential — it is the only secret that client holds. Never commit this value. |
| `SWARM_WORKER_REPO_ROOT` | Current working directory | Absolute path to the assigned repository checkout on a **DB-free remote worker**. This is host-local execution state: the control plane's `project.repoRoot` is omitted from `TaskAssignment`, and the daemon reconstructs the project with this path instead. Set it when launching `npm run dev:worker:connect` from anywhere other than the repository checkout. Provisioning verifies the checkout's `origin` remote resolves to the assigned project's repository and fails the run if it does not, so a mistyped path (or a second enrolled project) cannot be worked on silently; a checkout with no `origin` cannot be identified and is accepted. The same-host worker ignores it and keeps using the project's configured `repoRoot`. |
| `SWARM_OPERATOR_GH_TOKEN` | _(unset)_ | Worker-local **operator GitHub token** — the implementer persona's token (issue #396). Mirrors `SWARM_WORKER_CREDENTIAL`: it is held only on the machine, **never persisted** to `project_credentials`, **never in project config**, and **never sent over the transport**. It resolves the implementer persona behind the `getPersonaToken`/`getPersonaTokenOrNull` seam (`src/config/provider.ts`), so implementer commit/push/create-PR run under the operator's own account and the PR is authored by that account, while the project-scoped **reviewer** PAT stays a distinct identity. Required on every process that runs an implementer phase or resolves persona identities: the host **worker**, the **router** — for `personaForEvent` routing, and in control-plane delivery mode for posting a Respond-to-review reply under the implementer rather than under the reviewer it answers (`POST /worker/delivery/pr-comment`, issue #444) — and the **remote worker transport client** (`npm run dev:worker:connect`, `src/lib/env.ts` `resolveOperatorGitHubToken`, ADR-003 §2), which executes pushed assignments DB-free (`src/transport/connect-entry.ts`) and so has no secret store to resolve persona references against: this single operator token is the identity for every source-carrying delivery op it performs (commit / push / create-PR / find-PR / comment). It is **no longer needed to map a board or to gate board events**: since issue #537 the API server discovers boards with the project's own `credentials.pm.apiToken`, and the board-side `isSelfAuthored` gate resolves that same PM credential's identity — an SCM operator token no longer has any part in either. When unset, implementer operations fail with an actionable error; `dev:worker:connect` throws at startup, and the router logs a startup warning and answers `503 persona credential unavailable` on `/worker/delivery/pr-comment` for the implementer persona rather than a reason-less 500. SWARM's two "is this ours?" gates no longer need it at all: the Review trigger keys on work-item origin (issue #397) and comment loop prevention on the comment's own SWARM marker (issue #443), neither of which resolves an identity. Same-host assumption; federating it is a later phase. Never commit this value. |
| `SWARM_OPERATOR_BITBUCKET_TOKEN` | _(unset)_ | Worker-local **operator Bitbucket credential** — the implementer persona's credential for the Bitbucket SCM provider (issue #296), the exact mirror of `SWARM_OPERATOR_GH_TOKEN` above and subject to the same invariants: held only on the machine, **never persisted** to `project_credentials`, **never in project config**, **never sent over the transport**. Source delivery requires a `username:app_password` pair: it is the only form that can resolve `GET /2.0/user`; a workspace/repository access token fails identity resolution before delivery reaches the email lookup. An app password without the `email` scope still delivers using an unattributed noreply commit address; grant that scope for attributed commits. Only relevant to a host that runs Bitbucket implementer work — **nothing does yet**: the Bitbucket provider is registered but not runtime-ready, so leaving this unset changes nothing for a GitHub project. When unset, Bitbucket implementer operations fail with an actionable error naming it and persona identity resolution fails closed. Never commit this value. |
| `SWARM_OPERATOR_GITLAB_TOKEN` | _(unset)_ | Worker-local **operator GitLab token** — the implementer persona's token for the GitLab SCM provider (issue #295), the exact mirror of `SWARM_OPERATOR_GH_TOKEN` above and subject to the same invariants: held only on the machine, **never persisted** to `project_credentials`, **never in project config**, **never sent over the transport**. Any token form GitLab accepts in its `PRIVATE-TOKEN` header works — personal, group, or project access — since all of them resolve `GET /user` for persona identity (there is no credential-form branch as there is for Bitbucket). It needs the **`api` scope**: delivery writes merge-request notes, review verdicts, and merges, and `read_api`/`read_user` cannot perform those. Two consequences worth knowing before granting it: commit **attribution** follows the account email GitLab returns from `GET /user`, so a token whose scope withholds it — and a project/group access token's bot user, which has no address at all — still delivers, but under a `<username>@users.noreply.gitlab.com` author that keeps the right name and leaves the commit unlinked (GitLab links a commit only by a **verified** account email); and approving requires the account to be an **eligible approver** on the project, so a project that forbids self-approval leaves the merge request unapproved and merge automation reports the missing approval rather than merging. GitLab**.com** only; a self-managed host would need a base-URL setting that does not exist yet. Only relevant to a host that runs GitLab implementer work — **nothing does yet**: the provider is registered but not runtime-ready, so leaving this unset changes nothing for a GitHub project. When unset, GitLab implementer operations fail with an actionable error naming it and persona identity resolution fails closed. Never commit this value. |
| `SWARM_CONTROL_PLANE_URL` | _(unset)_ | Control-plane base URL, shared by two features that both point a worker at the router over the network. (1) **SCM + PM metadata delivery** (ADR-004 §2, `src/lib/env.ts`): set **together with** `SWARM_WORKER_CREDENTIAL` it opts a federated worker into **control-plane delivery mode** — the metadata-only delivery calls travel up the transport to the router's `POST /worker/delivery/*` routes, which perform the write under the per-project credential so that credential stays on the server and never reaches a worker. On the **SCM** side, submit-review runs under the per-project **reviewer PAT**, and post-PR-comment runs under the **persona the requesting phase named** — the reviewer for a Review's comment, the **implementer** for a Respond-to-review reply, which must not be authored by the reviewer it answers (issue #444) — defaulting to the reviewer when a client sends no persona (only the verdict + comment body + PR number + that persona cross the wire); on the **PM** side the two board writes (move a card, comment on the backing Issue/PR) run under the per-project **PM credential** (only the canonical status key / comment body crosses — never a board option ID). The repository tree never crosses in either case. Source-carrying / attribution ops (commit, push, create PR) and all PM **reads** stay worker-side under the operator's own token. (2) **Remote worker transport** (ADR-003 §1): the base URL the **remote** worker transport client (`npm run dev:worker:connect`) connects to — typically the same Cloudflare-tunnel base URL GitHub's webhooks use (e.g. `https://swarm.example.com`). The client derives the transport endpoints from it: `POST <url>/worker/session` for the HTTP handshake and a WebSocket at the matching `ws(s)://<url>/worker/stream` for heartbeats (`src/transport/worker-client.ts`). Unlike the in-process host worker, this client holds **only** this URL plus `SWARM_WORKER_CREDENTIAL` — no `DATABASE_URL`/`REDIS_URL`. That client also executes pushed assignments **DB-free** (ADR-003 §2) and reuses the delivery routes from (1) for everything its own token and its missing database cannot serve: Implementation's two board writes plus its `listBlockers` dependency lookup (`POST /worker/delivery/pm/blockers`), Respond-to-review's board-card lookup (`POST /worker/delivery/pm/find-item`) and its two status-report moves, Review's submitted verdict, Review's three review-verdict ledger calls (`POST /worker/delivery/review-ledger/prior|mark|abandon`, which front the `review_verdicts` table rather than a credential), the follow-up Review a pushed fix enqueues (`POST /worker/delivery/follow-up-review`, which fronts the dispatch store and queue), and Planning's board surface — its `findComment` replay guard plus the four writes a task split needs (`POST /worker/delivery/pm/find-comment|create-item|update-item|label|blocked-by`). **All six phases** run this way since issue #536 (`respond-to-ci`, `resolve-conflicts`, `implementation`, `review`, `respond-to-review`, `planning`), so no phase is refused for want of a database; a daemon built before #536 declares only the first five, and the eligibility gate routes around it rather than failing the dispatch. Required by `dev:worker:connect` (it throws if unset); for the same-machine host worker it's optional and irrelevant unless SCM delivery mode or `SWARM_DISPATCH_MODE=transport` (below) needs it. Must be an `http(s)` URL. Unset (the default, and every local host worker) keeps today's in-process delivery path byte-for-byte unchanged. |
| `SWARM_WORKER_TRANSPORT_CLIS` | _(auto-detect)_ | Optional comma-separated override of the agent CLIs the **remote** worker transport client declares at handshake — any of `claude`, `antigravity`, `codex`. When unset, the client probes the host's PATH for each CLI's binary (`claude`, `agy`, `codex`) and declares those it finds (`src/transport/cli-discovery.ts`); this DB-free probe is why the client needs no `runs`-table quota lookup. An unknown value fails startup loudly. The declared set must still include every CLI the worker's enrollments require, or the handshake is rejected (HTTP 409) — so discovery drops a CLI only on proof it is absent (`ENOENT`): a probe that times out is retried once with a wider budget and then declared anyway, and a rejected *discovered* set is re-probed before the daemon gives up (issue #559). Setting this override opts out of that recovery, since an explicit declaration is not something a re-probe should talk over. The host worker also reads this override when started in `transport` dispatch mode (below). |
| `SWARM_DISPATCH_MODE` | `in-process` | Where the BullMQ consumer + ADR-001 eligibility gate run (ADR-003 §2). Read by **both** the router (`src/router/index.ts`) and the host worker (`src/worker/index.ts`); set it the same on both. `in-process` (the default; unset/empty keeps it) runs today's consumer + `processJob` on the host worker unchanged, and the router serves only webhooks + the worker-session transport. `transport` **relocates the consumer + gate to the control plane (router)**: the router dequeues, runs the gate, composes the system prompt + target branch, builds a `TaskAssignment`, and pushes it to the selected **connected** worker (`src/router/dispatcher.ts`); the host worker instead runs the transport-dispatch client (`src/worker/transport-client.ts`), which connects to `SWARM_CONTROL_PLANE_URL` with `SWARM_WORKER_CREDENTIAL`, runs each phase locally (persona tokens still resolve from Postgres — the worker stays same-host with `DATABASE_URL`), and reports live output + a terminal `TaskExecutionResult` back over the transport back-channel for the router to settle the dispatch on. In `transport` mode the worker requires both `SWARM_WORKER_CREDENTIAL` and `SWARM_CONTROL_PLANE_URL`, its declared CLI set follows `SWARM_WORKER_TRANSPORT_CLIS` / the PATH probe, and the worker must be **enrolled** in the project (transport dispatch is federated: an unfederated project has no executor on the router and its dispatches stay durably pending). Not compatible with `SWARM_SINGLE_USER_MODE` (which routes every phase to an in-process host worker the router does not run). Any other value fails startup loudly. |
| `SWARM_MAX_JOB_AGE_MS` | `86400000` (24h) | Maximum age of a BullMQ job when the worker begins processing it (`src/worker/job-freshness.ts`). Older webhook or retry jobs are acknowledged as stale without starting an agent, preventing an offline worker from replaying board work completed manually. Must be a positive integer or startup throws. |
| `SWARM_WORKER_LOCK_DURATION_MS` | `900000` (15m) | BullMQ job-lock duration (`src/worker/runtime-options.ts`). Locks are renewed at least every 30s (or half the duration for a shorter override), while the longer expiry tolerates a sleeping laptop, event-loop starvation, or a transient Redis interruption without falsely reclaiming a still-running agent as stalled. Must be a positive integer or startup throws. |
| `SWARM_WORKER_HEARTBEAT_TTL_MS` | `60000` (60s) | How long a worker session lease stays live after its last heartbeat (`src/identity/worker-session-service.ts`). The host worker refreshes it at one third of this interval. An older session is expired and may be re-acquired with a bumped fencing token; dispatch execution atomically validates that token and session before reserving capacity, so a stale/replaced host is rejected. The same TTL governs a **remote** worker session established over the router's worker transport (`POST /worker/session` + `GET /worker/stream`, ADR-003 §1): the returned `heartbeatTtlMs` tells the daemon how often to heartbeat over the WebSocket to keep the lease live. Must be a positive integer or the operation throws. |
| `SWARM_WORKTREE_SWEEP_INTERVAL_MS` | `3600000` (1h) | How often the background worktree retention sweep runs on the control-plane host. Read by whichever process owns the sweep in the configured dispatch mode (issue #550): the host worker in `in-process` mode (`src/worker/index.ts`), the **API server** in `transport` mode (`src/api/maintenance.ts`), where the worker hands off to the transport-dispatch client and never reaches its own copy. Must be a positive integer or that process's startup throws. |
| `SWARM_AGENT_TIMEOUT_MS` | `1800000` (30m) | Default wall-clock timeout applied to **every** phase/agent run when the project sets no per-phase `agents.<phase>.timeoutMs` (`src/worker/consumer.ts`). The harness kills a run that exceeds it (SIGTERM, then SIGKILL after a 5s grace) so a hung agent can't hold a worker slot indefinitely. A genuinely-interrupted timeout is then **deferred and resumed** (the agent continues its prior CLI session in the preserved worktree — see the [pipeline guide](./pipeline.md#pipeline-phases)), bounded by the same retry cap as a rate-limit; only a run that trapped SIGTERM and still exited 0 is finalized `failed`. A per-phase `timeoutMs` in `swarm.config.json` overrides it. Must be a positive integer or startup throws. |
| `SWARM_STALE_RUN_SWEEP_INTERVAL_MS` | `300000` (5m) | How often the worker sweeps for stale `running` run-history rows while it keeps serving jobs — a phase whose process died without finalizing (`src/worker/index.ts`). A row still `running` past `max(configured timeout) + 10m` grace is reconciled to `failed`. Must be a positive integer or startup throws. |
| `SWARM_DEPENDENCY_RECHECK_MS` | `300000` (5m) | How often the worker re-checks the prerequisites of an Implementation deferred because its work item is `blocked by` an unfinished issue (`src/worker/dependency-recheck.ts`). The re-check is **token-free** — the dependency gate runs before any worktree or agent, so it costs one PMProvider read and zero model tokens (the same agent-less pattern as merge-automation). The federated dispatch gate (issue #339) deliberately shares this cadence for its own token-free wait (a dispatch with no eligible worker — wait reason `worker-eligibility`), tracked on a separate attempt budget. Must be a positive integer or startup throws. |
| `SWARM_DEPENDENCY_MAX_WAIT_MS` | `604800000` (7d) | Total time a dependency-blocked Implementation keeps re-checking before it gives up and settles `failed` with an actionable "must be done first" comment on the item (`src/worker/dependency-recheck.ts`), rather than waiting forever on an abandoned prerequisite. Divided by `SWARM_DEPENDENCY_RECHECK_MS` to get the re-check budget — also the budget the federated dispatch gate's `worker-eligibility` wait uses before it settles `failed` with the actionable reason (grant sharing consent, approve the enrollment, enroll a worker that can run the configured CLI). Must be a positive integer or startup throws. |
| `SWARM_ANTIGRAVITY_CONVERSATIONS_DIR` | `~/.gemini/antigravity-cli/conversations` | Where the harness looks for Antigravity's per-conversation `.db` files, used as the **fallback** way to capture the id of the session an `agy` run created so a deferred run can be resumed with `agy --conversation <id>` (`src/harness/antigravity-session.ts`). All three CLIs normally report their session id directly — Antigravity's arrives as the `conversation_id` on its `--output-format stream-json` stream (issue #465) — so this store diff only matters for an `agy` too old to support that flag, or a run killed before its opening event was captured. Override for a non-default `agy` install or in tests. |

**API server** — `src/api/server.ts`
| Variable | Default | Purpose |
| --- | --- | --- |
| `SWARM_SINGLE_USER_MODE` | `false` (coded default; **`true`** in `.env.docker.example`) | Local single-user API authentication **and dispatch** policy (issues #298, #373). Only the literal `true` enables it; unset/empty/any other value keeps the coded default. When enabled, the API atomically bootstraps a passwordless reserved `localhost-admin` `instanceAdmin` and resolves every `/trpc/*` request to that user **with no session cookie**, so a local install needs no `swarm users`, no password, and no `/login`; `/login` itself detects the resolved identity and enters the dashboard directly. The host worker also treats the host process as the implicit local executor for **every** project: it routes every pipeline phase through the existing unfederated/local path — local target selection, the project slot, a null worker identity — and **skips the federated roster entirely** even when worker/enrollment rows exist, so local development needs no `SWARM_WORKER_CREDENTIAL`, worker-project enrollment, admin approval, assignee linking, or sharing consent. It creates no synthetic workers, sessions, or enrollment rows. Disabling it (or leaving it unset) restores the full federated policy unchanged: per-user session-cookie auth (below) **and** the complete enrollment/consent/affinity/fencing/capacity dispatch gate. Not consumed by the router container — the API server and host worker read it. |
| `SWARM_SESSION_TTL_HOURS` | `168` (7 days) | Lifetime of a dashboard login session (multi-user mode). After this, the session cookie is rejected and the user must sign in again. A non-positive or non-numeric value falls back to the default. |
| `API_PORT` | `3101` | Port the API server listens on (bound to `127.0.0.1` only). |
| `CORS_ORIGIN` | `http://localhost:5173` | Comma-separated allow-list of browser origins permitted to make **credentialed** cross-origin requests (the session cookie rides every request). Only needed for the separate-origin setup — SPA and API on different origins; the default already covers the documented Vite dev workflow. A same-origin deploy never pre-flights, so this is inert there. Never `*` (illegal alongside credentials). |

Unless `SWARM_SINGLE_USER_MODE` (above) is enabled, the dashboard uses **per-user session auth** (issue #281 task 2), not a shared secret: a user set up with `swarm users add` + `swarm users set-password` signs in at `/login`, and the server issues an opaque session delivered as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost). Every `/trpc/*` request except `ping` is authorized by that cookie; `/health` stays public. No API token is configured — `DASHBOARD_TOKEN` and its browser copy `VITE_DASHBOARD_TOKEN` have been **retired**. Only a hash of the session token is stored (`user_sessions`), never the raw token. In single-user mode the cookie is not required at all: the API resolves the bootstrapped `localhost-admin` for every request directly.

For the recommended **same-origin** deploy (the API server serves the built dashboard SPA and the API from one process), no CORS config is needed. The separate-origin setup — running the SPA on the Vite dev server against the API on `API_PORT`, or `VITE_API_URL` pointing at a different host — is credentialed and therefore pre-flighted by the browser; the API allows it via `CORS_ORIGIN` (default `http://localhost:5173`, which matches `dashboard/vite.config.ts`). `SameSite=Strict` still delivers the cookie for the localhost dev case (ports don't change the *site*); a genuine cross-*site* production origin would additionally need different cookie attributes and is out of scope for SWARM's local-first model.

**Router** — `src/router/index.ts`
| Variable | Default | Purpose |
| --- | --- | --- |
| `PORT` | `3000` | Webhook-receiver port **inside the router container**; the host-published port is `ROUTER_PORT`. |
| `WEBHOOK_CALLBACK_BASE_URL` | _(unset → derived from the request)_ | SWARM's **own public base URL**, scheme and host with no trailing slash (e.g. `https://swarm.example.com`) — the same base URL the provider's webhook subscription and the Cloudflare Tunnel in front of it are configured with. The webhook receiver resolves the callback URL of each mounted route from it (`src/lib/env.ts` `resolveWebhookCallbackBaseUrl`, `src/router/webhook-callback-url.ts`) and hands it to the PM manifest's `verifyWebhookSignature` (issue #496), because a provider's signature can cover SWARM's own URL rather than the body alone: Trello signs `HMAC(rawBody + callbackUrl)`, so a verifier that cannot name the URL a delivery arrived at cannot verify it. **Not required today** — GitHub, GitHub Projects, and Linear all sign the raw body, so leaving it unset changes nothing for them — and required from the day a Trello-style provider is registered. When unset, the receiver derives the base from the request's own `Host` + `X-Forwarded-Proto` headers, which works behind a well-behaved proxy but is caller-controlled and silently wrong behind one that rewrites `Host`; with neither available it logs a warning naming this variable and continues (the resulting `https://undefined/...` would otherwise surface as an unexplained 401). Must reach the **router** process, which is the only one that serves webhooks — the Compose router container receives it from `.env`. |

**Credential secret values** (referenced by project config, not config themselves): the env vars a project's `credentials` block *points at* — by default `SCM_TOKEN_REVIEWER`, `SCM_WEBHOOK_SECRET` for a newly created project, plus whatever a `credentials.pm` role map names (issue #497; for GitHub Projects that is `PM_GITHUB_PROJECTS_TOKEN`, the board's own required API token — issue #537 — and for Linear the pair `LINEAR_API_KEY` + `LINEAR_WEBHOOK_SECRET`, issue #530; see [Per-project config](#per-project-config-swarmconfigjson)). `swarm config apply` reads those opaque reference *names* from the environment once and stores the resolved values (encrypted) in Postgres; the router/worker normally resolve credentials from the DB thereafter. The sole runtime fallback is an explicitly configured `credentials.pm[role]` whose store reference is absent: then that role's declared `envVarKey` is read from the host environment. A role with no `credentials.pm` entry — including GitHub Projects' inherited `webhookSecret` — never uses an ambient fallback and fails closed when its stored credential is absent. An unset reference is warned-and-skipped, not fatal. The default only changes what a *new* project is created with; a project already storing GitHub-named references (`GITHUB_TOKEN_REVIEWER` and friends) keeps resolving them unchanged — there is no migration and no dual-read fallback to reconcile. The **implementer** persona is no longer a project credential (issue #396): its token is the worker-local `SWARM_OPERATOR_GH_TOKEN` env var (see the Queue & worker table above), read live from each host's environment — not stored in Postgres. A legacy `swarm.config.json` still listing an `implementer` reference parses with the key stripped, so `swarm config apply` stays idempotent.

**`credentials`** — every value is a *reference* (a key into the secret store / an env-var name), never a raw token. `reviewer` and `webhookSecret` are required; `pm` is optional in shape but required in practice for a provider with a non-inherited role — GitHub Projects has one since issue #537, and Linear has two (see [`credentials.pm`](#credentialspm) below). Both fields are **provider-neutral** (issue #290, defaults `SCM_TOKEN_REVIEWER` / `SCM_WEBHOOK_SECRET`): a Bitbucket or GitLab project reuses these same two references rather than getting its own, and its implementer credential comes from `SWARM_OPERATOR_BITBUCKET_TOKEN` / `SWARM_OPERATOR_GITLAB_TOKEN` — so neither the Bitbucket provider (issue #296) nor the GitLab one (issue #295) added a project-config field. `repo` doubles as each provider's own project coordinates too: Bitbucket's `workspace/repo_slug`, GitLab's `namespace/project` path.
| Field | Purpose |
| --- | --- |
| `reviewer` | Reference to the reviewer-persona SCM token. |
| `webhookSecret` | Reference to the SCM webhook secret. What the provider does with it differs: GitHub and Bitbucket HMAC-sign the raw body with it, while GitLab echoes it verbatim in `X-Gitlab-Token` and the adapter compares the two (issue #295) — so for a GitLab project this value is a shared *token*, not an HMAC key, and it authenticates the sender rather than the body. |
| `pm` | Map of **PM-provider credential role → reference**, e.g. `{ "apiToken": "PM_GITHUB_PROJECTS_TOKEN" }` for GitHub Projects or `{ "apiKey": "LINEAR_API_KEY", "webhookSecret": "LINEAR_WEBHOOK_SECRET" }` for Linear (issue #497). Optional only when every role the provider declares is optional or inherited. See below. |

**`credentials.pm`** — the PM side needs credentials the two shared SCM references cannot express (Jira an email plus an API token, Linear an API key, Trello a key + token + secret), so **each PM provider declares its own roles on its manifest** (`PMProviderManifest.credentialRoles`, `src/integrations/pm/manifest.ts`) and this map supplies one reference per role. A role spec is `{ role, label, envVarKey, optional?, inheritsSharedCredential? }` (`PmCredentialRoleSpec`), and shared code resolves a role — never a reference or an env var — through `resolvePmCredential(project, role)` / `requirePmCredential(project, role)` (`src/config/provider.ts`).

Resolution order for one role: the reference configured here → the shared `credentials` reference the role declares it inherits → the role's `envVarKey` in the host environment **only when this map explicitly names that role** → nothing. That final fallback supports an opted-in PM role whose store row is absent; it never widens an inherited role with no `credentials.pm` entry. The references named here are applied exactly like the SCM ones: `swarm config apply` reads each from the environment by that name and stores the value encrypted in Postgres.

Validation is against the *registered* manifest for `pm.type`: a reference for a role the provider doesn't declare, and an omitted non-optional role, both fail with the declared roles named. The whole block is optional only when every one of the provider's roles is optional or inherits a shared credential.

**GitHub Projects declares two roles, and one of them is required here** (issue #537):

| Role | Env-var key | Purpose |
| --- | --- | --- |
| `apiToken` | `PM_GITHUB_PROJECTS_TOKEN` | **Required.** The GitHub token every board read, board write, and board/state discovery authenticates as. A project credential, resolved only on the control plane — never a worker's token. |
| `webhookSecret` | `SCM_WEBHOOK_SECRET` | Inherits the shared `credentials.webhookSecret` reference, because the board and the repo are literally the same GitHub webhook — one URL, one secret. Needs no entry of its own, and is configured on the dashboard's **Source Control** tab. |

**Required token permissions for `apiToken`:** a classic PAT needs `repo` (the board's cards are Issues/PRs — SWARM comments on them, labels them, reads their dependencies), `project` (read **and write**: it moves cards between Status options), and `read:org` (enumerating organization-owned boards for the board picker — a token without it fails discovery with an error naming the missing scope; a failure GitHub does *not* attribute to permissions, such as an outage or a rate limit, surfaces as itself rather than as a scope diagnosis). A fine-grained token needs the equivalent: repository **Issues** and **Pull requests** read/write, plus organization **Projects** read/write for an org-owned board. This token's account is also the identity the board's loop-prevention gate recognizes as SWARM's own, so a card *it* moves does not re-trigger the pipeline — do not point it at the account a human moves cards from.

**Linear declares two roles, and both are required here** (issue #530):

| Role | Env-var key | Purpose |
| --- | --- | --- |
| `apiKey` | `LINEAR_API_KEY` | **Required.** The personal Linear API key every board read, board write, and team/state discovery authenticates as. Its account is the identity board loop prevention recognizes as SWARM's, so don't point it at the account a human moves cards from. |
| `webhookSecret` | `LINEAR_WEBHOOK_SECRET` | **Required.** The signing secret Linear shows when the webhook is created, which it HMAC-signs each delivery's body with. |

**Neither inherits a shared SCM reference**, unlike GitHub Projects' webhook secret: a Linear board is a separate system from the GitHub repo it is paired with, so there is no shared account or shared webhook to borrow from — the board webhook's secret is Linear's, not the repository's. Both are also **required** rather than optional, the webhook secret included: SWARM's verifier fails closed on an absent secret, so an optional role would validate at `swarm config apply` and then reject every genuine delivery with a 401. So a Linear project's config carries `"pm": { "apiKey": "LINEAR_API_KEY", "webhookSecret": "LINEAR_WEBHOOK_SECRET" }` under `credentials`, with both variables exported before `swarm config apply`.

**Migrating a project written before #537.** Board access used to be borrowed from the SCM implementer persona — the worker-local `SWARM_OPERATOR_GH_TOKEN` — which is why `credentials.pm` could be omitted entirely. It no longer is: add `"pm": { "apiToken": "PM_GITHUB_PROJECTS_TOKEN" }` to the project's `credentials`, export that variable, and re-run `swarm config apply`. A config missing it fails validation with the role and its env var named, and a project already in Postgres keeps loading but fails every board operation with the same actionable error rather than silently reusing an operator token. The dashboard's **Project Management** tab configures the same credential without touching the file (it stores the secret encrypted and records the reference for you).

Defaults store a **model only**, never a reasoning level (a per-CLI default reasoning can be invalid for another model — see the `reasoning` field below).
- **Phases** — `planning`, `implementation`, `implementationUnplanned`, `review`, `respondToReview`, `respondToCi`, `resolveConflicts`. Each is an object. `implementationUnplanned` applies only when an Implementation run has no prior *completed* Planning run-history row for the same item — a failed or deferred attempt does not count; it falls back to `implementation` when unset, preserving current behavior, and is a dispatch-time config variant rather than a pipeline phase:
  | Field | Purpose |
  | --- | --- |
  | `targets` | The phase's model targets as an **ordered list** of `{ cli, model, reasoning }` objects — priority is list order (index 0 is the most preferred) and at most one entry may name any given `cli`. A model with **no** reasoning control has an empty list and rejects any level: **Claude Haiku** (no `--effort` support — budget-based thinking only) and Antigravity single-variant models (e.g. `claude-sonnet-4.6` "Thinking", `gpt-oss-120b`).   | `prompt` | Optional project-owned custom prompt for this phase, appended to SWARM's built-in phase instructions as a clearly delimited "Project instructions" section (after the static instructions, before the task context). Trimmed on load; a whitespace-only value is treated as unset (adds nothing, so the effective prompt is exactly the default). Bounded to 10,000 characters (checked against the trimmed value).   `cli`/`model`/`reasoning` are a **derived mirror of the highest-priority target**, not settings independent of `targets`: a phase that sets only those three — every config written before the list existed, including one storing a legacy antigravity combined string — is read as a one-element `targets` list, and when `targets` *is* given the three are rewritten from `targets[0]`. So a single-target config behaves exactly as it always has, and every reader that understands only one selection keeps resolving the top target. `timeoutMs` and `prompt` stay phase-level — they apply whichever target runs. The dashboard edits the list directly (**Agent Configuration → phase details**: add/remove/reorder targets, one per CLI) and saves only `targets`, leaving the mirror to be re-derived; a phase written as a single selection is shown as its one target and stays one unless you add another.

  **Target routing (issue #346).** When the phase runs, the worker walks the list in order and uses the first target whose CLI it can actually run — "can run" meaning the CLI was not discovered as `unavailable` on this machine (the `cli_quotas` snapshot written by capability discovery, the same signal the dashboard's CLI status shows). A target with no `cli` runs on the phase's coded default CLI and is always eligible. If **no** target's CLI is available — or capability discovery has never run, or the lookup fails — the highest-priority target is used anyway, so the run fails visibly on spawn instead of being silently skipped. A per-run override from the **Retry now** dialog pins one exact CLI/model/reasoning and bypasses routing. The chosen target is logged (at `info` when a preferred CLI was skipped, `warn` when nothing was available), and the run row records the target that actually ran. On a federated project, the eligibility gate applies the same ordered targets to enrolled workers' allowed CLI sets, selects a worker and target together, and the selected host atomically revalidates both before execution.

**`pipeline`** — controls which work items SWARM is allowed to start on at all (`automationLabel`), Planning board movement/splitting, whether SCM-event-driven phases run, and opt-in merging after a successful review response or approved review. Every field is optional. Review, Respond-to-review, and Respond-to-CI default to enabled when their setting or the whole `pipeline` block is omitted. Respond-to-review cannot be enabled unless Review is enabled. After successful delivery, Implementation moves the item to "In review" exactly when Review is enabled; this status report does not dispatch Review, which starts from PR lifecycle events:
| Field | Default | Purpose |
| --- | --- | --- |
| `pipeline.automationLabel` | `swarm` | The label a work item must carry before SWARM starts **any** phase for it — the explicit, human-controlled automation opt-in (issues #131 and #354). Re-checked at *every* dispatch — a fresh webhook, a delayed retry, the self-enqueued next phase, a capacity promotion, a manual "Retry now" — so removing the label stops all later phases; it never terminates a run already in flight. | `pipeline.maxContinuations` | `2` | How many times one run may be continued from its Tier 2 checkpoint (`docs/CHECKPOINTS.md`) — the bound on the fallback that takes over when an implementer phase is stopped involuntarily and native session resume cannot serve it (no session id was captured, or a resume attempt itself failed). Each continuation settles the run as `checkpointed`, keeps its checkout, and dispatches a *fresh* session seeded from the checkpoint's recorded remainder. Positive integer. Once the budget is spent, the next involuntary stop is a terminal failure whose reason says the continuation budget was exhausted, rather than a further hand-off — the point being that a phase which keeps stopping is better surfaced to a human than handed off indefinitely, since each continuation pays for a new session that re-reads the same remainder. Counted per run row (`runs.continuation_count`) and cleared only by "Reset & restart", not by an ordinary retry. Tier 1 (native resume) keeps absolute priority and spends none of this budget. |

### Global settings (`app_settings`)

App-wide settings that apply across **every** project, as opposed to the per-project `swarm.config.json`. Source of truth: `src/config/app-settings.ts` (`AppSettingsSchema`). Stored **DB-first** as one jsonb blob in the single-row `app_settings` table (id `global`) and edited through the dashboard API (the `settings` tRPC router — `get`/`update`), **not** a config file — so there is nothing to `swarm config apply`. When no row exists the coded defaults apply, so no seeding is required for correct default behaviour. The blob is extensible: future global settings (host URL, worker concurrency, …) are added as sibling keys without a migration.

**`agents.defaults`** — the **global** per-CLI default model: a map of `cli` (`claude` / `antigravity` / `codex`) → default `model`, each validated for that CLI per `src/harness/models.ts` (same rules as the project-level `agents.defaults`).

**`appearance.theme`** — the dashboard's theme choice (issue #250): `dark` (default), `light`, or `system` (follows the OS/browser `prefers-color-scheme` and updates live when it changes). Unlike `agents.defaults`, this key always materializes — `AppSettingsSchema` defaults it to `dark` even when parsing `{}` — so every `settings.get` response carries an effective theme rather than requiring callers to fall back manually. Applied dashboard-wide by `dashboard/src/components/theme/theme-provider.tsx`, which sets a `data-theme` attribute the whole palette (`dashboard/src/index.css`) responds to.

Before the four-tier chain runs, Implementation selects `agents.implementationUnplanned` for work items with no prior *completed* Planning run-history row (a failed or deferred attempt does not count), otherwise `agents.implementation`; an unset unplanned variant falls back to `implementation`. The worker then resolves the model for the selected config through a four-tier fallback chain, most specific first (`resolveModel`, `src/worker/consumer.ts`):

1. the phase's own `model` (project `agents.<phase>.model`);
2. the **project** default — project `agents.defaults[cli]`;
3. the **global** default — `agents.defaults[cli]` from these settings;
4. the coded default — `DEFAULT_MODEL_PER_CLI[cli]` (`src/harness/models.ts`: Claude `sonnet`, Antigravity `gemini-3.5-flash`, Codex `gpt-5.6-terra`).

Reasoning (issue #180) is **not** part of this model chain: it is resolved separately from the per-phase/per-run reasoning override and otherwise inherits the effective model's own default (see the per-phase `reasoning` field above). The run row records the requested reasoning (or `Default` when omitted) alongside the model, and the manual "Retry now" dialog can override it — an override incompatible with a changed CLI/model is dropped rather than launched.

### Editable via the dashboard UI

Today the dashboard exposes a **subset** of settings:

- **Projects** — create a project (`id`, `name`, `repo`, `repoRoot`) and delete one, plus per-project **General Settings** (`repo`, `repoRoot`, `worktreeRoot`, `baseBranch`, `branchPrefix`), **Agent Configuration** (a per-phase summary table where each row opens a phase-details screen for that phase's ordered `targets` list — add/remove/reorder `cli`/`model`/`reasoning` rows, at most one per CLI — plus its timeout, enable toggle, an optional custom `prompt`, and Planning's auto-advance toggle — plus the project-level `agents.defaults`), a **Pipeline** tab for the Respond-to-review merge-automation/minor-review controls and the Review check policy (`pipeline.review.checks`, a **Require CI checks** / **Review when no checks exist** choice defaulting to **Require CI checks**), and a **Project Management** tab (issue #201, renamed and widened by #537) with three sections: the PM provider's **credentials** — one masked-secret field per credential role that provider declares (`credentials.pm`), stored encrypted and never returned to the browser — then the **board** picker and the **status mapping**, which edit the configured provider's `pm` member through board/status pickers: it discovers that provider's containers and, for the selected one, its workflow states — using that project's own PM credential, resolved server-side — so you map by real names instead of typing opaque ids (which stay the persisted representation). Two PM providers are implemented — GitHub Projects and, since issue #530, Linear — and since issue #531 the screen reads *and* saves either one's mapping: a GitHub Projects **board** + **Status** options, or a Linear **team** + **workflow states**. The manifest supplies the credential roles, their labels/descriptions, and server-side discovery dispatch; the board/status picker catalogue supplies the correct provider vocabulary for each. Changing the PM provider is done in `swarm.config.json`, keeping one provider's ids from being saved as another's. A role that inherits a shared SCM credential — GitHub Projects' webhook secret — is shown read-only here and edited on the Source Control tab, so one secret never has two homes; Linear inherits nothing, so both of its roles are edited here.
- **Settings** — a top-level, app-wide **Settings** screen (sidebar → *Settings*) for [global settings](#global-settings-app_settings), with two tabs: **Agent Defaults** — the global per-CLI default model for Claude / Antigravity / Codex (writes `agents.defaults` via the `settings` tRPC router); leaving a CLI on its default option clears the global default so the coded default applies. **Appearance** — a Dark / Light / System default radio group (writes `appearance.theme`); selecting an option repaints the dashboard immediately and persists without a separate Save action.

The pipeline controls other than the board mapping, Planning auto-advance, Respond-to-review merge-automation/minor-review handling, and the Review check policy — plus all general/env settings — are **not** yet editable in the UI; change those in `swarm.config.json` / `.env` and re-apply. Board mapping and PM credentials (**Project Management** tab, issues #201/#537) and SCM credentials (**Source Control** tab, issue #200) are now editable in the dashboard — the Source Control tab edits the two shared SCM references, the Project Management tab the PM provider's own `credentials.pm` roles. Either surface is authoritative for what it wrote: the dashboard writes straight to the encrypted store (and records the reference), while `swarm config apply` re-applies whatever `swarm.config.json` names. Further global-settings sections are on the phase-6 backlog (see the [status snapshot](./status.md)).
