# Pipeline and architecture overview

This guide explains the user-visible pipeline and its security boundaries.
For implementation-level details, see [`ai/ARCHITECTURE.md`](../ai/ARCHITECTURE.md)
and the durable-dispatch ADRs under [`decisions/`](decisions/).

## Pipeline phases

Each phase's agent CLI, model, and reasoning level are configurable per project, per phase, via `swarm.config.json`'s `agents` block (`src/harness/models.ts` is the catalog of valid `cli`/`model` combinations and the reasoning levels each model supports) — the descriptions below are the code's own defaults when a project doesn't override them. Planning's `autoAdvance` setting defaults to **off**, so a human reviews the plan and moves it to "ToDo". Implementation's completion status is not independently configurable: it moves the item to "In review" exactly when `pipeline.review.enabled` is on, and otherwise leaves it "In progress".

**Automation is opt-in per work item.** Before SWARM starts *any* phase it checks that the work item behind the dispatch carries the project's `pipeline.automationLabel` (default `swarm`); an item without it is skipped with a log naming the missing label and the dispatch outcome `skipped-not-eligible` — no worktree, no agent, zero model tokens. The check runs at every dispatch, so removing the label stops the item's later phases too, though it never terminates a run already in flight. It is matched against the work item's labels through the provider-agnostic PM interface, so it works the same on any board. The two board-driven phases (Planning, Implementation) read the label off the item that entered the triggering status; the four PR-driven phases (Review, Respond to Review, Respond to CI, Resolve Conflicts) resolve the pull request back to its board card first — by the work item its task branch names, otherwise by a card tracking the PR itself. That resolution **fails open**: a PR with no board card behind it, and a board the provider can't read just now, both run normally, so an unlinked PR or a transient outage never wedges review and CI work. The label is an automation opt-in, **not** an access-control mechanism — it grants nobody access to anything. See [`configuration.md`](./configuration.md#project-config-swarmconfigjson).

**Every phase dispatch passes a worker-eligibility gate first** (issue #339), and it has **one rule for every deployment** — a single-user install registers and enrolls its one local worker exactly as anyone else does, since `SWARM_SINGLE_USER_MODE` is the API's authentication policy and stopped bypassing this gate with issue #552. Before any worktree is provisioned or any agent is launched, SWARM confirms that an eligible worker may take the phase: an active project enrollment, the worker owner's sharing consent, a live connection, free capacity, and the ability to run one of the phase's configured model targets. For **Implementation**, an item **assigned** to someone who is linked to a SWARM user runs *only* on a worker that person owns — SWARM never falls back to another user's machine, it waits. **Planning is central**: it is never routed by assignment (issue #469), because only a worker with database access can run it, so honouring the assignment could only ever prevent the work rather than place it better. An **unassigned** item — and any Planning item — goes to a free eligible worker, picked across the whole pool rather than simply first-in-order: when other work is queued, SWARM avoids handing a phase the one worker some other runnable phase uniquely needs, so spare project concurrency is actually used (issue #533). It still never *waits* for a better pairing — a dispatch that could run runs. **A refused dispatch says which kind of wait it is in** (issue #607): waiting for a machine to become available, or waiting for a human to authorize one. The Queue names the difference — the first clears by itself once a machine is free or idle, the second only once somebody grants sharing consent, approves an enrollment, permits the phase for that machine, or enrols a worker that can run the configured CLI — while both re-check on the same cadence and the same budget. The chosen host must authenticate as that worker with `SWARM_WORKER_CREDENTIAL`; in one database transaction SWARM re-validates its live fenced session, enrollment, consent, CLI, project limit, and `concurrencyAllocation`, then persists the worker/session claim on the dispatch and run. A different host cannot execute it, and simultaneous dispatches cannot observe the same free slot. **A continuation runs on the machine that holds its work** (issue #567). A run that stopped part-way and preserved its checkout — a checkpoint, a resumable session, a delivery sidecar — leaves that state on one machine and nowhere else, so SWARM records which machine it was and offers the continuation *only* there. If that machine is busy or offline the dispatch waits for it, for as long as it takes: there is no timer that starts the work over somewhere else, because doing so would silently discard the earlier attempt at full token cost. The run says which machine it is waiting for the whole time, and the way out is **Reset & restart** — an operator decision that abandons the preserved work and frees the phase to run on any worker, and that works whether or not the original machine is reachable.

When nothing is eligible the run is **deferred**, not dropped: it re-checks cheaply (no worktree, no agent, zero model tokens) and, if the situation never resolves, finally fails with the actionable reason — grant sharing consent, approve the enrollment, or enroll a worker that can run the configured CLI. **A wait for a machine ends the moment one turns up** (issue #610): a worker connecting, or finishing a run and freeing its slot, immediately starts the dispatches that were only waiting for that, instead of leaving them to the next re-check — so work no longer sits still next to an idle worker for up to a full interval. A wait for a *human* is untouched: nothing a machine does grants consent or approves an enrollment, so an authorization wait keeps the timed cadence and its budget. A woken dispatch re-enters the same gate and may simply wait again, spending the same budget, and the timed re-check stays the fallback whenever no worker turns up. Deferral clears the capacity claim; terminal dispatch states release it, an expired dispatch lease stops counting after a crash, and a newly fenced session immediately reaps claims left by that worker's older session. Revoking consent, suspending an enrollment, or losing a worker's health blocks the *next* dispatch and never terminates a run already in flight. A project with no enrolled workers is unfederated: the local worker runs every phase exactly as before.

Worker-spawned agents are scoped to exactly one phase. Their prompts prohibit the manual `solve-issue` skill, arbitrary subagents/skills, and continuing into another phase; the worker owns every phase hand-off and supplies the correct persona and worktree. The manual skill remains available for explicitly requested interactive sessions outside the worker.

1. **Planning** (Claude Code by default) — item moves to "Planning" → the worker provisions a detached worktree, the planning agent reads the code graph and writes `proposed_plan.md` → plan is posted back to the board. Moves the item to "ToDo" itself if `autoAdvance` is on for this project; otherwise a human moves it once they've reviewed the plan. If `autoSplit` is on (default) and the agent judges the item too large for a single PR, it **splits** it: the original item becomes the smaller first task (re-scoped, possibly renamed), and the rest ends as sibling items in **Planning**, tagged `swarm:split-child` and `planned` (a split child is born carrying the parent's plan, so it is marked planned once its plan is embedded and its card has reached Planning rather than waiting for its own Planning run), and carrying a comment explaining the split. SWARM creates each child in Backlog only long enough to publish that plan as a readable **Preplan** comment (the hidden marker is invisible in GitHub, so this is what an operator actually reviews) and write the parent's validated child-specific plan into the marker; it moves the card to Planning after that marker exists, so both the move event and a delayed creation event suppress the redundant Planning dispatch. A replayed delivery is caught before any child is re-prepared, so the preplan comment is never duplicated. A malformed/stale marker, `swarm:replan`, or a removed split-child label runs Planning normally; repo-level `issues` events dispatch that fallback even while the card remains in Planning. If marker/status preparation fails, the child remains in Backlog (and its comment reports that fallback honestly) and is left without the `planned` label. If marker embedding failed, it is un-planned until an agent plans it — moving it to Planning runs one normally. If the Planning move failed, its embedded plan remains valid, so moving it to Planning starts nothing at all: SWARM suppresses the Planning run the marker makes redundant, and the card simply stays unlabeled. To get a fresh plan (and the label) for such a card, force the fallback — with the card now in Planning, add the `swarm:replan` label or remove `swarm:split-child` — which does spend a Planning agent run. A human starts those siblings' implementation in order. Each split card is titled **`<shared task name> <phase>/<total>: <phase-specific task>`** — one shared name the agent picks for the whole split, applied by SWARM to the re-scoped original (phase 1) and to every child, so all phases of one issue are recognisable together in the Planning column even if the agent's own titles were generic. Every child also inherits the original task's labels (its type label, the automation label) alongside `swarm:split-child`. Each phase is chained as a dependency: SWARM records a cumulative `blocked by` relationship on every earlier phase (and lists them in the split comment), so a later phase can't be implemented before its predecessors land. The plan is held to a minimal-scope rule and a deterministic scope gate: the agent records why the work is one task (in `proposed_scope.json`), and an unsplit plan that declares two or more independent concerns fails Planning with a request to narrow or split rather than advancing an oversized plan to Implementation.
2. **Implementation** (Claude Code by default) — item moves to "ToDo" → **a dependency gate runs first**: if the item is still `blocked by` an unfinished prerequisite **recorded as a native relationship**, the run is **deferred** and re-checked cheaply — no worktree, no agent, **zero model tokens** — until the blocker closes (then it proceeds automatically), or it gives up after `SWARM_DEPENDENCY_MAX_WAIT_MS` and fails with an "issue X must be done first" comment. **A prerequisite named only in prose does not defer anything** (issue #643): SWARM still reads the item's description and the comments people wrote (its own comments, including a published plan, are never read as dependency declarations), but a reference it finds there is *surfaced* rather than enforced — logged, and posted once on the item as a "possible unrecorded prerequisite" notice asking whoever wrote the sentence to record the relationship if it is real — and the run proceeds. Prose gating stalled two runs in one morning on correct, well-written prose (an issue about dependencies has to quote error messages and give examples of dependency wording), and it is redundant now that every dependency must carry a native relationship. A provider that models no dependencies at all (Trello) gates on nothing here, exactly as before, and relies on the human-readable prose Planning writes into each split child. Otherwise → the phase reports the pickup by moving the item to "In progress" → the agent implements and verifies the change, then writes a structured hand-off. SWARM validates the prepared tree, commits and pushes it under the implementer persona, reuses or creates the PR, and links it back to the board. Successful delivery moves the item to "In review" when Review is enabled; with Review disabled it remains "In progress".
3. **Review** (Claude Code, reviewer persona) — a PR-opened or successful check-suite lifecycle event dispatches Review independently of the Projects status transition → the agent writes a structured verdict and review body; SWARM submits the formal review under the reviewer persona. When `pipeline.respondToReview.autoMerge` is enabled, a submitted `approve` persists a durable **merge dispatch** (issue #292): an agent-less unit of dispatch work that merges the PR **directly** under the project's implementer credential, pinned to the reviewed head SHA. GitHub's native auto-merge is never requested — it is unavailable on many private repositories and has no portable equivalent in other SCMs. The dispatch's outcome (merged, waiting, or a terminal refusal) is persisted on the Review run and shown on its dashboard detail page. A transient `not-ready` result — including GitHub still converging on the review it just submitted — is retried on the dispatch's bounded backoff (a handful of attempts over a few minutes), surviving worker/Redis restarts and cancellable like any queued dispatch; each retry re-checks the PR's current state and approval, so a changed head or an overridden approval reports `not-eligible` instead of merging stale content. Retry exhaustion, and every other terminal outcome (`not-eligible`/`policy-blocked`/`unsupported`/`provider-error`), stays visible on the run but never fails the completed review.
4. **Respond to Review** (Claude Code, implementer persona) — the agent processes the review and leaves fixes plus a structured reply; SWARM commits/pushes any fix and posts one idempotent response comment.
5. **Respond to CI** (Claude Code, implementer persona) — the agent diagnoses CI and leaves a surgical fix or no-fix decision; SWARM performs any commit/push and posts the explanation. A per-PR attempt cap stops a fix that never turns CI green from looping forever.
6. **Resolve Conflicts** (Claude Code, implementer persona) — the agent resolves conflicting intent and leaves the verified tree; SWARM rechecks the observed remote head, creates the normal merge commit, pushes without force, and posts the result.

Deterministic delivery uses durable operation identities and a step-progress sidecar in the retained worktree. Equivalent PRs, reviews, and comments are detected and reused, so a failed delivery step can resume without duplicating already-completed external mutations.

That sidecar lives on one worker's filesystem, though, while an interrupted dispatch is re-dispatched to whichever worker is eligible — so a resumed attempt may hold none of the earlier state (issue #558). **Implementation therefore asks the SCM, not only the sidecar**: an attempt that finds its task branch already pushed with a PR open adopts that delivery — no second agent run, no second commit — and finishes only the reporting the interrupted attempt still owed (the PR-link comment, which carries a per-delivery marker so it is posted once, and the move to "In review"). Two related guarantees back it up: a push that **cannot** fast-forward (the delivered commit is not a descendant of the remote head) fails immediately with both SHAs named instead of retrying an identical rejection until the budget runs out, and a checkout **preserved** for its own retry no longer denies its branch to other phases — a phase needing the same branch checks it out detached at the remote tip and delivers exactly as it would have.

## Security model

- **Per-user session auth, localhost-bound** (issue #281 task 2): The dashboard binds to `127.0.0.1` rather than `0.0.0.0`, and every request except `/health` and the `ping` probe is authorized by a per-user session — a password login mints an opaque token delivered as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost); only its hash is stored, and logout revokes it. This replaced the earlier shared-secret `DASHBOARD_TOKEN` bearer guard.
- **Project-scoped authorization** (issue #281 task 4): on top of session auth, every project-keyed tRPC procedure is scoped to the caller's project membership (`src/api/authz.ts`). An ordinary user sees and acts only on projects they are a member of — read needs `contributor`, driving runs needs `member`, and administering config/credentials or deleting a project needs `projectAdmin`; a non-member gets `NOT_FOUND` (existence hidden), a member below the required role gets `FORBIDDEN`. An `instanceAdmin` overrides all of it and sees every project. See `ai/ARCHITECTURE.md` for the full role → capability matrix.
- **Open-project policy: discovery ≠ joining ≠ execution** (issue #281 task 5): a project may opt in to `visibility: discoverable`, which exposes a **limited** public read (`projects.listDiscoverable` — id + name only, never credentials/config/repo/run internals) to any authenticated user and lets them file a **pending** membership request (`projects.requestMembership`). A `projectAdmin`/`instanceAdmin` approves it into a `contributor` (read-only) membership or rejects it — joining an open project grants no access on its own (resolving ADR-001 open question #1 for request/approve over immediate membership). Discovery and joining are deliberately kept separate from worker registration (#132) and task routing (#130): public visibility never equates to execution permission, and the highest role a join ever yields is `contributor`.
- **Dual-persona GitHub credentials** (MVP): separate implementer/reviewer tokens, borrowed from Cascade's loop-prevention model — a persona never reacts to its own output. The **reviewer** token is a project-scoped credential stored in Postgres, not a cloud secret manager (see `PROJECT.md` §6.1); the **implementer** token is the worker operator's own token, the worker-local `SWARM_OPERATOR_GH_TOKEN` env var (issue #396) — never persisted, so implementer PRs are authored by the operator's account and stay distinct from the reviewer.
- **Agent-CLI containment is a setting, not a constant** (issue #614): a run happens in a disposable worktree with stdin closed, so *something* has to make tool calls run unattended. That answer used to be one hard-coded permission bypass per CLI — which handed the agent the worker user's whole filesystem and network, with only `cwd` and the phase prompt's wording keeping it in its worktree. It is now resolved per run (`SWARM_AGENT_CONTAINMENT`, `src/harness/containment.ts`): `bypass` is still the default and still exactly today's behavior, and `worktree` puts the run under the CLI's own OS-level sandbox so writes outside the worktree fail. Achievable for `codex` and `claude`, **not** for `agy`, which stays on the bypass and says so in the log. Containment as adopted is write-only — credentials outside the worktree stay readable — and the network allowance the phases' `gh`/`git` work needs is explicit. Full per-CLI record, costs, and the re-runnable proof (`npm run check:containment`): [`docs/agent-containment.md`](./agent-containment.md).
- **Zero-knowledge codebase, still**: everything above is local — router, worker, Postgres, Redis. Nothing leaves the machine except webhook payloads and PR/comment metadata.
- *(Future, once `PROJECT.md` §2.2's cloud engine exists)*: board/SCM API keys move into Google Cloud Secret Manager; the daemon authenticates to the cloud via a bearer token + device hardware ID (`PROJECT.md` §6.2).
