# Architecture (MVP)

`PROJECT.md` describes SWARM's long-term vision: a stateless GCP cloud orchestrator (Cloud Run + Pub/Sub + Firestore) talking gRPC to a local daemon. **For the MVP, skip the GCP layer entirely** and mirror Cascade's architecture instead — a router + queue + worker running locally (Docker Compose, same as Cascade), reachable from GitHub via a Cloudflare Tunnel instead of a cloud ingress service. The gRPC/cloud-engine design in `PROJECT.md` is not being built yet; treat it as a possible future phase once the local-only version works end-to-end for one user, not as the current target. If this changes, update this file and `README.md` in the same change.

## Why copy Cascade's shape instead of `PROJECT.md`'s

`PROJECT.md` was written before we had a concrete reference implementation to copy. Cascade already solves "webhook comes in → figure out which project/task it belongs to → run an agent → report back" for exactly this kind of pipeline, in the same language, and its author knew Node.js well. Rebuilding that shape from scratch (or building the gRPC/Pub/Sub version) is strictly more work for no MVP-stage benefit. SWARM's two product differences from Cascade are:

1. **PM provider = GitHub Projects** first, which Cascade has no adapter for at all — that piece is net-new. (Linear has since landed too, issue #530, then Jira with #580 and Trello with #588, and for all three Cascade *is* the precedent; `PMType`'s four values now all resolve to a registered provider.)
2. **SCM = GitHub**, same as Cascade — copy this piece close to verbatim.

Everything else — router/queue/worker split, manifest-based provider registration, credential scoping, loop prevention — should be copied, not reinvented.

## Components (MVP)

```
GitHub (repo + Projects v2)
   │  webhooks (pull_request, pull_request_review, issue_comment, issues, check_suite, projects_v2_item)
   ▼
Cloudflare Tunnel (external, not our concern — just a public HTTPS URL pointed at the router)
   ▼
Router  (Hono HTTP server, local Docker container)
   — verifies webhook signatures
   — resolves which SWARM project the event belongs to
   — records a durable dispatch (Postgres, ADR-002) and publishes its BullMQ
     wake-up (PR review-lifecycle jobs are prioritized ahead of PM-board jobs,
     so a review never queues behind a planning or implementation run —
     `src/queue/producer.ts`'s `priorityFor`)
   ▼
Worker  (host process — NOT containerized, one job at a time or a small pool)
   — looks up the trigger handler for the event
   — provisions a Git worktree (see "Worktree lifecycle" below)
   — spawns `claude` or `antigravity` CLI with the worktree as CWD
   — validates structured agent hand-offs and performs deterministic SCM delivery
   — persists step progress, then posts results back to GitHub Projects

API server (Hono HTTP server + tRPC, host process)
   — exposes a `/health` check and mounts a tRPC API under `/trpc`
   — self-hosted, single-process model running locally on the host
   — binds to `127.0.0.1`; authorizes every request except `/health` and `ping` by a per-user session cookie (issue #281 task 2) — or, when local single-user mode is enabled (`SWARM_SINGLE_USER_MODE`, issue #298), by resolving a bootstrapped `localhost-admin` with no cookie at all — then scopes every project-keyed procedure to the caller's project membership (issue #281 task 4)
   — serves the built dashboard SPA (`dashboard/dist`) statically as a fallback when present (self-hosted mode)
```

Redis (for BullMQ) and Postgres (for project config, credentials at rest, and run history — same role it plays in Cascade) run in the same Docker Compose stack as the router. The **worker and the API server are the exceptions**: they run directly on the host rather than in containers — the worker because it provisions Git worktrees and spawns the `claude` / `antigravity` CLIs (which need the developer's own PATH, auth, and config), and the API server (scaffolded via Hono and tRPC, and serving the dashboard SPA) for local-first, single-process execution. They connect to Redis/Postgres over their published host ports (`REDIS_URL` / `DATABASE_URL` in `.env`). There is no separate "cloud" process for the MVP; router, worker, API server, Redis, and Postgres are all local.

**How a worker connects (ADR-003 §1).** There is **one** worker program and one way to run it (issue #553, closing ADR-004's open question 2): `src/transport/connect-entry.ts`, started with `npm run dev:worker`, holding **only** `SWARM_WORKER_CREDENTIAL` + `SWARM_CONTROL_PLANE_URL` — never `DATABASE_URL`/`REDIS_URL`, even on a host that has them, and, since issue #765, no operator SCM credential either (it arrives per assignment — see "Per-worker operator SCM credential" below). The in-process, DB-direct executor that used to serve the same-machine case was deleted rather than kept behind a flag: a second path kept "just in case" is how the DB-free one stopped being exercised (issue #535 found a phase body that had never once run on it). It reaches the router's authenticated `/worker/*` endpoint (`POST /worker/session` handshake, then a `/worker/stream` WebSocket carrying heartbeats), reconnecting with exponential backoff. **Including the one on the control-plane host** (issue #551): that machine used to run a second, database-holding executor of its own, so the same role shipped as two programs and only one of them was exercised on a given run; it now points `SWARM_CONTROL_PLANE_URL` at its own router over loopback (`http://localhost:<ROUTER_PORT>`) and runs the identical program a remote worker does, over the identical code path. A remote worker reaches the same URL through the Cloudflare tunnel instead. Both keep the same `worker_sessions` liveness lease fresh, so the eligibility gate treats a remote worker exactly like a local one. The transport carries a session handshake, heartbeats, and the split-delivery back-channel (ADR-003 §2, issue #407): a `TaskAssignment` pushed cloud→worker and `TaskExecutionResult`/`StreamLog`/`TaskProgress` reported worker→cloud. Never source. Beyond the handshake and heartbeats, a transport worker **executes** a pushed `TaskAssignment` DB-free (`src/transport/assignment-execution.ts` `runAssignmentDbFree`, ADR-003 §2): it reconstructs the `ProjectConfig` from the assignment's non-secret slice (`src/transport/db-free-project.ts`) plus its own checkout path (`SWARM_WORKER_REPO_ROOT`, default cwd), runs source-carrying delivery under the operator's own token (`SWARM_OPERATOR_GH_TOKEN` → `SCMProvider.operatorDeliveryProvider`, resolved through the registry since issue #462), and streams `ack → running → live logs → terminal result` back over the #406 back-channel — no `DATABASE_URL`/`REDIS_URL`, no source on the wire, live output streamed rather than written (the **control plane** persists every worker's `stream-log` batches to `run_output_events` — `src/router/stream-log-persistence.ts`, issue #544), and cancellation delivered as a pushed `task-cancel` frame (issue #549) rather than read from Redis — a frame the worker now *answers* rather than only applies (issue #724): it is the only party that knows whether the phase is still executing there, so a cancel it cannot apply settles the dispatch as the terminal cancelled result, and one whose real result it still holds undelivered re-reports that instead. **That back-channel sink spans sessions (issue #718):** a phase runs independently of the heartbeat loop, so it routinely outlives the session it was pushed on, and its terminal `TaskExecutionResult` used to be dropped with the dead socket — a one-second blip discarded the outcome, a *successful* one included, and the dispatch settled ~30 minutes later on the back-channel timer as "did not report a result within the lease window". The sink now lives for the process: a terminal result that could not be written is held in a bounded, one-per-dispatch queue and delivered on the next session, and a re-pushed assignment for a dispatch whose result is still held is answered with that result instead of re-running the phase. Exactly-once stays the control plane's property (`deliverDispatchResult` consumes the waiter, so a duplicate frame is a logged no-op) and its waiter survives the disconnect untouched, so a re-sent result settles the dispatch normally. Output is deliberately *not* queued — it is unbounded and best-effort, so a lost session still costs a window of `stream-log` lines, never the run's outcome. **The control plane now says so out loud (issue #723):** the router is the only side that knows the moment a `/worker/stream` socket closes and the moment one opens, so it records the interruption against every dispatch it is awaiting on that worker (`src/router/dispatch-results.ts`) and writes one control-plane-authored note into each of their runs' output streams on loss and on restore (`persistControlPlaneNote`, on the same per-`runId` append chain as the streamed batches, so it never interleaves with real output and never blocks the socket handler on Postgres) — a superseded socket's stale close writes none, since nothing was interrupted. Otherwise a run whose output merely stopped *arriving* — heartbeat line included — is indistinguishable from one that stopped progressing. The same bookkeeping is what a result-wait timeout is then attributed to: a dispatch whose transport was interrupted fails with a message naming the drop, its count, and the worker's own `assignment phase finished — sending result` line to check against, instead of the "did not report a result within the lease window" that blamed a worker which may well have delivered. A timeout with no interruption keeps that original wording. Output itself is still not replayed — this is the legibility half only. Worktree coordination is host-local on this path (`src/worktree/host-local-runtime.ts`): atomic filesystem leases prevent two local provisioners from reclaiming one checkout, preservation pins retain resumable work, and no Redis/Postgres lease, liveness, reclaim-pin, or cancellation lookup is loaded. One scope above those per-`(project, task)` leases, the daemon holds a single lock on the *checkout* for its whole life (`src/worktree/checkout-lock.ts`, issue #689 — below), so two separately registered workers cannot be pointed at one working tree. Everything a DB-free worker cannot do itself reaches its backing resource through the router's delivery API instead (below), called with the worker's *own* credential (`src/transport/delivery-client.ts`), so no project credential and no database connection is ever needed on the worker: **Implementation**'s two board writes and **Respond-to-review**'s board-card lookup + two status-report moves go up as PM delivery calls under the project's PM credential, **Review**'s `submitReview` goes up as an SCM delivery call under the project's reviewer PAT, and two things whose backing store is the control plane's *database* go up too — Review's three **review-verdict ledger** calls (`src/pipeline/review-ledger.ts` → `src/transport/review-ledger-delivery.ts`), so the review-verdict cap (issue #235) and the re-review signal (issue #328) keep working rather than being skipped for want of a `DATABASE_URL`, and Respond-to-review's **follow-up Review** enqueue (`src/pipeline/follow-up-review.ts` → `src/transport/follow-up-review-delivery.ts`), which writes a dispatch row and queues a synthetic event so a pushed fix is re-reviewed (issue #241). Since issue #536 a transport worker runs **all six** phases — `respond-to-ci`, `resolve-conflicts`, `implementation`, `review`, `respond-to-review`, `planning` — so phase support no longer depends on which machine a worker happens to be. **Planning** was the last holdout, and what it added was width rather than a new kind of operation: its whole server-side surface is board metadata, so five more PM delivery routes (`pm/find-comment`, `pm/create-item`, `pm/update-item`, `pm/label`, `pm/blocked-by`) cover it, and its agent run, `proposed_plan.md`, split contract and deterministic scope gate all stay worker-side. The split's idempotency travels unchanged, and **issue #543 then closed the hole it travelled with**: `findComment` on the plan-delivery marker short-circuits a replayed delivery *before* `applySplit` runs, and `planned` still marks only children whose preparation completed — but that marker is the plan comment, and `applySplit` runs before it is posted, so a split that died partway used to leave its already-created children unmarked and have the retry re-create them (confirmed by execution; pre-existing and identical on the in-process path, but `createWorkItem` is the one write outside the per-child `try` and it is now on the wire). The split is therefore **resumable**: every child is created carrying a per-delivery `<!-- swarm-split-child:<runId>:<index> -->` marker in its own body, and each iteration resolves that marker first (`findWorkItemByDescriptionMarker`), adopting the card this delivery already made instead of spawning a second one — while a genuine replan, a new run row hence a new id, still performs its own split. The three board-driven phases get the delegate-less transport writer (`createWriteOnlyTransportPmProvider`): every board write plus five narrow reads — `listBlockers`, `findWorkItemByUrlSuffix`, the repository-scoped `findWorkItemForArtifact`, `findComment`, and `findWorkItemByDescriptionMarker` — ride the transport, and the two *enumerating/whole-item* reads (`getWorkItem`, `listWorkItems`) refuse loudly rather than guessing, because the control plane already performed the reads the assignment was composed from. `listBlockers` is transported, not stubbed, precisely because nothing else gates dependencies — `findGatingBlockers` runs inside the Implementation phase, not in the dispatcher — so answering "no blockers" would build a task whose prerequisites are still open (issue #330). It answers with both blocker sources, because the gate needs the prose-only ones to *surface* even though it no longer defers on them (issue #643), and the notice it posts rides the same transported `addComment`. `findWorkItemByUrlSuffix` and `findWorkItemByDescriptionMarker` are the *narrow* form of the board read (one URL tail or one marker in, at most one card out), which is why `listWorkItems` keeps refusing: a worker has no business enumerating a board to answer a one-card question. Respond-to-review's fix commit, push and response comment stay on the operator token — that reply is the *implementer* answering the review, so routing it through a composite built for the reviewer persona would have the reviewer answering itself. (The same attribution now holds on the control-plane delivery path, where the reply *does* ride the transport: the `/pr-comment` frame names the implementer, so the router writes it under that persona rather than the reviewer's — issue #444.) (A dependency block detected on the worker still enters the control plane's bounded recheck: the worker reports it as a `dependency` deferral carrying the still-open blockers, and the control plane rebuilds `DependencyBlockedError` from that frame so the token-free `recheck` budget and its terminal "must be done first" board message apply unchanged — issue #438.) The supported-phase gate remains as the worker-side backstop even though no phase is excluded from it any more — a daemon predating #536 still declares only five, and its dispatches must keep routing rather than failing. Which phases a *machine* can run is **enforced by the dispatcher rather than only stated here** (issue #467): the daemon declares its phase repertoire at handshake (`HandshakeRequestSchema.supportedPhases`, persisted as `workers.supported_phases`), so the eligibility gate refuses a candidate for a phase it cannot run (`missing-phase-capability`) and the dispatch waits for a capable worker instead of being pushed to one that answers with a terminal failure. A daemon that declares no phases is recorded as supporting all of them, which is how the dispatcher behaved before the field existed. **A third declaration rides the same handshake (issue #687):** which repository the daemon's one local checkout actually is (`HandshakeRequestSchema.repository`, persisted as the nullable `workers.repository`), resolved once at startup from that checkout's `origin` remote through the shared normaliser `GitWorktreeManager.assertRepoIdentity` already uses (`normalizeRepoSlug` / `repoSlugFromRemoteUrl` / `RepoSlugSchema`, extracted into the provider-neutral `src/scm/repo-slug.ts`) — no new environment variable, since `SWARM_WORKER_REPO_ROOT` already names the checkout. The control plane has no other way to learn it: `repoRoot` is host-local and never travels, and `hostname` is diagnostic and unpersisted. Optional and additive in both directions, so `TRANSPORT_PROTOCOL_VERSION` is not bumped — a daemon that predates the field omits it and the column records NULL, which is exactly today's behaviour, and a checkout with no identifiable `origin` declares nothing rather than failing to start. An omitted field *clears* the column, the one deliberate asymmetry with `supportedPhases`: the row states the checkout of the program currently operating it, so a stale-but-wrong declaration would be worse than an absent one. **The first thing gated on that fact is the worker's own pre-flight check (issue #688):** `runAssignmentDbFree` compares the assignment's `projectConfig.repo` against the declaration — both through the shared `repoSlugsMatch` — right after the supported-phase gate and *before* it reconstructs the project or touches the checkout, and settles the dispatch terminal-`failed` with a message naming both repositories and `SWARM_WORKER_REPO_ROOT`. That case is reachable because enrollment is per `(worker, project)`: a worker enrolled in two projects with different repositories is pushed both, and holds one checkout to run them in. Terminal rather than deferred, deliberately — no retry on *this* worker can make the two repositories match, so a deferral would re-push impossible work until the budget ran out (the same reasoning the phase gate applies). A daemon whose checkout it could not identify declares nothing and so refuses nothing, keeping exactly today's behaviour, and `assertRepoIdentity` stays as the provision-time backstop for both. **The second thing gated on the checkout is the checkout itself (issue #689):** before it handshakes, the daemon takes a host-local lock on its `SWARM_WORKER_REPO_ROOT` (`src/worktree/checkout-lock.ts`), so two separately *registered* workers cannot both run against one working tree and contend on the same main repository's `index.lock` — the session lease (`src/identity/worker-session.ts`) only ever stopped two daemons sharing one *credential*. The guard is host-local because the control plane cannot be: `repoRoot` never travels, and two checkouts of one repository (on one machine or two) are legitimate capacity, so what is being protected is the checkout rather than the repository. It is the same atomic `mkdir` + `owner.json` claim `host-local-runtime.ts` makes for a `(project, task)` checkout — with the liveness/expiry primitives now shared rather than duplicated (`src/worktree/local-lock.ts`) — kept at `~/.swarm/checkout-locks/<sha256(realpath(repoRoot))>/` rather than inside the checkout, because a daemon holds no project config at startup and so knows no `worktreeRoot`, and writing to `<repoRoot>/.swarm-state` would litter the operator's own repository. Keying on the **realpath** means a symlinked, relative, or trailing-slash spelling is recognised as the same checkout. It carries its **own** 15-minute TTL, restamped every third of it by the holder, deliberately not that module's unrefreshed 4h `LEASE_TTL_MS`: a worker process lives for days where an agent run does not, so reusing that TTL would leave a dead daemon's checkout blocked for hours. So the lock is reclaimable on liveness grounds — at once when the holder's pid is gone, on the lapsed refresh when a recycled pid impersonates it, and immediately when the holder released it on a graceful stop — and never permanently blocks its own checkout. A second daemon exits non-zero *before* handshaking, with a line naming the holder: its `workerId` once the holder's own handshake told it which worker it is (delivered worker-side only through `WorkerTransportOptions.onSession`, so there is no wire or schema change), its pid and host until then. **The last thing gated on the declaration is the enrollment itself (issue #690):** the control plane now polices the `(worker, project)` pairing at both moments it becomes knowable — `enrollWorker` refuses a write whose project is not the worker's declared repository (`EnrollmentRepositoryMismatchError` → `BAD_REQUEST` / one CLI line), and `handleHandshake` suspends the enrollments a reconnecting daemon's declaration contradicts — so the mismatch is stated on the roster rather than only surfacing as the daemon's refused assignments (see "Worker-project enrollment" below for what it deliberately does *not* do). The daemon declares its repertoire at the moment it proves it owns the row — at handshake — which is deliberate rather than incidental: the stored set must never outlive the program that wrote it, or a row narrowed by one older daemon would keep refusing `planning` on a host that can run it, with no path to widen it again. Separately from what a machine *can* run, what a project may *give* it is the enrollment's own `allowedPhases` (issue #509) — and that is the whole of it: **every worker has the same permissions**, `planning` included (issue #542). `planning` was for a time permitted only on an instance admin's own worker (`PlanningRequiresInstanceAdminError`, now deleted); that gate is gone, because `instance_admin` is an installation role rather than a statement about a machine, and board authorship is already authorized at a better scope — the owner picks `allowedPhases`, a project administrator approves the enrollment, and since issue #537 the board writes run control-plane side under the *project's* PM credential, which no worker holds. Migration `0043_backfill_planning_instance_admin.sql` had stripped `planning` from every non-admin owner's enrollment; those rows stay stripped, so re-granting it is an explicit owner choice rather than something the removal does silently. **The agent's own identity is the worker operator's, on every worker** (ADR-004 §2, and universal since #551/#553 retired the host's second executor): the implementer *is* `SWARM_OPERATOR_GH_TOKEN`'s account, which authors the branch, the commits, the PR and the implementer-side comments. `credentials.implementer` is not read on the execution path and is not even in `ScmCredentialReferencesSchema` (issue #396) — what changes with a project is the repository, not who commits to it. The two identities that *are* per-project, the **reviewer** PAT and the **PM** credential, never reach a worker at all: those writes ride the delivery API, so a submitted review's author and a board write's actor are the same whichever machine ran the phase. See **Control-plane dispatch** below.

### Process responsibilities — who owns what (issue #550)

Beyond executing a phase, a SWARM installation has a handful of recurring chores. Each has **one** stated owner, so nothing depends on a process happening to reach it on the way to something else. The worker is `src/transport/connect-entry.ts` on every host — a DB-free daemon that executes phases and nothing else — so none of these can live there.

| Responsibility | Owner | Where |
| --- | --- | --- |
| Database migrations | **Router** | `src/router/index.ts` |
| BullMQ dispatch consumer + ADR-001 eligibility gate | **Router** | `src/router/dispatcher.ts`, `src/worker/consumer.ts` (`processJob`, the shared machine it drives) |
| Dispatch-lease + stale-`running`-run reconciliation | **Router** | `src/router/dispatcher.ts`, `src/dispatch/reconciler.ts` |
| Run cancellation delivery | **Router** | `src/router/dispatch-cancellation.ts` (pushes `task-cancel`, issue #549) |
| Startup orphaned-`running` reap (worker-less runs) | **API server** | `src/api/maintenance.ts` |
| CLI capability/quota discovery for **its own host** (periodic, 6h) | **API server** | `src/api/maintenance.ts` |
| Worktree retention sweep (`SWARM_WORKTREE_SWEEP_INTERVAL_MS`) | **API server** | `src/api/maintenance.ts` |
| Executing a pipeline phase | **Worker** (host or remote — one program either way) | `src/transport/assignment-execution.ts`, `runAssignedPhase` (`src/worker/consumer.ts`) |

The three host-local chores go to the **API server** rather than the router because the router runs in Docker (`docker-compose.yml`) with no agent CLIs on PATH and no repository checkout — exactly what quota discovery probes and what the sweep prunes — while the API server runs on the control-plane host with `DATABASE_URL`, the operator's PATH, and the checkout, and already performs on-demand CLI discovery for `quota.refreshQuotas`. `startHostMaintenance` (`src/api/maintenance.ts`) starts unconditionally there. The reap it runs is scoped to **worker-less** runs (`workerId = null`): this process is no worker, and a federated run is already owned by the dispatch-lease reconciler plus `failStaleRunningRuns`, so it is deliberately not widened to another host's in-flight runs. Quota discovery is also why a *launch/authentication* failure no longer triggers a recovery probe from the dispatch path (issue #553): that failure describes the worker's PATH and logins, not the control plane's.

The sweep reads the lease store *this host's worker writes* (`retentionWorktreeRuntime`, `src/worktree/retention.ts`): the host-local filesystem leases/pins under `<repoRoot>/<worktreeRoot>/.swarm-state`, which is what the DB-free daemon writes. Asking Redis instead — the store the retired in-process worker used — would find every checkout unleased and prune one out from under a live phase (issue #551). It also **sweeps** that store: `sweepStaleHostLocalState` removes expired lock directories, preservation pins, takeover guards and stranded `preserve()` staging files under `.swarm-state` by the TTLs the module already defines (issue #721). It rides this sweep rather than a schedule of its own precisely because those TTLs are otherwise evaluated only by the next provisioner *for that same task*, so a task never dispatched again kept its debris indefinitely — and the `<pin>.<uuid>.tmp` staging file has no next reader at all. Being TTL-only is the design: this process is not the daemon, so it can neither see a daemon's in-flight set nor trust a pid it did not write, and since issue #717 the recorded timestamp is the authority on every liveness path anyway.

**Two modules survive with the router as their only caller**, and are named here so a future reader does not mistake them for worker code: `src/worker/consumer.ts` (`processJob`, the dispatch/settle machine — `runAssignedPhase` in the same file is the worker's half) and `src/worker/eligibility-gate.ts`. They stayed under `src/worker/` when the in-process executor was deleted; moving them to `src/dispatch/` is a rename worth doing separately.

Two gaps are known and stated rather than papered over, both of them *background* facts about a host the control plane cannot see: a **remote** worker's checkout has no retention sweep — no process on the control-plane host can see that filesystem — and only the control-plane host runs quota discovery, so a worker host's own allowance is never reported. The snapshot itself is no longer ambiguous about *whose* allowance it shows: `cli_quotas` is keyed on `(host, cli)` and both writers stamp the discovering process's `os.hostname()` (`discoveryHost`, `src/harness/quota-discovery.ts`), so a row is one machine's installation and the CLI Quotas page groups by host rather than presenting one host's allowance as the installation's (issue #703). What remains — a worker daemon reporting its own snapshot — is a new reporting mechanism and a deliberate follow-up. The **operator-invoked** recovery actions are no longer among them (issue #592). They reach a remote checkout without reaching its filesystem, by carrying the recovery intent on the assignment (`TaskAssignment.recoveryMode`) so the worker that holds the checkout applies it in its own recovery gate: "Reset & restart" sends `'discard'` — on every reset since issue #744, not only a forced one — and the worker removes the wedged checkout, dirty and unpushed work included, before provisioning. That is why no worktree-teardown frame pair exists: the reset's own replacement dispatch already routes back to the worker holding the checkout (worker affinity), so the intent is enough.

### Observability

All code logs through one shared logger (`src/lib/logger.ts`) — a deliberately tiny, dependency-free wrapper (no pino/winston) mirroring Cascade's `logger.info/warn/error/debug(message, context)` shape. It emits **structured JSON** (one `{level,time,msg,...context}` object per line) for machine parsing, or — for a human watching a terminal — a local-clock timestamp, a colored level tag, the bound `component` as a `[component]` prefix, and remaining context as `key=value` pairs (color only on a real TTY, never when `NO_COLOR` is set). Format follows `SWARM_LOG_FORMAT` (`json`|`pretty`) and auto-picks pretty on an interactive TTY, json when piped/containerized — **leave it unset** in `.env` rather than hardcoding either value: the router's own `docker-compose.yml` environment block already pins it to `json` for that container regardless of `.env`, so setting it in `.env` only ends up overriding the host worker's auto-detection (and silently losing pretty/color) without changing the router at all. `SWARM_LOG_LEVEL` (`debug|info|warn|error`, default `info`) sets the minimum emitted level. Because router and worker share a log stream, each entry point calls `configureLogger({ component })` at startup so every line it emits is tagged `component: "router"` / `"worker"` and stays attributable.

## Project record vs. scoped project config (issue #684)

A project's configuration has **two shapes**, and which one a module takes says what it is allowed to touch.

**`ProjectRecord`** is the authored and persisted project (`ProjectRecordSchema`, `src/config/schema.ts`; the `projects` row): everything genuinely shared — `pm`, `credentials`, `agents`, `pipeline`, `repoRoot`, `worktreeRoot`, `visibility`, `maxConcurrentJobs`, and the project's `scm` provider — stated once, plus `repositories`, a list whose entries carry what is genuinely per-repository (`repo`, `baseBranch`, `branchPrefix`, and the optional `pmRoutingToken` below). Only the config-management surfaces speak it: `swarm.config.json` via `validateConfig`/`applyConfig`, `swarm init`'s template, and the projects/credentials tRPC routers.

**`scm` is the project's, not a repository's** (issue #727). An entry could override it between #684 and #727, and that was incoherent rather than merely unimplemented: SCM credentials are project-wide and single-provider — `credentials.scm` is resolved under `project.scm` alone (issue #628) and the dashboard's Source Control tab edits exactly that one provider's block — so an overriding repository named a provider whose credentials no surface could enter, and every operation scoped to it threw out of `requireScmCredential`. A project spanning two providers is **two projects**, each with its own `repoRoot`, credentials and board mapping, which is what those models already assume; reintroducing the field as the obvious symmetry with `baseBranch` means moving credentials per repository first. An entry stored before #727 keeps parsing — the key is stripped, not rejected — and its repository resolves the project's provider even where the two differed.

**`ProjectConfig`** is that record **scoped to one of its repositories** — the per-repository fields flattened back to the top level beside the project's own `scm`, produced by `scopeProjectToRepository(record, repo?)` (`src/config/project-repository.ts`). It is what every runtime call site takes, and its field set is deliberately **unchanged** by #684 and #727: the SCM provider contract's twelve methods, all six pipeline phases, every trigger, the worker-safe projection (`WORKER_SAFE_KEYS`) and the non-secret transport slice all keep reading `project.repo` / `.baseBranch` / `.branchPrefix` / `.scm` exactly as before. That is also the boundary's teeth: a scoped config carries **no list**, so nothing downstream of the scoping call can act on a repository other than the one its work names.

**The boundary is why a PM provider is *handed* the repository list rather than reading it** (issue #686 phase 1). A repository entry declares an optional `pmRoutingToken` — the opaque provider-native id a board card carries to claim it (a Jira component id, a Linear label id, a Trello label id; GitHub Projects needs none) — and `PMProvider.resolveItemRepository(id, candidates)` answers which entry a card belongs to. The candidates are an **argument**, built by the caller from the record, precisely because the provider is constructed from a scoped `ProjectConfig` that carries no list: re-opening the boundary so a provider could look the mapping up itself is the alternative, and it is the one thing this split exists to prevent. Uniqueness of the tokens within a project is a `ProjectRecordSchema` refinement, so `swarm config apply` rejects two entries claiming one token rather than leaving a card ambiguous at dispatch. Phase 2 acts on the answer — see "Repository routing for a board card" below.

The repository lookups mirror the split (`src/db/repositories/projectsRepository.ts`). `findProjectByRepoFromDb` matches *any* entry by jsonb containment and scopes to the **matched** one, so a delivery from repository B runs against repository B's settings; the id/board/container lookups and `listAllProjectsFromDb` scope to the **default** (first) entry. A board lookup keeps doing so on purpose: it answers "whose board is this?", which is what authenticates a delivery, and *which repository the card runs against* is then decided separately (below) and named on the job, so the by-id read scopes to it. Dropping the `repo` column took its `UNIQUE` index with it, so a write-seam guard (`assertRepositoriesUnclaimed`, raising `ProjectRepositoryConflictError`) refuses a repository another project already owns, and the read orders by `id` so it can never resolve arbitrarily.

### How the repository travels: ingress → job → run → assignment (phase 2)

**Phase 1's one-entry cap is gone.** It existed only because a second repository was not routable — a webhook from repository B would have resolved the project and then run the phase against repository A. Phase 2 closes that by deciding the repository **once**, at the top of the worker's composition root, and letting the existing scoped-config shape carry it the rest of the way. Phase 3 still owes the dashboard a list editor, so a second entry is authored in `swarm.config.json` plus `swarm config apply` for now.

Four hops, and the load-bearing property is that only the first one is new:

1. **Ingress** resolves the project from the delivery's repo (`findProjectByRepoFromDb`), already scoped to the **matched** entry by phase 1. The normalized `ScmEvent.repoFullName` on the durable job is the record of which repository the delivery was for.
2. **The job answers for itself.** `repositoryForJob(job)` (`src/queue/jobs.ts`) is one `switch` exhaustive over the envelope's discriminator: an `scm` job → its event's `repoFullName`, a `merge-automation` job → its own `repo` (which stopped being observability-only here), a `pm` job → the repository its card routed to (`Repository routing`, below — `undefined` only on a row written before that, which means the **default** entry). Exhaustive rather than a lookup with a fallback, so a fourth job type must decide instead of silently inheriting the default. A dispatch row written before either phase answers exactly as it did then.
3. **`processJob` scopes the project to it** (`findProjectByIdFromDb(job.projectId, repositoryForJob(job))`, `src/worker/consumer.ts`) — the seam the whole phase turns on. Everything downstream reads `project.repo` / `.baseBranch` / `.branchPrefix` / `.scm` off that one value and so needed **no change**: the trigger context, all six phases, the SCM provider calls, the worktree and task branch, the review ledger, the delivery ids, the run row's `repository` column, and the `TaskAssignment` the router pushes to a federated worker (`pushAndAwaitResult`, `src/router/dispatcher.ts`, reads the same scoped project — it never re-reads by id). A job naming a repository the project no longer owns throws out of the read (`requireProjectRepository`) and **fails the dispatch** rather than falling back: running a phase against the wrong repository would push a branch, open a pull request, and post reviews in a repository nobody asked for.
4. **The run row is the durable answer afterwards.** `runs.repository` (issue #683, below) is written from that same scoped project, so every control-plane action that starts from a *run* rescopes from it instead of from the project's default: Force re-review (`src/dispatch/force-re-review.ts` — its ledger key, cap override, and synthetic event's `repoFullName`), Reset & restart and the runs API's deferred-termination settlement (`src/dispatch/run-reset.ts`, `src/api/routers/runs.ts` — the `GitWorktreeManager` is built from the entry whose branch settings the run actually used), and startup reconciliation's legacy merge-follow-up import (`src/dispatch/reconciler.ts`, which warns and skips rather than throwing — it is a best-effort one-time import). The queue read model resolves `QueuedRun.repo` through `repositoryForJob` too (`toQueuedRun`, `src/queue/queued-runs.ts`), so the PR link a waiting row renders and the repository its phase will run in cannot drift.

The by-id read is where the choice is stated: `findProjectByIdFromDb(id, repo?)` scopes to the named entry, or to the default when none is named. Its two failure answers are deliberately different kinds of "no" — an unknown **project** is `undefined`, because a caller reading a project id off a durable row must cope with deletion, while a project that exists but does not own `repo` **throws**, naming the project and the repositories it does own.

**One gap this phase surfaces and deliberately does not close: worker checkout roots.** A worker host resolves **one** `repoRoot` per project and declares the one repository its checkout actually is (issues #687–#689), so a run for a non-default repository fails loudly at provisioning — refused up front by the assignment's repository check (`src/transport/assignment-execution.ts`) or by `assertRepoIdentity` (`src/worker/git-worktree-manager.ts`) — rather than working in the wrong tree. That is safe, not silent, but it does mean a second repository is not yet *usable* end to end; per-repository checkout roots are host-local execution state and are a follow-up. Because provisioning is where a non-default repository stops, the DB-free delivery API's own project reads (`src/router/worker-delivery.ts`, which derives the review-ledger key and the server-side SCM delivery provider from the authenticated project's **default** entry) are unreachable for one and are deliberately left for that same follow-up.

### Repository routing for a board card (issue #686 phase 2)

Hop 2 above used to answer `undefined` for every `pm` job, which is what pinned board-driven Planning and Implementation to the project's default entry. Phase 2 routes the card instead, and the decision is made **at ingress** — in `handlePmEvent` (`src/router/webhook-receiver.ts`), after authentication, the status-field filter and loop prevention, so a delivery that is dropped pays for no board read (the same ordering, and the same reason, as `resolveChecksPullRequest` on the SCM side). The answer is recorded on the envelope as `PmWebhookJob.repository`, so a redelivery, a dependency recheck, and an operator's "Retry now" re-parse the stored payload and route identically rather than re-asking the board.

That choice is what makes the change small: `repositoryForJob` is already the one place a job states its repository and `processJob` already scopes the project from it, so **no** consumer, phase, trigger, run-row, or read-model code changes — the worktree, branch, PR, `runs.repository` and `QueuedRun.repo` all name the routed repository because they always named `repositoryForJob`'s answer.

Three properties are load-bearing:

- **A project owning one repository short-circuits.** `resolveCardRepository` (`src/pm/repository-routing.ts`) answers from the record when there is exactly one entry, and takes a provider **factory** rather than a provider so nothing is constructed and no board read is made. With one repository there is nothing to choose; that is arithmetic, not a provider decision, and it is what keeps every existing Jira/Linear/Trello project working without declaring a token.
- **An unroutable card is refused, never defaulted.** `unrouted` (no entry claims it) and `ambiguous` (two do) each ack `202 { ok: true, ignored: true, reason }` with their own reason and a `logger.warn` naming the project, the card, and the repositories it could have gone to. Nothing is enqueued: with two repositories declared, "the first one" is a coin toss that pushes a branch and opens a pull request where nobody asked for one. A failed board read is the same refusal with a `500`, so the provider redelivers.
- **The worker's self-enqueued next phase carries the repository forward.** `selfEnqueueNextPhase` sets it from the run's own scoped project (`src/worker/consumer.ts`) rather than re-deriving it; without that, an auto-advanced Implementation would silently jump back to the default entry. That path needs no board read — the completed phase already ran in the answer.

A `pm` row written before this carries no `repository` and still means the default entry, so there is nothing to migrate.

## Provider abstraction

Three integrations, each following the manifest/registry pattern from `ai/CODING_STANDARDS.md`:

### Per-provider SCM credentials (issue #628)

A project's source-control credentials are **per provider**, not one shared pair. Before #628 `credentials.reviewer` / `credentials.webhookSecret` were a single role-keyed pair, so storing a GitLab reviewer token overwrote the GitHub one in place and a project could hold only one provider's secrets at a time. The shape is now `credentials.scm[<providerId>][<role>]` (`src/config/scm-credentials.ts`, composed into `CredentialsSchema` — `src/config/schema.ts`), with `SCMProviderManifest.credentialRoles` declaring each provider's own conventional reference name for the two roles the contract itself names (`SCM_CREDENTIAL_ROLES` = `reviewer` + `webhookSecret`, `src/scm/types.ts`) — the #497 PM precedent, minus its open role vocabulary, because every SCM provider needs exactly those two and only the *name* differs (`GITHUB_TOKEN_REVIEWER`, `BITBUCKET_TOKEN_REVIEWER`, `GITLAB_TOKEN_REVIEWER`, and their `*_WEBHOOK_SECRET` siblings; the conformance suite asserts no two providers share a key, which is the structural guard against the overwrite).

Resolution is `(project, providerId, role) → secret` — `resolveScmCredentialOrNull` / `requireScmCredential` (`src/config/provider.ts`) — and reads **only** the provider it was asked for. The callers each supply the provider the operation belongs to: `'github'` for the `getPersonaToken` pair (explicitly GitHub's), `'bitbucket'` / `'gitlab'` for their own folders' twins, the *delivering* manifest's id for the receiver's webhook-secret lookup (so a GitLab delivery is never checked against the project's GitHub secret), and `project.scm` for the one PM role that inherits an SCM credential. **Deliberately not a fallback chain**: switching the dashboard's provider selector leaves the previous provider's secrets stored — so switching back restores them, and evaluating a provider costs no re-entry — and those retained credentials are stored but never resolved. A missing credential for the provider asked for throws naming the project, provider, role, and that provider's conventional key, never another provider's secret.

Two decisions worth not re-deriving. **Presence is enforced at resolution, not at parse.** The schema validates only structure (every key a real provider id, every role one that provider declares), because the Source Control tab persists a provider switch on its own — so "provider selected, credentials not yet entered" is a state one click legitimately creates, and a parse-time presence error would leave `swarm config apply` rejecting a config the dashboard just made. **The PM side is switchable too since issue #642, and still keeps its parse-time presence rule**, because the two tabs write in opposite orders: the PM switch flow enters the incoming provider's credentials *before* the new `pm` member is saved (`validatePmCredentialRoles` rule 3, `src/config/schema.ts`), so a half-configured `pm.type` is never something a save produces — and `projects.update` refuses one outright rather than relying on a parse that path never performs. `requireScmCredential` is therefore the single enforcement point, firing when the credential is actually needed. **Migration copies reference names verbatim.** A SQL backfill (`src/db/migrations/0045_scm_credentials_per_provider.sql`) files each persisted project's legacy pair under `credentials.scm[scm_type ?? 'github']`, and `adoptLegacyScmCredentials` does the same at parse time for a `swarm.config.json`; neither rewrites the name to the manifest's `envVarKey`, because the secret sits in `project_credentials` under the old key and renaming the reference without moving the row would break resolution outright. A project created since issue #290 keeps the neutral `SCM_TOKEN_REVIEWER` / `SCM_WEBHOOK_SECRET`, so a reference diverging from its manifest's conventional key is the **common** case — anything that *displays* a credential key must show the reference the role resolves through, never `envVarKey`. There is no runtime fallback from a per-provider reference back to the legacy pair, which is what stops a newly selected GitLab from silently receiving the GitHub secret.

**The API and the Source Control tab followed in issue #632**, which is what makes the shape visible to an operator. `projects.credentials.list`/`set`/`delete` (`src/api/routers/credentials.ts`) are now addressed by `(providerId, role)` exactly as the PM family is: `list` takes an optional provider id (defaulting to the one the project runs on) and answers `{ providerId, providerLabel, providerRegistered, roles: [{ role, envVarKey, referenceKey, isConfigured, maskedValue }] }` built from the manifest's `credentialRoles`, and the writes name a role while the **server** resolves the store key. That is the fix, not a refactor: the pre-#632 `set` took the key itself, so the browser saving GitLab's reviewer token wrote it over GitHub's row. A provider id nothing runtime-ready is registered for answers `providerRegistered: false` rather than throwing, because the tab's provider catalogue is a hand-kept browser list that can name one this installation lacks. The tab queries per selected provider (the id is part of the query key, so a switch refetches), renders `referenceKey`, and takes every field label from per-provider copy in `dashboard/src/lib/credentials.ts` — `getScmProviderCopy(...).roleLabels`, beside the descriptions that already lived there — because "Reviewer PAT" is GitHub's word for a Bitbucket app password and a GitLab access token. Phase 1's interim legacy mirror in `projects.create` is gone with it; the deprecated legacy keys stay in `CredentialsSchema` for the adoption path alone.

### Instance-level default SCM credentials (issue #769)

An **instance-level default** is the value an installation records once for a source-control role that one account normally serves across every project — today exactly GitHub's `reviewer`. It is a third credential tier: `project_credentials` holds a project's own secret (resolved through a reference key), `worker_scm_credentials` a worker operator's own identity, and `instance_scm_credentials` (`src/db/schema/instanceScmCredentials.ts`) one row per `(provider_id, role)` slot with no project and no worker at all. The write surface is `settings.credentials.{list,set,delete}` (`src/api/routers/instanceCredentials.ts`), driven by General Settings → **Credentials**.

Four decisions worth not re-deriving:

- **Its own table, not a key in the `app_settings` blob.** `settings.get` returns that whole object to any authenticated caller, so a secret there would be echoed back verbatim. A separate table also lets the read path select the *key columns only* (`listConfiguredInstanceScmCredentials`) and never decrypt anything merely to mask it — unlike `project_credentials`' own `resolveAllProjectCredentials` + `maskCredential` pair, which has a reference-key indirection to resolve first.
- **Keyed by `(provider_id, role)`, not by a reference key.** The indirection in `project_credentials` exists because a *project* names its own reference (`SCM_TOKEN_REVIEWER` vs `GITHUB_TOKEN_REVIEWER` — see "Per-provider SCM credentials" above). An instance default has no project and therefore no reference to honour: it is the value for one slot. `provider_id`/`role` are `text` rather than pg enums, like `projects.scm_type`, so a fourth provider opting in needs no migration.
- **A new AAD that names the slot**, `instance:scm:<providerId>:<role>` (`instanceScmCredentialAad`), not a bare `'instance'` constant. This preserves the property `project_credentials` gets from using `projectId` as AAD: a ciphertext moved into another slot's row fails GCM authentication instead of resolving as that provider's secret. Same primitive (`src/db/crypto.ts`), no second encryption scheme.
- **Eligibility is manifest data**, `ScmCredentialRoleSpec.instanceDefault`, mirroring `PmCredentialRoleSpec.inheritsSharedCredential`: the admin surface offers exactly the roles a provider says are installation-wide (`listInstanceDefaultScmRoles`, filtered to *runtime-ready* manifests for `runtimeReadyScmProvider`'s reason), so a fourth provider opts in without an edit to shared code. `webhookSecret` can never opt in — it is tied to one project's own webhook endpoint, so an installation-wide value would be wrong rather than merely redundant — and the conformance suite asserts that structurally, alongside a tripwire pinning the eligible set to exactly `[{ github, reviewer }]`.

**`resolveScmCredentialOrNull`'s no-fallback rule is untouched, and the creation-time copy does not reintroduce the risk it exists to prevent.** Nothing reads this table at resolution time: a project with no credential of its own still throws naming the project, provider, role and that provider's conventional key. The rule exists because a *runtime* fallback would hand a newly selected GitLab the GitHub secret — the resolved value would silently stop matching the provider the project actually names. Copying a default into a **new** project's own `project_credentials` row at creation is a different thing: after the copy the project's stored credential is its own, attributed to one provider, visible and editable on its Source Control tab, and resolution still reads only that row. Nothing becomes ambient, and nothing changes for an existing project.

That copy is phase 2/2, `seedInstanceScmCredentials` in `projects.create` (`src/api/routers/projects.ts`). Four properties are what keep it a copy rather than a tier:

- **The project's own provider, and only opted-in roles.** It walks `listInstanceDefaultScmRoles()` filtered to `project.scm` — never a block per registered provider, which is the fallback shape `adoptLegacyScmCredentials` refuses for the same reason. `webhookSecret` can never opt in, so it is never seeded, and a Bitbucket or GitLab project is seeded nothing today.
- **The destination key is the one the project resolves the role through**, `scmCredentialReferenceFor(...) ?? envVarKey` — the same `scmReferenceKeyFor` rule `projects.credentials.set` writes under (`src/api/routers/credentials.ts`), shared rather than re-derived, so a seeded value and a hand-entered one land on the same row.
- **Re-encrypted under the project's AAD.** The instance value is decrypted under `instance:scm:<providerId>:<role>` and re-encrypted under `projectId` by `writeProjectCredential`, leaving the project row self-contained: rotating or clearing the instance default afterwards cannot reach it, and cannot break it.
- **Best-effort, and outside the creation transaction.** The project and its membership are already committed atomically and `writeProjectCredential` takes no transaction handle, so a failing seed is a `logger.warn` and a successful creation rather than a client-visible error — the degraded outcome is exactly the pre-#769 one (set the credential on the Source Control tab), while re-running `create` to recover it would only earn a `CONFLICT`.

Nothing re-seeds afterwards: `projects.update`, `swarm config apply` and the Source Control tab's own `projects.credentials.set` are untouched, and bulk-applying a default to already-created projects is deliberately not offered.

Authorization is enforced in the router, not on the screen: every procedure, `list` included, is `instanceAdmin`-only (a local `FORBIDDEN` guard rather than `assertInstanceAdmin`, whose copy describes a read-only installation *view*). That is the deliberate difference from the `agents` tab, whose admin-only-ness is a screen-level visibility boundary with `settings.get`/`update` unchanged — a secret must not be writable, nor its configured state readable, by any authenticated user just because a tab is hidden.

### Per-worker operator SCM credential (issue #765)

The **worker operator's own** account credential — the identity every commit, push, pull request and implementer-side comment a phase makes is authored as, on every worker for every phase since issue #551 made it universal — is a durable, encrypted, per-`(worker, scmProvider)` row in `worker_scm_credentials` (`src/db/schema/workerScmCredentials.ts`). It used to be one process env var, `SWARM_OPERATOR_GH_TOKEN`, read unconditionally at worker startup: no validation, no rotation flow, nothing stopping a duplicate `.env` key from silently shadowing the intended value, and hardcoded to GitHub regardless of `project.scm`.

Four decisions worth not re-deriving:

- **Keyed by `(workerId, scmProviderId)`, so a worker enrolled across providers holds one credential per provider.** `scm_provider_id` is `text` and not a pg enum, for the same reason `projects.scm_type` is: `ScmProviderIdSchema` is the value list's source of truth and a fourth provider must not need a migration. The unique index on the pair is the upsert target, which makes a rotation an update rather than a second row; the FK to `workers` is `ON DELETE CASCADE`.
- **Encrypted with the existing primitive, bound to both parts.** `src/db/crypto.ts` (AES-256-GCM, opt-in on `CREDENTIAL_MASTER_KEY`) with `workerScmCredentialAad(workerId, scmProviderId)` = `<workerId>:<scmProviderId>` — so a ciphertext copied onto another worker's row, or onto the same worker's other provider row, fails GCM authentication instead of resolving. No second encryption scheme.
- **Resolved control-plane side at dispatch, and carried on the assignment frame.** The worker is DB-free by design (ADR-003 §2) and cannot read the store; the control plane is also the only side that knows *which* worker was selected and *which* provider the project targets, so it is the only side that can fail with both names before the run starts. `src/router/dispatcher.ts` resolves `requireProjectSCMProviderId(project)` (a registry lookup with the same three throws as `requireProjectSCMProvider` — never `project.scm ?? 'github'`) and then `requireWorkerScmCredential` (`src/identity/worker-scm-credential.ts`), re-raising a miss as an `AgentRunError` of kind **`error`** so the shared settle path records a run-row reason and posts the usual board/PR failure comment. The kind matters and is easy to get wrong: `pushAndAwaitResult`'s two other pre-push throws are `aborted` and `DeliveryDeferredError`, and `handlePhaseFailure` (`src/worker/consumer.ts`) treats **both as deferrable** — correctly, since both describe a transient race. An unset credential is not transient, so deferring it would retry until the budget ran out and only then surface the one message naming the worker and the provider; `'error'` is the kind `isDeferrable` excludes, the same reason `adaptResultToPhaseRun` uses it for a worker's terminal frame. A consequence worth having: rotation takes effect on the **next dispatch**, with no worker restart — which is what phase 2/3's dashboard form needs.
- **`TaskAssignment.operatorCredential` narrows the frame's secret boundary, deliberately.** `src/transport/assignment.ts` is still the single place the *project* secret boundary is enforced (it derives `NonSecretProjectConfig` itself), and no project credential reaches a worker. The new field is the **worker's own** identity, delivered to the one machine that must perform the commit and the push, over TLS on a socket already authenticated by that worker's own `SWARM_WORKER_CREDENTIAL` — so the older claim that this credential is "never sent over the transport" is superseded for this one credential and nothing else. It is required on `BuildTaskAssignmentInput` (so the control plane cannot assemble a frame without having resolved one) and optional on the wire; `TRANSPORT_PROTOCOL_VERSION` is **not** bumped, following the same convention as `repository` and `boardItemId` — a bump rejects every frame from a mismatched daemon rather than only the affected ones. The skew that leaves is one-directional and loud: a new worker settles a credential-less frame `failed` with an explicit reason, an old worker ignores the field. Rollout order is therefore store → router → workers (`docs/onboarding-worker.md`).

The write surface is `swarm workers set-scm-credential <worker-id> <scm-provider-id>` (`src/cli/commands/workers.ts`), which validates against `ScmProviderIdSchema` rather than the registry — the closed value list, so validity does not depend on which provider modules the CLI process imported — checks the worker exists, and reads the secret without echo through `src/cli/_shared/secret-input.ts` (never argv). A dashboard form is phase 2/3, and live verification of a pasted credential against the provider API belongs with it.

**Deliberately left behind.** `src/config/operator-token.ts` keeps reading `SWARM_OPERATOR_GH_TOKEN` on the **router** for three things this change does not touch: trigger-side persona identity resolution (`resolvePersonaIdentities` → `getPersonaTokenOrNull(project, 'implementer')`, used by `respond-to-review`'s author gate and `resolve-conflicts`' candidate filter), the Review trigger's `getPullRequest` fallback for a project with no reviewer credential (`src/triggers/handlers/review.ts`), and `POST /worker/delivery/pr-comment` with `persona: 'implementer'`. All three run on the router, which holds one value for every worker it serves; deciding whose operator identity those should use in a multi-worker installation is a real design question and not this one's.

### SCM: GitHub (`src/integrations/scm/github/`)

The integration itself lives under `src/integrations/scm/github/` — consistent with the PM provider (`src/integrations/pm/github-projects/`) and the module shape in `ai/CODING_STANDARDS.md` — but its internals are ported close to verbatim from Cascade's `src/github/*`, so match Cascade's file shapes (`scm-integration.ts`, `client.ts`, `personas.ts`) rather than reinventing them. Webhook ingress lives beside them in `webhook.ts`: it was Cascade's router adapter (`src/router/adapters/github.ts`), and issue #385 moved it under the provider it belongs to once ingress started running through the contract.

- **The contract + registration (issue #294).** Shared code programs against the provider-neutral `SCMProvider` (`src/scm/types.ts`), which `GitHubSCMIntegration` declares (`implements SCMProvider` is the compile-time conformance check; the runtime one is the multi-provider harness that landed with Bitbucket's phase 4/4 — `tests/unit/integrations/scm/scm-conformance.test.ts`, which asserts every *registered* manifest's surface and that no method is a stub). It composes the pre-existing neutral seams rather than duplicating them: it extends `ScmMergeProvider` (`src/scm/merge.ts`) and returns `ScmDeliveryProvider` (`src/scm/delivery.ts`), and its `deliveryProvider(project, persona)` is documented as *one* producer of a delivery provider, not the only one (the operator-token and transport-backed composites below are the others). Neutral homes for the shapes shared code reads — `ScmPersona`/`ScmPersonaIdentities`, `PullRequestDetails`, `CheckRunState`/`AggregateCheckStatus` — live in the same file, with GitHub-local aliases (`GitHubPersona`, `ConflictCandidatePullRequest`, `CheckSuiteStatus`) kept in the GitHub module so nothing had to be renamed at once. GitHub self-registers an `SCMProviderManifest` into `scmProviderRegistry` (`src/integrations/scm/{manifest,registry}.ts`) from `src/integrations/scm/github/index.ts`, loaded by the one canonical entrypoint alongside PM — a **shared instance**, not a `createProvider(project)` factory, because the integration is stateless and takes `project` per call.
- **Neutral ingress + triggers (issue #385).** Webhook ingress and the SCM-driven triggers now run entirely through the contract, which widened with the four methods the receiver needs: `readWebhookRequest` (which header names the event / carries the delivery id / carries the signature), `parseWebhookEvent` (raw body → normalized event), `verifyWebhookSignature`, and `isSwarmGeneratedEvent` (the comment drop gate). The normalized event is `ScmEvent` (`src/scm/events.ts`) — a Zod schema, because it is also the durable queue payload — whose `kind` is a neutral vocabulary (`pull-request`, `pull-request-review`, `work-item`, `work-item-comment`, `checks`) that each adapter maps its own event names onto. The manifest gained a `webhookRoute` (`/github/webhook` for GitHub, which GitHub Projects' `projects_v2_item` board webhook shares; `/bitbucket/webhook` since issue #618), and the receiver mounts one route per runtime-ready registered manifest instead of hardcoding a path — which is why making a second provider reachable took no receiver edit. Since #618 that handler also completes a `checks` event whose provider named no pull request, through the contract's `listPullRequestsForCommit` (see the Bitbucket section). Issue #496 extended that rule to the PM side without touching this loop — a PM manifest declaring the same path is served *inside* the SCM route's handler as a co-tenant (see the PM section below), never as a second `app.post()` Hono would shadow.
- **Registry-resolved outbound call sites (issue #386).** The project-scoped mutations resolve their provider through the registry too, so no pipeline, worker, or router module constructs one: the lazy delivery-provider default in the five delivery-owning phases (`implementation`, `review`, `respond-to-review`, `respond-to-ci`, `resolve-conflicts`), the worker's `resolveScmDelivery` local delegate, its run-row PR-title read and its phase-failure/interrupted-job PR comments (`src/worker/consumer.ts`), the durable merge executor's default merge capability (`src/worker/merge-automation.ts`), and the router's server-side `buildScmDelivery` default (`src/router/worker-delivery.ts`). Two lookups, picked by what the caller holds: `requireSCMProvider(job.providerId)` where a durable job already names its provider (the interrupted-job comment), `requireProjectSCMProvider(project)` everywhere else. The latter selects on the `ProjectConfig.scm` discriminator (issue #478) — the manifest the project names, which must be registered *and* runtime-ready, or the sole runtime-ready manifest when the project names none — a fallback that stopped resolving with issue #618, since GitHub and Bitbucket are now both ready, so every project states its provider. Every other case is a loud, specific throw naming the project and what it asked for, and never a fallback onto another provider. Only the *source* of the provider changed, never when it is built: every default stays inside the phase's own `??`, so persona-credential resolution keeps happening inside the delivery try/catch and the `legacyMode` guard, injection precedence, merge outcomes, and retry policy are untouched. The durable merge executor resolves its default inside the attempt's own `try` rather than in a default parameter, so an unresolvable provider settles the claimed dispatch as `provider-error` like any other provider failure instead of throwing out of `processJob` and leaving the dispatch in flight.
- **The DB-free worker's operator-credential delivery (issue #462).** The last concrete outbound import. `SCMProvider` now carries a second documented delivery producer beside `deliveryProvider`: `operatorDeliveryProvider(repo, credential)`, a delivery provider authenticated as the worker operator's *own* account rather than a per-project persona (ADR-003 §2 / ADR-004 §3) — the shape a federated worker needs, since it holds no secret store. GitHub implements it by delegating to the same `src/integrations/scm/github/operator-delivery.ts` body as before (`submitReview` still throws there — a reviewer verdict is the server's write), and the DB-free executor resolves it via `requireProjectSCMProvider(project)` inside its own `try`, so an unresolvable provider — an unloaded entrypoint, a `project.scm` naming something unregistered or not runtime-ready, or an unstated `scm` with no single runtime-ready manifest to fall back on — settles the assignment as a terminal `failed` frame rather than throwing out of `runAssignmentDbFree`, which is documented never to throw. The discriminator reaches that worker because `scm` is worker-safe (`WORKER_SAFE_KEYS`, `src/config/worker-config.ts`), so the assignment's config slice carries it. The remote-worker entry (`src/transport/connect-entry.ts`) gained the `src/integrations/entrypoint.js` side-effect import that populates the registry — safe on a DB-free worker because nothing in that module graph opens Postgres or Redis at load (`getDb()` is lazy). What did *not* move behind the contract is where the credential itself comes from — still not a `ProjectConfig` field, because it is the operator's rather than the project's, but no longer a worker env var either: issue #765 replaced `resolveOperatorGitHubToken` with a per-`(worker, provider)` store resolved at dispatch (see "Per-worker operator SCM credential" below). `DbFreeAssignmentDeps.buildDelivery` stays the `(repo, credential)` test seam, now an optional override rather than a defaulted one.
- Dual-persona tokens (`implementer`, `reviewer`) scoped via `AsyncLocalStorage` (`src/integrations/scm/github/client.ts`'s `withGitHubToken`), never passed as plain arguments. Both resolve behind the same `getPersonaToken`/`getPersonaTokenOrNull` seam (`src/config/provider.ts`) but from different sources (issue #396): the **implementer** is the worker operator's own token, never in project config — read from `SWARM_OPERATOR_GH_TOKEN` (`src/config/operator-token.ts`) on the **router**, which is the only side that still reads that variable since issue #765 moved the worker path onto the per-worker store below; the **reviewer** stays a project-scoped credential *reference*, resolved from Postgres (`src/db/repositories/credentialsRepository.ts`) — and since issue #628 that reference is GitHub's **own**, `credentials.scm.github.reviewer`, resolved through the provider-parameterised `resolveScmCredentialOrNull`/`requireScmCredential` seam rather than a pair shared with every other provider. The `getPersonaToken` pair is therefore explicitly GitHub's, which is why Bitbucket's and GitLab's twins live in their own folders. Two distinct GitHub identities remain required for persona routing (`getPersonaForLogin`/`personaForEvent`), the Respond-to-review reviewer gate, and the independent-reviewer invariant (PROJECT.md §5.3), while comment loop prevention keys on content markers (see below). The board's status-change drop gate is **no longer one of them**: since issue #537 it resolves the identity of the *PM* provider's own board credential, the account board writes are actually made by (see "PM: GitHub Projects"). (The router's three readers still hold one `SWARM_OPERATOR_GH_TOKEN` for every worker they serve; moving those onto the per-worker store is a follow-up.)
- GitHub's webhook module (`src/integrations/scm/github/webhook.ts`) parses `pull_request`, `pull_request_review`, `issue_comment`, `issues`, and `check_suite` into the neutral `ScmEvent` kinds; the receiver resolves the SWARM project from the event's repo and the worker dispatches with the right persona's credentials in scope. Raw event names, header names, payload paths, and the `sha256=` signature framing exist only here.
- Loop prevention on comment events by **SWARM-origin marker**, not author login (issue #443, exactly as described in `ai/CODING_STANDARDS.md`): `SCMProvider.isSwarmGeneratedEvent` reads the comment's own body off the normalized event (`commentBody`, populated for comment events only and for this gate only) and drops it when `isSwarmGeneratedBody` (`src/scm/swarm-origin.ts`) finds a hidden `<!-- swarm-… -->` marker or the `_Generated by SWARM…_` footer — so SWARM never reacts to its own ack/reply whichever account posted it, and the operator's *hand-written* comments from that same account still get through. Every SWARM comment body must therefore carry one of the two markers; both the delivery markers (`swarmMarker`) and the footer are built from that module's constants so producer and detector can't drift. The gate needs no credential and so has no failure mode. PR/review lifecycle routing between personas is handled by `getPersonaForLogin`, not by the drop gate.
- Pipeline code requests deterministic mutations through the provider-neutral `ScmDeliveryProvider` seam (`src/scm/delivery.ts`). Agents write Zod-validated semantic hand-offs and never commit, push, create PRs, submit reviews, or post comments. The GitHub adapter supplies persona-scoped implementations, durable delivery markers, existing-PR recovery, and safe expected-SHA pushes. - **Server-side SCM metadata delivery (ADR-004 §2, config-gated).** The metadata-only delivery calls — `submitReview` and `postComment` — can run on the router instead of the worker, so a federated worker never holds the per-project reviewer PAT. The router hosts a small authenticated delivery API (`src/router/worker-delivery.ts`: `POST /worker/delivery/review` + `/pr-comment`, mounted in `src/router/index.ts`) whose pure `handleSubmitReview`/`handlePostComment` authenticate the worker credential, confirm a routable enrollment in the target project, resolve the acting persona's credential **server-side** (`getPersonaToken`), and perform the GitHub write — the review lands as a genuine GitHub review, keeping the `pull_request_review` respond-to-review trigger working. **The `/pr-comment` frame carries the requesting persona** (`PostCommentDeliveryRequestSchema`): a Review's comment is the reviewer's, a Respond-to-review reply is the *implementer* answering that review, and a server left to infer it posted that reply under the reviewer being answered (issue #444). The field defaults to `reviewer`, so a client that sends none is unchanged and the wire stayed compatible without a protocol bump; `/review` carries no persona because only Review submits a verdict and it is always the reviewer's. The router resolves `implementer` through the same seam to its own `SWARM_OPERATOR_GH_TOKEN` — the same-host assumption that variable already documents (issue #396), so on a genuinely different-machine deployment the reply is authored by the *server* operator's account, which the federation gap ADR-004 §3/§4 (#397/#398) owns. Every worker uses it: `src/transport/assignment-execution.ts` hands the phase a transport-backed provider (`src/scm/transport-delivery.ts`) built for the phase's persona, which POSTs only the verdict + comment body + PR number (+ that persona) up the wire (never the repository tree) and delegates every source-carrying / attribution op (commit, push, create PR) to a delegate built from the operator's own token. That composite survived issue #553's deletion of its PM twin precisely because its delegate is the **operator-credential** provider rather than an in-process one — the pair expresses what the operator's token can and cannot sign for, not which worker is running. The frames are Zod schemas in `src/transport/protocol.ts`, and the wire mechanics (URL join, bearer header, protocol stamp, throw-on-non-2xx) live in one shared client, `src/transport/delivery-client.ts`; the server writes are marker-idempotent, so a retried transport call can't double-post. A worker composes the transport provider over its operator-token provider (ADR-003 §2), and four sibling routes front a **database** rather than a credential for it — same worker-credential auth and enrollment check: `POST /worker/delivery/review-ledger/prior|mark|abandon` over the `review_verdicts` table, and `POST /worker/delivery/follow-up-review`, which performs the dispatch-row write + queue enqueue a `fixed` Respond-to-review response owes its new commit (issue #241). That last one stays a *call the phase makes* rather than a fact reported in its terminal result, so a failed enqueue still defers inside deterministic delivery and the resumed retry re-schedules; the scheduler's deterministic dispatch identity absorbs the retry.
- **Server-side PM metadata delivery (ADR-004 §2, the independent Phase 2/2 half).** The same split applies to the two metadata-only **PM** board writes — `moveWorkItem` and `addComment` — so a federated worker never holds the per-project PM credential either. The same delivery API gains two sibling routes (`POST /worker/delivery/pm/move` + `/pm/comment`) whose pure `handleMoveWorkItem`/`handleAddPmComment` run the identical worker-credential auth + active-enrollment authorization, then resolve the PM credential **server-side** by building the project's provider through the registry (`requireProjectPMProvider(project)`, issue #297) and calling `moveWorkItem`/`addComment`. Only the canonical `PmStatusKey` (`src/pm/pipeline.ts`) or the comment body crosses the wire — never a board option ID (the adapter resolves it server-side, RULES.md §2) and never the repository tree. A worker gets its `pm` from `src/transport/assignment-execution.ts`, which builds the delegate-less `createWriteOnlyTransportPmProvider` (`src/pm/transport-delivery.ts`) — it holds no database and so has no in-process provider to delegate to. A composite variant existed for the DB-holding host worker and was deleted with it (issue #553), so this module now exports one shape. Its board writes POST to the control plane, as do six transported **reads** — `POST /worker/delivery/pm/blockers`, so Implementation's dependency gate still gates (issue #330); `POST /worker/delivery/pm/dependents`, the reverse edge that gate's cycle backstop reads, so a federated Implementation cannot defer on a blocker the item itself natively blocks (issue #639 — the gate runs inside the phase, so refusing this read would leave the backstop inert on exactly the path the reported deadlock ran on); `POST /worker/delivery/pm/find-item`, which resolves the one card whose backing URL ends with a given suffix so Respond-to-review can still report In progress / In review; `POST /worker/delivery/pm/find-artifact`, which resolves a repository-scoped issue or pull-request card for the automation gate; `POST /worker/delivery/pm/find-comment`, which answers whether a marker is already on a card so a replayed Planning delivery reuses its plan comment instead of re-splitting (issue #536); and `POST /worker/delivery/pm/find-item-by-marker`, which resolves the one card whose description carries a given marker, so a Planning delivery that died *between* children adopts the child it already created rather than duplicating it (issue #543) — and the two enumerating/whole-item reads refusing rather than guessing. Both card lookups are `PMProvider` methods (`findWorkItemByUrlSuffix`, `findWorkItemByDescriptionMarker`), not a URL or body match at the call site: widening the interface (RULES.md §2) is what lets the server answer with one card instead of proxying a whole board, and keeps the pipeline free of any provider-specific URL shape. Issue #536 added Planning's four remaining board **writes** on the same pattern (`POST /worker/delivery/pm/{create-item,update-item,label,blocked-by}` → `createWorkItem`/`updateWorkItem`/`addLabel`/`addBlockedBy`), which is what took the delivery API to sixteen routes (seventeen since #543 added the split's resume lookup, eighteen since #639 added the reverse-edge read) and made Planning runnable off the database — the credential still resolves server-side, and the project a card is created on is the **authenticated** enrollment's, never the request's. The reads with no route are `getWorkItem`/`listWorkItems`/discovery, which stay worker-side on the DB-holding worker; the out-of-band failure/interrupted-run board comments run on that worker's `processJob`, not on a remote worker, so they need no routing here. Both delivery halves have now landed, so **ADR-004 §2 is built** — and so is its §3, in two phases: the Review trigger's ownership gate now keys on work-item origin (`isSwarmManagedPullRequest`, issue #397) and comment loop prevention on SWARM-origin markers (`isSwarmGeneratedBody`, issue #443), so neither reads a persona login and auto-review fires on the federated path.
- **Worker→PR attribution on the run row (ADR-004 §4, issues #398 + #446).** The control plane keeps a durable `(work item, phase, worker, user, PR url)` record so it can say which worker/user produced a given PR or review even if the token model later changes — all of it on the existing `runs` row (`src/db/schema/runs.ts`) rather than a parallel table, written through that row's normal lifecycle. Two nullable columns join `worker_id`/`worker_fencing_token`: **`worker_user_id`** (→ `users.id`, `ON DELETE SET NULL`), written at dispatch from the owner the gate already resolved (`DispatchSelection.ownerUserId`, `src/worker/eligibility-gate.ts`) in all three run-row entry points (`createRun` plus both `resetRunToRunning` paths), and **`produced_pr_url`**, written at settle from the phase result (`PhaseRunResult.prUrl` → `CompleteRunInput.producedPrUrl`). Both ends are the control plane's to record because a DB-free worker (ADR-004 §2) cannot write them itself: the produced PR travels home on the terminal result frame as an optional `TaskExecutionResult.prUrl` (`src/transport/protocol.ts`), emitted by `succeededResult` (`src/transport/assignment-execution.ts`) and mapped back into the shared settle path by `adaptResultToPhaseRun` (`src/router/dispatcher.ts`) — optional, so it needs no protocol-version bump and an older worker simply omits it. The user id is denormalized rather than joined through `workers.owner_user_id` so removing a worker (which nulls `worker_id`) cannot erase the attribution, and `produced_pr_url` is deliberately *not* cleared on a retry: the PR is a real external artifact that outlives the attempt. Nullable throughout — an unfederated / single-user run records no worker at all, and only a PR-producing phase (Implementation) reports a PR; a produced *review* needs no column, since `review_verdicts` plus the run's `pr_number`/`review_verdict`/`review_ordinal` already identify it. Phase 2/2 (issue #446) surfaces the record on the run detail view: `runs.getById` (`src/api/routers/runs.ts`) resolves the recorded ids into display labels with the same `getWorker` + `getUserById` pair `assembleDashboardWorker` uses — naming each safe field explicitly, and only *after* `assertProjectAccess`, so a caller who may not see the run triggers no identity read — and returns them as an additive `attribution` object (`{ workerId, workerName, userId, userDisplayName }`) on the existing payload, no new procedure. The page shows **Worker** / **Worker owner** in its Execution Environment grid and links `produced_pr_url` as **PR opened by this run**, labelled apart from the `PR #n` a Review / Respond-to-review run acted on. Nullability carries through to the UI: a run with no recorded worker renders the same neutral `—` the other optional fields use (never a raw UUID, never a fabricated owner), a historical row with `worker_id` but no `worker_user_id` attributes through the worker row's current `owner_user_id`, and a deleted worker/user or a failed lookup degrades to the recorded id rather than erroring the page. So **ADR-004 §4 is built**. The Runs *table* and the Queue view stay unattributed by design (a fixed-width layout change, and a waiting dispatch has no bound worker yet).
- **The repository a run acted on, on the run row (issue #683).** `runs.repository` (`src/db/schema/runs.ts`) records it in the same `owner/repo` form `ProjectConfig.repo` uses, denormalized alongside `project_id` exactly as `review_verdicts.repository` already is rather than joined back through `projects`. The reason is the same one that column has: a project id identifies a repository only while a project owns exactly one, so every value derived from `project.repo` — a PR link, a prior-review lookup — becomes ambiguous the moment a project spans several, and the run itself should be the answer to "which repo was this for?". `text` NOT NULL, backfilled in migration `0047` from each row's owning project before the constraint is added (total, because `project_id` is NOT NULL with an FK and `projects.repo` is NOT NULL) — deliberately unlike `projects.scm_type`, where "states no provider" is a meaningful state and NULL means it. Written once by `createRun` from `CreateRunInput.repository`, which is **required**: the dispatcher (`tryCreateRun`, `src/worker/consumer.ts`) is the party that resolves *which* of a project's repositories an event was for — since issue #684 phase 2 it reads it off the project `processJob` already scoped to the job's repository — so deriving it inside the repository layer would put that resolution in the wrong place. A retry deliberately leaves it alone (`resetRunToRunning`) — the same work re-runs against the same repository. **The dashboard is its first reader (issue #691):** every run-facing surface — the run detail page's three PR links (the cap callout, the merge callout, and GitHub References) and the shared `WorkItemCell` the Runs table and the Workers screen's Active job column both render — now builds its PR link and work-item reference from `run.repository`, so `runs.getById`/`runs.list` need no change (they return the row as-is) and the `projectsMap`/`projectRepos` lookups that existed only to supply a repo are gone, along with the `project` prop on the components whose only use for it was that repo. `DashboardWorkerRun`/`WorkerActiveRun` (`src/identity/worker-enrollment-service.ts`) carry the field for the same reason. **The Review phase is its second reader (issue #692):** `RunReviewPhaseOptions.repository` is a **required** input that `runReviewPhase` keys its `review_verdicts` rows on — the `verdictKey` both ledger writes use and the `getPriorSubmittedReview` re-review lookup — plus the repository the review prompt names, so none of the three reads `project.repo` any more. It does **not** read the run row to get there: the phase runs on a worker with no database (ADR-003 §2), so the value travels on the assignment as an additive optional `TaskAssignmentSchema.repository` (`src/transport/protocol.ts`) and reaches the phase through `AssignedPhaseInputs.repository`, exactly the shape `boardItemId` established in issue #498 — additive in both directions, so `TRANSPORT_PROTOCOL_VERSION` is deliberately not bumped, and `src/transport/assignment-execution.ts` falls back to the reconstructed project's repo purely for router/worker version skew. It is filled in `src/router/dispatcher.ts`'s `pushAndAwaitResult` from the same source `tryCreateRun` writes the column from, so the frame and the row are resolved by the same two siblings and cannot disagree about what a run acted on. Two consumers deliberately stayed project-derived, and phase 2 settled both differently than #692 expected. The trigger-side slot *reservation* (`reserveReviewVerdict`, `src/triggers/handlers/review.ts`) and the respond-to-review verdict reads read `project.repo` — correct now without being migrated, because phase 2 scopes that project to the job's own repository before the trigger ever sees it. Review's `deliveryIdentity(['review', project.repo, …])` genuinely stays put, and for its own reason: it is a resume-idempotency key a preserved worktree's sidecar was already written under, so re-deriving it from a different input would orphan a run in flight across a deploy. The two that *did* move are `src/dispatch/force-re-review.ts`, which now scopes its whole project read from `run.repository` (phase 2 — a forced continuation must answer the review in the repository whose PR was reviewed), and the *queued*-runs read model, which resolves `QueuedRun.repo` through `repositoryForJob(jobPayload)` rather than each variant's own field — still per dispatch, since a fresh dispatch has no run row to read, but now through the same helper the worker scopes with. While a project holds one repository every rendered and keyed value is exactly what `project.repo` supplied before, so nothing changes for an existing installation; what changes is that the run — not a join through its project — is now the answer. **Issue #685 phase 1 stops that from being merely true and makes it asserted.** Every SCM-driven key is now pinned by a cross-repository regression case driven through the code path that owns it — the two trigger handlers, the five delivery-owning phase bodies, `followUpReviewDeliveryId`, and `forceReReview` — each observing the key where it is already observable (the `.swarm_delivery.json` progress sidecar, the exported builder, the `claimReviewDispatch` / `reserveReviewVerdict` / `getReviewVerdict*` / `getSubmittedReviewSlot` call arguments) rather than re-deriving `deliveryIdentity` in the test, which would prove the hash works and nothing about the wiring. The fixture is `createMockProjectRepositoryPair` (`tests/helpers/factories.ts`): the real `scopeProjectToRepository` over one two-entry record, so the pair is what `processJob` genuinely hands a trigger or a phase. No key's *inputs* changed — re-deriving one would orphan the sidecar of a run in flight across a deploy — and the five in-tree justifications that read "…while a project holds exactly one repository" now give the reason that is actually load-bearing: the two values agree because both are resolved from the job's own repository. One criterion was deliberately handed on to phase 2 rather than met there — a PM provider resolving `WorkItem.taskRef` against the work item's own repository — and **issue #710 met it by routing around the obstruction rather than removing it**: a board-wide provider still cannot see the project's repository list, so instead of being given one, the *linkage* now names its own repository (`WorkItem.taskRepository`) and whether the project owns it is decided by the consumer, which holds the run's scoped `project.repo`. Which repository a board card resolves to at all remains issue #686's. See "Task identity".
- Merging an approved PR goes through the provider-neutral `ScmMergeProvider` seam (`src/scm/merge.ts`, issue #253; direct-merge-only per issue #292): a single `mergePullRequest(project, prNumber, approvedHeadSha)` capability returning a terminal `MergePullRequestOutcome` — `merged`, `not-ready`, `not-eligible`, `policy-blocked`, `unsupported`, or `provider-error` — never a thrown error, so a refusal can't retroactively fail an already-completed Review. Pipeline code never merges: after an eligible Review approval the worker persists a **durable merge dispatch** (`src/worker/merge-automation.ts`, see "Durable dispatch state machine" below) whose executor invokes this capability. GitHub is the first implementation: every attempt re-reads the PR's current state, verifies the approved head SHA and approval still hold, and performs the **direct** REST merge (`pulls.merge` via `src/integrations/scm/github/client.ts`'s `mergePullRequestDirect`) under the project's implementer PAT, pinned to the approved head so a concurrent push produces GitHub's non-merged stale-head response rather than merging unreviewed code. GitHub's native auto-merge is deliberately never requested (issue #292): it is unavailable on many private repositories, has no portable equivalent in other SCMs, and its error text (`Auto merge is not allowed for this repository`) once bypassed merge automation entirely. GitHub-specific classification (which REST error means what — a merge-queue requirement is `unsupported`, 405/409 are `not-ready`, 403 is `policy-blocked`) stays inside the adapter. Bitbucket and GitLab implement the same interface against their own direct merge endpoints and error vocabularies (see their sections below), with no dispatch or worker changes — GitLab's is the one whose endpoint takes an expected head like GitHub's, and its status table is a third distinct one (409 → `not-eligible`, 405/422/406 → `not-ready`, 401/403 → `policy-blocked`).

### SCM: Bitbucket (`src/integrations/scm/bitbucket/`) — complete and runtime-reachable (issues #296, #618)

The runtime wiring and its HTTP boundaries are unit-verified, but a real Bitbucket Cloud repository has not yet been exercised end to end. In particular, the commit→pull-request read is mocked in tests; production verification must confirm that Bitbucket accepts the normalized 12-character commit revision on its pull-request association endpoint. GitHub skips that read only for a `check_suite` payload that already names a pull request; unresolved branch and default-branch checks use the same neutral lookup.

The second SCM provider, built out over four ordered phases — **all landed**, so no contract method is stubbed. Bitbucket **Cloud** only (`https://api.bitbucket.org/2.0`); Server / Data Center is out of scope. It mirrors the GitHub folder's file shapes (`client.ts`, `credentials.ts`, `personas.ts`, `webhook.ts`, `scm-integration.ts`, `index.ts`) rather than inventing a layout, and adds no npm dependency. Three files have no GitHub counterpart, because Octokit supplies for GitHub what they supply here: `pull-requests.ts` holds the endpoint-shaped reads that GitHub keeps in `client.ts` alongside its transport, `writes.ts` the write half of the same, and `commits.ts` the commit vocabulary — the abbreviated-hash spelling, the same-commit compare, and the build-status state table — that ingress, the reads, and the merge recheck must not spell three different ways.

- **Phase 1/4 (landed): the credential-scoped foundation.** `client.ts` binds the **credential string** (not a client object — Bitbucket has no Octokit) to the async context via `AsyncLocalStorage` (`withBitbucketCredential`), builds each request over the global `fetch`, throws `BitbucketApiError` carrying a `status` that mirrors Octokit's `RequestError#status` (so phase 4's merge classifier reads it the same way), follows the `next` cursor in `paginateBitbucket` (rejecting off-origin or non-HTTPS cursors and capping total pages at `MAX_PAGES`) and refuses a cyclic one, and resolves an account login (`nickname`, returning `null` when no nickname is exposed so persona resolution fails closed) for loop prevention. It is the only place that branches on the credential's *form*: a `username:app_password` pair goes out as HTTP Basic (the one form that can answer `GET /2.0/user`), anything else as a bearer token. `credentials.ts` resolves the implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN` and the reviewer from Bitbucket's **own** per-provider reference, `credentials.scm.bitbucket.reviewer` (issue #628; through phases 1–4 it read the then-shared provider-neutral `credentials.reviewer`) — deliberately *not* by widening `getPersonaToken` (`src/config/provider.ts`), whose implementer branch returns the *GitHub* operator token and whose reviewer branch resolves GitHub's reference. `project.repo` (`owner/repo`) doubles as Bitbucket's `workspace/repo_slug`, so no repo-coordinates field was added. `personas.ts` caches both persona identities per project with the same 60s TTL, fails closed when either can't be resolved, and matches logins case-insensitively (a Bitbucket `nickname` has no canonical case) with no `[bot]`-suffix handling — that suffix is a GitHub App artifact.
- **Phase 2/4 (landed): webhook ingress** (`webhook.ts`, issue #455). Signature verification frames Bitbucket's `X-Hub-Signature` as `sha256=<hex>` over the raw body and delegates the constant-time compare to the shared `verifyHmac` (`src/webhook/signature-verification.ts`); it **fails closed**, since Bitbucket omits the header entirely for a hook configured without a secret. Header reading takes the event from `X-Event-Key` and the dedup identity from `X-Request-UUID` — not `X-Hook-UUID`, which names the hook configuration, so every delivery from one hook would collapse into one job. Parsing maps `X-Event-Key` onto the neutral `ScmEvent`: four `pullrequest:*` keys fan in to `pull-request` (with `merged` read off the key — Bitbucket splits merge into `fulfilled` and decline into `rejected`), the four approval / changes-request keys to `pull-request-review`, `pullrequest:comment_created` to `work-item-comment`, and the two `repo:commit_status_*` keys to `checks`; every other key returns `null` (acknowledge-and-drop). Two provider gaps are handled explicitly rather than papered over: Bitbucket has **no review object**, so `reviewId` is *synthesized* as `<prId>:<reviewState>:<accountUuid>:<headSha>` — a format the review-verdict ledger and its two-verdict cap (issue #235) key on, so it must stay stable across deliveries, which is why it prefers the immutable account `uuid` over a renameable `nickname`; and a `commit_status` payload carries **no PR association at all** (unlike GitHub's `check_suite.pull_requests`), so `workItemId`/`prBranch` stay unset pending the commit→PR lookup, which is a credential-scoped call and so belongs to whichever ingress layer serves this provider's route rather than to the pure parse. It also records the **abbreviated-hash invariant** (now owned by `commits.ts`, shared with the reads): a PR payload's `source.commit.hash` is 12 characters while a build status's `links.commit.href` ends in the full 40, but the adapter narrows both to Bitbucket's canonical 12-character spelling for every `headSha`. Shared exact-match consumers — the review-dispatch dedup key (`src/triggers/review-dispatch-dedup.ts`) and the `reviewVerdicts.headSha` SQL predicate (`src/db/repositories/reviewVerdictsRepository.ts`) — therefore never see two spellings for one commit. Every API read narrows its SHAs the same way; the merge-eligibility recheck compares prefix-tolerantly anyway (`sameBitbucketCommit`), because its `approvedHeadSha` comes from a *caller* and need not have been narrowed by this adapter. Loop prevention reuses the provider-neutral SWARM-origin test (`src/scm/swarm-origin.ts`) unchanged: the markers travel in the comment body, so they read the same whichever provider delivered it.
- **Phase 3/4 (landed): pull-request and build-status reads** (`pull-requests.ts`, issue #456). Each read mirrors a GitHub one so the two adapters' surfaces line up, runs under the persona the caller scoped (`getPullRequest` and the aggregate check status default to the reviewer, the title read and conflict candidates to the implementer — GitHub's defaults for the same operations), paginates fully through `paginateBitbucket`, and lets a `BitbucketApiError` propagate rather than swallowing a 404 into "no conflicts" or "CI is green". Four mappings carry the provider's differences from GitHub:
  - **`mergeable` is always `null`.** Bitbucket Cloud exposes no mergeability flag at all, so there is nothing to report and deriving one would take a diff or a merge dry-run (a possible follow-up, not this phase). `null` is the contract's "not known yet", and `src/triggers/handlers/resolve-conflicts.ts` answers it by scheduling a bounded recheck — so a Bitbucket conflict candidate exhausts its rechecks and is dropped rather than ever being mislabelled cleanly mergeable. That is the deliberate cost of this phase: the Bitbucket conflict side-car never decides.
  - **One `state` field stands in for GitHub's `state` + `merged` + reviews.** `MERGED` is the only state that merged and everything but `OPEN` (`MERGED`, `DECLINED`, `SUPERSEDED`) is closed; approvals come from `participants[]` (`approved` / `changes_requested`, mapped to GitHub's uppercase spelling so phase 4's recheck reads identically for both providers). Bitbucket pins a participant's verdict to **no commit**, so each returned verdict carries the PR's *current* head SHA — exactly right only when the repository enables "reset approvals on new commit", which is where Bitbucket gets the head-change protection GitHub reads off a review's own `commit_id`.
  - **Build statuses aggregate like check runs, deduped by `key`** keeping the newest `updated_on` — the same rationale as GitHub's dedupe by `workflow_id`: a re-run reports under the same key, and letting its stale failure into the aggregate would make a green commit look failed. A single `state` splits into the neutral `status`/`conclusion` pair, and an *unrecognized* state is deliberately non-terminal so the aggregate decision defers and re-reads rather than judging a build it doesn't understand.
  - **Conflict candidates filter server-side** through Bitbucket's query language (`q=state="OPEN" AND destination.branch.name="…"`, with quotes in the branch name escaped so the literal can't be broken out of), then drop forks the way GitHub's equivalent does — a cross-repository PR's head branch doesn't exist here, so SWARM cannot push a resolution to it.
- **Phase 4/4 (landed): the writes** (`writes.ts` + the class's own merge/delivery, issue #457). Three provider gaps shape all of it:
  - **The delivery marker is the only idempotency anchor**, because Bitbucket has no review object. GitHub's `pulls.createReview` submits body + verdict atomically and returns a review id; Bitbucket splits them into a comment and a separate `approve` / `request-changes` POST, neither of which yields anything durable. So the shared per-delivery marker (`deliveryMarker`, `src/scm/swarm-origin.ts` — extracted there from the GitHub client so both providers cannot drift) travels in the comment body, that comment's id *is* the neutral review id, and every delivery write scans for the marker before posting. The verdict is applied **before** the comment on purpose: the marker is what a retry matches on, so it must be written last — a crash between the two then leaves no marker and the retry re-applies a verdict that is idempotent by construction (Bitbucket records a standing participant state, not an event), whereas the opposite order would strand a marked comment whose verdict never landed.
  - **The merge endpoint takes no expected-head parameter.** GitHub pins its merge to the approved SHA and gets a stale-head refusal from the API; Bitbucket cannot, so `mergeReadyBitbucketPullRequest` *is* the protection: re-read state on every attempt (already merged → `merged`; head moved, draft, or not open → `not-eligible`; a standing `changes_requested`, or no approval at the approved head → `not-eligible`), then merge. Head comparison is prefix-tolerant with a 12-character floor (`sameBitbucketCommit`), so a caller's full 40-character SHA and this adapter's abbreviated spelling are one commit while a truncated value fails closed. The classifier maps 409/555 → `not-ready`, 403 and a named merge-check refusal → `policy-blocked`, everything else → `provider-error`; nothing maps to `unsupported`, since Bitbucket Cloud has no merge-queue analogue — the case GitHub reserves it for. `mergePullRequest` never throws, credential resolution included.
  - **Commit attribution needs an email Bitbucket may not disclose.** `deliveryProvider` names the commit author by `nickname` (there is no `username`). It requires a `username:app_password` credential, because workspace/repository access tokens cannot resolve `GET /2.0/user` and fail identity resolution before the email lookup. An app password without the `email` scope falls back to `<nickname>@users.noreply.bitbucket.org` so a delivery still commits. The cost is explicit: Bitbucket links a commit to an account by matching a **confirmed** account email, so a placeholder commit shows the right name but stays unattributed. `pushBranch` keeps GitHub's shape — `git push --no-verify <url> <expectedSha>:refs/heads/<branch>` with the credential in a `GIT_CONFIG_*` extraheader rather than argv — against `https://bitbucket.org/<workspace>/<slug>.git`, framed as Basic (`x-token-auth:<token>`, or the app-password pair as-is; `client.ts` stays the only place that branches on the credential's form).
- **Reachable since issue #618.** `BitbucketSCMIntegration implements SCMProvider` with no method stubbed — the multi-provider conformance suite (`tests/unit/integrations/scm/scm-conformance.test.ts`, landed with phase 4/4 per `ai/TESTING.md`) asserts that for every registered manifest, including that no method's source still carries the not-implemented sentinel. #618 supplied the wiring that was left: the manifest declares `runtimeReady: true` (`src/integrations/scm/manifest.ts`), so `requireProjectSCMProvider` routes a project that states `"scm": "bitbucket"` here and the receiver mounts `/bitbucket/webhook` from its ordinary per-manifest loop — **a Bitbucket project runs end to end.** Two shared pieces landed with it rather than as Bitbucket specials:
  - **`SCMProvider.listPullRequestsForCommit`, the commit→PR seam.** A `commit_status` payload names no pull request at all, so a `checks` event arrives with no `workItemId`/`prBranch` and the Review trigger would drop it. The receiver completes it after authentication and loop prevention by asking the *contract* which pull requests the commit belongs to and adopting the first **open** one — never `listBitbucketPullRequestsForCommit` directly (`ai/RULES.md` §2: widen the interface). GitHub implements it over `repos.listPullRequestsAssociatedWithCommit` and GitLab over `commits/:sha/merge_requests`, each normalizing its own state vocabulary to the neutral `open`/`closed`; GitHub's ingress never calls it, since `check_suite` already names its pull requests. It **fails open**: a lookup error logs and enqueues the event unresolved (matching no trigger) rather than 500-ing a delivery no provider redelivers on its own, and the commit's next CI event retries.
  - **The registry's "zero or two-plus runtime-ready" throw became reachable.** A project naming no `scm` no longer resolves the sole runtime-ready provider, so every project must state one; see `ai/RULES.md` §2 and the migration note in `docs/status.md`.

### SCM: GitLab (`src/integrations/scm/gitlab/`) — complete and runtime-reachable (issues #295, #619)

The runtime wiring and its HTTP boundaries are unit-verified against the real registered manifest, but a real gitlab.com project has not yet been exercised end to end — the same gap the Bitbucket section records. In particular the commit→merge-request read is mocked in tests; production verification must confirm gitlab.com answers `commits/:sha/merge_requests` for a branch pipeline's commit under the reviewer token's scope.

The third SCM provider, built out over four ordered phases along the same seams Bitbucket used. GitLab**.com** only (`https://gitlab.com/api/v4`); a self-managed host would need a base-URL config field this phase does not add, and GitLab **subgroup** paths stay out of scope because `ProjectConfig.repo` is validated as exactly two segments. REST v4 throughout — every operation SWARM needs exists there, so no GraphQL client is built. It mirrors the Bitbucket folder's file shapes (`client.ts`, `credentials.ts`, `personas.ts`, `scm-integration.ts`) and adds no npm dependency.

- **Phase 1/4 (landed): the credential-scoped foundation.** `client.ts` binds the **token string** to the async context via `AsyncLocalStorage` (`withGitLabToken`), builds each request over the global `fetch`, and throws `GitLabApiError` carrying a `status` that mirrors Octokit's `RequestError#status` and `BitbucketApiError#status`, so phase 4's merge classifier reads it the same way. Two deliberate divergences from Bitbucket's client: there is **no credential-form branch** — a personal, group, or project access token all go out in the `PRIVATE-TOKEN` header and all resolve `GET /user`, so Bitbucket's `Basic`/`Bearer` fork has no analogue here and must not be reintroduced; and `paginateGitLab` walks GitLab's **offset** pagination (`per_page` + the `x-next-page` response header) rather than following a server-supplied URL. That changes which guards apply: Bitbucket asserts same-origin and HTTPS on every `next` cursor it follows, while GitLab's cursor is a page *number* appended to a URL built from a constant base, so no off-origin link is reachable and the equivalent "don't trust the server's cursor" guard is a numeric-format check — alongside the same `MAX_PAGES` bound and cycle detection, since a server that keeps pointing at a page it already served is the failure mode those exist for. `projectPath()` URL-encodes `ProjectConfig.repo` whole (GitLab addresses a project by its `namespace/project` path), so unlike Bitbucket there is no `workspace`/`slug` pair to split. `credentials.ts` resolves the implementer from a worker-local `SWARM_OPERATOR_GITLAB_TOKEN` and the reviewer from GitLab's **own** per-provider reference, `credentials.scm.gitlab.reviewer` (issue #628; through phases 1–4 it read the then-shared provider-neutral `credentials.reviewer`) — deliberately *not* by widening `getPersonaToken` (`src/config/provider.ts`), whose implementer branch returns the *GitHub* operator token and whose reviewer branch resolves GitHub's reference. `personas.ts` caches both persona identities per project with the same 60s TTL, fails closed when either can't be resolved, and matches case-insensitively; identities are always the GitLab `username`, the same field merge-request / note / pipeline webhook payloads carry as `user.username`, and there is no `[bot]`-suffix handling because that suffix is a GitHub App artifact.
- **Phase 2/4 (landed): webhook ingress.** `webhook.ts` owns the whole inbound half, keeping every scrap of GitLab webhook vocabulary inside the folder. Headers: `X-Gitlab-Event` names the event (`'unknown'` when absent, so an unrecognized POST is acknowledged rather than crashing the receiver), `X-Gitlab-Event-UUID` is the dedup identity — deliberately the **per-delivery** id, not the per-*configuration* `X-Gitlab-Webhook-UUID`, which every delivery from one hook would share and the durable queue would then collapse into a single job (the same trap Bitbucket's `X-Hook-UUID` documents) — and `X-Gitlab-Token` carries the secret. **Authentication is a shared token, not an HMAC:** GitLab echoes the operator-chosen webhook secret verbatim (`credentials.scm.gitlab.webhookSecret` since issue #628), so `verifyGitLabWebhookToken` is a constant-time comparison (`node:crypto`'s `timingSafeEqual`, gated on equal byte length) that fails closed on an absent, empty, or mismatched token. `verifyHmac` is not reusable — there is no digest to compute — and the consequence is explicit: this authenticates the *sender*, not the body's integrity in transit. GitLab 19.0's Standard-Webhooks signing tokens (`webhook-signature: v1,<base64>` over `${webhook-id}.${webhook-timestamp}.${body}`) would close that gap, but the signed message needs headers `SCMProvider.verifyWebhookSignature(rawBody, signature, secret)` never sees — so adopting it still means widening the contract, recorded as a follow-up rather than built alongside the token path. Its *other* blocker is gone: a GitLab-minted `whsec_…` key could not be the operator-chosen secret the same project's GitHub Projects PM webhook shared, and issue #628 made that secret per provider. Normalization gates on the header-supplied event name and cross-checks the body's `object_kind` before reading any payload path: merge-request lifecycle (`open`/`reopen` → `opened`, `update` → `updated`, `close`/`merge` → `closed`), approval/withdrawal (`approval`/`approved` → `submitted` + `approved`; `unapproval`/`unapproved` → `dismissed`, which keeps a withdrawal out of the Respond-to-review trigger), merge-request notes → `work-item-comment`, and pipelines → `checks`, `completed` only once the status is terminal so a running pipeline enqueues but wakes no review. Everything else returns `null`, system notes and notes on non-merge-request targets included. Three provider-specific holes are handled rather than guessed: GitLab exposes **no review object**, so `reviewId` is synthesized as `<iid>:<verdict>:<user id>:<head SHA>` — a composition the issue-#235 verdict ledger keys on, so it must stay stable, and it prefers the numeric `user.id` over the renameable `username`; GitLab has **no "request changes" action** (its vocabulary is `open`/`close`/`reopen`/`update`/`approval`/`approved`/`unapproval`/`unapproved`/`merge`, verified against GitLab 19.1's webhook reference), so that verdict is derived from the *acting* reviewer's own `reviewers[].state === 'requested_changes'` — keyed on the acting user precisely so the implementer's push doesn't re-cast a standing verdict, at the documented cost that a later `update` by that same reviewer reads as the same verdict again; and a **branch** pipeline carries no `merge_request` at all, so `workItemId`/`prBranch` stay unset for phase 3's credential-scoped commit→merge-request lookup, exactly as Bitbucket's commit statuses do. `pipelines.ts` holds the status vocabulary (`success` → `success`, `failed` → `failure`, `canceled` → `cancelled`, `skipped` → `skipped`; terminal set the same four) so an event and phase 3's aggregate read cannot spell one pipeline two ways — and an *unrecognized* status is deliberately non-terminal, so `aggregate-check-decision.ts` defers and re-reads. It is the counterpart of `bitbucket/commits.ts` minus the abbreviation invariant: GitLab reports full 40-character SHAs everywhere, so `abbreviateBitbucketSha` has no analogue here and must not be ported.
- **Phase 3/4 (landed): the merge-request and commit-status reads.** `merge-requests.ts` is the endpoint-shaped caller of the phase-1 client, mirroring `bitbucket/pull-requests.ts` file for file: one narrow `interface` per response shape, a private `toPullRequestDetails` that throws on a missing load-bearing field, and a documented persona default per contract method (`getPullRequest` → reviewer, `getPullRequestTitle` → implementer, `getAggregateCheckStatus` → reviewer, `listConflictCandidates` → implementer). Four provider facts shape it:
  - **`mergeable` is real here**, unlike Bitbucket's permanent `null`, so the conflict-resolution side-car actually decides for GitLab. `merge_status` is preferred (`can_be_merged`/`cannot_be_merged`/`checking`/`unchecked`) precisely because it is the *git-only* signal — which is what the contract's `mergeable` means — even though GitLab deprecated it in 15.6; `detailed_merge_status` is the documented fallback for an undocumented internal value (`cannot_be_merged_recheck`) and for `merge_status` eventually disappearing. Collapsing the detailed field needs one decision stated once: `mergeable` → `true`, `conflict`/`commits_status` (the current spelling of `broken_status`) → `false`, `checking`/`preparing`/`unchecked` → `null`, and **every other blocker** (`not_approved`, `ci_still_running`, `discussions_not_resolved`, `draft_status`, `need_rebase`, `requested_changes`, anything GitLab adds later) → `true`, because answering `false` for a policy blocker would send the trigger to rewrite a branch that has no conflict.
  - **`baseSha` is `diff_refs.base_sha`, the merge base** — not the target-branch tip GitHub's `base.sha` reports. That is the value the conflict-resolution claim key wants (`buildConflictResolutionKey`, `src/triggers/resolve-conflicts-dedup.ts`): stable per (head, base) pair, so one claim covers one genuine conflict state instead of a fresh one per unrelated push to the target. It is also populated *asynchronously* after a merge request is created, which is one of the cases the mapper throws on rather than substituting a stand-in — `headSha`/`baseSha` are exact-match key material, so a stand-in would key a claim on the wrong commit.
  - **Conflict candidates cost one extra read each.** The listing filters server-side (`state=opened&target_branch=`) and drops forks (`source_project_id !== target_project_id`) as GitHub's and Bitbucket's do, then re-reads every survivor individually — because GitLab's *list* response omits `diff_refs` entirely and reports whatever `merge_status` was last cached, while reading a *single* merge request is itself what asks GitLab to recompute mergeability. Mapping list entries directly would yield candidates with no merge base and a stale `mergeable`, and would make the trigger's bounded recheck re-read the same cached answer 20 times instead of converging.
  - **Commit statuses reuse `pipelines.ts` unchanged**, since GitLab spells a commit status's `status` with the same vocabulary a pipeline reports — so no second spelling was introduced and an event and an API read of one pipeline still agree. Deduped by `name` keeping the newest `finished_at ?? created_at` (a re-run reports under the same name, and its stale failure would make a green commit look failed), with non-terminal and unrecognized statuses mapping to `in_progress`/`null` so the aggregate defers. `totalCount` is the deduped count. Two reads exist for phase 4's merge-eligibility recheck rather than for a caller of their own — the merge state (which also carries `changesRequested`, derived from `detailed_merge_status`, because that is the only place one merge-request read exposes a reviewer's blocking verdict) and the standing approvals (`approved_by[]` → GitHub's `APPROVED` spelling; GitLab pins an approval to no commit and the approvals entity carries no SHA at all, so each verdict carries the merge request's *current* head and is only exactly right when the project resets approvals on new commits, the same caveat Bitbucket's participant read documents; approvals are Free, approval *rules* are Premium, and a changes-requested verdict lives on `reviewers[].state`, not here) — plus the commit→merge-request lookup that closes phase 2's branch-pipeline hole and the source-branch find the delivery seam reuses its own pull request through.
- **Conflict reads are refreshed but bounded.** The list request uses GitLab's `with_merge_status_recheck=true` parameter, then the required single-merge-request reads run in batches of ten: the list response still omits `diff_refs`, so it cannot provide the merge base even when its merge status is refreshed.
- **Advisory statuses are visible but non-blocking.** A deduped status with `allow_failure: true`, including an optional manual job, maps to `completed`/`skipped` regardless of its raw status. GitLab ignores those jobs in its pipeline result, so they must neither fail nor defer SWARM's aggregate; retaining them rather than dropping them makes an all-advisory pipeline reviewable under the normal required-check policy.
- **Phase 4/4 (landed): the writes** (`writes.ts` + `operator-delivery.ts` + the class's own merge/delivery, issue #485). GitLab sits between the other two providers on every gap that shaped Bitbucket's writes:
  - **The delivery marker is the only idempotency anchor**, exactly as on Bitbucket and for the same reason: GitLab has **no review object** either. The shared per-delivery marker (`deliveryMarker`, `src/scm/swarm-origin.ts`) travels in the note body, that note's id *is* the neutral review id, and every delivery write scans for the marker before posting. The scan skips `system: true` notes — GitLab files its own activity entries into the same listing, one of which quotes the note it describes, so treating one as this delivery's write would return an id SWARM never created and leave the real body unposted. The verdict is applied **before** the note for Bitbucket's documented reason (the marker is the retry anchor, so it must be written last).
  - **A redundant verdict is refused rather than absorbed**, which is where GitLab differs from Bitbucket's standing participant state: `approve` answers 401 for an account that has already approved and `unapprove` answers 404 when there is nothing to withdraw — precisely the state a retry re-enters after the verdict landed and the note POST did not. `writes.ts` tolerates exactly those two statuses (the marker scan already proved the token can read the merge request, so neither can mean a dead credential), which is what makes the marker-last ordering safe here at all.
  - **There is no REST "request changes".** A reviewer's `requested_changes` state is UI/GraphQL-only on GitLab 19.1's REST surface, so `request-changes` is `unapprove` plus the findings note: the verdict lives in the *absence* of an approval. The cost is explicit — GitLab's own blocking reviewer badge is not set — and the merge-eligibility recheck compensates by reading a *human's* standing `requested_changes` off `detailed_merge_status` and reporting it as `not-eligible` rather than the `not-ready` GitLab's own 405 would produce, since a reviewer decision does not clear on its own.
  - **The merge is pinned like GitHub's, not blind like Bitbucket's.** `PUT .../merge` takes `sha`, so `mergeGitLabMergeRequestDirect` passes `approvedHeadSha` and gets a 409 rather than merging a commit nobody reviewed; the pre-merge recheck (already merged → `merged`; moved head, draft, not open, changes requested → `not-eligible`; no standing approval at the reviewed head → `not-eligible`) is defence in depth *and* what turns GitLab's single undifferentiated 405 into the specific terminal outcomes the dispatch needs. Head comparison is exact — GitLab reports full 40-character SHAs, so Bitbucket's prefix tolerance has no analogue. Three omissions from the request body: no merge method or `squash` (the project's default wins), no commit message (GitLab composes one from the merge request, and a squashing project reads `squash_commit_message` instead — naming one would produce a SWARM-written subject on some projects only), and `should_remove_source_branch: false` because the worktree lifecycle owns the branch. Nothing maps to `unsupported`: merge trains, the configuration that would earn it, refuse with 405 until the required pipeline is green and then accept the direct merge, so retrying is correct rather than declaring the merge impossible. `mergePullRequest` never throws, token resolution included.
  - **Commit attribution needs one request, not two.** `GET /user` returns `username` and `email` together (`getScopedGitLabUser`), where Bitbucket needs a second call to `/user/emails`. A token whose scope withholds the email — and a project/group access token's bot user, which has none — falls back to `<username>@users.noreply.gitlab.com`, with the same cost Bitbucket documents: GitLab links a commit by matching a **verified** account email, so the placeholder keeps the name and leaves the commit unlinked. `pushBranch` keeps the shared shape — `git push --no-verify <url> <expectedSha>:refs/heads/<branch>` with the credential in a `GIT_CONFIG_*` extraheader rather than argv — against `https://gitlab.com/<repo>.git`, framed as Basic under GitLab's reserved `oauth2` user; there is no credential-form branch to make, since every token form authenticates that way.
- **Reachable since issue #619.** `GitLabSCMIntegration implements SCMProvider` with no method stubbed, which is what let `gitlab/index.ts` register at all: the conformance suite (`tests/unit/integrations/scm/scm-conformance.test.ts`) asserts that no *registered* manifest stubs a contract method, and `ai/TESTING.md` frames that as the gate on the third provider — so registering earlier would have forced an exemption that disabled the gate for both providers already passing it, and registration deliberately landed with the last stub's removal. #619 supplied the wiring that was left, exactly as #618 did for Bitbucket: the manifest declares `runtimeReady: true`, so `requireProjectSCMProvider` routes a project that states `"scm": "gitlab"` here and the receiver mounts `/gitlab/webhook` from its ordinary per-manifest loop — **a GitLab project runs end to end.** Nothing shared had to be built for it: `listPullRequestsForCommit` landed with #618, so a **branch** pipeline (which names no merge request at all) has its `workItemId`/`prBranch` filled by the receiver's neutral commit→merge-request read, and a *merge-request* pipeline skips that read because the payload already names one.
  - **The webhook trade-off #619 accepted, rather than deferring again.** Serving the route makes GitLab's sender-only authentication live: `X-Gitlab-Token` is the operator-chosen secret echoed verbatim, so unlike GitHub's and Bitbucket's HMAC it says nothing about the body's integrity in transit. Judged acceptable — GitLab's own mechanism, failing closed on an absent/empty/mismatched token and comparing in constant time, and an attacker able to tamper with or replay a delivery has already broken the TLS the secret itself travels under. GitLab 19.0's Standard-Webhooks signing tokens remain the recorded follow-up (they need `verifyWebhookSignature` widened for the `webhook-id`/`webhook-timestamp` headers it never sees *and* a per-provider secret reference). The decision is recorded at the flag itself, in `gitlab/index.ts`.
  - **Operator configuration came with it.** The dashboard's Source Control tab and project-create dialog offer GitLab (`SCM_PROVIDERS`, `dashboard/src/lib/credentials.ts`) and write `project.scm`, and `scm.verifyGitLabToken` (`src/api/routers/scm.ts`) checks a pasted token against the account it resolves to — one procedure per provider, since there is no project yet to resolve a `SCMProvider` from. Its credentials became the tab's own since issue #632 (see "Per-provider SCM credentials" above): selecting GitLab shows GitLab's references under GitLab's labels — a reviewer *access token* and the *secret token* it echoes back — rather than one shared pair under GitHub's vocabulary. Still deferred, explicitly: any webhook-registration automation — the GitLab project hook is created by hand.

### PM: GitHub Projects (`src/integrations/pm/github-projects/`) — net-new, no Cascade equivalent

GitHub Projects (v2) is GraphQL-only; there is no REST equivalent for reading/writing item fields. Shape the provider around:

- **Work item** = a Projects v2 item (usually backed by an Issue or PR in the repo).
- **Status** = the item's single-select "Status" custom field — moving a task through the pipeline (Backlog → Planning → In Progress → In Review → Done) means updating that field's option value via `updateProjectV2ItemFieldValue`.
- **Events** = the `projects_v2_item` webhook event (`created`, `edited`, `reordered`, `deleted`), filtered to status-field edits — this is the equivalent of Cascade's `pm:status-changed` trigger. It is **never** a repo-level event: GitHub delivers it on an **organization** webhook or to a **GitHub App** with the Projects permission (there is no plain user-account webhook). For SWARM's user-owned board the App route is effectively the only option — see `docs/github-projects-v2-api.md` §5. Those raw action names and payload paths stop at the adapter: shared code sees only the normalized `PmEvent` (below).
- **Comments** = GitHub Projects items don't have their own comment thread; write agent output (e.g. Antigravity's plan) as a comment on the linked Issue/PR, not as a Projects-native comment.
- **Assignees** = the backing Issue/PR's assignees, read in the same round-trip as the item and mapped to the provider-neutral `WorkItemAssignee` (`handle`/`displayName`/`providerId`) on every `WorkItem` — GitHub's `login` vocabulary stops at the adapter. `assignees` is always present (`[]` when nobody is assigned), and the capability flag `PMProvider.supportsAssignees` lets a provider with no assignee concept opt out explicitly, exactly like `supportsDependencies`. SWARM resolves a handle to one of its own users through the identity-linking seam (below), never by pattern-matching a GitHub identity.
- **Repository routing** = the card's own backing Issue/PR (issue #686). `resolveItemRepository` reads `repository { nameWithOwner }` out of the item read it already makes and compares it to the project's repository entries through the shared `repoSlugsMatch` (`src/scm/repo-slug.ts`). This is the one provider that needs no `pmRoutingToken` and ignores the field: a card wraps at most one Issue/PR, which lives in exactly one repository, so it can never answer `ambiguous` — only `routed` or, for a draft card or a repository the project does not own, `unrouted`.

Credentials are the provider's own: since issue #537 board work authenticates with the project-scoped `apiToken` role this provider declares (`credentials.pm['github-projects']`, per provider since issue #631), never with an SCM persona (see the credential-roles bullets below).

It is implemented against the provider-neutral `PMProvider` interface (`src/pm/types.ts`, mirroring Cascade's file of the same name and trimmed to what SWARM's pipeline actually performs) so the router/trigger/dispatch code stays provider-agnostic. That surface is now settled, and it is what a second provider owes: fifteen methods — the board reads (`getWorkItem`, `listWorkItems`, `findWorkItemByUrlSuffix`, `findWorkItemForArtifact`, `findWorkItemByDescriptionMarker`), the writes (`moveWorkItem`, `addComment`, `findComment`, `createWorkItem`, `updateWorkItem`, `addLabel`), the dependency gate (`listBlockers`, `listDependents` — the native-only reverse edge, issue #639 — and `addBlockedBy`), and repository routing (`resolveItemRepository`, issue #686 — which of the project's repositories a card belongs to, answered from each provider's own axis and returning `routed | unrouted | ambiguous`; the candidate repositories are an *argument* rather than config, because a provider is built from a repository-scoped project config that carries no list) — plus two capability flags a provider without the concept opts out with (`supportsAssignees`, `supportsDependencies`) and one *optional* method, `discover`, declared per provider on the manifest rather than required of everyone. Its inbound twin is the five-method `PMRouterAdapter` (below).

- **One-card lookups are lookups, not scans (issue #735).** `findWorkItemByUrlSuffix`, `findWorkItemForArtifact` and `findWorkItemByDescriptionMarker` are wider than `listWorkItems` for one reason — so that nothing has to read a whole board to answer a one-card question, least of all a federated worker proxying that board through the control plane (`src/pm/transport-delivery.ts`). That is a **cost** contract as much as a signature, and it was honoured at the surface and given back inside every implementation: all three GitHub Projects lookups, plus one apiece on Linear, Jira and Trello, answered by calling `listWorkItems()` and filtering. Measured on the live 325-card board, one such lookup cost **four GraphQL requests and eight rate-limit points**, several times per run, until the board credential's hourly budget ran out and a day's dispatches went with it — a Planning run failed terminally on `pm/find-comment`, a Status-change dispatch produced no phase, and the failure comments that would have recorded it could not be posted either. Each provider now addresses its backend with the key it was handed: GitHub Projects resolves the Issue/PR by `repository` + `number` and walks to *its* project items (**one request, one point**, board size irrelevant), and answers a marker from the project repository's newest issue bodies — a consistent listing rather than the eventually-consistent search index Planning's retried split cannot use. Linear parses its own `/issue/<KEY>` grammar and filters by number within the team; Jira parses `/browse/<KEY>` and reads that issue; Trello parses `/c/<shortLink>` and reads that card. A suffix a provider's URLs could never produce is answered `undefined` **without a request at all**, which is how a GitHub-shaped `/issues/<n>` stays the honest miss it already was on the other three boards. Where a provider genuinely has no index it says so in its own module instead of scanning silently — Jira's remote-link scan already did, and Trello's two (attachments and descriptions are indexed by nothing it can query) now do, both bounded and logged when the bound bites. `tests/unit/integrations/pm/pm-conformance.test.ts` holds the floor for the next provider: no registered provider's one-card lookup may call `listWorkItems`. The dashboard's two "which card backs this PR?" reads went the same way (`src/api/routers/runs.ts`).

- **Neutral ingress + registry-resolved provider (issue #297).** The PM side now has the same two-part shape the SCM side got from #385: `PMProvider` (`src/pm/types.ts`) is the *outbound* contract, and **`PMRouterAdapter`** (`src/pm/router-adapter.ts`) is the *inbound* one — `parseWebhook` (raw body → normalized event), `resolveProject` (by the board's container id, since a board event carries no repo), `isStatusChange` (the state-field filter, which compares the event's opaque `changedField` against the provider's own board mapping so no shared code reads the provider's own `statusFieldId`), `isSelfAuthored` (loop prevention), and `synthesizeStateChange` (the synthetic event the worker's auto-advance self-enqueue needs — see `selfEnqueueNextPhase` below). `PMProviderManifest.routerAdapter` is typed to that interface, and `src/integrations/pm/index.ts` is the category barrel. The normalized event is **`PmEvent`** (`src/pm/events.ts`) — a Zod schema, because it is also the durable queue payload — carrying `itemId`, `containerId`, a neutral `action` (`created` | `updated` | `moved` | `deleted`, with anything else riding through verbatim and matching no trigger), and the opaque `changedField`/`contentId`/`actorHandle`. It has **no `kind` discriminator**: PM has exactly one ingress concept today ("a board item changed"), so a provider bringing a genuinely different one adds the discriminator then. The durable envelope is `{ type: 'pm', providerId, event }`, and `SwarmJobSchema` still reads the pre-#297 `{ type: 'github-projects', event: { eventType: 'projects_v2_item', itemNodeId, … } }` rows a deploy's in-flight dispatches and historical `runs.jobPayload` snapshots carry, upgrading them in place.
- **One route per registered PM manifest, co-tenanting a shared path (issue #496).** `PMProviderManifest` declares its own `webhookRoute` and `verifyWebhookSignature`, and `src/router/webhook-receiver.ts` mounts routes from `listPMProviders()` — it names no provider and no longer imports `PROJECTS_V2_ITEM_EVENT`. GitHub Projects declares the shared `/github/webhook` path, which is the interesting case: GitHub delivers `projects_v2_item` to the same URL with the same secret as the repo's own events (`docs/github-projects-v2-api.md` §5), so mounting a second POST handler on that path would leave Hono with a shadowed handler that never runs. The rule instead: runtime-ready SCM manifests mount first; a PM manifest whose route is one of theirs becomes a **co-tenant** of that handler, which offers the raw `(eventName, payload)` to each co-tenant's `parseWebhook` before SCM parsing and lets the first non-null result take the request down the PM path (`parseWebhook` already answers `null` for anything that isn't its own event — the neutral form of the old hardcoded branch); a PM manifest whose route nothing else serves mounts its own GET ping + POST pair exactly as the SCM loop does. Authentication is the manifest's own `verifyWebhookSignature(PmWebhookVerification)`, deliberately wider than the SCM triple so no planned provider forces a later change: it takes the raw body, a header reader (each provider names its own signature header), `secret: string | null`, and **SWARM's own public callback URL** for the route, because Trello signs `HMAC(rawBody + callbackUrl)`. That URL comes from the `WEBHOOK_CALLBACK_BASE_URL` general setting, falling back to the request's `Host` + `X-Forwarded-Proto` with a warning naming the setting when neither is available (`src/router/webhook-callback-url.ts`, ported from Cascade's `buildTrelloCallbackUrl`). GitHub Projects' verifier delegates to the GitHub SCM provider's existing HMAC check — the shared-secret reality, the same deliberate reach `isSelfAuthored` makes — and fails closed when the project has no secret, since an absent secret is not an empty key.
- **Project→provider selection is a plain lookup.** `requireProjectPMProvider(project)` / `requireProjectPMAdapter(project)` (`src/integrations/pm/registry.ts`) resolve `getPMProvider(project.pm.type)` and throw a wiring-bug error on a miss. The SCM side selects the same way since issue #478 (`project.scm`), with one extra step this side does not have: an SCM manifest must also be `runtimeReady`, because an SCM provider needs a served ingress route before it can carry traffic, so there is no such flag on a PM manifest. Every project-scoped PM call site resolves through those two — the PM-driven triggers, the worker's phase provider and board comments, and the router's server-side delivery default — so no pipeline, worker, or router module constructs `createGitHubProjectsProvider` anymore.
- **Shared code speaks canonical status keys, not board option ids.** `WorkItem.statusKey` carries the canonical `PM_STATUS_KEYS` value (`src/pm/pipeline.ts`) the provider resolved from its own opaque native status on the way out of every board read, so a pipeline phase is resolved with `resolvePipelinePhaseForStatusKey(workItem.statusKey)` rather than by inverting the board mapping's `statusOptions` at the call site. It is a field, not a new `PMProvider` method — the provider already has its mapping in hand during the read. It rides the transport's `AssignedWorkItem` frame too, so a federated assignment carries it.
- **`PMType` names four providers, and every one of them now resolves.** `'github-projects' | 'jira' | 'linear' | 'trello'` — widened exactly as `ScmType` named `bitbucket`/`gitlab` before either registered, so a connector's own issue adds a folder and a manifest instead of editing the shared type. `linear` stopped being vocabulary with issue #530 (see "PM: Linear" below), `jira` with issue #580 (see "PM: Jira"), and `trello` with issue #588, its own phase 5/6 (see "PM: Trello") — so `getPMProvider` answers for all four and `requireProjectPMProvider` throws for none of them. The shared surface each of the three needed was already in place: the per-provider webhook route + signature scheme landed with #496 and the per-provider credential roles with #497 (both above), and the card↔SCM-artifact mapping with #498 ("Task identity", below).
- **`project.pm` is a discriminated union over the providers' own config schemas (issue #495).** `ProjectPmSchema` (`src/config/schema.ts`) is `z.discriminatedUnion('type', […])` whose GitHub Projects member is `{ type: 'github-projects' } & githubProjectsConfigSchema` — so a board mapping lives under the provider it maps, and the old top-level `githubProjects` key is gone. It also carries Linear's member — added ahead of that provider's manifest and resolvable since issue #530 registered it — Jira's, added by issue #490 phase 1/6 and resolvable since #580 registered that manifest, and Trello's, added by issue #492 phase 1/6 and resolvable since #588 registered that manifest. It persists **split**: `projects.pm_type` (the discriminator) + `projects.pm_config`, one *generic* jsonb column keyed by it (renamed from `github_projects`), which `projectsRepository` re-joins into the union member on read and splits again on write. Narrowing a member back to a concrete config is the provider's own job — `requireGitHubProjectsConfig` (`src/integrations/pm/github-projects/config-schema.ts`), `requireLinearConfig` (`src/integrations/pm/linear/config-schema.ts`), `requireJiraConfig` (`src/integrations/pm/jira/config-schema.ts`), and `requireTrelloConfig` (`src/integrations/pm/trello/config-schema.ts`), the only sanctioned `pm.type` assertions, each used by its own provider and router adapter and nowhere else. Consequences worth knowing: `pm` has **no default** (its mapping has none), `SERVER_ONLY_KEYS` drops `githubProjects` because excluding the `pm` block now excludes the board ids with it, and the only queries that reach inside the blob are the two container lookups, each provider-specific by construction — `findProjectByBoardFromDb`'s hard-coded `pm_config->>'projectId'` (GitHub Projects) and `findProjectByPmContainerFromDb`, which takes the `pm_type` *and* the container key from the provider that owns them (issue #529, the shape the former's own comment anticipated). Adding a provider's config is a new union member plus a manifest — no change to the table or repository — plus a board-mapping catalogue entry with its vocabulary, projection branches that map its container to/from the neutral form, and save/dirty gates for any provider context it requires; a provider that also resolves a project from a board event adds a one-line `src/config/provider.ts` facade over that parameterised lookup, not a new query.
- **A PM provider declares its own credential roles (issue #497), and a project holds one block per provider (issue #631).** `PMProviderManifest.credentialRoles` is a `{ role, label, envVarKey, optional? }` list (Cascade's `CredentialRoleSpec` is the precedent), and a project supplies one *reference* per role under `credentials.pm[<providerId>]` (`src/config/pm-credentials.ts`, composed into `CredentialsSchema` — `src/config/schema.ts`) — a `z.record` keyed by role inside a `z.record` keyed by provider id, so registering a provider never rebuilds `ProjectConfigSchema`. The SCM block is its sibling, for the credentials the SCM roles cannot express (Jira an email + API token, Linear an API key, Trello a key + token + secret) — and that block has been per provider since issue #628 (see "Per-provider SCM credentials" below), which #631 is the exact PM twin of: the role names genuinely collide (`apiToken` is GitHub Projects' *and* Jira's, `apiKey` both Linear's and Trello's, `webhookSecret` all four's), so on the pre-#631 flat map storing an incoming provider's reference overwrote the outgoing provider's in place, and the dashboard switch flow could not enter one provider's credentials without destroying the other's before a save. Three consequences worth not re-deriving. **Resolution reads only `pm.type`'s block** — `pmCredentialReferenceFor(project, project.pm.type, role)` — so a retained block is stored and never resolved; deliberately not a fallback chain, since resolving it would hand a newly selected Jira the GitHub Projects token. **The presence rule survives here**, unlike on the SCM side, and that divergence is the point: the PM switch flow enters the incoming provider's credentials *before* the `pm` member is written, so "provider selected, credentials not yet entered" is never a state a save produces, and the parse-time rule is what makes a half-switched config unparseable. **Migration copies reference names verbatim** — `adoptLegacyPmCredentials` is a `z.preprocess` on `ProjectConfigSchema` (before *field* validation, because the legacy and live shapes share the one `credentials.pm` key, unlike #628's sibling keys), plus a one-time SQL backfill (`src/db/migrations/0046_pm_credentials_per_provider.sql`) because `rowToProjectConfig` is a dumb re-join with no validation; neither rewrites a name to the manifest's `envVarKey`, since the secret sits in `project_credentials` under the old key. `ProjectConfigSchema`'s `validatePmCredentialRoles` refinement validates every key against the `PM_TYPES` value list (`src/pm/types.ts`, `SCM_TYPES`' twin — a value list rather than the registry, so validity never depends on which provider modules a process imported), each block's roles against the *registered* manifest for the id it is filed under, and `pm.type`'s own non-optional, non-inherited roles for presence — while the three schemas derived by `.pick()`/`.omit()` (the worker-safe projection, the non-secret transport slice, the projects API's write input) derive from the base object and drop `credentials` anyway. Shared code resolves a role, never a reference: `resolvePmCredential(project, role)` / `requirePmCredential` (`src/config/provider.ts`) try the configured reference, then the shared `credentials` reference a role declares it `inheritsSharedCredential`, then the role's `envVarKey` in the host env only when the current provider's block explicitly names that role. That last rule preserves fail-closed authentication for an unprovisioned inherited credential while retaining the env escape hatch for a PM role the project opted into: GitHub Projects' `webhookSecret` role inherits the repo side's webhook secret — since issue #628 the *per-provider* one for the SCM provider `project.scm` names (an unstated `scm` attributes to `github`, the same rule the legacy adoption uses) — so the receiver's board path resolves the PM credential (`PM_WEBHOOK_SECRET_ROLE`) instead of borrowing the SCM `getWebhookSecret` dep and still authenticates against the very same stored secret; a provider that declares no `webhookSecret` role at all reaches its verifier with `secret: null` and decides for itself, which is what keeps the receiver from assuming every scheme has one. Linear, Jira, and Trello each declare their own, uninherited (their boards are separate systems from the repo), and Trello's is the case that shows why the *role* name is the receiver's rather than the provider's: the credential behind it is Trello's per-integration API secret, but a role named `apiSecret` would not be the one the receiver resolves, so its verifier would see `null`.
- **The board authenticates as its own credential, not as an SCM persona (issue #537).** GitHub Projects declares a **second, required** role, `apiToken` (`PM_GITHUB_PROJECTS_TOKEN`), and every board read, write, and discovery call runs inside `withGitHubProjectsCredentials(project, …)` (`src/integrations/pm/github-projects/credentials.ts`) — a project credential resolved from the encrypted store, scoped through the same `withGitHubToken` AsyncLocalStorage seam. It replaces the provider's old `GitHubSCMIntegration.withPersonaCredentials(project, 'implementer', …)`, which authenticated the board with the worker-local `SWARM_OPERATOR_GH_TOKEN`: that made a *worker's* SCM identity a hidden requirement of the API host (board discovery failed outright when it lacked `read:org`), gave a project admin no way to configure board access, and cut across the DB-free worker boundary, where PM credentials belong to the control plane. Three consequences: the API host needs no operator token to map a board; `requirePmCredential` throws a typed `MissingPmCredentialError` that the discovery API turns into an actionable `PRECONDITION_FAILED` naming the role (never a silent fallback); and **loop prevention moved with the write identity** — `GitHubProjectsRouterAdapter.isSelfAuthored` resolves this credential's own login (`resolveGitHubProjectsIdentity`, 60s per-project cache keyed on a fingerprint of the credential so a rotation is seen at once, `[bot]` suffix allowed) instead of the SCM personas, still failing *open* with a log on a resolution error so a real human status change is never dropped. The Dashboard's **Project Management** tab (renamed from Board Mapping) configures the roles a provider declares through `projects.credentials.listPm`/`setPm`/`deletePm`, which name a *role* rather than a store key and refuse a role that inherits a shared SCM credential (one secret, one home).
- **Those five procedures address a *named* PM provider, not necessarily the persisted one (issue #641).** `credentials.listPm`/`setPm`/`deletePm` and `pm.discoverContainers`/`discoverStates` each take an optional `providerId` defaulting to `project.pm.type`; omitted, every one behaves exactly as before, and supplied it is never resolved back to the persisted provider — that fallback is what would write an incoming provider's secret over the outgoing one's reference (#631's collision, one layer up). This is what makes a provider switch enterable *before* it is saved: credentials land in the incoming provider's own `credentials.pm[providerId]` block, and discovery runs against a **projected** project — the real one with `pm` replaced by `PMProviderManifest.blankPm`, that provider's mapping-free member, declared as data so shared code branches on *whether* the persisted provider was asked for and never on which one it is. The projection replaces nothing else, so the incoming provider still authenticates as itself (`resolvePmCredential` reads `pm.type`) and the browser still never handles a secret. Two refusals stay distinct: an undeclared `discovery` capability is `NOT_IMPLEMENTED` (checked before anything is built), while a provider whose blank member cannot support discovery at all declares `blankPmDiscoveryBlocker` and gets `PRECONDITION_FAILED` carrying its own copy — Jira's site URL being the one case (see "PM: Jira" below). `projectAdmin` remains the boundary on all five, and no `pm` member is written here; persisting the switch is a later phase.
- **The switch itself is a client-held draft on the Project Management tab (issue #642).** The circular dependency — a mapping needs a provider, a provider needs credentials, credentials are only useful once discovery works — is resolved by an **explicit order** rather than by writing an invalid intermediate state: select provider → supply that provider's manifest-declared credential roles → discover its containers and states → map the six canonical status keys → Save. There is deliberately **no server-side pending state and no draft table**. The draft is "the mapping form selects a provider the project isn't persisted on" (`switchedPmProviderId`, `dashboard/src/lib/board-mapping.ts`) — *derived*, so nothing can desync: a save closes it by making the two agree, Reset closes it by reprojecting from `project.pm`, and the route's own `diffProjectForSync` freezes the `boardMapping` slice while it is open so a background refetch can't discard a half-built mapping. Everything the tab's four cards query is addressed to that provider (issue #641's parameter above), and `withSelectedProvider` already produced the correct blank form for it. Atomicity comes from *not writing* until Save: `handleBoardMappingSubmit` sends one `projects.update` carrying `buildPmUpdate`'s whole new union member, which reads nothing from the outgoing member across a provider change, so the project never names a provider whose mapping is absent, incomplete, or still the previous provider's. Four things are worth not re-deriving. **The outgoing provider's credentials are retained** — the #628 decision, made possible on this side by #631's per-provider blocks — so switching back needs nothing re-entered, and nothing on this path deletes a secret. **The existing Save gates are untouched**: `canSaveBoardMapping` and `isBaseUrlMissing` still decide, with the same copy, so a switch *to* Jira is gated on `pm.baseUrl` exactly as an edit of a Jira mapping already was. **`projects.update` carries the server-side half** (`assertPmProviderSwitchable`, `src/api/routers/projects.ts`): a `pm.type` change requires the incoming provider to be registered and every non-optional, non-inherited role it declares to have a reference in its own block — the backstop `validatePmCredentialRoles`' rule 3 cannot provide on a path that merges and upserts without parsing, and what makes a half-switched project impossible even from a hand-rolled client. **A switch is not refused while runs are active, by decision.** Refusing would add a cross-cutting lifecycle gate for a rare operator action and a queued run can outlive any such check anyway, so the review step in front of the save states the consequence instead: in-flight runs and the durable `runs.work_item_id` links behind them refer to the outgoing provider's board and will not resolve on the new one. Nothing is migrated, and `docs/configuration.md` records the same.
- **The conformance suite is the gate on the second provider (issue #499).** `tests/unit/integrations/pm/pm-conformance.test.ts` runs one suite per *registered* PM manifest — the PM twin of the SCM one, deferred until now precisely because the five phases above were still moving the surface it asserts. It checks the manifest metadata shared code reads, every `PMProvider` **and** `PMRouterAdapter` method's presence, and that no method's own source carries the not-implemented sentinel; `PM_CONTRACT_METHODS` is compile-checked against the interface, so widening `PMProvider` fails to build until the list catches up. One assertion has no SCM counterpart — every capability a manifest declares in `discovery` must be one `PMProvider.discover` actually dispatches on, since a declared-but-unanswered capability otherwise surfaces as a runtime `NOT_IMPLEMENTED` at the board-mapping screen — and two of the SCM suite's are deliberately absent: there is no runtime-ready count (nothing to select between, per the bullet above), and webhook-route uniqueness is asserted among PM manifests only, because co-tenanting an SCM route is the supported case. Behavioral conformance (Cascade's `lifecycle` fixture harness) stays out of scope; a provider's own folder tests own its semantics. So **the PM provider abstraction is complete**: another PM provider is a folder, a manifest, a `ProjectPmSchema` union member, and a fixture in that suite — no pipeline, trigger, receiver, or config-schema edit. Linear (below) was the second provider, Jira (below it) the third, and Trello the fourth; each landed as exactly those four things, with **no exemption** in the suite — Trello included, whose `supportsDependencies: false` is a declared opt-out the suite accepts (it asserts the flag is a boolean and that no method carries the stub sentinel) rather than a stub needing one.

### PM: Linear (`src/integrations/pm/linear/`)

The second implemented PM provider (issue #491's six phases, registered by #530) and the first test of the abstraction above: it added a folder, a manifest, its `ProjectPmSchema` union member, a conformance fixture, and one `src/config/provider.ts` lookup facade over the parameterised container query. Issue #531 added its board-mapping catalogue vocabulary, neutral-form projection branches, and provider-context-aware save/dirty gates. No pipeline, trigger, worker, or receiver edit, and no change to the `projects` table or its repository. Cascade ships a Linear adapter, so unlike GitHub Projects this one has precedent; the mappings and the vocabulary are SWARM's own.

- **GraphQL-only, with the API key scoped, never passed.** Linear has no REST surface at all (`https://api.linear.app/graphql`), so there is no second protocol to keep straight. Every method's work runs inside `withLinearProjectCredentials(project, …)` and `linearGraphQL` picks the key up off the async scope (`client.ts`, `credentials.ts`); a **personal API key goes out in a bare `Authorization` header** — `Bearer` is OAuth-only and makes Linear reject a personal key with a 400.
- **A container is a Linear *team*; a status is that team's *workflow state*.** Workflow states belong to teams, so the team is the smallest scope whose states are a complete mapping — hence `pm.teamId` plus `statusOptions`, canonical `PmStatusKey` → workflow-state **UUID** (`config-schema.ts`, `status-mapping.ts`). The mapping is explicit and operator-chosen: Linear's state `type` (`backlog`/`started`/`completed`/…) is only a picker *hint* and is not even selected, since `DiscoveredState` carries `id` + `name` and nothing else. A missing mapping fails loudly rather than reading as "match everything". Discovery declares both `containers` (the teams the key can see) and `states` (one team's states, ordered by Linear's own `position`).
- **Comments land natively on the issue.** A Linear issue *is* the card, so `addComment` posts to it directly — no backing Issue/PR to redirect onto, and no draft-card case that leaves nowhere to post. `findComment` pages the whole thread looking for SWARM's own marker, so a retry doesn't duplicate.
- **Both capability flags are `true`.** `supportsAssignees` — `Issue.assignee` is native (at most one, folded into the shared array). `supportsDependencies` — Linear models prerequisites as an issue **relation**, so `listBlockers` reads the native `blocks`/`blockedBy` relations *plus* the prose references the shared dependency helper finds, deduplicated by URL, and `addBlockedBy` creates the relation with the *blocker* as its source (`issueRelationCreate`'s `issue` is the source, `relatedIssue` the target). The provider-neutral dependency gate (`src/pipeline/dependency-guard.ts`) therefore defers a blocked Linear item with no gate-side change — on the **relations**; the prose references it also reports are advisory since issue #643 (surfaced on the card, never deferring), same as every other provider's. Its reverse edge, `listDependents` (issue #639), is the exact mirror of that read — the issue's own `relations` rather than its `inverseRelations`, each dependent being the relation's `relatedIssue` target — which is the pairing `addBlockedBy` writes.
- **Ingress is its own route** (`webhook.ts`, `src/router/adapters/linear.ts`): `/linear/webhook`, which no SCM manifest owns, so the receiver mounts a GET ping + POST pair for it rather than co-tenanting as GitHub Projects does. Authentication is an **unprefixed hex HMAC-SHA256** of the raw body in `linear-signature` — deliberately *not* routed through the GitHub-shaped verifier, which requires the `sha256=` framing and would reject every genuine delivery; what is shared is only the provider-neutral `verifyHmac` primitive. It fails closed on an absent secret. Linear's recommended 60s `webhookTimestamp` replay window is deliberately **not** enforced: a board event is a doorbell, and the authoritative downstream re-read plus `pm-status-dedup.ts` make a replay a no-op. The own-route receiver currently has no Linear delivery-id reader, so it creates no dispatch-layer delivery dedup key; a repeated delivery may create an extra dispatch and queue wake-up, but `pm-status-dedup.ts` absorbs it before it can start a duplicate phase. The event name comes from the **body** (`type` + `action`), not a header, so the receiver hands this adapter `OWN_ROUTE_EVENT_NAME` (`''`); a column drag needs no special case, because moving a card *is* a `stateId` edit in `updatedFrom` (GitHub Projects' `reordered` → `moved` hack has no analogue, and no `moved` action is ever produced).
- **Its project lookup is by team, and its loop prevention is its own identity.** `resolveProject` goes through `findProjectByLinearTeam` (`src/config/provider.ts`), a one-line facade over the parameterised `pm_type` + container-key query issue #529 added. `isSelfAuthored` compares the delivery's actor **id** against the identity of the provider's *own* API key (`identity.ts`, uncached — one round-trip per actor-carrying delivery), never a GitHub persona: a Linear board paired with a GitHub repo shares no identity with the source-control side. It fails **open** with a log, so a Linear outage never silently drops a human's status change.
- **Two credential roles, neither inherited** (`index.ts`): `apiKey` (`LINEAR_API_KEY`) and `webhookSecret` (`LINEAR_WEBHOOK_SECRET`). Inheriting the repo side's webhook secret is forbidden here by `PmCredentialRoleSpec`'s own rule — the board is a separate system from the repo, so there is no one secret to share — and the webhook role is **required** rather than optional (as Cascade marks it) precisely because SWARM's verifier fails closed: an optional role would pass `swarm config apply` and then 401 every delivery, so the failure is moved to config validation, which names the role and its env var.
- **`taskRef` comes from the card's GitHub *issue* attachment**, and `taskRepository` from that same attachment's own `owner/repo` — Linear records its GitHub linkage as an attachment (see "Task identity" below). Since issue #710 the repository is the *card's*, never the one this provider's config happens to be scoped to, so a card linked in any of the project's repositories resolves and a board-wide read answers per card. Nothing else about the task id changes: it stays SCM-derived.
- **Repository routing is by label id** (issue #686). The `teamId` is already the board container, so a label is what is left to claim a card for one of the project's repositories: `resolveItemRepository` reuses the same `IssueLabels` read `addLabel`'s idempotence check makes and matches the ids against each entry's `pmRoutingToken`. Ids, never names — which is also what keeps it clear of the automation opt-in gate, the one thing here that matches a label by *name*.

### PM: Jira (`src/integrations/pm/jira/`)

The third implemented PM provider (issue #490's six phases, registered by #580) and the second confirmation of the abstraction above: a folder, a manifest, its `ProjectPmSchema` union member, a conformance fixture, and one `src/config/provider.ts` lookup facade over the parameterised container query. Issue #581 added its board-mapping catalogue vocabulary, neutral-form projection branches, and the save/dirty gates for the one piece of provider context it carries (`baseUrl`, below). No pipeline, trigger, worker, or receiver edit, and no change to the `projects` table or its repository. Cascade ships a Jira adapter, so the precedent exists; the mappings, the id-over-name choices, and the vocabulary are SWARM's own.

- **REST v3 over `fetch`, with basic auth scoped, never passed.** Jira Cloud's `/rest/api/3` is the whole surface (`client.ts`) — no SDK, and Jira Server / Data Center is a non-goal. Every method's work runs inside `withJiraProjectCredentials(project, …)` and `jiraRequest` picks the credential up off the async scope (`credentials.ts`), exactly as Linear's provider does. The credential is a **pair**: Jira Cloud authenticates with basic auth, so the account email is the username and the API token the password, and neither half authenticates a request alone.
- **`baseUrl` is config, not a credential.** The site URL is board *identity*, the same category as `projectKey`, and it must be readable back by an operator — a `credentials.pm` role is a masked, write-only secret, which is the wrong treatment. Cascade makes it a synthetic credential only to feed its setup wizard, which discovers before any config row exists; SWARM has no wizard, so the hook buys nothing here. Any URL is accepted: sandbox and developer tenants are not on `atlassian.net`. Being identity rather than mapping, it is also the one field the dashboard's board-mapping screen does **not** edit (issue #581): it rides through the form's opaque `providerContext` — cleared on a provider switch, kept across a *container* switch, since the site is not a property of the selected project — so a save preserves it, and a Jira form carrying none can't be saved at all rather than writing a member `jiraConfigSchema` then rejects.
  - **The "discovery only runs on a persisted `ProjectConfig`" half of that argument expired with issue #641**, and this is the provider it cost. The discovery API now also serves a provider a project is *not* persisted on — against `PMProviderManifest.blankPm`, so the incoming board can be picked before a switch is saved — and a blank `baseUrl` is the one case that cannot be served at all, since it is the origin every REST call is addressed to. Jira therefore declares the manifest's optional `blankPmDiscoveryBlocker` (`index.ts`) and the API answers `PRECONDITION_FAILED` with that copy, naming `swarm.config.json`, rather than failing on an unresolvable URL. It is the API-side twin of the dashboard's existing base-URL Save gate, and it is deliberately *not* a decision to make the value editable.
- **A container is a Jira *project key*; a state is a workflow *status id*.** The key (`SWARM`), not the numeric project id, because it prefixes every issue key and is what a webhook carries at `issue.fields.project.key`. `statusOptions` maps canonical `PmStatusKey` → status **id** (`config-schema.ts`, `status-mapping.ts`) — ids, never names, which is the one part of Cascade's Jira precedent SWARM deliberately does not copy: names are rename-prone, and a transition is resolved by comparing ids. Discovery declares both `containers` (the projects the credential can browse) and `states` (one project's statuses).
- **`moveWorkItem` executes a *transition*, which is the one structural difference from every other provider.** A status is not a writable field on a Jira issue: the provider reads the issue's available transitions and POSTs the one whose target *is* the mapped status id. So a move can fail for a reason no other board has — the workflow may simply not offer that transition out of the card's current status — and it fails **loudly**, naming the current status, the target, and the transitions Jira did offer, rather than silently leaving the card put. Re-asserting the status a card already holds is answered as a no-op before the workflow is consulted, since `autoAdvance` does exactly that.
- **Comments land natively, in ADF.** A Jira issue *is* the card, so `addComment` posts to it directly — no backing Issue/PR to redirect onto. Jira's comment bodies are Atlassian Document Format, so `adf.ts` converts SWARM's plain text out and back; `findComment` pages the whole thread looking for SWARM's own marker, so a retry doesn't duplicate.
- **Both capability flags are `true`.** `supportsAssignees` — `fields.assignee` is native (at most one, folded into the shared array). `supportsDependencies` — `listBlockers` reads the issue's **`is blocked by`** issue links *plus* the prose references the shared dependency helper finds, deduplicated by URL, and `addBlockedBy` creates that link, resolving the site's own link-type **name** from `issueLinkType` rather than assuming the English built-in (link types are site data an administrator can rename). The provider-neutral dependency gate (`src/pipeline/dependency-guard.ts`) therefore defers a blocked Jira item with no gate-side change — on the **links**; the prose references it also reports are advisory since issue #643 (surfaced on the card, never deferring), same as every other provider's. Its reverse edge, `listDependents` (issue #639), reads the same `issuelinks` and takes each "is blocked by" link's `outwardIssue` where the blocker read takes its `inwardIssue` — direction is carried by which side the entry names, not by the link type.
- **Ingress is its own route** (`webhook.ts`, `src/router/adapters/jira.ts`): `/jira/webhook`, which no SCM manifest owns, so the receiver mounts a GET ping + POST pair for it rather than co-tenanting. Authentication is an HMAC-SHA256 of the raw body framed as `sha256=<hex>` in **`x-hub-signature`** — GitHub's framing, one header name older, and emphatically **not** GitHub's secret: routing it through the GitHub Projects verifier would authenticate against the *repository's* webhook secret, which Jira never signs with. What is shared is only the provider-neutral `verifyHmac` primitive. It fails closed on an absent secret. The event name comes from the **body** (`webhookEvent`), not a header, so the receiver hands this adapter `OWN_ROUTE_EVENT_NAME` (`''`), and a status change is detected from a `status` entry in the delivery's `changelog.items[]` — never the mere presence of a changelog, which every field edit carries. A column drag needs no special case (it *is* a transition, so it is a `status` changelog entry), and no `moved` action is ever produced.
- **Its project lookup is by project key, and its loop prevention is its own identity.** `resolveProject` goes through `findProjectByJiraProject` (`src/config/provider.ts`), a one-line facade over the parameterised `pm_type` + container-key query issue #529 added. `isSelfAuthored` compares the delivery's actor **`accountId`** against the Atlassian account of the provider's *own* API token (`identity.ts`, `GET /myself`, uncached), never a GitHub persona: a Jira site paired with a GitHub repo shares no identity with the source-control side. It fails **open** with a log, so a Jira outage never silently drops a human's status change.
- **Three credential roles, none inherited** (`index.ts`): `email` (`JIRA_EMAIL`), `apiToken` (`JIRA_API_TOKEN`), and `webhookSecret` (`JIRA_WEBHOOK_SECRET`). Inheriting the repo side's webhook secret is forbidden here by `PmCredentialRoleSpec`'s own rule — the board is a separate system from the repo, and the shared `sha256=` framing makes borrowing it *look* plausible while pointing the verifier at a key Jira never signs with. The webhook role is **required** rather than optional (as Cascade marks it) precisely because SWARM's verifier fails closed: an optional role would pass `swarm config apply` and then 401 every delivery, so the failure is moved to config validation, which names the role and its env var.
- **`taskRef` comes from the card's GitHub *issue* remote link**, and `taskRepository` from that link's own `owner/repo` — since issue #710 the card's, never the repository this provider's config happens to be scoped to. A *pull-request* remote link deliberately does not qualify, since a PR is an artifact of the task rather than its id (see "Task identity" below). Both cost a second round trip per card, so they are resolved only on the reads that answer with a single card; a whole-board read leaves both unset, which makes Jira the one provider whose board-wide read resolves *nothing* per card rather than per card. The Jira issue key is never a task id: that stays SCM-derived.
- **Repository routing is by component id** (issue #686). The `projectKey` is already the board container, so components — a per-project subdivision an issue carries zero or more of — are the routing axis: `resolveItemRepository` makes its own narrow `fields=components` read, modelled on `fetchStatus`, rather than widening `ISSUE_FIELDS` and making every other board read pay for it.

### PM: Trello (`src/integrations/pm/trello/`)

The fourth implemented PM provider (issue #492's six phases, registered by #588) and the third confirmation of the abstraction above: a folder, a manifest, its `ProjectPmSchema` union member, a conformance fixture, and one `src/config/provider.ts` lookup facade over the parameterised container query — plus, in the same phase this time, the board-mapping catalogue vocabulary and neutral-form projection branches Linear's #531 and Jira's #581 added separately. No pipeline, trigger, worker, or receiver edit, and no change to the `projects` table or its repository. Cascade ships a Trello adapter, so the precedent exists; the mappings, the id-over-name choices, and the vocabulary are SWARM's own.

- **REST v1 over `fetch`, with the key/token pair scoped, never passed.** `https://api.trello.com/1` is the whole surface (`client.ts`) — no SDK. Every method's work runs inside `withTrelloProjectCredentials(project, …)` and the client picks the credential up off the async scope (`credentials.ts`), exactly as Linear's and Jira's providers do. The credential is a **pair** appended as query parameters: the API key names the integration and the token names the member who authorized it, so neither half authenticates a request alone.
- **A container is a Trello *board*; a state is one of that board's *lists*.** A Trello card has no status field at all — its status *is* the list it sits in — so `statusOptions` maps canonical `PmStatusKey` → list **id** (`config-schema.ts`, `status-mapping.ts`), and the key stays the provider-neutral `statusOptions` rather than Cascade's `lists` so the dashboard's projection keeps reading it generically. Ids, never list names: names are rename-prone, and a card read reports its list as `idList`. Discovery declares both `containers` (the boards the token can see) and `states` (one board's lists).
- **The write half is unusually plain, and `addLabel` is the one exception.** A move is one `PUT /cards/{id}` with a new `idList`, and a comment lands natively on the card — a Trello card *is* the work item, so there is no backing Issue/PR to redirect onto; `findComment` pages the thread looking for SWARM's own marker so a retry doesn't duplicate. A Trello *label*, though, is a board-scoped object rather than a free string, so `addLabel` resolves-or-creates the board label before applying it.
- **The capability flags split, and the `false` one is a declared opt-out.** `supportsAssignees` — card members are native (folded into the shared array). `supportsDependencies` is **`false`**, and `listBlockers`/`listDependents`/`addBlockedBy` are the contract's declared opt-out (`[]`, `[]` and a no-op) rather than unfinished methods: a Trello board models no cross-card blocking relationship at all — lists, labels and checklists, and nothing that says one card must finish before another. The only prerequisites a card can express are prose in its description, and in SWARM those are GitHub issue numbers whose open/closed state only an **SCM** provider could resolve, which would be the cross-category reach ai/RULES.md §2 forbids. Synthesising a blocker SWARM could never answer `open` for would be worse than reporting none — the gate would defer work on a prerequisite it could never see finish — so callers fall back to the provider-neutral human-readable comment guard (`src/pipeline/dependency-guard.ts`). Issue #643, which stopped prose deferring a run anywhere, takes nothing further away here: the gate short-circuits on this flag *before* it asks for blockers, so a Trello project never had an automated gate to lose, and the guard it does have — the prose Planning writes into each split child, for a human — is unchanged. Issue #639's cycle backstop is the same story from the other side: a provider that gates on nothing has no cycle to suppress, and answering the reverse read from prose would be worse than answering `[]`, since that read is what *excuses* a blocker.
- **Ingress is its own route, and its verifier is the only one that signs SWARM's own URL** (`webhook.ts`, `src/router/adapters/trello.ts`): `/trello/webhook`, which no SCM manifest owns, so the receiver mounts a GET ping + POST pair for it rather than co-tenanting. Authentication is a **base64 HMAC-SHA1** in `x-trello-webhook` — not GitHub's and Jira's `sha256=<hex>` framing, not Linear's bare SHA-256 hex — computed over `rawBody + callbackUrl`. That is why `PmWebhookVerification` carries a callback URL at all, and why the URL must stay the *receiver's* value (`WEBHOOK_CALLBACK_BASE_URL`, `src/router/webhook-callback-url.ts`) rather than one re-derived from a spoofable `Host`: the signed string has to match the subscription's `callbackURL` exactly, and a caller-controlled value in a signed string is a caller-controlled signature input. What is shared is only the provider-neutral `verifyHmac` primitive. It fails closed on an absent secret, and carries no replay-window check for the same reason Linear's doesn't. Trello also confirms a subscription with a **`HEAD`** request to that URL and refuses to create the webhook unless it answers 200 — which needs no receiver change, since Hono dispatches `HEAD` onto the mounted `GET` ping, and is pinned by a receiver test. The event name comes from the **body** (`action.type`), not a header, so the receiver hands this adapter `OWN_ROUTE_EVENT_NAME` (`''`), and a status change is detected from `data.listAfter` — Trello's own "this card changed column" marker, never an `updateCard` on its own, which every rename, description edit, due date, and archive also sends. A column drag needs no special case for the opposite reason to GitHub Projects': on Trello dragging *is* that `listAfter` action, so no `moved` action is ever produced.
- **Its project lookup is by board, and its loop prevention is its own identity.** `resolveProject` goes through `findProjectByTrelloBoard` (`src/config/provider.ts`), a one-line facade over the parameterised `pm_type` + container-key query issue #529 added. `isSelfAuthored` compares the delivery's `action.idMemberCreator` against the **member id of the provider's own token** (`identity.ts`, `GET /members/me`, uncached), never a GitHub persona: a Trello board paired with a GitHub repo shares no identity with the source-control side. A member *id* rather than a username, since usernames are rename-prone. It fails **open** with a log, so a Trello outage never silently drops a human's card move.
- **Three credential roles, none inherited** (`index.ts`): `apiKey` (`TRELLO_API_KEY`), `token` (`TRELLO_TOKEN`), and `webhookSecret` (`TRELLO_API_SECRET`). The last is the one place the role name and the credential diverge on purpose: the credential is Trello's **API secret** — a per-integration value Trello signs every delivery with, not a per-webhook secret SWARM chooses — while `webhookSecret` is the *receiver's* vocabulary, the one role it resolves into `PmWebhookVerification.secret`, so an `apiSecret` role would reach the verifier as `null` and 401 every delivery. Inheriting the repo side's webhook secret is forbidden here by `PmCredentialRoleSpec`'s own rule — the board is a separate system from the repo — and all three are **required** rather than optional (as Cascade marks the secret) precisely because SWARM's verifier fails closed: an optional role would pass `swarm config apply` and then 401 every delivery, so the failure is moved to config validation, which names the role and its env var.
- **The board webhook is a resource SWARM creates, so it has an operator command** (`webhooks.ts`, `src/cli/commands/pm.ts`, issue #589). GitHub's repo/org hook, Linear's signing-secret screen, and Jira's WebHooks screen are all configured once by a human in the provider's UI; a Trello subscription is a REST object bound to one board (`idModel`) and one `callbackURL`, owned by the token that created it, so registering one is an *operation* — `swarm pm webhook list|create|delete`, which resolves the project's own key/token pair, builds the callback URL as `WEBHOOK_CALLBACK_BASE_URL` + the manifest's `webhookRoute` (so the subscription and the served route cannot drift), and matches board + callback URL before creating so a re-run reports rather than duplicates. It **refuses** when that base URL is unset, because the delivery HMAC covers the exact URL a webhook was registered with, and it names Trello's `HEAD` confirmation when creation fails, which is what a rejection almost always means. Two placement decisions: not on `PMProvider` (no pipeline, trigger, or worker may create a webhook — this is provisioning, and the contract is what the pipeline programs against), and not inside `swarm config apply` (a local-file → Postgres loader with no outbound provider calls; making it create remote resources would give every seed run a network dependency and a partial-failure mode). The `pm.type === 'trello'` assertion stays in `requireTrelloConfig`, so the command carries no provider branch of its own.
- **`taskRef` comes from a GitHub *issue* URL on the card**, and `taskRepository` from that URL's own `owner/repo` — since issue #710 the card's, never the repository this provider's config happens to be scoped to. Its attachments are read first (the linkage Trello's GitHub Power-Up records, and the deliberate one), then its description, where a hand-pasted link ends up. A *pull-request* URL deliberately does not qualify, since a PR is an artifact of the task rather than its id (see "Task identity" below). The Trello card id is never a task id: that stays SCM-derived.
- **Repository routing is by label id** (issue #686). A card's list is already its status, so a label is what is left to claim it for one of the project's repositories: `resolveItemRepository` reads the plain `fields=idLabels` array rather than the whole label objects the shared card query selects. Matching on the id is what makes a colour-only label — legitimately nameless on a Trello board — route exactly like any other.

## Pipeline phases

Per `PROJECT.md` §5, adapted to GitHub Projects as the board and the project's configured SCM provider:

Each worker-spawned agent is scoped to one phase. A shared prompt guard forbids the manual
`solve-issue` skill, arbitrary subagents/skills, and later-phase work; only the worker owns
phase hand-offs, personas, and worktrees.

**Automation opt-in gate (issues #131 and #354).** **Every** phase below only dispatches for a work
item carrying the project's `pipeline.automationLabel` (default `swarm`). The check is
provider-neutral: `resolveAutomationLabel` / `hasAutomationLabel` (`src/pm/automation-label.ts`)
match the configured name against `WorkItem.labels`, the canonical PM capability every adapter
already populates from its own native labels — no `PMProvider` method was widened, and the Linear
provider (issue #530), the Jira one (issue #580), and the Trello one (issue #588) each inherited the gate for free. It is evaluated at the single dispatch choke
point (`processJob`, `src/worker/consumer.ts`), *before* the in-flight guard and
`acquireProjectSlot`, so a skip costs no slot, no worktree, and no tokens; because it lives there it
is re-evaluated on every fresh webhook, delayed retry, self-enqueued next phase, capacity promotion,
reconciler republish, and manual "Retry now" — removing the label therefore stops all later
dispatches, but never terminates an agent already running. A skip logs the missing label and settles
the dispatch `completed` with outcome `skipped-not-eligible` (a retried run row is finalized `failed`
with the same reason rather than left `deferred`). That outcome is deliberately named for eligibility
in general, not for the label: #339's worker-authorization gate lands at the same call site and
settles through the same value with its own reason. Split children Planning creates carry the
configured label so SWARM's own siblings aren't gated out of its pipeline. An explicitly empty
`automationLabel` disables the gate. The label is an automation opt-in, **never** an access-control
mechanism — ADR-001's authorization layers are separate and unaffected.

The two board-driven phases carry their work item on the `TriggerResult`. The four SCM-driven
continuation phases (3–5 below, plus Resolve-conflicts) carry a *pull request*, so the gate resolves
one for them (`resolveGatedWorkItem` → `findWorkItemForPullRequest`,
`src/pm/pull-request-work-item.ts`): the PR's head branch decodes to the item it implements
(`<branchPrefix><number>`, which is why the `review` result now carries `prBranch` — the trigger
already holds the PR details, so no second SCM round-trip is spent), and the card is found through
`PMProvider.findWorkItemForArtifact` (a repository-scoped narrow read) matching the backing issue
first and the pull request second — no GitHub URL shape enters worker code (§2), and a federated
worker can serve the same question as one card rather than a whole board. That resolution **fails open** — an
unlinked PR, a branch outside the project's `branchPrefix`, an unreadable board, and an
unresolvable PM provider all dispatch normally — because a board blip must never wedge review/CI
work, and it is skipped entirely while the gate is disabled so an opted-out project pays no board
read. Because these dispatches consume no phase work, a skip returns every pre-gate claim: the
Review dedup and verdict reservation, the Respond-to-CI dedup and attempt, and the
Resolve-conflicts claim, so the correctly-labelled retry at the same head
would be dropped as a duplicate.

1. **Planning** — item enters "Planning" status → worktree provisioned → the planning agent writes `proposed_plan.md` → plan posted as a comment on the linked Issue. On successful completion the item's backing issue is also labeled `planned` via `PMProvider.addLabel` (issue #384) — an idempotent, provider-visible marker (the label is auto-created if missing) that a run *finished* planning, applied on both the normal-agent and preplanned-split-child completion paths and independent of the `autoAdvance` Status move. **Since issue #737 that label is also the phase's only entry gate**: a card entering "Planning" starts a run unless it already carries `planned`, so a completed run is what stops a later re-drag from re-planning, and **re-planning is the explicit act of removing `planned` and moving the card Backlog → Planning** (see "Trigger wiring" for what that replaced). By default the item stays in "Planning" (a human reviews the plan, then moves it to "ToDo" to greenlight Implementation); `pipeline.planning.autoAdvance` flips that to an automatic move. When `pipeline.planning.autoSplit` is on (default) and the agent judges the item too large for one PR, it also writes `proposed_split.json`: the original item is re-scoped into the smaller **first** task (`proposed_plan.md` is that task's plan) and the remaining work is spawned as sibling items via `PMProvider.createWorkItem`. Each sibling ends in **Planning**, is tagged `swarm:split-child` **and `planned`** (issue #426 — a split child is planned by construction, so the marker is accurate as soon as it holds the parent's plan; that label is what stops a Planning agent run being spent on it, and the `applyPlannedLabel` on any run that does reach it is idempotent), and gets a comment explaining the split. SWARM first creates its card in Backlog, publishes the child's complete plan as a normal, human-readable **Preplan** comment (issue #431 — GitHub does not render the hidden marker, so this is the copy an operator reviews; it carries its own `<!-- swarm-preplan-comment:… -->` provenance marker, which also keeps it out of the dependency gate's prose scan; a replayed delivery is short-circuited by the plan-delivery marker before any child is re-prepared, so no per-child duplicate check is needed), writes the parent-generated validated preplanned marker (`<!-- swarm-preplan:v1 … -->`, `src/pipeline/preplan.ts`) into its issue body, applies `planned`, and only then moves it to Planning. Publishing before the marker write is deliberate: a failed publication leaves no marker, so the child stays in Backlog — with a split comment that claims no published preplan — and a later Planning move runs a normal agent, rather than leaving a child holding a plan nobody can read. **Labelling before the move is deliberate for the same reason (issue #737): the move is the event that dispatches**, so a label applied after it would race every single child into the Planning dispatch it exists to stop. The `planned` label is therefore applied once the child really holds its plan — not in the `createWorkItem` labels — so a child whose marker never landed is never labeled up front (issue #436), and the two failure modes stay distinguishable: if marker embedding failed the child stays unlabeled in Backlog and owes a full Planning agent run, which a later Planning move dispatches normally; if the *Planning move* failed the child sits in Backlog already carrying its marker **and** `planned`, so it keeps its plan and a later move to Planning dispatches nothing at all — which is the right answer, and an improvement on the pre-#737 behaviour where such a card stayed unlabeled indefinitely because the thing suppressing its dispatch was the marker rather than a label. That label write stays best-effort like `addBlockedBy`, logged and swallowed so it can never abort the split mid-loop. What a swallowed failure costs was re-decided when the label became load-bearing, and it is affordable: the child moves to Planning unlabeled, that move dispatches a Planning run, and the run finds the still-valid preplan marker and reuses it — spending no agent — then re-applies the label as a hard step. The cost is one dispatch and a second copy of the same plan in the card's comments, and the marker heals; that is why it did not become a hard step that would fail an otherwise-complete parent Planning run over a label. A malformed or stale marker on a dispatched run still falls back to a normal Planning agent. This keeps splitting behind the provider-agnostic `PMProvider` (no GitHub Projects specifics leak into the phase). A split also **names every card it writes for scanning** (issue #594): the agent picks one concise shared task name for the split, and SWARM titles the re-scoped original and every child `<shared task name> <phase>/<total>: <phase-specific task>` — so all phases of one issue are recognisable together in the Planning column. The convention is *enforced*, not merely requested: `resolveSplitNaming` (`src/pipeline/split-naming.ts`) strips whatever prefix the model supplied and re-emits the shared one, falling back to a prefix the model already used or to a name derived from the first task when `proposed_split.json` declares no `sharedName`, so a phase-first response cannot leave `Phase 2/6: …` cards on the board — and the original card is renamed to phase `1/<total>` on **every** split, including one whose response omits `mainTask`. Each child is also created with the original task's own labels (type labels such as `bug`, plus the automation label) on top of `swarm:split-child`, deduplicated; `planned` is deliberately not inherited, since it is a claim about the *parent* card's lifecycle — and, now that it gates Planning, inheriting it would leave a child whose preparation failed permanently un-plannable. A split also **chains the phases as dependencies** (issue #330): the phases are ordered by that same numbering, and for each spawned sibling the phase records a cumulative `blocked by` relationship on *every* preceding phase (phase 3 ← phases 1 and 2; phase 4 ← 1, 2, 3; …) — via `PMProvider.addBlockedBy` (behind `supportsDependencies`, so a provider that can't model dependencies degrades gracefully) *and* by naming those blockers in the sibling's split comment. The two guards mean a later phase is never startable before its predecessors land.
2. **Implementation** — item enters "ToDo" → **a dependency gate runs first** (issue #330): before the "In Progress" move, the worktree, or the agent, the phase asks the `PMProvider` for the item's still-open blockers (`listBlockers` — native `blocked by` relationships plus prerequisites named in the item's description or in a **human** comment; SWARM's own comments are excluded from that prose scan by `isSwarmGeneratedBody`, so a published plan saying "requires #N" never invents a blocker for the item it plans, issue #431; and since issue #636 that scan is **direction-aware** — a dependency phrase binds only the reference on its own object side, only within a bounded character window of it, and binds nothing at all when its object is the item itself ("blocked by this phase, #N will follow")) and, if any are unfinished, **defers** the run as a token-free `recheck` (no worktree, no agent → zero model tokens; re-checked every `SWARM_DEPENDENCY_RECHECK_MS` on its own budget, separate from the rate-limit budget, until the blocker closes or `SWARM_DEPENDENCY_MAX_WAIT_MS` is exhausted, at which point it settles `failed` with an "issue X must be done first" comment). **Only a *recorded* relationship defers a run; prose is advisory** (issue #643). `findGatingBlockers` (`src/pipeline/dependency-guard.ts`) splits the provider's answer on `WorkItemBlocker.source` (`partitionBlockersBySource`, `src/pm/dependencies.ts`): a native `blocked by` relationship gates exactly as before, while a prerequisite found only in prose is **surfaced and stepped over** — logged, and posted once on the item as a "possible unrecorded prerequisite" notice asking whoever wrote the sentence to record the relationship if it is real (idempotent on a marker keyed to the reference set, so the five-minute re-check does not repeat it, and best-effort, so a failed board write can never fail the run). The information is therefore not lost, but it cannot stall anything. **And no cycle can gate a run, whatever the parser concluded** (issue #639). Whatever survives that split is checked against the item's *own* outgoing edges — `PMProvider.listDependents`, a native-only reverse read every provider implements (`[]` for one that models no dependencies) — and any blocker the item natively blocks is dropped, because it cannot close until the gated item lands, so gating on it could only exhaust the wait budget and settle the run failed. That is exactly what happened: item 633 deferred on 631 while 631's own `blocked_by` list named 633 — ~2000 pointless rechecks over the seven-day budget, then a failure naming a dependency the native graph never asserted in that direction. Each suppression is logged with the blocker's reference and source, so it is visible rather than silent; a *failed* reverse read keeps the blockers gating (the check could not run, which is not evidence there is no cycle, and the existing recheck retries). Only the **direct** edge is checked — walking further would need each dependent's provider-native item id, which a reverse read need not yield. Being a structural backstop on the shared gate rather than a parsing improvement is the point: it makes any future miss in the prose scan, or a mis-recorded relationship, non-fatal. **Why prose lost its authority:** it gated on correct, well-written prose twice in one morning — item 633's Implementation deferred on an issue that stated the *reverse* relationship and was itself natively blocked by 633 (a deadlock: the blocker could not close until the gated item landed), and item 636's deferred on the same issue parsed out of *quoted evidence*, with no cycle at all, simply waiting behind unrelated work. Sharper parsing (#636) shrinks that class but cannot remove it — an issue about dependencies must quote error messages and give examples of dependency wording — and naming the source (#638) makes a false positive diagnosable, not preventable. The tell was the workaround: three issue bodies had to be reworded until the regex stopped matching, so contributors were writing defensively around a parser. What prose gating existed to catch, an unrecorded real dependency, is redundant now `ai/RULES.md` §5 requires a native relationship for every dependency — and the notice is what chases the one that lacks it. **A provider that declares `supportsDependencies: false` is unaffected and loses nothing**: the gate short-circuits on the flag before `listBlockers` is called, so it never gated on prose either (Trello, whose only expressible prerequisites are GitHub issue numbers it cannot resolve state for — see "PM: Trello"); its guard stays the prose Planning writes into each split child, for a human. **The deferral message and the worker's deferral log line still name each blocker's source** — `native blocked-by relationship` or `prose mention in the item description or comments` (issue #638) — which now reads as a statement of the gate's authority rather than a warning about it, and is what makes "prose does not gate" checkable from the board. All of this is what stops a later phase from being implemented before its predecessors land (the out-of-order build that produced the PR #326/#327 conflict). Otherwise → the phase moves it to "In Progress" to report the pickup → the agent implements/verifies and writes a semantic hand-off → SWARM validates the prepared tree, commits/pushes, opens or reuses the PR, and links it back to the item. Successful delivery moves the item to "In review" exactly when `pipeline.review.enabled` is on; otherwise it remains "In progress".
3. **Review** — PR opened / checks pass (independent of the Projects status report) → the reviewer agent writes a structured hand-off of **fields** → **SWARM renders the review body from them** (`src/pipeline/review-body.ts`, issue #470) and submits the formal review under the reviewer persona. The agent authors no layout at all: it fills `summary`, `verification`, `docsChecked`, `preExisting`, `findings[{id, title, severity, category, evidence, …}]`, and (on a re-review) `carried`, and the renderer owns every heading — so a review is structurally identical whichever CLI/model produced it, instead of each harness inventing its own format. Two rendering tiers key off severity: `blocker`/`major` carry the full Evidence / Failure scenario / Impact / Fix plan / Tests slots, while `minor`/`nit` carry one compact paragraph. `ReviewHandoffSchema`'s refinement (`src/scm/delivery.ts`) enforces what a prompt cannot: each tier's required and forbidden slots, unique `F<n>` finding ids, the rule that every `carried` item a re-review did **not** resolve must reappear in `findings` under the same id (without it a disposition table reading "F1 ❌ not addressed" could sit above an `approve`, clearing the review gate and merging a PR whose requested changes were never made), and the **verdict as a pure function of the severity histogram** — any `blocker`/`major` requires `request-changes`, and `request-changes` requires at least one. Routing an unresolved carried item through `findings` rather than binding it to the verdict directly is what lets a still-outstanding *nit* be approved while a still-outstanding blocker cannot. A hand-off that fails that validation gets **one repair pass** — the agent is re-run in the same worktree with the validator's own complaint and the field contract (`buildReviewHandoffRepairPrompt`), resuming its session so it still holds the diff — before the run fails; otherwise the agent never learns why, and the queue re-runs the whole review up to three times over the same mis-shaped JSON. The rendered header names the pass from the ledger ordinal below (`pass 2 of 3`, marked as the final permitted verdict at the cap), derived as `getPriorSubmittedReview`'s ordinal + 1 rather than counted by the agent, whose count a retry would drift; the pass's *name* follows whether it actually is a re-review, so a full pass at ordinal 2 (a push after an approval that didn't merge) reads "Review", not "First re-review". **The verdict vocabulary is two, not three:** `comment` was removed in issue #470 — it mirrored `gh pr review`'s third event flag rather than any SWARM state, and it cleared no review gate, dispatched no Respond-to-review run under the default `skipOnMinors`, consumed a verdict slot anyway, and set no `manual-intervention-required` signal, so a PR that received one looked reviewed and was silently terminal. A reviewer that cannot reach a verdict now fails its run (which retries) instead. This is SWARM's *outbound* vocabulary only — `ScmReviewState` still observes an inbound `commented` review, which humans submit routinely. A durable, restart-safe ledger (`review_verdicts`, one row per `(project, repository, PR, head SHA)`, issue #235) caps every PR at **three** submitted verdicts — an initial review plus at most two **re-reviews** (`REVIEW_VERDICT_CAP`, the single place the number is defined): the `pr-review` trigger reserves a slot before dispatching (reusing a same-head retry's existing slot rather than charging it again) and refuses one past the cap; the phase marks its reservation `submitted` once GitHub confirms the review (idempotently, so a crash between delivery and this write is repaired by a retry without a duplicate submission). **The cap is the *automatic* ceiling, and an operator can deliberately step past it once** ("Force re-review", issue #511): `grantReviewCapOverride` records the override on the capped record's own row (`cap_override_granted_at`), `reserveReviewVerdict` spends one such grant inside the same advisory-locked transaction that creates the slot it pays for — so a grant can never license two reviews — and `isCapReachingRequestChanges` compares `>=` rather than `===`, so the forced pass at ordinal 4 stops the cycle again exactly as the pass it continued did. Nothing SWARM does on its own produces an ordinal above the cap. **The re-review is scoped, not a fresh full pass (issue #328):** when the phase finds a prior `request-changes` verdict already submitted for this PR (`getPriorSubmittedReview`), it builds the re-review variant of the prompt (`buildReviewPrompt(..., isReReview=true)`), which tells the reviewer to verify *only* whether the previously requested changes were implemented correctly — approve when they were, otherwise request changes with a strong, specific fix instruction — and **not** to surface newly-noticed pre-existing issues the first review missed (the only admissible new findings are regressions the fix commits themselves introduced). This keeps each permitted re-review spent on confirming the fix rather than restarting the cycle over unrelated work. Only a submitted `approve` requests a merge (`pipeline.respondToReview.autoMerge`, issue #235) — the worker's Review success path persists one durable merge dispatch per approving run (`requestMergeAutomationIfEligible`, `src/worker/consumer.ts` → `src/worker/merge-automation.ts`, issue #292), and the dispatch's executor performs the direct PAT merge through the provider-neutral `ScmMergeProvider`, retrying transient `not-ready` outcomes on a bounded backoff (15s doubling to 5min, six retries). Every outcome lands on the Review run's `review_merge_*` columns; a terminal refusal (`not-eligible`, `policy-blocked`, `unsupported`, `provider-error`, `retry-exhausted`) is visible there and on the dispatch record but never fails the completed Review.
4. **Respond to review** — by default, the reviewer persona's `changes_requested` review → the implementer addresses the batch and writes a structured response → SWARM commits/pushes any fix and posts the response idempotently. `pipeline.respondToReview.skipOnMinors` defaults to true so approvals and comment-only reviews do not consume a separate agent run; set it false to respond to every reviewer-persona verdict. (SWARM's own Review no longer submits a comment-only verdict at all — issue #470, §3 above — so that clause now covers only a human's comment review arriving as the reviewer persona. Because an approval is skipped by default, a Review that approves with `minor`/`nit` findings states in its rendered body that nothing downstream will act on them, rather than leaving them reading as queued work.) The trigger resolves the submitted review's ledger record (by review id, falling back to PR/head for the narrow webhook race before the Review phase has stored it) and, on the safety cap's **last permitted** `changes_requested` verdict, stops here instead of dispatching — that PR needs a human, and the outcome is recorded as `manual-intervention-required` rather than starting an unbounded further cycle; a lookup failure for a `changes_requested` event fails the same way (closed) rather than risk reopening the cycle on a persistence outage. The one way past that stop is an operator's explicit **Force re-review** (`src/dispatch/force-re-review.ts`, issue #511), whose synthetic review event carries `forcedReReview` — the only flag that stands the cap gate down here, and with it the reviewer-persona gate, since a forced event is SWARM's own ledger record replayed by an operator rather than an inbound webhook whose author still has to be established. Respond-to-review's own outcomes (`fixed`/`pushed-back`/`no-findings`) never request a merge themselves — addressing feedback isn't a fresh approval. Like Implementation, it reports progress on the board as a status *report*, not a trigger: the card moves to "In progress" while the implementer works and back to "In review" once it has responded (best-effort — a card it can't resolve or move is logged and skipped, never failing the response). Neither status starts a phase, so bouncing the card can't re-fire Review; only a new fix commit does.

**Reliable follow-up Review after a `fixed` push (issue #241).** A `fixed` outcome whose commit was actually pushed and differs from the reviewed head reliably enqueues exactly one follow-up Review for the new SHA — reusing the same Review trigger, aggregate-check routing (`decideAggregateCheckOutcome`), reviewer persona, PR/head dispatch dedup, and durable review-verdict ledger a real `checks` webhook would drive, via a synthetic `checks` `completed` event (`src/pipeline/follow-up-review.ts`) carrying the PR number/branch/repo and new head. Unlike `selfEnqueueNextPhase`'s best-effort PM hand-off, this is part of the phase's own deterministic delivery: it runs after the push/comment delivery steps and before the delivery-progress checkpoint (`DeliveryProgress.followUpEnqueued`) is saved, so a queueing failure raises `DeliveryDeferredError` (preserving the worktree for a resumed retry) instead of silently dropping the follow-up, and the enqueued job's id is a deterministic hash of `(project, PR, new head)` so a crash between a successful enqueue and that checkpoint write can't duplicate the job. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head (the pushed commit somehow matching what was reviewed) enqueue nothing. A follow-up Review that approves may still request the same approval-only merge described above; Respond-to-review itself still never requests it.
5. **Respond to CI** — a PR's check suite completes with a failing check → worktree on the PR's task branch → Claude Code (implementer persona) inspects the failing checks, fixes the build surgically and pushes (or reports no code change was warranted) — mirrors Cascade's `respond-to-ci` agent. A per-PR fix-attempt cap stops a never-sticking fix from looping (each fix commit is a new SHA, so it re-triggers CI).

### Trigger wiring (SWARM-53)

The phases are self-contained orchestrators; the trigger registry (`src/triggers/`) is what connects inbound events to them. `registerBuiltInTriggers` (`src/triggers/builtins.ts`) registers four handlers under `src/triggers/handlers/`:

- **`pm-status-changed`** — one handler for both PM-driven phases. It names no provider (issue #297): `matches` delegates the "is this worth waking the pipeline for?" gate to `requireProjectPMAdapter(project).isStatusChange` — the one place that answers it, shared with the router's ingress filter — and `handle` re-reads the item authoritatively through the `PMProvider` the worker injected on the context (`ctx.pm`), never trusting the webhook's Status value (`docs/github-projects-v2-api.md` §5). Per `resolvePipelinePhaseForStatusKey(workItem.statusKey)` it starts Planning (→ Planning) or Implementation (→ ToDo), or returns `null` for any other status — including "In progress", which Implementation itself moves an item *to* as a status report, not a trigger. The Board view's drag-and-drop actually fires GitHub's `reordered` action (no `changes.field_value` at all — a real delivery confirmed this), not `edited`, so the adapter maps it to the neutral `moved` and accepts it alongside `updated`; a Redis-backed dedup (`pm-status-dedup.ts`) stops the resulting harmless within-column reorders from re-dispatching the same phase.
  - **The Planning gate is the `planned` label, and nothing else (issue #737).** A card entering Planning starts a Planning run unless it already carries `planned`; **to re-plan, an operator removes `planned` and moves the card Backlog → Planning.** A deferred phase resuming from its original event (`resumePmPhase`) is exempt. That replaced three concepts, one of which could not fire: a gate keyed on the preplan contract embedded in a split child's description plus its `swarm:split-child` label, an operator override label `swarm:replan` that invalidated the contract (**removed — nothing reads it, nothing creates it**), and a `preplan-invalidated` handler registered here to observe those label/body edits in place. The last one required a `work-item` event, which only GitHub's `issues` event maps to (`src/integrations/scm/github/webhook.ts`) — and the repository webhook subscribes to `check_suite`, `issue_comment`, `pull_request` and `pull_request_review`, never `issues` — so none of its three cases could happen; it is deleted rather than left registered and unreachable, and no `issues` subscription is needed to replace it. The preplan contract itself stays, demoted from gate to **content**: a run that *is* dispatched still reuses a split child's embedded plan rather than spending an agent (`evaluatePreplan`, `src/pipeline/preplan.ts`), and its `descriptionHash` still refuses a plan written against since-edited scope, because "should this dispatch happen" and "is the plan this dispatch found still about the same work" are different questions. A split child costs no agent run because the split labels it `planned` **before** moving it to Planning — the move is the event that dispatches, so labelling after it would race every child into the dispatch the label exists to stop.
- **`pr-review`** — the PR-lifecycle handler. Starts Review on a non-draft, **same-repo**, **SWARM-managed** PR opening or its checks passing, and routes a *failing* check suite to Respond-to-CI. A `review` disposition also reserves the durable review-verdict safety-cap slot (see Pipeline phases §3) after the dispatch dedup claim; `respond-to-ci` never consumes one. On a `checks` completion it re-queries *every* check on the head SHA (`SCMProvider.getAggregateCheckStatus`) rather than trusting the single event's own conclusion — a provider fires one event per workflow — and decides via `aggregate-check-decision.ts`: review if all complete and none failed, **respond-to-ci** if a check failed, or **defer** if a check is still running, scheduling a coalesced recheck (`scheduleCoalescedDispatch`) that re-queries fresh state. **A defer draws on one of two budgets, classified by why the handler could not decide** (issue #720): a *state-pending* defer — the provider answered but not finally (a check still running, no checks registered, `mergeable` still `null`) — spends `recheckAttempt` on a fixed ~30s cadence, capped at 20; a *read-failed* defer — the read never answered, because the provider threw (unreachable, 5xx, rate-limited, no resolvable reviewer token) or the run-history lookup threw — spends its own `readFailureRecheckAttempt`, capped at 15 on a capped exponential backoff (30s doubling to 5 min, ~62 min of outage outlasted). A read-failed defer carries `recheckAttempt` through untouched and a defer that *did* get an answer clears the read-failure count, so a source-control outage can no longer draw down the allowance reserved for CI that is still running — the failure mode that dropped a synthetic follow-up Review (`src/pipeline/follow-up-review.ts`), which has no later webhook to fall back on, when 17 of 20 attempts went to a DNS failure. Both caps stay bounded: for a webhook-driven review the fresh `checks` webhook every completing suite emits re-triggers anyway, but for that synthetic follow-up exhausting a budget really does abandon the review, which is why the reasons no longer share one. **A closed pull request ends a chain before either budget is touched** (issue #772): the mergeability gate reads the contract's `PullRequestDetails.state` — the same neutral `open`/`closed` pair `CommitPullRequest.state` carries, normalized by every provider — and skips a closed or merged pull request outright, because no provider ever reports a final `mergeable` for one. Without it a chain still in flight when the PR merged polled to its cap and reported a `failed` run for work that had already finished (PR #768: a stray `checks` chain kept polling for ~16 minutes after the PR was reviewed, approved and merged). That is a plain skip with no durable trace and no comment — the give-up records below are for a provider that failed to answer, not for a question that stopped mattering. **A terminal give-up leaves a durable trace** (issue #742): whichever path exhausts its budget writes one `failed` Review run (`createFailedRun`, `src/db/repositories/runsRepository.ts`) naming the pull request, head SHA, exhausted budget, attempts spent and last read, and carrying this event's payload so the abandonment is retryable from the dashboard. It goes to SWARM's own Postgres rather than the provider precisely because the give-up is usually *caused* by that provider being unreachable — in the incident behind issue #720 the give-up comment failed against the same DNS failure and the abandoned review left no trace anywhere, settling as an ordinary `no-trigger`. The pull-request comment (`scmCommentReviewGaveUp`, worded per budget) stays a best-effort extra on the mergeability path; the aggregate-check path, which posts none, is covered by the record alone. Fork PRs are dropped from the Review path (their head SHA is unreachable for the detached review checkout). A **work-item origin gate** (`isSwarmManagedPullRequest`, `src/triggers/swarm-managed-pr.ts`, issue #397) reviews only PRs SWARM manages, so a human- or third-party PR never burns a review: the PR's head branch must be exact `<branchPrefix><taskId>` (digits) **and** SWARM must hold an `implementation` run row for that work item in that project (status-agnostic — Implementation opens the PR from inside its own still-running process). It replaced an author-persona gate, which stopped carrying the signal once the implementer credential became the worker operator's own GitHub account (ADR-004 §3): a federated PR is authored by a plain user, and the control plane cannot even resolve another operator's identity. The gate is evaluated **once** for both entry events, inside the mergeability check that already fetches the PR — so it still runs *before* the `checks` path's heavier aggregate query, and that path no longer needs an author PR read at all. A failed run-history lookup degrades to the same bounded mergeability recheck as a failed PR fetch rather than dropping a legitimate review — both on the read-failure budget above, since neither read answered. The respond-to-ci dispatch reuses the same per-SHA dedup slot (review and respond-to-ci are mutually exclusive for a commit) and adds a per-PR fix-attempt cap (`respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- **`resolve-conflicts`** — a side-car handler for merged pull requests. It lists open same-repository, SWARM-authored PRs targeting the advanced base, retries GitHub's asynchronous mergeability result with bounded coalesced jobs, and dispatches only confirmed conflicts. Redis dedup keys each attempt by PR/head/base state; the implementer phase merges the base normally and checks the remote head before pushing. **A merged `src/db/migrations/` conflict gets a deterministic backstop, not just prompt guidance (issue #503/#508's own incident).** Drizzle's numbered `.sql` files and `meta/_journal.json` are generated artifacts with invariants a generic "preserve both sides' intent" merge does not know to hold — every journal entry must name a `.sql`/snapshot file that exists, and `when` must strictly increase across entries, or `PgDialect.migrate` silently *skips* an out-of-order entry rather than erroring on it. Confirmed live: three resolve-conflicts merges into one long-lived branch left the journal naming a `.sql` file that was never committed and gave the branch's own renumbered migration a `when` earlier than the entry `main` had already moved past — reaching review as two brand-new blocking findings unrelated to anything the implementer had actually been asked to fix, on every pass a further merge happened. The prompt now tells the agent to resolve a migrations-folder conflict by keeping `main`'s migrations untouched and running `npx drizzle-kit generate` for whatever this branch's schema still needs, rather than hand-editing the journal/snapshot — and `runResolveConflictsPhase` still runs `validateMigrationJournal` (`src/db/migration-journal.ts`) against the merged worktree before any commit/push, giving the same agent session **one** repair pass with the validator's own complaint (mirroring `readReviewSubmission`/`repairReviewHandoff`'s shape in `src/pipeline/review.ts`) and failing the phase — nothing delivered — if the journal is still inconsistent after that.
- **`pr-review-submitted`** — starts Respond-to-review on a `pull_request_review` `submitted` with `changes_requested`, authored by the *reviewer* persona (`getPersonaForLogin`). `pipeline.respondToReview.skipOnMinors: false` restores dispatch for approve verdicts (and for an inbound `commented` one — a state SWARM's own Review stopped producing in issue #470, but which a human still submits). Stops instead of dispatching on the safety cap's last permitted `changes_requested` verdict (see Pipeline phases §4).

A matched handler returns a `TriggerResult` naming the phase plus its resolved inputs; the worker's `processJob` (`src/worker/consumer.ts`) dispatches on that phase and calls the matching `runXPhase`, resolving the project's `PMProvider` from the PM registry (`requireProjectPMProvider`) for the two board-driven phases and for the automation-label gate on the four SCM phases (which fails open if that resolution cannot be read). The review handler is guarded by a cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62): a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, claimed before dispatch and normally left to expire by TTL (a dispatch that provably ran nothing hands it back instead — one that re-evaluated to `no-trigger`, or one the automation-label gate skipped; a *failed* run still leaves it to the TTL), so a PR that opens *and* then passes checks (or emits several check-suite successes) is reviewed once per commit rather than once per event. It fails closed — a claim it can't obtain (duplicate, or Redis down) skips the dispatch — and the respond-to-ci path shares that same slot before its own attempt cap runs.

`processJob` also self-enqueues the hand-off from Planning's `autoAdvance` to Implementation, rather than waiting on GitHub to echo that move back as a webhook (`selfEnqueueNextPhase`, `src/worker/consumer.ts`). The router's loop-prevention gate (`PMRouterAdapter.isSelfAuthored`) correctly drops *every* board status-change webhook authored by a SWARM persona — but Planning moves its own card to "ToDo" using the `implementer` persona, the very identity that gate checks against, so the direct webhook for that move is dropped every time by design. Left as webhook-only, the pipeline only ever advanced when some other, differently-attributed event for the same item happened to arrive later — unbounded, and observed live leaving an item in "ToDo" for hours with Implementation never dispatching. Instead, once a PM-driven phase's own move lands on a status that starts the next phase (`resolvePipelinePhaseForStatusKey`, `src/pm/pipeline.ts`), the worker enqueues a synthetic `pm` job for the same item — its event built by the provider's own `synthesizeStateChange`, since assembling one needs the board mapping the adapter owns — directly onto the BullMQ queue (`enqueueJob`, no `deliveryId` — the same "synthetic/manual" carve-out `src/queue/producer.ts` already documents), which re-enters the normal trigger-match → authoritative-re-read → dedup path a real webhook would. Best-effort: a failure to self-enqueue is logged, not thrown, so it can't turn an already-succeeded phase into a failed job.

## Task identity (issue #498)

**`taskId` is SCM-derived, and stays that way.** It names the worktree (`task-<id>`), pairs with the branch (`<branchPrefix><id>`) and with the pull request opened from that branch — all SCM artifacts. Deriving it from a PM key instead (a Jira `PROJ-123`, a Trello card id) would rename directories and branches without making anything more portable, and would break every existing worktree, branch, and run row for no gain. So the *shape* of a task id does not change when the board provider does.

What changed is **who derives it**. Two seams carry the card↔artifact relationship now, and neither is a URL pattern:

- **Card → task: `WorkItem.taskRef` + `WorkItem.taskRepository`** (`src/pm/types.ts`). The provider resolves its card's SCM artifact reference from its own linkage and hands it back on the item — GitHub Projects fills it from the backing Issue/PR's `number`, read in the same GraphQL round-trip that already yields `contentNumber`. Fields rather than a 16th `PMProvider` method, for the same reason as `statusKey`: the provider holds the linkage during its own board read. `undefined` means the card has no SCM artifact (a draft card, or a board with no SCM linkage at all), and an SCM-driven phase cannot run for it — `pm-status` logs and skips, exactly as it always has for a draft.
  - **The pair travels together, and the repository is the *card's* (issue #710).** A bare number names nothing, so `taskRepository` reports the `owner/repo` the linkage itself named — never the repository the provider's `ProjectConfig` happens to be scoped to. That is what lets a board-wide read answer per card: a board is project-wide, so one page can hold cards linked in several of the project's repositories, where matching them all against one scoped `repo` silently resolved nothing for the rest. GitHub Projects reports the backing Issue/PR's own `repository { nameWithOwner }` — the same authority `resolveItemRepository` routes on — rather than a declared token.
  - **Whether that repository is one the project owns is decided by the caller, not the provider.** A provider is built from a config *scoped to one repository*, which deliberately carries no repository list at all (`scopeProjectToRepository`; "Project record vs. scoped project config" above), so it cannot know. `src/triggers/handlers/pm-status.ts` — the one consumer — compares `taskRepository` against the run's own scoped `project.repo` through `repoSlugsMatch` (`src/scm/repo-slug.ts`, so casing and a `.git` suffix are noise, matching how ingress routed the card in the first place) and skips with both repositories logged when they disagree. So an honest miss stays a miss and a wrong-repository guess is impossible, and the *shared* code still holds no URL regex and no `pm.type` branch. It also closes a live defect: GitHub Projects used to hand `pm-status` a foreign card's issue number with no repository comparison at all, so a card for another repository sitting on a shared org board dispatched a phase in the wrong place.
  - **Linear answers it from a GitHub *issue* attachment** (issue #530's provider, `src/integrations/pm/linear/provider.ts`) — Linear's GitHub integration records the link as an issue attachment, so that URL's number *is* the SCM artifact reference and its `owner/repo` is the repository. Three deliberate consequences: a *pull-request* attachment does not qualify, since a PR link is an artifact of the task rather than its id; the Linear issue's **own `number`** is never used, because it would name an unrelated GitHub issue in a PR's closing keyword; and an unlinked card (including one this provider just created) leaves both fields unset and cannot start an SCM-driven phase, which is the honest answer rather than a guess. `findWorkItemForArtifact` is the same linkage read backwards, through `attachmentsForURL`. Shared code reads `workItem.taskRef`; the old `issueNumberFromUrl` regex over `WorkItem.url` in `src/triggers/handlers/shared.ts` is gone.
  - **Jira answers it from a GitHub *issue* remote link** (issue #490's provider, `src/integrations/pm/jira/provider.ts`), under the same three rules: a pull-request link doesn't qualify, the Jira issue **key** is never a task id, and an unlinked card leaves both fields unset. Two Jira-specific costs are visible rather than hidden: remote links are a separate round trip, so the pair is filled only on the reads that answer with a single card (a whole-board read leaves both unset — the one provider that meets the per-card rule by resolving nothing), and Jira indexes nothing on a remote link's URL, so `findWorkItemForArtifact` is a **capped scan** of the board's cards rather than a lookup.
  - **Trello answers it from a GitHub *issue* URL on the card** (issue #492's provider, `src/integrations/pm/trello/provider.ts`) — attachments first, then the description — under the same three rules, with the same `owner/repo` read off the matched URL.
  - **The one case a card can still be keyed against a repository the operator did not intend** is a card carrying GitHub issue links in *two* repositories: the first match wins, since only the caller knows which repositories the project owns and the provider cannot rank them without re-introducing the scope it was just taken off. Previously the scope silently picked; now the pair is reported and, if it is not the run's repository, refused and logged.
- **PR → card: `runs.work_item_id`** (`src/db/schema/runs.ts`). Every board-driven run persists the card it came from next to its `(project_id, task_id)`, so a later PR-driven phase recovers the card from SWARM's own durable link rather than guessing a URL: `findBoardItemIdForTask` (`src/db/repositories/runsRepository.ts`) returns the most recent run for that pair carrying a card. The task id it keys on comes from the PR branch (`issueNumberFromBranch` + the project's own `branchPrefix`), which is SWARM's naming convention, not a provider's.

That lookup is resolved **control-plane side**, where the DB is — by the assignment builder (`src/router/dispatcher.ts` → `boardItemId` on `TaskAssignment`), for every dispatch since issue #551 left one execution path — and injected into the phase, because a federated worker must not need a database (ADR-003 §2 / ADR-004 §3). `src/pipeline/respond-to-review.ts`'s `resolveBoardItemId` prefers the injected id and falls back to `PMProvider.findWorkItemByUrlSuffix('/issues/<n>')` only when there is none — a PR opened before this change, or a run row that was pruned. **That fallback is the last GitHub-shaped assumption in the card↔artifact mapping**, deliberately kept so pre-existing PRs keep reporting board status; it simply resolves nothing for a board whose item URLs have another shape, and the report is best-effort anyway.

Rejected alternative: stamping a `<!-- swarm:work-item id=… -->` marker into the PR body. It would need `PullRequestDetails` (`src/scm/types.ts`) to carry `body`, implemented by all three SCM providers — a wider blast radius for the same result — and it would still not help a PR created before the marker existed.

**Two sequential phases sharing one `taskId` is required, not a smell** (issue #759). Planning and Implementation both resolve their id from the same card (`src/triggers/handlers/pm-status.ts`, one handler serving both board-driven phases), because they work in the same `task-<id>` checkout on the same `issue-<n>` branch — giving Planning its own would put the plan somewhere Implementation does not read. The PR-driven phases suffix theirs (`<pr>-respond`, `<pr>-conflicts`, `<pr>-ci`) for the opposite reason: they run *alongside* a Review holding `task-<pr>`, so they need distinct checkouts. **Serialising the shared pair is therefore the dispatch layer's job, not the id's** — it admits one phase to `task-<id>` at a time, and it orders the pair (issue #761, below): the in-flight guard (`processJob`, `src/worker/consumer.ts`) keys on `(taskId, phase)` to tell a repeated delivery from the next phase, and makes the next phase *wait* for the checkout (`task-in-flight`, "Durable dispatch state machine" above) instead of dropping it. It had keyed on `taskId` alone, which made the ordinary progression "Planning finished → the operator moves the card to ToDo" indistinguishable from a duplicate webhook and dropped both — issue #754's Implementation dispatch was discarded 71 seconds before Planning finished, leaving the card in ToDo with both workers idle until a transition was produced by hand hours later.

**Ordering the pair is one-directional** (issue #761, which closed the caveat #759 left). #759's guard admitted one phase at a time but chose nothing between two deliveries that had *both* not started, so an Implementation could claim first and run without the plan it was dispatched to consume. The window is queue time *plus* execution time: on issue #754 a Planning dispatch sat queued for 6.5 minutes with nothing running, and the board gives an operator no sign that execution has not begun. **Implementation now defers while a non-terminal Planning dispatch exists for the same task; Planning never defers to Implementation.** That asymmetry is the point — a total order over two phases cannot be derived from the dispatch table at claim time (PR #760 tried over three passes; each ordering exposed its mirror), so nothing derives one. A yielding Implementation lands back in `pending`, which the executing read does not count, so no pair of dispatches can defer to each other and no interleaving can be produced by fixing one direction. A task with **no** Planning dispatch — the ordinary Backlog → ToDo path, which is most tasks — finds no hold and starts immediately: the rule is "do not overtake a Planning that exists", never "Implementation requires a plan".

The signal is the dispatch record's own `(task_id, phase, state)` (`findActivePlanningDispatchForTask`), not the `planned` label. The label's write is deliberately best-effort — `markSplitChildPlanned` swallows a failed `addLabel` so a refused label cannot abort a split mid-loop (issue #737) — so gating a second thing on it would let one swallowed failure both un-gate Planning and mis-order Implementation; and "a plan exists" is the wrong question anyway, since it would block the ordinary unplanned path. The dispatch row is normalized SWARM state that no provider payload is read for (`ai/RULES.md` §2), and the wait reuses #759's vocabulary rather than a new mechanism: the same `task-in-flight` deferral, visible as a `pending` dispatch plus a `deferred` run row with its reason stated, woken by Planning settling, with the reconciler's republish underneath. **The one residual window** is a Planning dispatch that has never been claimed, whose `task_id`/`phase` are still `NULL` — a queue hop rather than a wait. Closing it would need either a provider-shaped payload path or a new normalized column, and matching unresolved rows by `phase IS NULL` instead would make two duplicate Implementation deliveries defer to each other.

## Worktree lifecycle

Unchanged from `PROJECT.md` §4 — this part of the original spec is SWARM-specific and already correct:

- Main repo at `~/swarm/{project-name}/`, worktrees under `~/swarm/{project-name}/.swarm-workspaces/task-<id>/`.
- `git worktree add` per task; config/caches and the `cascade` sibling-checkout pointer (`.env`, root and nested package dependencies such as `node_modules` / `dashboard/node_modules`, `cascade`, build caches) grafted in via symlinks with **absolute** targets — a relative link would dangle at the worktree's `.swarm-workspaces/<name>/` depth (see `ai/RULES.md` §1).
- **The base is read through `origin/<baseBranch>`, not the local branch of that name.** Provisioning fetches `origin` first so the task branch starts from the current base, but a fetch only advances `refs/remotes/origin/*` — it never moves the local `main`. Cutting from the bare branch name therefore started every task off whatever that host last *pulled*, which on a host nobody pulls on is silently many commits behind the real base and lands as merge conflicts the pipeline then spends a Resolve-conflicts phase on. `createFreshWorktree` resolves `refs/remotes/origin/<baseBranch>` and uses it when it exists, falling back to the literal value otherwise — the same preference `hasUnpushedWork` already applied. The fallback is load-bearing rather than defensive: `ProvisionOptions.baseBranch` is not always a branch (Review detaches at a head SHA), and `refs/remotes/origin/<sha>` never resolves. Fetch failures stay best-effort, so an offline host still provisions from whatever it has.
- `git worktree remove --force` on completion.
- **Provision-time collision reclamation (issue #367).** When a phase provisions `task-<id>` and a checkout is already there, it runs the shared reclaim gate (`src/worktree/reclaim.ts`) before doing anything destructive. The gate applies one ordered, fail-closed safety check — a live worktree lease, a resumable deferred/failed run or checkpointed continuation pinning the checkout, uncommitted changes, then unpushed local commits. Only a checkout that clears all four is *reclaimed*: the phase atomically holds the task lease across removing the stale checkout and re-provisioning a fresh one (releasing the lease on any failed provision), so two concurrent provisioners can't both remove it. A checkout protected by any check is left untouched and the run settles **terminally** as a `BlockedRecoveryError` — it is no longer treated as a transient `worktree-exists` deferral that retried against the same protected checkout forever — persisting `recovery.state = "blocked"` with the exact reason (`live-leased`, `resumable-owner`, `dirty`, `unpushed`) and posting an actionable message on the item/PR.
- **A lease is only honoured while it has a live owner (issue #427).** The lease key carries an opaque token, not an owner id, so a run that died — or completed — without releasing it left an orphan that wedged every later run for that task as `live-leased` until the 4h TTL expired, recoverable only by hand. The collision gate therefore checks *liveness in the database* before honouring a lease it could not claim (`src/worktree/lease-liveness.ts`): an owner is another `running` run (`hasLiveRunForTask` — the same query the reset path's `hasLiveOwner` resolver uses, so the two paths cannot drift), or another `leased`/`running` dispatch, for the same `(projectId, taskId)`. The asking attempt's own `runId` — threaded in through `ProvisionOptions.runId`, which `runAssignedPhase` passes to **every** phase and each phase forwards to `provision` — is excluded, since its run row is already `running` by the time it provisions, and a retry of a crashed run reuses that id so its own leftover lease reads as stale. With an owner, the run blocks as `live-leased` exactly as before. With none, the orphan lease is adopted by compare-and-set against the token actually observed (`takeOverWorktreeLease` — a provisioner that legitimately claimed it in between still wins) and the checkout behind it goes through the *same* ordered reclaim gate, so a dirty, unpushed, or resumable-pinned checkout is still retained and never force-removed. The token is read *before* liveness is evaluated, so a run that becomes the genuine owner after that check invalidates the compare-and-set instead of losing its checkout. Every uncertain outcome — no `runId`, a database or Redis error, a lost compare-and-set — reports "live" and blocks, so the fix only ever removes protection where the owner is provably gone. Liveness is deliberately not extended to `worker_sessions` heartbeats: a worker still writing after its run and dispatch have both been reaped as timed out has no database owner, and that window is accepted rather than closed because the reclaim gate behind this one still retains any dirty or unpushed checkout — only a provably clean, fully pushed one can be reclaimed there.
- **The DB-free runtime coordinates only its own host (issue #535).** `GitWorktreeManager` receives a `WorktreeRuntime`: the store-backed default keeps the Redis lease + Postgres liveness/pin/cancellation implementation above unchanged, while `runAssignmentDbFree` injects `host-local-runtime.ts`. The **retention sweep picks the same one** (`retentionWorktreeRuntime`, `src/worktree/retention.ts`, issue #551), keyed on the dispatch mode, so it reads the markers this host's worker actually writes rather than a store nothing sets. Its atomic lock directories and takeover guards serialize provisioners on that filesystem, its owner record checks this daemon's in-flight dispatches (or a live peer PID), and a preservation pin outside the checkout retains a resumable deferred/failed run without making the worktree dirty. The same reclaim gate still checks lease → pin → dirty → unpushed in that order. A different host cannot see or block on these files, and this path never creates an `ioredis` client. **Every artifact it writes carries an expiry**, because the Redis lease it replaces had a 4h TTL and that TTL was load-bearing (issue #427): a lock, a takeover guard, or a preservation pin stranded by a crash is reaped by the next provisioner rather than wedging the task until an operator deletes a file by hand. **An expiry only the next provisioner evaluates is not enough on its own** (issue #721): a task never dispatched again keeps its lapsed artifacts forever, and `preserve()`'s `<pin>.<uuid>.tmp` staging file — strandable by a crash between its `writeFileSync` and its `renameSync` — has no next reader at all, so the retention sweep applies the same TTLs proactively (`sweepStaleHostLocalState`, above), TTL-only because the sweeping process is not the daemon and can trust neither an in-flight set it cannot see nor a pid it did not write. Liveness (this daemon's in-flight set, or a peer PID) still answers sooner and more precisely than the clock, but **the recorded timestamp is checked before either liveness answer** (issue #717), so no liveness path is unbounded; it remains the backstop for what liveness cannot see — a recycled PID, a crash between two syscalls, a truncated write, an in-flight entry the daemon never cleaned up. That ordering is the fix for a recurrence of #427's failure class on the lease that replaced the Redis one: the same-process branch used to return first, and since the recorded PID is the *daemon's* — it outlives every phase it dispatches — virtually every lease on a worker host takes that branch, so one leaked in-flight entry reported "live" with no bound at all (task `702-conflicts`, wedged 8h42m, cleared only by restarting its daemon, because no control-plane action reaches a `.swarm-state` file on a worker host). The standing rule that follows is that a branch here may answer *sooner* than the expiry but never be *exempt* from it. The ordering costs nothing real: a configured per-phase timeout caps at 45 minutes (`AgentConfigSchema`), far inside the 4h lease TTL, and the Redis lease was never heartbeated either — it lapsed under a live phase too. Expiry never force-removes work: the reclaim gate behind it still refuses a dirty or unpushed checkout. `repoRoot` follows the same ownership rule: it is omitted from `TaskAssignment` and resolved from `SWARM_WORKER_REPO_ROOT` (default cwd) on the executor — and because that one path serves every project the worker is enrolled in, provisioning first asserts the checkout's `origin` actually resolves to the assigned `project.repo`, so a daemon launched in the wrong directory fails loudly instead of cutting task branches in an unrelated repository. That one path can also be handed to *two* daemons, which is why the daemon locks it for its whole life before handshaking (`src/worktree/checkout-lock.ts`, issue #689): same atomic-`mkdir` claim, same shared liveness primitives (`src/worktree/local-lock.ts`), but its own short, refreshed TTL — a process that lives for days cannot be bounded by a TTL sized for one agent run.
- **A checkout provisioning cannot have exactly as asked is adapted, not failed (issue #558).** Git enforces one checkout per branch and refuses `-b` for a branch that exists, and both rules turned ordinary leftovers into a phase that could not start at all. `createFreshWorktree` therefore resolves *how* to check out from what the repository actually holds: a task branch that survived `reapOrphanedBranch` (kept because `origin` has it, so a PR may depend on it) is **checked out** rather than cut again — the state a hand-removed preserved checkout leaves, which used to fail the next attempt with `a branch named '<x>' already exists` — and a branch another worktree already holds is checked out **detached** at `origin/<branch>`, so a *preserved* checkout kept for its own retry stops making every other phase that needs that branch unrunnable (`'<branch>' is already used by worktree at …`, which is how a Respond-to-review for an open PR failed on sight). Detaching costs the delivery nothing: commits are made on the detached HEAD and pushed as `<sha>:refs/heads/<branch>`, so the phase runs and pushes exactly as it would have, and the handle still names the branch it targets. The lookups are skipped where they cannot apply (a create-path branch that survived no reap can be held by nothing), so an ordinary first provision runs the same git commands it always did.
- **A reset's discard intent travels to the worktree, not the other way round (issue #592).** "Reset & restart" (`resetRun`, `src/dispatch/run-reset.ts`) runs in the API server, so the `reconcileTerminatedWorktree` it performs settles only the control-plane host's filesystem — right for a checkout that host's own worker holds, a no-op otherwise. In a federated deployment the checkout is usually somewhere else, where that teardown reported `absent` and the replacement dispatch then failed on the exact `Worktree collision for task '<id>' … uncommitted changes` the reset was issued to clear. A reset therefore also puts `recoveryMode: 'discard'` on the replacement dispatch's payload — the fourth `RecoveryMode` (`src/queue/jobs.ts`), and the only one permitted to destroy protected work — which rides `TaskAssignment` to whichever worker holds the checkout and is honoured by `executeRecoveryGate` there: remove it unconditionally, then provision fresh. It is **one-shot**, dropped by `deriveRetryJobPayload` like `'checkpoint'`, so a later automatic deferral of the same run cannot destroy a checkout that deferral had just preserved for a resume. Since issue #744 *every* reset carries it: the provision-time reclaim gate's dirty/unpushed/pinned protections still govern every other path, but a reset is the deliberate "this checkout is worthless" action and no longer has a variant that leaves them in charge. No teardown request/result frame pair was added — `resetRun` has no request channel to the router (only Redis pub/sub and BullMQ), and worker affinity already routes the restart to the host holding the checkout.
- Stale `task-<id>` worktrees left behind by interrupted runs are reclaimed by a retention sweep running periodically in the background of the **API server** — the control-plane host process that owns it (see "Process responsibilities" above), since the worker is DB-free and executes phases only — or manually on-demand via `swarm worktrees prune`. The sweep preserves up to a configurable number of most-recently-active worktrees (defined by `worktreeRetention.maxWorktrees` in the project config, defaulting to 10), and runs the *same* reclaim gate on each prune candidate so it never removes a worktree that is leased (in-flight), pinned by a resumable deferred/failed run, has uncommitted changes (`git status`), or carries unpushed local commits.

## Harness (agent-CLI execution engine)

Once the worker has a provisioned worktree, it hands off to the harness (`src/harness/agent-cli.ts`, `runAgentCli`) to actually run the agent. The harness is deliberately narrow: it spawns `claude` or `antigravity` (Node's `child_process.spawn`, no subprocess library) with the worktree as CWD, streams stdout/stderr line-by-line (optional callbacks + `logger.debug`) while accumulating the full output, and resolves with `{ exitCode, signal, stdout, stderr, durationMs, timedOut }`. A non-zero exit is a normal outcome the caller inspects — only a spawn failure (e.g. the CLI isn't installed) throws. `timeoutMs` and an `AbortSignal` both kill the run (SIGTERM, escalating to SIGKILL). Prompt construction, persona/token selection, and the queue→worktree→harness→cleanup lifecycle live in the worker (SWARM-17), not here.

**Live output (issue #356).** Claude runs in print mode with `--output-format stream-json --verbose`, not `json`: the single-document format is buffered until the process exits, so a run's log stayed empty for its whole duration and got one event at termination. `src/harness/claude-stream.ts` decodes those NDJSON records incrementally into readable lines (assistant progress, `Tool started/completed/failed: <name>`, and a one-line rendering of a failed terminal `result` record) and forwards them through the same `onStdout` callback every CLI uses — tool inputs, tool results, and thinking are never rendered, and unparseable protocol lines are dropped rather than leaked. The terminal `result` record still supplies the run's final text, session id, and usage (`src/harness/usage.ts`), and its rendered error line is what failure classification reads, so a streamed 429 stays a deferred, resumable rate limit. **The control plane performs that write, for every run** (issue #544). The worker streams its lines up as `stream-log` frames — batched every 100ms by the transport executor's own wrapper (`createAssignmentRunAgent`, `src/transport/assignment-execution.ts`), flushed on every settle path, and, for Claude only, carrying a "still running" heartbeat after 30s of silence so a working run is distinguishable from a hung one — and the control plane appends them to `run_output_events` (`src/router/stream-log-persistence.ts`), fire-and-forget but ordered per run. `src/worker/live-output.ts` is what remains of the retired in-process batcher: the heartbeat's cadence and its rendered line, shared so that one *user-visible* string has one definition. The worker never persists locally, so every worker — the control-plane host's own included — produces identical output.

**Capability-aware target routing (issue #346).** A phase's agent config holds an *ordered* list of `targets` (`agents.<phase>.targets`, `src/config/schema.ts`). **#339's eligibility gate is what walks that list against a real host's capabilities** — the CLIs an enrolled worker declares — selecting a worker and a target together and binding the target to an authenticated worker execution claim. `selectTarget` (`src/worker/target-selection.ts`) is the pure ordered walk the gate's decision is adapted back into (`targetSelectionFor`, `src/worker/consumer.ts`); a dispatch the gate selected no worker for resolves **no availability set at all** and so keeps the phase's highest-priority target. Nothing is routed against the control plane's own installed CLIs: `processJob` runs there and executes nothing, so the `cli_quotas` snapshot — which describes the hosts that ran discovery, not the host that will execute — no longer has a routing consumer (issue #703). `agentOverrideFor` (`src/worker/consumer.ts`) feeds the resolved `cli`/`model`/`reasoning` into the unchanged four-tier model chain. A per-run pinned retry (`cliOverride`/`modelOverride`/`reasoningOverride`) bypasses routing and is evaluated as one exact target.

**Model + reasoning mapping (issue #180).** The harness takes a *logical* `model` plus a normalized `reasoning` level and turns them into per-CLI launch args through `resolveModelLaunch` (`src/harness/models.ts`), the one place provider-specific reasoning semantics live: Claude gets `--model <alias> --effort <level>`, Codex gets `--model <id> -c model_reasoning_effort="<level>"`, and Antigravity — which has no reasoning flag — gets the reasoning folded back into the combined `agy models` variant string it passes to `--model` (e.g. logical `gemini-3.5-flash` + `high` → `"Gemini 3.5 Flash (High)"`). A pre-#180 config that stored the combined string directly is recognized and passed through verbatim, so it keeps launching that exact variant. Omitting reasoning preserves each CLI's own default (no flag for Claude/Codex; the model's default variant for Antigravity). `src/harness/models.ts` is the versioned capability catalog — logical models, their supported reasoning levels, and known defaults — cached in code, never discovered by invoking a model.

### Durable dispatch state machine (issue #284, ADR-002)

Every attempt to start or resume a pipeline phase is one row in the Postgres
`dispatches` table — the single source of truth for pending/in-flight
orchestration state (`docs/decisions/ADR-002-durable-dispatch-state-machine.md`).
BullMQ jobs are pure wake-ups carrying a `dispatchId`; the worker acts only
after atomically claiming the dispatch (`pending`/`retry-scheduled` → `leased`),
so a cancelled, completed, or superseded dispatch refuses every late delivery —
redelivery, delayed retry, slot release, or reconciliation. The lifecycle is
`pending → leased → running → completed/failed`, with `retry-scheduled` for
deferred attempts (the derived retry payload is persisted on the row *before*
any queue work, so a crash never loses retry intent) and `cancelled` for
user/operator cancellation. Wake-up job ids are deterministic per
(dispatch, wake sequence), so the reconciler's re-publish is a queue no-op when
the wake-up already exists. Project-capacity waits are `pending` dispatches with
wait reason `project-capacity`, woken by slot releases under the
continuation-priority policy — there is no separate Redis registry. **A second
event-woken `pending` wait sequences the phases of one task** (issues #759 and
#761): a dispatch whose task has an *earlier* phase that has not settled waits as
`task-in-flight` and is woken by that phase settling
(`promoteTaskInFlightWaits`, from `processJob`'s `finally` — every settle path,
success or not), rather than being discarded. The *same* phase arriving twice is
still completed `skipped-duplicate`, so the two halves of that collision stay
distinguishable on the row; and the collision is read from the dispatch table as
well as from the worker's in-process map, so the verdict does not depend on which
worker the dispatch was routed to. Two durable reads answer it, under one wait
reason: `findExecutingDispatchForTask` (`leased`/`running`, excluding the asking
dispatch and `merge-automation`), which every phase waits behind, and
`findActivePlanningDispatchForTask` (any non-terminal state), which **only
Implementation** asks — so it cannot overtake a Planning dispatch that is merely
queued (issue #761, "Task identity" above). Nothing asks the mirror question, so
the second read can never produce a mutual defer. Both
pre-run waits share one deferral (`deferBeforeRun`): no attempt spent, the run
row visible while it waits, continuation dedup claims retained, and the
reconciler's republish underneath (a `pending` row is wakeable unless it waits on
project capacity). A worker
startup + periodic reconciler (`src/dispatch/reconciler.ts`) reclaims expired
leases (failing the dispatch and its still-`running` run together), re-publishes
lost wake-ups, and — once, at startup — imports legacy shapes (Redis
pending-continuation entries, deferred runs with no active dispatch, and
pre-#292 `not-ready` merge-follow-up intent) as durable dispatches.
Merge automation is the one agent-less dispatch kind (issue #292): a
`merge-automation` payload (dedup key `merge:<reviewRunId>`, linked to the
approving Review run) skips triggers, worktrees, and project slots entirely —
`processJob` routes its claimed wake-up straight to
`processMergeAutomationDispatch`, which merges via the `ScmMergeProvider` and
settles the dispatch itself (`completed` with a `merge-*` outcome, `failed` on
a provider error, or `retry-scheduled` while transiently `not-ready`).

The dashboard deliberately exposes two complementary read models (issue #313):

- **Queue is dispatch-centric.** The Queue API/UI (`runs.queued`) reads every waiting
  dispatch from Postgres — state, wait reason, priority, and scheduled time — never a
  BullMQ snapshot. `swarm queue clear` cancels those canonical records first. A fresh
  dispatch with no `runId` is Queue-only because no persisted attempt exists yet.
  The *view* is narrower than the table, deliberately: `runs.queued` returns
  `{ items, noTrigger }`, partitioning out a board dispatch whose card status the
  enrichment's own board read proved maps to no pipeline phase (issue #570 — SWARM's
  own `In progress` status report echoing back, a card being filed, a column reorder).
  Nothing about the dispatch lifecycle changes: those rows are still created, claimed,
  and settled as no-triggers, and they stay observable as a counted, expandable group
  under the queue. The decision is the server's — the code that already read the board —
  so no client has to learn to hide them, and it keys on the proven case only, leaving
  the enrichment's fail-open behaviour intact.
- **Runs is run-centric.** The Runs list (`runs.list` / `listRunsFromDb`) reads persisted
  attempts by their normal lifecycle, but hides a retry-pending (`deferred` or `checkpointed`) attempt linked to a pending
  or retry-scheduled dispatch to avoid displaying a duplicate row (issues #279/#316).
  Retry-pending attempts with no waiting dispatch remain visible in Runs as history and for operator recovery.

### Failure handling & rate-limit retries (issue #91)

A phase whose agent exits non-zero throws, and `processJob` turns that into a `phase-failed` `JobOutcome` rather than rethrowing — an agent run isn't idempotent, so a BullMQ retry storm is worse than surfacing the failure (the phase already logged the agent's stdout/stderr, and the `attempts: 3` default only ever fires for the infra throws that happen *before* the agent runs). The exceptions are transient failures: a **usage/session-limit** hit where the agent never did any work, an **aborted** run where the worker itself shuts down mid-phase, or a deterministic-delivery failure after the agent has already produced a valid checkpoint. Delivery deferrals preserve the worktree and expose the wrapped push/hook/API cause in the run rather than misreporting it as a worker shutdown.

**Not every delivery failure is deferrable, and delivery state is not only local (issue #558).** The progress sidecar that makes a delivery resumable lives on one worker's filesystem, while an interrupted dispatch goes back to the pool and may be re-dispatched to a machine holding none of it — so a resumed Implementation used to re-run the agent and produce a *second* implementation of the same task, on a branch whose remote already carried the first. Two rules close that: Implementation asks the SCM whether its task branch already has an open PR **before** running the agent (`findPullRequest`, the same answer on every host) and, finding one, adopts that delivery — no second agent run, no second commit — completing only the reporting the interrupted attempt still owed, with the PR-link comment carrying a per-delivery marker (`implementationDeliveryMarker`, mirroring Planning's) so a resumed attempt reuses its own comment instead of posting a duplicate. And a push that cannot fast-forward is classified as a terminal `DeliveryDivergedError` by `pushDeliveredBranch` (`src/scm/delivery.ts`) — the shared wrapper every pushing phase goes through — rather than a `DeliveryDeferredError`: only a *proven* divergence (the remote head is not an ancestor of the delivered commit) qualifies, so a transient rejection keeps its retry, while the unwinnable one settles at once with both SHAs named instead of spending four attempts on an identical rejection and holding the branch away from the phase that could unblock the PR. `shouldDeferDeliveryFailure` is the single predicate all five delivery-owning phases apply, so the two cannot drift. Both rules live in the phase and the shared delivery seam, so a control-plane-delivered write and an operator-token one behave identically.

`src/harness/agent-failure.ts` classifies a failed run (`classifyAgentFailure` → `rate-limit` | `capacity` | `auth` | `timeout` | `aborted` | `stalled` | `error`). Harness timeout and abort take precedence, followed by capacity and quota signals; a recognised auth banner then outranks only a trailing response-stall marker. This keeps a provider quota condition from being hidden by auth prose while ensuring a real login failure is not deferred as a generic stall. `auth` (issue #343) is the one recognised kind that is *not* a retry signal: it is classified so the run headline reads `… (authentication failed) …` instead of a bare `exited with code 1`, and is deliberately absent from the deferral list below — no wait restores a login, only a human re-`/login`. On a `rate-limit`, `capacity`, `aborted`, or genuinely-interrupted `timeout` error, `processJob` returns a `phase-deferred` outcome with a computed delay instead of `phase-failed`, having already persisted the derived retry intent on the durable dispatch record and published its delayed wake-up, capped by retry budgets. The retry delay is floored above the review-dispatch-dedup TTL.

`capacity` is a transient **provider-capacity** signal, matched per CLI so one CLI's provider error isn't triggered by another merely quoting it: Codex's structured `error` / `turn.failed` events containing `selected model is at capacity` anywhere in captured output (or its textual terminal banner), and Claude/Claude Code's terminal `529 Overloaded` / `overloaded_error` banner (Anthropic's documented temporary-overload response — issue #229). It defers on a shorter capacity budget (`MAX_CAPACITY_RETRIES`, `MIN_RETRY_DELAY_MS` backoff) and retries **fresh, not resumed** — the provider rejected the request before the model did any work, so there is no partial reasoning or edit to continue. Only a bare status number never matches; human-readable provider banners use a conservative terminal-output window, so borrowed CI logs or reviewed code mentioning these numbers stay a plain `error`.

When Tier 1 session recovery cannot serve an involuntary stop, a parseable phase-matching `swarm_checkpoint.json` selects a Tier 2 continuation. Its run settles as retry-pending `checkpointed`, carries no session id, and the bounded continuation starts fresh from that checkpointed checkout.

A retry **reuses the originating `runs` row** rather than inserting a second one (issues #136 and #146): the `phase-deferred` outcome carries the run's `runId`, the dispatch settle path (`settleDispatchRetry`, `src/worker/consumer.ts`) persists it in the derived retry payload on the dispatch record, and on the next claim `processJob` resets that same row to `running` (clearing `completedAt`/`error`/`nextRetryAt` and the outcome columns) instead of creating a new one. A fresh webhook that intentionally reruns a deferred, checkpointed, or failed task/phase also claims and resets its latest terminal row, so automatic retries, manual retries, and user-triggered reruns all remain one logical dashboard run. A **manual "Retry now"** (the `runs.retryNow` tRPC mutation, offered for `deferred`, `checkpointed`, and `failed` runs) never flips the run row itself — the run turns `running` only when the worker actually claims the dispatch, so a failed enqueue can't strand a false `running` run (issue #284). It re-opens the run's active dispatch for an immediate attempt with `rateLimitRetryAttempt` reset to 0 (bypassing the automatic cap), folding any cli/model/reasoning overrides into the stored payload; a run with no active dispatch (terminally `failed`, or a legacy orphan) gets a fresh dispatch reconstructed from the row's persisted `jobPayload`. The conditional dispatch transition plus the one-active-dispatch-per-run unique index prevent concurrent automatic/manual retries from starting the same row twice. **"Reset & restart"** (the `runs.reset` mutation over `resetRun`, `src/dispatch/run-reset.ts`, issue #424) is the last-resort variant for a row "Retry now" cannot move: it additionally cancels the run's active dispatch, clears the Redis cancellation flag, tears down the checkout and its worktree lease (including a *stale* lease no live run owns), and clears the recovery record and captured session id before re-dispatching that same row from its stored `jobPayload` with a fresh agent session. **That replacement payload is composed as a first attempt, not as a retry** (issue #741): it is built by `reconstructResetJob` rather than the manual-retry builder, which strips every member of `RecoveryIntentSchema` — the session to re-enter, the delivery progress, the provisioned task branch, and any stored `recoveryMode` — by schema, so a latch added to the intent is dropped with no edit there, and sets only the reset's *own* mode (`'discard'`, on every reset since issue #744). The run row's stored payload is sanitised the same way, because that column is what a *second* reset and "Retry now"'s reconstruct-from-row path read; a failed sanitisation warns and continues, since the restart itself is already clean. Inheriting the intent is what made a run whose payload recorded `implementationBranchProvisioned` re-provision with `createBranch: false` against a branch that no longer existed on *every* reset, dying on `fatal: invalid reference: <branch>` while an ordinary fresh dispatch of the same task ran fine. The replacement dispatch is created last, so a partial reset leaves the run terminal-and-idle — the state a second reset retries from. **It never refuses and always discards** (issue #744): there is no `force` option, and a `running` row, a dispatch a worker just claimed, dirty/unpushed/pinned/stale-`live-leased` work, and a local teardown that throws are all handled rather than refused. **It also stops the agent that row already spawned** (issue #745) — the step that ended the two-step "Terminate, then Reset" dance. It reuses the delivery path that already exists rather than inventing one: the run-id-keyed cancellation `runs.terminate` records (`requestRunCancellation`, `src/queue/cancellation.ts`), which the router's bridge (`src/router/dispatch-cancellation.ts`, issue #549) turns into a pushed `task-cancel` frame to the worker actually executing the run — the only channel a DB-free worker has. The **wait** after it is the load-bearing half: `resetRun` polls the run row (500 ms, capped at 15 s — `AGENT_STOP_POLL_INTERVAL_MS`/`AGENT_STOP_WAIT_MS`, deliberately not configurable) until it leaves `running`, and only then clears the marker, tears the checkout down and creates the replacement dispatch, so the dying attempt's terminal result settles the *old* dispatch id rather than landing on top of the restart. The marker is cleared between the wait and the restart for the same reason it always was — earlier would let the worker's start-check miss the stop, later would kill the fresh attempt. A wait that expires proceeds anyway and says so (`agentStop: 'not-running' | 'stopped' | 'timed-out'`, reported by both surfaces): a reset that refused on an unconfirmed stop would strand the wedged run it exists to free. Only two answers are not a restart, and neither leaves a run un-reset: `run-not-found` (nothing to reset) and `already-resetting` (the one-active-dispatch-per-run unique index says a restart *is* happening). A run that cannot produce a dispatch at all — no stored payload, or a project that no longer exists — has its dispatch, flag and recovery record cleared just the same and is then settled `failed` with the stated reason, returned as `{ outcome: 'terminated', reason }` beside the ordinary `{ outcome: 'restarted', dispatchId }`. The dashboard surfaces it on the run-detail page for a `failed` (incl. recovery-`blocked`), `deferred`, or `checkpointed` run (issues #428 and #504): a confirmation modal names each step and states plainly what is destroyed — the checkout with any uncommitted and unpushed work in it, a dispatch a worker just claimed, and (for a `running` row) the agent process that is stopped first, taking its in-progress work with it — rather than offering an opt-in, and renders the mutation's per-step report — the agent stop, dispatch outcome, this host's checkout removed/retained (+ reason) or the error its teardown threw, the discard intent the replacement dispatch carries to the worker holding the checkout (issue #592), new dispatch id or the terminal reason — so an operator can tell a reset that freed the checkout from one that left it for the holding worker to clear. For a `checkpointed` row, that same "Retry now" control is labelled "Continue now" and invokes the unchanged `runs.retryNow` mutation with `recoveryMode: 'checkpoint'`. **How those actions are offered differs by state (issue #593).** A `deferred` or `checkpointed` run has not ended in an error — one waits on a scheduled retry, the other on a scheduled continuation — and keeps "Retry now"/"Continue now", "Terminate", and "Reset & restart" as side-by-side buttons. A `failed` run instead exposes **one "Recover" control**: a popup listing whichever recovery choices are currently eligible (the retry-family action under its own resume/recheck label plus the cli/model/reasoning overrides, and "Reset & restart" with its unchanged confirmation), where choosing one closes the popup, submits only that action, and turns the trigger into a disabled status label (`Retrying…`, `Resetting…`, `Waiting to restart…`) until it resolves. Retry and reset are two ways to recover the *same* errored run, so as two live buttons both could be submitted while the first was unresolved; consolidating them puts both behind one pending state. That state is the durable one — both mutations open a `manual-retry` dispatch, so `resolvePendingRunRequest` reports either as the run's outstanding `restart` request (issue #561) and the block therefore holds for a second viewer and across a reload — with the local mutation adding only what the derived fact cannot say: *which* choice this operator picked, so the label can name it during the HTTP round-trip. `swarm run reset <runId>` (`src/cli/commands/run.ts`, issue #429) is the second surface over the same service, printing that same per-step report and exiting non-zero with the refusal message: like `swarm queue clear` / `swarm worktrees prune` it goes straight to Postgres + Redis, so a wedged run can be freed with the worker — and the API serving the dashboard — stopped. **"Force re-review"** (the `runs.forceReReview` mutation over `forceReReview`, `src/dispatch/force-re-review.ts`, issue #511) is the run-recovery action for a different stuck state — not a wedged row but a *deliberately stopped* one: a completed Review run whose cap-reaching `request-changes` verdict set `manual-intervention-required`. It grants the PR one extra review slot on its ledger record and enqueues the corrective Respond-to-review run as a synthetic `pull-request-review` event carrying `forcedReReview`; the ordinary pipeline (response → follow-up Review) then continues unchanged. Guards run before either mutation and the grant precedes the dispatch, so a failure between them leaves an unconsumed grant and no work — which the next call re-uses. Both writes are conditional (the grant fires only while none exists; the dispatch's dedup key is a deterministic hash of (repo, PR, reviewed head)), so repeated clicks and concurrent requests resolve to one corrective cycle rather than duplicating it. That deterministic key is permanent, though, and a dispatch can resolve *dead* — `no-trigger`, `skipped-not-eligible`, `skipped-duplicate`, `superseded`, `failed`, `cancelled` — without ever starting Respond-to-review (confirmed live: a worker process that hadn't yet picked up this feature's own code evaluated the synthetic event as an ordinary, author-less webhook and refused it). `publishForcedDispatch` treats only a non-terminal dispatch or a `completed`/`phase-succeeded` one as "already handled"; anything else is dead, and it chains a fresh dedup key off the dead row's own id (`forceReReview`'s `dispatch: 'retried'` result) rather than reporting the dead attempt as done — bounded at five chained attempts so a persistently broken corrective path fails loudly instead of looping. It is authorized exactly like "Reset & restart" — `member`+ on the run's project — and the dashboard renders it inside the existing "Manual action required" callout using that action's interaction shape (confirmation modal, disabled-pending trigger and confirm button, per-step success report, refusal message inline).

### User-initiated termination (issue #166)

A **running** or **deferred** run can be terminated from the dashboard (the `runs.terminate` tRPC mutation). The API server and worker are separate processes, so termination never touches a PID: `terminate` records the intent in a durable, run-id-keyed Redis set and publishes a notification (`src/queue/cancellation.ts`). For a **running** run the worker aborts the agent via the per-run `AbortController` threaded into the phase (the same SIGTERM→SIGKILL path shutdown uses), and settles the row as `failed` with a user-termination reason — `handlePhaseFailure` checks the cancellation set to tell a user termination apart from a worker-shutdown abort (which still defers). For a **deferred** run `terminate` atomically cancels the canonical dispatch record and flips the row `deferred → failed` together (`cancelDeferredRunInDb` — a cancelled dispatch refuses every future claim, so no retry, slot release, or reconciliation can resurrect the work; issue #284); if a concurrent automatic pickup wins that race, the transition loses, the run is now `running`, and the cancellation flag drives the worker to terminate it instead. Keying on the immutable run id (not the task id) means a later retry of the same task is never terminated by an old request, and `retryNow` clears the flag before re-running. The mutation is idempotent: an already-terminal run returns its settled state rather than erroring. Captured logs are preserved (the aborted agent's output is stored like any failed run); only the board "failed" comment is skipped, since an intentional stop isn't a stall to investigate.

**Reaching the worker (issue #549).** A worker holds no `REDIS_URL` to read the cancellation marker with. The notification is therefore forwarded rather than consumed: the control-plane dispatch consumer subscribes (`src/router/dispatch-cancellation.ts`), resolves the run id to the dispatch it pushed and the worker it pushed it to (the run-id index on `src/router/dispatch-results.ts`), and pushes a `task-cancel` control frame down that worker's socket. The worker aborts the matching in-flight assignment through the same per-run `AbortController` (`cancelAssignment`, `src/transport/assignment-execution.ts` — a `dispatchId`-keyed registry of this daemon's in-flight assignments) and settles the dispatch terminal-`failed` with `cancelled: true`, which `src/router/dispatcher.ts` raises as a `RunTerminatedError` so the *shared* settle path applies the same user-termination outcome the pre-start marker check does — never a deferral, which would re-run the killed phase. The frame is additive, so `TRANSPORT_PROTOCOL_VERSION` is not bumped: a daemon predating it logs and ignores the frame rather than closing its socket. Two things stay durable-first: a cancellation recorded *before* the assignment was pushed is caught by a single marker read straight after the push (its notification predates the index entry, so it found nothing), and a run that is not executing on a connected worker — queued, deferred, already settled — is left entirely to the marker, exactly as before. **The worker answers a cancel it cannot apply (issue #724).** A frame naming a dispatch that is *not* executing on the receiving worker used to be logged and dropped — `handleTaskCancel` answered nothing — so the click changed only the run's final label and the row still settled on the `timeoutMs + RESULT_WAIT_MARGIN_MS` back-channel timer (verified live on 2026-08-12: markers written at 18:18, rows settled at 18:23 and 20:56 regardless). The worker is the only party that knows whether the phase is still executing there, so it now settles such a cancel with the same terminal `failed` + `cancelled: true` result an in-flight cancellation produces, and re-reports the *real* terminal result instead when it still holds that dispatch's undelivered (issue #718's queue) — so a Terminate arriving after the phase actually finished settles the run on its true outcome. That answer needs the phase and task a terminal result frame requires, which a cancel frame did not carry: `TaskCancelSchema` gained them as **optional** fields, filled from what the router recorded at registration (`src/router/dispatch-results.ts`), additive in both directions and so still no version bump — an older control plane omits them and the worker keeps the log-only behaviour rather than sending a malformed frame, and an older worker ignores them. No new settle path and no new router policy: the answer rides `deliverDispatchResult` → `adaptResultToPhaseRun` → `RunTerminatedError` → the shared settle, and a dispatch this router is no longer awaiting drops the frame, so the answer can never settle an unrelated attempt. One case still waits out the lease window and is deliberately left to issue #719: a worker whose transport is down, where nothing can be pushed and the phase may genuinely still be executing, so writing the row from the API would take the terminal state away from its owner.

**Saying that a request is outstanding (issue #561).** Both `terminate` and `reset` return as soon as the intent is recorded, so there is a period — up to the router's own result wait on the transport path, and non-zero even with #549 delivering the frame, since the agent still has to unwind — in which the row is unchanged and nothing on the page says a request landed. `runs.getById` therefore resolves an additive `pendingRequest` (`resolvePendingRunRequest`, `src/api/routers/runs.ts`) from facts the request paths *already* write: the run-id-keyed Redis cancellation marker, for a `running` run, and otherwise the run's active dispatch when it is still waiting and carries `waitReason: 'manual-retry'` — the reason only `resetRun`/`retryNow` record, so an ordinary deferred run's scheduled auto-retry never reads as an operator request and never disables the button meant to unwedge it. Nothing new is stored and no write path changes: gating terminate-pending on `running` and restart-pending on a *waiting* dispatch is what makes the settle (or the worker's claim) clear the state on its own. The dashboard disables the matching button, relabels it from the action to the wait ("Waiting to stop…" / "Waiting to restart…"), and renders the explanation plus the bound the run records (`describeTerminateWait` / `describeRestartWait`) — so the state survives a reload, reads the same for every viewer, and a second click cannot record the same intent again. A read that throws degrades to "no request outstanding" rather than failing the page.

**Worktree settlement when a termination settles (issue #361).** Once a terminated run has fully stopped, its checkout, worktree lease, and persisted recovery record are reconciled to one consistent outcome by `reconcileTerminatedWorktree` (`src/worktree/termination-cleanup.ts`), shared by both paths: the running-run path calls it from the worker's `finalizeFailedRun` after the agent exits (the phase deliberately *preserves* a cancelled run's worktree so this reconciler owns the decision), and the deferred path calls it from `runs.terminate` after the atomic `deferred → failed` claim succeeds (so it never touches a checkout while the run might still be active — a lost race leaves cleanup to the running-run path). An **explicit resumable session** is preserved (`recovery.state = "preserved"`): the checkout is kept and its live lease released, because the database recovery record — not a live lease — pins the checkout for retention (`hasResumableDeferredRun`) until a resume. With **no resumable session** a checkout is removed only once it is provably safe — not owned by a *different* live run, `isClean()`, and free of unpushed commits — and a session id never outlives the checkout it would have resumed. Otherwise the work is **retained** with a blocked reason (`dirty`, `unpushed`, or `live-leased`), recorded on the run without reopening the cancelled dispatch. It fails closed: any git-validation error surfaces as a blocked reason rather than a forced removal. A later fresh run may still encounter an older clean collision; automatic collision-time reclamation is a follow-up phase. A third caller, **"Reset & restart"** (`resetRun`, `src/dispatch/run-reset.ts`, issue #424), is the only one that passes the settlement's opt-in options: it supplies a `hasLiveOwner` resolver (`hasLiveRunForTask`, shared with the provision-time liveness check above — which additionally weighs executing dispatches, a stricter bar suited to an automatic gate than to a deliberate operator override), so a lease **no live run owns** is recognised as a stale marker and reclaimed instead of being reported `live-leased` forever, and — on every reset since issue #744 — `discardProtectedWork`, which discards a dirty/unpushed checkout with a loud warning and reports what was thrown away. Both stay opt-*in* at the settlement: without them the settlement fails closed exactly as above for every other caller, and a checkout a *different* live run genuinely holds stays `live-leased` even for a reset.

On a **terminal** `phase-failed` (such as `error`, `timeout`, or `stalled`), `processJob` also posts a failure comment on the backing Issue for the work-item-carrying phases (planning/implementation) via `reportPhaseFailureToBoard` → `pm.addComment`, so a human watching the board sees *why* the item stalled. For a recognised response stall, `src/worker/failure-diagnosis.ts` labels the task **likely scope exceeded** only when the captured run shows at least ten minutes and 1,000 non-terminal output bytes *and* the latest successful Planning artifact declares multiple independent concerns; missing metadata or a lookup error falls back to **provider stalled early**, and a harness timeout alone never claims task size. Quota/rate-limit, capacity, launch/authentication, worker-shutdown, and user-termination conditions take precedence. The serialised diagnosis is persisted beside the raw error and rendered on both the board and run detail; the comment is best-effort and skipped for intentional user termination.

## Single-user scope

No per-org config and no multi-tenant Firestore layer. One Postgres row per SWARM project, one set of GitHub credentials (per persona) per project. The API server is loopback-only (`127.0.0.1`) and, as of #281 task 2, gated by per-user session auth (below) rather than a shared secret; as of #281 task 4 each request is then scoped to the caller's project membership (below), so an authenticated user no longer sees every project. As of #281 task 5 a project may *opt in* to a `discoverable` visibility that layers a limited public-discovery view and a request/approve join flow on top of that strict members-only default (below), without wiring any execution/routing permission to visibility. Revisit the per-project credential model as remaining ADR-001 work (worker registration/routing) lands.

**Multi-user foundation (ADR-001, issue #281) — in progress.** The identity domain landed first: a `SwarmUser` Zod schema (`src/identity/schema.ts`), a `users` table (`src/db/schema/users.ts`), a provider-neutral identity read-model service (`src/identity/service.ts`), the installation-level `instanceAdmin` flag, and a `swarm users` operator CLI. A SWARM user is a person who signs in to this installation — **not** an SCM identity and **not** an implementer/reviewer GitHub credential.

**Session auth (task 2) is now live.** The shared `DASHBOARD_TOKEN` bearer guard is gone: a user gets a password via `swarm users set-password` (stored as a `scrypt` salt+hash in `users.password_hash`, never plaintext), signs in at `/login`, and receives an opaque session token — stored only as a SHA-256 in `user_sessions`, delivered as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost), never in a response body or log. The tRPC context (`src/api/trpc.ts`) resolves the caller from that cookie (`src/identity/auth.ts` `resolveSession`); every procedure except `ping` is an `authedProcedure` that 401s without a session, and logout revokes it. Because every request now carries a cookie via `credentials: 'include'`, the API server fronts all routes with a credentialed CORS layer (`src/lib/cors.ts`, `CORS_ORIGIN`, default `http://localhost:5173`) so the documented separate-origin dev setup (SPA on Vite, API on `API_PORT`) can send it — inert for the recommended same-origin deploy, which never pre-flights.

**Local single-user mode (issue #298).** For a single-operator local install, `SWARM_SINGLE_USER_MODE=true` (`src/lib/env.ts`; disabled-by-default, only the literal `true` enables it, and set in `.env.docker.example`) swaps the cookie requirement for a zero-setup identity: `createApiApp` resolves the mode once per instance and, in `createContext`, lazily bootstraps and caches a passwordless reserved `localhost-admin` `instanceAdmin` (`ensureLocalAdminUser`, an atomic idempotent upsert on the existing `users.identifier` unique constraint — no schema, no migration) and supplies it as `ctx.user` even with no `swarm_session` cookie, so a project-scoped procedure runs against a real installation admin exactly as if signed in. The `resolveSession` path, `/auth/login`, `/auth/logout`, and session minting are untouched and remain in force whenever the flag is disabled; the single-user path never mints or reads a session. The dashboard `/login` route consults `auth.me` and, when an identity already resolves, redirects into the app rather than showing the form — so a direct visit to `/login` is skipped in single-user mode without any browser-visible mode flag. **The mode is an authentication policy and nothing else.** It also bypassed the dispatch gate for a time (issue #373), and issue #552 removed that: one flag governing both decisions made the mode unusable with control-plane dispatch — the control plane has no local executor to bypass to, so `gateDispatch` (`src/worker/consumer.ts`) answering "no selection" left every dispatch durably pending. A single-user install now registers and enrolls its one local worker (`docs/onboarding-worker.md`) and is routed to it like any other deployment; nothing on the dispatch path reads the flag.

The same flag also governs **dispatch (Phase 2/2, issue #373)**: the host process is the implicit local executor for *every* project. `gateDispatch` (`src/worker/consumer.ts`) short-circuits to its `undefined` no-selection result — the same one an unfederated project yields — *before* reading the roster (`listProjectDispatchCandidates`) or constructing the assignee provider, so `processJob` reuses the existing local path (`acquireProjectSlot`, capability-aware local target selection, a null worker identity) and never touches enrollment, sharing consent, assignee affinity, live sessions, worker fencing, or worker capacity even when worker/enrollment rows exist. It creates no synthetic workers, `worker_sessions`, or `worker_project_enrollments` rows, mutates no consent, and rotates no credential — the federated eligibility, fencing, affinity, and capacity behavior are fully preserved and simply restored the moment the flag is disabled.

**Project membership (task 3, layer 2) is the read model — data only, not yet enforced.** It adds a `ProjectMembership` Zod schema and per-project role (`projectAdmin | member | contributor`, ordered by privilege) with `canAdministerProject`/`canWriteProject`/`canReadProject` predicates (`src/identity/membership.ts`), a `project_members` table (`src/db/schema/projectMembers.ts`, unique per `(project, user)`, cascade-deleting with either its project or its user), a repository (`src/db/repositories/projectMembersRepository.ts`), a provider-neutral membership read-model service (`src/identity/membership-service.ts`, whose `listAccessibleProjectIds` resolves an installation admin to *all* project ids and any other user to their membership set), and a `swarm members` operator CLI to seed membership before the dashboard UI exists. Membership is created directly (repository/CLI/admin) or, as of task 5 (below), via an approved open-project join request. It is the read model that **project-scoped authorization (task 4, now live — below)** and **open-project policy (task 5, now live — below)** build on.

**Project-scoped authorization (task 4, layer 2) is now enforced.** `src/api/authz.ts` turns the membership read model into the API's enforcement layer — the second of ADR-001's three authorization layers (installation role → project membership → worker enrollment). Every project-keyed tRPC procedure (`routers/projects.ts`, `routers/runs.ts`, nested `routers/credentials.ts`) calls `assertProjectAccess(user, projectId, minRole)` or scopes a cross-project list through `filterAccessibleProjects` / `accessibleProjectScope`. An `instanceAdmin` bypasses every check (layer 1 override); a user with no membership cannot even learn a project exists (reads and mutations alike surface `NOT_FOUND`, never `FORBIDDEN`, so real project ids never leak); a member below the required role gets `FORBIDDEN`. The role → capability matrix, defined once in `authz.ts` and mapped from the `canReadProject`/`canWriteProject`/`canAdministerProject` predicates:

| Capability | Min role | Procedures |
| --- | --- | --- |
| Read a project, its runs, its (masked) credentials | `contributor` | `projects.getById`/`list`/`viewerAccess`, `runs.list`/`queued` (with a `projectId`)/`getById`/`getLogs`/`getOutput`, `credentials.list` |
| Drive a project's runs | `member` | `runs.retryNow`/`terminate`/`putBack` |
| Administer config, credentials, or delete the project | `projectAdmin` | `projects.update`/`delete`, `credentials.set`/`delete` |

Creating a project (`projects.create`) is open to any authenticated user, and the creator is written a `projectAdmin` membership row in the same call, so they can administer what they just made without an operator seeding membership first. Host-level procedures that are not keyed to a project (`ping`, `auth.me`, `settings.*`, `scm.verifyGithubToken`, `quota.*`) stay `authedProcedure` only — installation-admin gating of global settings is a separate, later concern, not project-scoped authorization.

**Installation-wide views are layer 1, not layer 2 (issue #647).** Three reads name no project at all and instead span the whole instance: the *unscoped* `runs.list`, `runs.queued`, and `workers.list`, which back the global `/runs` and `/workers` screens. Those are an operator's view of the installation — the workers roster includes machines enrolled in no project — so they are gated by `assertInstanceAdmin(user, view)` (`src/api/authz.ts`) on the installation role alone, and no project membership grants them. That check is synchronous (the flag is already on `ctx.user`, so it implies no database read) and throws **`FORBIDDEN`, not the `NOT_FOUND`** the project-scoped helpers use: the caller named no project id, so there is no existence to hide and the honest answer is that the view is not theirs. Because only an admin now reaches those branches, they no longer derive `accessibleProjectScope` — the membership-filtered variants are gone rather than unreachable. Everything **project-scoped** is untouched, which is the point: an enrolled worker owner still reads their runs and their workers per project (`runs.list`/`queued` with a `projectId`, `workers.list` with a `projectId`, `workers.roster`) under `assertProjectAccess(…, 'contributor')`, and `workers.getById` deliberately stays on `accessibleProjectScope`, because a worker owner reaches worker detail by clicking through their own project's roster. The dashboard mirrors the boundary rather than defining it: `InstanceAdminOnly` (`dashboard/src/components/layout/instance-admin-only.tsx`) *is* the component both routes mount, so a typed URL, a filtered deep link, and an in-app link hit one frame and a denied screen never mounts (its cross-project queries are never issued); the two sidebar links are hidden for a non-admin; and `/` forwards by role (`landingRouteFor`, `dashboard/src/lib/instance-admin.ts`) — an admin to `/runs`, anyone else to `/projects` — which also settles where the login screen lands. Single-user installs are unaffected: `SWARM_SINGLE_USER_MODE` resolves the reserved `localhost-admin` as an `instanceAdmin`.

**The project screen's configuration tabs are layer 2, and the dashboard now says so (issue #655).** The `projectAdmin` row of the table above was enforced but not *reflected*: a `contributor` or `member` could open the project-detail page's Settings, Agent Configuration, Pipeline, Project Management, and Source Control tabs, where every read and write came back `FORBIDDEN` — a read-only credential-management screen that could do nothing. Those five tabs are now the administrator's alone (`PROJECT_ADMIN_TABS`, `dashboard/src/lib/project-nav.ts`), while **Runs and Workers stay every enrolled member's** — the same split issue #647 drew between an installation-wide screen and a member's view of their own work, one level down. The client learns the boundary from the server rather than guessing at it: `projects.viewerAccess` reports `{ canAdminister }` via `mayAccessProject(user, projectId, 'projectAdmin')` — the non-throwing twin of `assertProjectAccess`, exactly as `workers.getById` reports per-enrollment `viewerCanAdminister` (issue #477) — under the same `contributor` gate and existence-hiding `NOT_FOUND` as `getById`, so asking what you may do never answers that a project exists. It is deliberately its own query rather than a field on `getById`, whose cache is overwritten by `projects.update`'s result (a plain `ProjectConfig`, carrying no viewer capability) on every config save. `ProjectAdminOnly` (`dashboard/src/components/projects/project-admin-only.tsx`) is the frame the whole configuration half renders through, so a typed URL, a bookmarked `?tab=` deep link, and an in-app tab click hit one gate and a denied tab's panels never mount — none of their `projectAdmin`-gated queries (credential lists, PM provider lists, board discovery) is issued — with the tab bar's omission of the tab a courtesy on top. An absent access read fails closed, and the screen waits for it alongside the project so the tabs never flash in and back out. **Nothing server-side changed and no capability widened**: `projects.update`, `projects.credentials.*`, and the whole `pm` router still each assert `projectAdmin` for themselves, and an `instanceAdmin` still administers every project (which is what `mayAccessProject` answers, so the dashboard needs no separate installation-role branch).

**Open-project policy + join/request flow (task 5) — the final foundation slice.** Task 4's default is strictly members-only; task 5 adds an *opt-in* public face without loosening it. It keeps four permissions deliberately separate — **discovery ≠ joining ≠ worker registration ≠ task routing** — so public visibility never equates to execution permission (ADR-001 access model). A per-project `visibility` policy (`src/config/schema.ts` `ProjectVisibilitySchema`: `private` default | `discoverable`, a `text` column on `projects`) drives it:

- **Discover** — `projects.listDiscoverable` (any authenticated user) returns a **limited** read of `discoverable` projects the caller cannot already access: `id` + `name` only, projected in the query itself (`listDiscoverableProjectsFromDb`) so credentials/config/repo/run internals never even leave the DB. It excludes the caller's own projects; an `instanceAdmin` (who already sees everything) gets nothing new.
- **Join / request** — `projects.requestMembership(projectId)` files a **pending** membership request (`project_membership_requests` table, mirroring `project_members` with a `pending|approved|rejected` status and a *partial* unique index allowing one pending request per `(project, user)`). This resolves ADR-001 open question #1 in favour of **request/approve over immediate membership**: joining an open project grants no access on its own. A private/unknown project is `NOT_FOUND` (existence never leaks); an existing member or pending request is `CONFLICT`.
- **Approve / reject** — `projects.listMembershipRequests`/`approveMembershipRequest`/`rejectMembershipRequest` reuse `assertProjectAccess(user, projectId, 'projectAdmin')`, so only a `projectAdmin`/`instanceAdmin` acts on requests (a non-member gets `NOT_FOUND`, a lower-role member `FORBIDDEN`). Approval creates a `contributor` (**read-only**) `project_members` row atomically with resolving the request, and is idempotent w.r.t. an existing higher role.

Critically, visibility and membership remain separate from worker registration (#132) and task routing (#130): public visibility never grants execution permission. The highest role joining ever yields is `contributor`, which grants read and nothing more.

**Registered worker identity (#132 Phase 1).** Where a `SwarmUser` is *who* a person is and a `ProjectMembership` is *what* they may do on a project, a **worker** is *where* a user can execute — a locally operated execution environment they own (ADR-001's third identity layer). It adds a `Worker` Zod schema (owner user id, a safe machine `displayName`, declared CLI `capabilities` reusing `AgentCliSchema` — `claude | antigravity | codex` — and, since issue #467, the declared `supportedPhases` its daemon can execute; `src/identity/worker.ts`), a `workers` table (`src/db/schema/workers.ts`, FK to `users` `ON DELETE CASCADE`, unique per `(owner, displayName)`, unique credential hash), a repository (`src/db/repositories/workersRepository.ts`), a provider-neutral `worker-service` (`src/identity/worker-service.ts` — credential issue/hash primitives, `registerWorker` returning the raw credential **once**, `refreshWorkerCapabilities`, `renameWorker` (the owner's own machine label, dashboard-only — `workers.rename`, strict ownership, no `instanceAdmin` override), and the `resolveWorkerByCredential` auth seam), and a `swarm workers` operator CLI. The **worker credential** is distinct from an SCM PAT, stored only as a SHA-256, and returned raw once; a federated host supplies that raw value as `SWARM_WORKER_CREDENTIAL` so #339 can bind execution to its authenticated worker identity.

**Worker session leases (#336 Phase 2) — one live claim per worker, fenced.** On top of Phase 1's identity, a **worker session** is the single live claim on a registered worker's execution environment, so two daemons can never drive the same machine at once. It adds a `WorkerSession` Zod schema (`src/identity/worker-session.ts` — a per-worker monotonic **fencing token**, `lastHeartbeatAt`, a nullable `currentRunId`), `worker_sessions`, its atomic acquire/heartbeat/release repository, and the provider-neutral `worker-session-service`. A session expires after `SWARM_WORKER_HEARTBEAT_TTL_MS` (default 60s); re-acquisition bumps the fencing token and stale holders cannot heartbeat or attach work. The host worker now acquires and refreshes this lease from `SWARM_WORKER_CREDENTIAL`, and #339 atomically locks the session row to validate its id/token and reserve dispatch capacity before execution.

**A reconnecting daemon reclaims its own live lease (#608).** A control plane that dies never releases the leases of the sockets it held, so the returning daemon used to meet a live row with a seconds-old heartbeat and had to wait out the remainder of the TTL — a plain router restart cost a machine that never went away its session for most of a minute. The handshake therefore carries an optional **proof of possession** (`reclaim`: the `sessionId` + `fencingToken` the control plane minted for that daemon — `WorkerSessionReclaimSchema`, `src/identity/worker-session.ts`), and `acquireLease` refuses a live lease only when the caller does *not* present a matching one (`isReclaimOf`). Three properties make that safe, and none of them is new: the fencing token still **bumps** on a reclaim, so a superseded holder's heartbeats, run attachments, and dispatch results stay rejected; `currentRunId` is still **cleared**, so a reclaimed lease never silently adopts an in-flight run; and a caller with only the shared `SWARM_WORKER_CREDENTIAL` — a genuinely competing second daemon, or a *restarted* daemon, since the pair lives in memory alone and is never persisted — presents no proof and is still refused with `worker session already held` (HTTP 409). The field is additive and optional, so `TRANSPORT_PROTOCOL_VERSION` is deliberately not bumped. What remained bounded by backoff rather than by the lease was the daemon's own reconnect ladder, and **issue #611 split that ladder in two** (`src/transport/worker-client.ts`, `createReconnectLadders`). A handshake the control plane *answered and refused* — a 409 session conflict, a capability rejection, a 500 it generated itself — still climbs the original exponential schedule (`DEFAULT_BACKOFF.maxMs`, 30s), unchanged. A handshake **nothing answered** — the request never completed, or an edge returned 502/503/504/520–524/530 for an origin that is not there (`WorkerTransportUnreachableError`) — climbs a *separate* counter capped at `unreachableMaxMs` (5s), and an answer of any kind clears it. The length of an outage therefore stops deciding how long a daemon idles once the router is serving again: that gap is the low cap plus equal jitter, rather than the up-to-30s wait a 60-second redeploy used to earn while nobody was home. It is a bound rather than a reset, deliberately — a 502 *is* a recovering server, so the equal-jitter floor is kept and a fleet still spreads its retries across `[2.5s, 5s]` instead of stampeding a control plane that has just come up.

**That same handshake decides the *previous* generation's fate (#719).** The token bump was, until this issue, inert: `dispatches.worker_fencing_token` was written at bind time and compared exactly once, pre-execution (`sessionClaimRefusal`), so a dispatch whose worker session had been superseded stayed `leased`/`running` — holding that worker's allocation and a project slot — until the control plane's own wall-clock guard gave up at `timeoutMs + RESULT_WAIT_MARGIN_MS`. The transport's fencing closed the stale *socket* (4408) and nothing else. Each daemon now mints one memory-only `instanceId` and carries it on every handshake; the control plane persists it on `worker_sessions` and reports whether an acquire replaced the same instance. The handshake settles the old claims only when the acquiring daemon is a **different** instance: it fails every `leased`/`running` dispatch of that worker bound to a different token, settles their `running` run rows on the same reason, and ends each one's control-plane result wait (`reconcileSupersededWorkerClaims` + `failDispatchResultWait`) so the awaiting job unwinds now — releasing the project slot and running the existing capacity/availability promotions from its own `finally` — instead of parking for the rest of the window and then settling the same run a second time. This keeps a live daemon safe when a successful handshake response was lost and it later returns with a stale proof, or with no proof after the intervening 409. A daemon predating `instanceId` falls back to `isReclaimedSession` (`src/identity/worker-session.ts` — the returned session's own id at exactly `reclaim.fencingToken + 1`), preserving the prior wire behaviour. The handshake rather than the 5-minute reconciler tick remains essential: a tick cannot tell a takeover from the same daemon coming back to a phase that is still executing (and, since #718, still holding its terminal result), so keying it on the token mismatch alone would reap a live run. The settle reason names the supersede rather than the timer's "did not report a result within the lease window", so run history says which actually happened; a claim this router is no longer awaiting (it restarted since the push) still gets its durable row settled, and the lease reconciler remains the backstop when the transport is down and no successor handshakes.

**Worker-project enrollment, sharing consent, and rosters (#337 Phase 3) — the routability seam + read models.** An enrollment links a worker to a project with `pending|active|suspended` status, allowed CLIs, **allowed pipeline phases** (`allowedPhases` — `NOT NULL`, non-empty, defaulting to every phase; issue #509), a per-worker `concurrencyAllocation` (`NOT NULL`, a positive integer defaulting to `1` — issue #480; "no per-worker cap" is not an expressible state), and owner-controlled sharing consent. The provider-neutral service owns those writes and secret-free roster/owner views.

`allowedPhases` is the worker owner's **per-project routing choice** and is deliberately a different axis from `Worker.supportedPhases`, which is what the machine's daemon declares it can execute and re-declares on every reconnect. The two are ANDed by the eligibility predicate (`permitsPhase(e, phase)` is the named seam, beside `isRoutable`), so the same worker can be offered `implementation` on one project and the whole repertoire on another, and a project-wide `pipeline.<phase>.enabled: false` still overrides both. Unlike `allowedClis`, it is **not** validated as a subset of what the machine declares: a CLI capability reduction is refused while an enrollment still requires it (`WorkerCapabilityReductionError`), which makes `allowedClis ⊆ capabilities` a maintained invariant, whereas a daemon narrows its phase repertoire freely — that is the point, since the owner's selection must survive a reconnect — so containment cannot be an invariant and enforcing it on the write path would reject a save that merely preserves stored state. The column default is every phase rather than the worker's own repertoire for the same reason: `supported_phases` states whichever *program* last operated the row, and since issue #536 a narrower set means a daemon on an older build rather than a different kind of program, so seeding a durable owner choice from it would permanently narrow enrollments nobody chose to narrow — and defaulting to every phase leaves dispatch behaviour identical for every enrollment that predates the field. Busy/capacity is derived from the worker's live session plus unexpired selected-worker claims on durable dispatches (with the older `currentRunId` pointer as a compatibility fallback), never client-supplied. `isRoutable(e) = e.status === 'active' && e.sharingConsent` is consumed by #339; revocation blocks future claims but never terminates running work.

**An enrollment must name the repository the worker's checkout is (issue #690).** A worker holds one local checkout, so a project for any other repository can only produce refused work — and both moments that pairing becomes knowable are policed in `worker-enrollment-service.ts`, against the declaration issue #687 persists: `enrollWorker` compares `normalizeRepoSlug(project.repo)` with the worker's stored `repository` (through the shared `repoSlugsMatch`, so the *config* side is normalised too) and throws `EnrollmentRepositoryMismatchError` naming both, which the tRPC router surfaces as `BAD_REQUEST` and `swarm workers enroll` as one actionable line; `suspendEnrollmentsForMismatchedRepository(workerId, declaredRepository)` walks the worker's enrollments after a handshake persisted a declaration and suspends each one whose project is a different repository, logging both. Four decisions are deliberate. **It only ever suspends** — nothing here creates, approves, or re-activates an enrollment, including when a later declaration matches again: enrollment is a human decision (ADR-001 — a project administrator approves, the owner consents), and a machine must not be able to restore its own routability by re-pointing a checkout. **Suspension rather than deletion**, so the enrollment keeps its constraints for the operator who fixes the pairing, and (like every other revocation here) blocks only future dispatch. **A worker that declared no repository is neither refused nor suspended**: an unidentifiable checkout — never connected, an older daemon, no readable `origin` — must not lock an operator out of enrolling their machine. And **a failure of the handshake-time pass never blocks a handshake** (`policeEnrollmentsAgainstDeclaration`, `src/router/worker-transport.ts`, logs and continues): it is housekeeping on the control plane's side of the connection, and the worker's own pre-flight check (issue #688) refuses a mismatched assignment regardless. There is deliberately **no `suspension_reason` column** — the reason *is* the two repositories, which the read models below carry live and which therefore cannot go stale the way a stored sentence would.

**Worker connectivity roster (#133) — the dashboard's read-only aggregate.** On top of the same foundations, `listDashboardWorkers(projectScope)` (`src/identity/worker-enrollment-service.ts`) composes the one cross-project view the dashboard's **Workers** screen renders: machine display name, owner identity, declared CLI capabilities, the declared `supportedPhases` repertoire (issue #467, so version skew is visible on the screen — a daemon built before #536 declares five phases rather than six — rather than being inferred from work that never starts; the repertoire is shown in full on the worker detail view, with no phase promoted over another, and the Workers table's Capabilities column lists CLIs only, issue #542), `online`/`offline`, a nullable `lastSeenAt`, the job it is executing, and per-project enrollment/approval summaries — each summary now also naming its own `allowedClis`, so the table's Capabilities column can show the CLIs at least one visible enrollment actually allows (a cross-project union, `effectiveClis` in `workers-table.tsx`) rather than the raw declared set: a machine can declare more than any project has turned on for it, and showing the declared superset there would read as "this project can dispatch here with any of these" when it can't. It adds no schema and no second liveness rule — `online` is `getLiveSessionForWorker` (so `SWARM_WORKER_HEARTBEAT_TTL_MS` stays the single TTL), and `lastSeenAt` comes from a new *retained*-session read (`getRetainedSession` → `getRetainedSessionForWorker`) that deliberately ignores liveness so an expired or gracefully released worker keeps its last heartbeat; a worker that never connected reports `null`. **Authorization on the unscoped read is the installation role** (issue #647): the roster spans the whole instance — every registered worker, un-enrolled machines included — so `resolveRosterScope` asserts `instanceAdmin` and passes the unrestricted `null` scope, and a non-admin gets `FORBIDDEN` rather than a membership-filtered subset (their view is the project-scoped one below). `workers.getById` still scopes by `accessibleProjectScope`, stripping inaccessible enrollments from the row, because a worker owner reaches one machine's detail from their own project's roster. The active job is validated against run lifecycle exactly as `deriveWorkerRunState` does *and* filtered by project, so an in-flight run in an inaccessible project never leaks through a worker the viewer shares another project with. Since issue #473 it is returned as a `currentRun` summary (`DashboardWorkerRun` — run id, project, task id, phase, and the work-item/PR title, URL and number) rather than a bare run id, so the screen can describe the job the way the Runs table's Task column does instead of printing a UUID; the summary is assembled field-by-field from the run row, so a job payload, error text, or usage can never ride along on a roster read model. The tRPC `workers.list` query (`src/api/routers/workers.ts`) exposes it read-only, serializing `lastSeenAt` to ISO at the boundary; no machine path, credential, token, or routing affordance is on this surface. Since issue #574 that query also serves **one project's** roster — the project detail page's Workers tab, and the view an enrolled worker owner keeps — through an optional `projectId`: `resolveRosterScope` swaps the installation-admin gate for `assertProjectAccess(…, 'contributor')` plus a single-project scope, so the tab reuses `listDashboardWorkers` with no service change and inherits its three scoping rules verbatim (no enrollment elsewhere, no out-of-scope active job, and no un-enrolled machine even for an `instanceAdmin`), under the same access rule and the same existence-hiding `NOT_FOUND` as `workers.roster`. Since issue #657 the unscoped variant comes back **viewer-first**: `viewerWorkersFirst` (the same router) puts the machines the caller owns ahead of everyone else's, with a stable sort so the read model's own oldest-first order survives inside each group and a viewer who owns no visible worker sees it unchanged. That is ordering alone — it runs *after* scoping has decided what is visible, reads the row's existing `owner.userId`, and adds no field, no query, and no second answer to "which machines may I see". **The project-scoped variant orders by the project's own configured worker order instead** (issue #750): `inProjectOrder` sorts the rows by `listProjectWorkerIdsInOrder(projectId)`, one extra scoped read, so a project's Workers tab shows the same sequence the dispatch gate schedules by rather than a per-viewer one — showing each operator their own machines first would misdescribe a project whose order is now a real, persisted, administrator-set fact. The unscoped global roster keeps viewer-first because it spans projects and has no such order.

**Per-worker detail read model (#477).** `getDashboardWorkerDetail(workerId, projectScope)` returns that same row for **one** worker, widened with the full per-project enrollment detail (`DashboardWorkerEnrollmentDetail` — enrollment id, status, effective allowed CLIs, effective allowed pipeline phases (issue #509), concurrency allocation, sharing consent, the derived `isRoutable`, and the enrollment's own `projectRepo` — issue #690) plus the worker's `ownerUserId`, so the dashboard's worker detail view explains routability without a roster query per project. It adds no schema, no second visibility rule, and no second assembler: the row half is still built by `assembleDashboardWorker`, the enrollment half names each safe field explicitly, and **visibility is `listDashboardWorkers`' rule verbatim** — an administrator (`projectScope === null`) sees any registered worker including an un-enrolled one, any other viewer only a worker enrolled in a project they may access, with inaccessible enrollments stripped. It returns `null` both for an unknown worker and for one the viewer may not see, and the tRPC `workers.getById` query turns both into the same `NOT_FOUND`, so worker existence never leaks. That procedure additionally reports **what the viewer may change** — `viewerIsOwner` for the worker (the machine's *actual* owner only, no `instanceAdmin` override, mirroring `resolveStrictlyOwnedWorker`/`resolveOwnedEnrollment`) and `viewerCanAdminister` per enrollment (via the non-throwing `mayAccessProject(user, projectId, 'projectAdmin')`, `src/api/authz.ts`) — so the screen offers only controls that would succeed while the write procedures stay the enforcement point, re-checking ownership/role for themselves. `rename` (the machine's own `displayName`), `setConsent`, `updateConstraints`, `approveEnrollment`, and `setStatus` are the detail view's five drivers; `enroll` (offering a worker to a *new* project) is the one owner-self-service write that still admits the `instanceAdmin` override (`resolveOwnedWorker`) — it reads as administering the project side of the offer rather than a decision about the machine itself, and it isn't exposed on this view at all.

**The reason a mismatched enrollment isn't taking work is two live facts, not a stored sentence (issue #690).** The row carries the machine's declared `repository` and each enrollment detail its project's `projectRepo`, **both in the shared normalised `owner/repo` form** — so the screen's plain equality test (`repositoryMismatch`, `dashboard/src/lib/worker-enrollment-view.ts`) *is* the comparison the write path makes, without importing `src/scm/repo-slug.ts`, whose slug reader spawns `git` and cannot be bundled for a browser. The worker detail view reports the declared repository beside the two capability axes (all three are self-declared and read-only) and renders the mismatch on the enrollment block as "this machine's checkout is X, but this project is Y", derived on every render rather than from a sentence stored when the mismatch was detected. It is shown whatever the enrollment's status is: a mismatch normally *is* a suspension, but an active mismatched one (a policing pass that failed, say) is exactly the case an operator most needs explained, since the gate routes work there and the daemon then refuses it. Both fields are non-secret by the same standard as the rest of this surface — a repository slug is not the machine's path (`SWARM_WORKER_REPO_ROOT` never travels) and not a credential — and they are named explicitly in the assembler like every other field.

**Assignee resolution + identity linking (#130 Phase 1) — the affinity lookup.** ADR-001's routing rules make assignment an *execution-affinity* rule: a work item assigned to a PM identity that maps to a SWARM user may run only on that user's eligible worker — **for the phases affinity is gated on** (`AFFINITY_GATED_PHASES`, `src/worker/eligibility-gate.ts`; ADR-001 as amended by issue #469). Today that is `implementation` alone: `planning` is exempt, and the PR-driven phases carry no assignee at all. Planning's exemption was originally argued from portability — only a database-holding worker could run it, so routing it by assignment could only ever prevent work rather than place it better. Issue #536 removed that premise (a DB-free worker now runs Planning), and the exemption is deliberately kept on the reason that outlived it: Planning produces no branch, worktree-bound artifact, or PR, so there is nothing about it that belongs on a particular person's machine, and gating it on affinity would only make a plan wait for one worker. Revisiting that is a routing decision of its own, not a consequence of the phase becoming portable. **(1) A provider-neutral read of who an item is assigned to**: `WorkItemAssignee` + `WorkItem.assignees` + the `PMProvider.supportsAssignees` capability flag (`src/pm/types.ts`), populated by the GitHub Projects adapter from the backing Issue/PR (see "PM: GitHub Projects" above). Because `trigger.workItem` is already built from an authoritative `pm.getWorkItem()` (`src/triggers/handlers/pm-status.ts`), assignees flow to the trigger layer. **(2) A SWARM identity-linking seam**: a `UserIdentity` Zod schema (`src/identity/user-identity.ts` — a `(provider, handle)` pair owned by one `users` row), a `user_identities` table (`src/db/schema/userIdentities.ts`, FK to `users` `ON DELETE CASCADE`, **unique per `(provider, handle)`**), a repository (`src/db/repositories/userIdentitiesRepository.ts`), and the resolver `src/identity/assignee-resolver.ts` (`resolveUserForAssignee(assignee, provider)` / `resolveAssignedUser(workItem, provider)`), whose `provider` argument is the caller's `PMProvider.type` so the seam stays provider-agnostic. This answers ADR-001 open question 5 by construction: a handle maps to **at most one** SWARM user (the unique index), keys are normalized (trimmed + lowercased, so casing never splits a link), and an unlinked handle resolves to `undefined` rather than a guess. Links are seeded by an operator (`swarm identities link`) — automatic linking (OAuth / SCM account discovery) and a dashboard UI are deliberately out of scope. The worker eligibility gate consumes these links to enforce owner affinity before execution.

**Worker eligibility evaluation (#338, #130 Phase 2) — the pure half of the dispatch gate.** `evaluateWorkerEligibility` (`src/identity/worker-eligibility.ts`) folds ADR-001's routing prerequisites into one structured verdict: `{ eligible: true }` or `{ eligible: false, reason }`, where `IneligibilityReason` is `missing-enrollment` (no enrollment, or one not yet `active`) | `missing-consent` (consent never granted or revoked) | `worker-unavailable` (no live session, or the enrollment's `concurrencyAllocation` — this worker's share of the project, always a positive integer — fully used; the worker's `SWARM_WORKER_CONCURRENCY` and the project cap bound it further) | `repository-mismatch` (the machine's one local checkout is a different repository than the task's — issue #714) | `missing-phase-capability` (the machine's daemon never declared this phase — issue #467) | `phase-not-permitted` (the machine declares it, but this enrollment's owner did not select it for this project — issue #509) | `missing-cli-capability`. Checks run in the ADR's order — active enrollment → sharing consent → connection/health → free capacity → the repository the checkout is → declared phase support → the enrollment's allowed phases → declared CLI capability — and the **first** missing signal is returned, so a caller has one reason to show rather than a set; the first two checks are `isRoutable` split apart only so a revoked consent reads as `missing-consent`. **The repository check** (issue #714) takes the *task's* repository as a required input — the scoped project's own `repo`, which issue #684 phase 2 pins to the job's repository rather than the project's default entry — and compares it against the candidate's declared `Worker.repository` (issue #687) through the shared `repoSlugsMatch` (`src/scm/repo-slug.ts`), which normalises the config side too. It sits ahead of every capability because a checkout is the most fundamental property of the pairing: a worker holding the wrong tree can run no phase of this task at all, whichever phases and CLIs it declares — while connection and capacity stay ahead of *it*, because "some worker is merely busy" remains the best news available and a machine that does hold the repository but is offline must still read as `worker-unavailable`. A worker that declared **no** repository is deliberately not refused (an unidentifiable checkout must not become unroutable — the provision-time `origin` verification and issue #688's assignment refusal remain its guards, exactly as issue #690 decided for enrollment). It is **target-scoped, never target-choosing**: it judges exactly one candidate target from `agents.<phase>.targets` against that target's effective CLI (its own `cli`, else the phase's coded `DEFAULT_*_CLI` passed as `phaseDefaultCli`) and requires that CLI to be both a declared worker capability *and* allowed by the enrollment — it never reorders or falls back across targets, so Phase 3 can call it once per target and keep configured target priority across workers instead of collapsing back to a single model. The module is dependency-light and side-effect-free (like `src/pm/dependencies.ts`): the DB-backed signals arrive as a caller-resolved `WorkerAvailability` (`connected` from the fenced worker session, `activeRuns` from unexpired durable dispatch claims). The dispatch wiring, scheduler ordering, assignee affinity, and the scheduler-only `assignee-worker-unavailable` reason are Phase 3 (below).

**Federated dispatch gate (#339, #130 Phase 3) — the scheduler that consumes all three.** The gate (`src/worker/eligibility-gate.ts`) runs inside `processJob` **after** trigger resolution and **before** any worktree provisioning or agent invocation, on every phase and every (re)dispatch — with **one rule for every deployment**, single-user installs included, since issue #552 deleted the `isSingleUserMode()` bypass that used to short-circuit it (see "Local single-user mode" above). It reads the project's enrolled workers (`listProjectDispatchCandidates`, `src/identity/worker-enrollment-service.ts` — worker + enrollment + resolved availability in the project's **configured worker order**, which is the documented "first free eligible worker" sequence; since issue #750 that order is a persisted, `projectAdmin`-settable property of the enrollment row — `worker_project_enrollments.order_index`, read as `(order_index, created_at, id)` — rather than enrollment-creation order, which is exactly what a project nobody has reordered still gets, since every existing row migrated to position `0`. Ordering is a preference *between* otherwise-eligible workers and never a grant: an unavailable, over-capacity, unapproved or otherwise ineligible worker is still skipped for the next eligible one, and neither target priority, assignee affinity, the preserved-worker pin, nor pool scheduling is affected), applies ADR-001's affinity rule **for the phases it covers** (issue #469 — Planning is exempt and takes the unassigned path), and judges each candidate with Phase 2's predicate. Selection is **target-priority-first, worker-choice-second**: it walks `agents.<phase>.targets` in configured order and stops at the first target *some* eligible worker can run, so a higher-priority Codex target wins whenever some enrolled worker can run Codex even if a Claude-only worker is free for a lower-priority Claude target — and it never silently falls back to `targets[0]`. A per-run "Retry now" override still pins exactly one target, which the gate evaluates rather than routes around; `src/worker/target-policy.ts` is the one place that reading of the policy lives, so the gate, local capability routing (#346), run creation, retry reset, and the phase invocation all agree on the chosen target.

**Which of several eligible workers wins is a pool decision (issue #533).** "First in enrollment order" is only correct when one dispatch is in play; with the consumer processing several at once it can spend a scarce capability another runnable phase uniquely needs — a Review eligible on two machines taking the only Planning-capable one, leaving Planning nowhere to run while the other machine idles. So once the chosen target has more than one eligible worker, the gate reads the project's other runnable dispatches (`loadRunnableDispatchDemands`, `src/worker/pool-demand.ts` → `listRunnableDispatchesForPool` — non-terminal, no worker claimed yet, due now, in the queue's own `priority` → `availableAt` → FIFO order, capped at `POOL_DEMAND_LIMIT`), turns each into the workers that could serve it, and computes a **maximum bipartite matching** over the pool's free slots (`src/worker/pool-scheduling.ts`), taking its own share. Four properties make that safe to run per dispatch, with no new coordination: it is **pure and deterministic**, so the same input always yields the same assignment (not the same thing as two concurrent gates agreeing — each substitutes its own affinity-narrowed set for itself and reads contenders as supersets, so two gates can pick the same worker and race the claim, which costs the one deferral a raced claim already costs); it **never withholds work** — an unmatched dispatch falls back to its own first-eligible pick, because the demand that won the slot may be a dispatch whose wake-up has not fired, so nothing here can defer a phase that could otherwise run (which is also why it adds no starvation risk, and why priority/ageing stay entirely in the dispatch row's existing ordering); it **never overrides a hard constraint** — eligibility, affinity, and target priority are decided before it, and `claimWorkerForDispatch` remains the only authority on capacity, so a raced snapshot costs at most the same one deferral it does today; and a **failed or absent pool read is not an error** (`undefined` → today's behaviour). A contender's demand is reconstructed from its dispatch row without assignee affinity or the `implementationUnplanned` target variant, both of which would cost a read per waiting dispatch, and a contender whose stored payload names no repository is judged against every machine rather than narrowed by a guessed one (issue #714 — `undefined` means the project's *default* entry, which the project a gate scoped need not be) — each approximation only widens a contender's reconstructed set, so the gate errs towards keeping its own pick rather than diverting for contention that isn't real. A contender that *does* name its repository is narrowed by it, so contention is only ever counted between dispatches that could actually share a machine.

Routing outcomes:

- **Unassigned item** (no assignees, or none linked to a SWARM user — ADR-001 open question 5) → a free eligible project worker: the pool's choice among them when other work is contending (issue #533, above), otherwise the first in that deterministic order.
- **Assigned item** whose assignee resolves to a SWARM user, on an **affinity-gated phase** (`AFFINITY_GATED_PHASES` — `implementation` today) → *only* a worker owned by that user. There is **no cross-user fallback**: the work waits. On a non-gated phase — `planning` (issue #469, whose portability premise issue #536 removed without changing the exemption; see "Assignee resolution" above) — the assignment is not read at all and the item takes the unassigned-item path above.
- **Continuation of a preserved checkout** (issue #567) → *only* the machine that holds it, which outranks affinity and every other narrowing. See "Preserved-checkout pinning" below.
- **Nothing eligible** → a structured refusal, never a silent drop. `DispatchIneligibilityReason` is Phase 2's seven reasons plus the two scheduler-only ones, `assignee-worker-unavailable` and `preserved-worker-unavailable`; the gate throws `WorkerIneligibleError`, and `handlePhaseFailure` treats it exactly like a dependency block — a **token-free** deferral (nothing was provisioned, no model spend) on the dependency gate's cadence with its own `workerEligibilityRecheckAttempt` budget, settling `failed` with an actionable board comment (grant sharing consent, approve the enrollment, enroll a worker that can run the configured CLI) only once that budget is exhausted. **The row records which kind of wait that is** (issue #607): `isAvailabilityRefusal` (`src/worker/eligibility-gate.ts`) partitions the whole reason vocabulary — a `Record` over the union, so a new reason fails to compile until it is classified rather than defaulting into a bucket — into the refusals a machine becoming available clears (`worker-unavailable`, `assignee-worker-unavailable`, `preserved-worker-unavailable`), which keep the dispatch wait reason `worker-eligibility`, and the refusals only a human can clear (`missing-enrollment`, `missing-consent`, `missing-cli-capability`, `missing-phase-capability`, `phase-not-permitted`, `repository-mismatch` — a checkout is re-declared only at handshake, so nothing a connecting machine does re-points one), which read as `worker-authorization`. The split is durable and read-model-visible only: **both kinds keep the same cadence, attempt counter, and budget**, and `preserved-worker-unavailable` still records its own `preserved-worker` reason ahead of either (below). It exists because the two waits behave differently for an operator — one clears by itself in seconds, the other never does until somebody acts — and because a wake-up policy has to be able to tell them apart.

**The availability wait is woken, not polled (issue #610).** That deferral schedules its re-check on a fixed 5-minute timer, so a dispatch refused a moment before a worker connected sat still next to an idle machine for up to the whole interval (observed live: two board deliveries deferred `reason=worker-unavailable retryDelayMs=300000` at 07:24Z, both workers idle from 07:24:46Z, nothing running until the timer fired at 07:29Z). Two moments now promote it — the same move issue #262 made for the concurrency wait:

- **A worker connects** — the authenticated `/worker/stream` open (`handleWorkerStreamOpen`, `src/router/worker-transport.ts`), the one place the control plane learns a machine became reachable. Kept there rather than in `registerConnection` so the connected-worker registry keeps owning no scheduling decision.
- **A worker frees capacity** — a dispatch bound to it settles, releasing its execution claim, in `processJob`'s `finally` (`src/worker/consumer.ts`) next to the capacity promotion. That is the correct signal for a **federated transport worker** too: its phase runs remotely and the settle happens here, after the result frame arrives.

Both call `promoteAvailabilityWaitsForWorker` (`src/dispatch/dispatcher.ts`), which asks two different questions of the two waits: a `worker-eligibility` row is offered by any project the worker is **routable** enrolled in (active enrollment + sharing consent), while a `preserved-worker` row is keyed on the **recorded machine** (`runs.recovery.preservedWorkerId`) and never on enrollment, because the pin is honoured for a machine that is no longer an enrolled candidate at all. `worker-authorization` is never promoted: no machine coming online grants consent, so waking it would only spend its budget faster.

Per row the order is **remove the delayed wake-up → conditionally re-date → publish the replacement**, so a dispatch never holds two live wake-ups. Only rows whose wake-up is still delayed are candidates, which is what makes the removal deterministic; the re-date is conditional on the row still sitting on the exact `wake_seq` that was read, so concurrent wake-ups from two workers resolve to at most one promotion. Nothing else about the deferral changes: the stored payload and `workerEligibilityRecheckAttempt` are untouched, so the woken job re-enters the full gate spending the budget the previous settle persisted and may defer again; the timed re-check is still the fallback when no wake-up arrives; and the whole promotion is best-effort and fully swallowed — a queue hiccup must never fail a settled run or keep a socket from opening.

**Preserved-checkout pinning (issue #567) — the narrowing that keeps a continuation's work.** A continuation's state is machine-local and has no server-side copy: a Tier 2 checkpoint file, a resumable agent session, and a deterministic-delivery sidecar all live in `.swarm-workspaces/task-<id>` on the worker that stopped. Worker selection had no notion of *where the state is*, so a continuation re-dispatched to any other eligible machine found nothing to adopt, provisioned a fresh checkout, and re-ran the phase from scratch — at full token cost, with nothing in the run record saying so (observed live on task 549: a rate-limited Implementation checkpointed on `m3_pro_tp`, and "Continue now" started it over on `m5_pro` three seconds after that machine created its own empty checkout).

Two halves fix it. **Recording**: every settle that leaves a checkout for a continuation to adopt — a resumable/checkpointed/delivery-resume deferral, and a cancellation that preserved its session — copies the attempt's own `runs.worker_id` into `runs.recovery.preservedWorkerId` (`recordRunPreservedWorker`). It has to be recorded at that moment because `worker_id` is the *last attempt's* worker and is overwritten at every bind; `recovery` is free-form `jsonb`, so no migration. The key survives the rewrite that a re-bind performs (`resetRunToRunning` carries it onto the `recovered` record) and is dropped only when the run stops recovering. **Enforcing**: `jobContinuesPreservedCheckout` (`src/dispatch/preserved-worker.ts`) recognizes the four payload shapes that adopt a checkout — `recoveryMode: 'resume'`, `recoveryMode: 'checkpoint'`, `resumeSession` (the automatic retry's equivalent of the first), and `resumeDelivery` — and never `recoveryMode: 'fresh'`; for those, the gate's permitted set becomes that one machine. The pin **replaces** affinity rather than intersecting with it: the two can only disagree when the item was reassigned after the checkout was preserved, and intersecting would wait forever for a machine that cannot hold the state anyway.

Its refusal is `preserved-worker-unavailable`, with the dispatch wait reason `preserved-worker`, and it is **the one wait with no budget**. Failing the run abandons work that is still on disk, and a timed fallback to another machine is this defect with a delay on it — so the wait is unbounded, names the machine — on the dispatch row (`lastError` carries the refusal in full, not just the `waitReason` category) and in a run-detail callout (`runs.getById` resolves `preservedWorker` to a display label, and reports whether the run is *currently* waiting on the pin rather than merely carrying one) — and ends only when an operator chooses. It deliberately does **not** write the run's `error` column: the gate refuses before `tryCreateRun`, so a continuation's wait has no run row of its own to settle, and writing onto the row it carries would clobber the `checkpointed` status and session id that row exists to hold. A *structural* refusal from the pinned machine (consent revoked, enrollment suspended, phase not permitted there) keeps its own reason and its own bounded budget: those name something only a human can fix and will not resolve on their own.

Two consequences elsewhere. The **token-free re-check deferrals** (this gate's and the dependency gate's) now carry their payload through verbatim (`deriveRetryJobPayload`) instead of re-deriving recovery intent: both refuse before anything is provisioned, so their "retry" is the same attempt still waiting, and re-deriving would drop a `'checkpoint'` mode outright and replace a `'resume'` session id with a freshly minted one — turning the wait into the start-over it exists to prevent. And **"Reset & restart" is the escape hatch**: it clears the pin (`clearRunRecovery`), converting `preservedWorkerId` into `abandonedWorkerId` so the run durably records that it started over rather than continued, and it needs nothing from the pinned machine — the dispatch is cancelled control-plane side and the local checkout reconciliation is a no-op for a checkout on another host — which is exactly what makes it usable while that machine is unreachable. The abandoned checkout is then an ordinary orphan on its machine, reclaimed by the normal provisioning/prune path rather than pinned forever.

Because the gate sits on the common dispatch path it re-checks **before retries and later phases**: a consent revocation, enrollment suspension, health loss, or capability removal between attempts blocks the *next* dispatch, while a run already in flight is untouched. A selection becomes executable only when the dequeuing process authenticates as that exact worker and `claimWorkerForDispatch` locks its live fenced session, re-validates enrollment/consent/CLI, counts active unexpired claims, and persists the worker/session/fencing token on the dispatch (and worker/token on the run). A different host defers; simultaneous claims serialize on the session row and cannot exceed the enrollment's `concurrencyAllocation` (the project's `maxConcurrentJobs` and the worker's `SWARM_WORKER_CONCURRENCY` bound it further); retries clear the claim, while terminal/expired dispatch states cease consuming capacity. A project with no enrollments remains unfederated and runs locally as before.

**Control-plane dispatch (ADR-003 §2, issue #407).** The BullMQ consumer + this gate live on the **router** (`src/router/dispatcher.ts`), which makes every dispatch true split delivery: the control plane decides *and* the worker executes in a different process, on the same host or a remote one — the same program either way since issue #551, and the *only* arrangement since issue #553 deleted the in-process alternative. It reuses `processJob` verbatim — the whole claim → trigger → automation gate → eligibility gate → `bindSelectedWorker` → run-row → durable settle → self-enqueue → merge-automation machine is shared. `processJob` takes a small `ProcessJobDeps` seam (`src/worker/consumer.ts`), built in one place (`createControlPlaneDispatchDeps`); it injects three things: a **connectivity predicate** folded into the gate so only workers holding a live `/worker/stream` socket here are selectable (`isWorkerConnected`, `src/router/worker-connections.ts` — a DB-live-but-not-connected worker is skipped as `worker-unavailable`, so on an affinity-gated phase an assignee's offline worker still waits rather than routing elsewhere — `planning`, being exempt from affinity, routes to any other capable worker instead, issue #469); a **bind identity** resolved from the *selected* worker's live session (the control plane claims the fenced slot on its behalf); and an **executePhase** that composes the system prompt + target branch server-side (`src/router/assignment-composition.ts`, reusing the pure `src/pipeline/prompts/*` builders), builds a `TaskAssignment` carrying the **non-secret** project-config slice (never a persona token — `src/transport/assignment.ts`), pushes it to the worker, and awaits the worker's `TaskExecutionResult` (correlated by `dispatchId` through `src/router/dispatch-results.ts`) to adapt back into the shared settle path. That adaptation rebuilds the classified failure a reported deferral stands for — `DeliveryDeferredError`, an `AgentRunError` carrying the reported kind, or, for a `dependency` frame, a `DependencyBlockedError` reconstructed from the blockers the worker reported (issue #438) — so each one lands on the budget its kind names, exactly as a failure raised on this side would. With no eligible/connected worker the dispatch stays durably `pending` via the same `WorkerIneligibleError` token-free deferral. The control-plane host's own worker is the same DB-free transport entrypoint every other worker runs (`src/transport/connect-entry.ts`, over loopback), so the router is the queue's only consumer and there is one executor program rather than two (issues #551/#553). A worker that drops before reporting is reclaimed by the dispatch-lease reconciler — no new mechanism — except when a **different daemon process** takes that worker's lease, which the handshake settles from that signal itself (issue #719, above). The **DB-less remote worker** this once listed as out of scope has since landed (issues #394, #417, #418 — see "Worker connection modes" above): it resolves no persona token and opens no database, running source delivery under the operator's own token and routing the credentialed metadata reads/writes, the review-verdict ledger, and the follow-up-Review enqueue through the delivery API. Since issue #536 it also runs **`planning`**, the last phase the DB-free gate refused, so no phase is excluded from that path any more — the eligibility gate's phase check (issue #467, above) remains what routes around a *daemon* that declares fewer, rather than being a permanent carve-out for one phase. Still out of scope: over-the-wire secret delivery (unnecessary — the split keeps each project credential server-side instead).
