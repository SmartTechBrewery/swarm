# Architecture (MVP)

`PROJECT.md` describes SWARM's long-term vision: a stateless GCP cloud orchestrator (Cloud Run + Pub/Sub + Firestore) talking gRPC to a local daemon. **For the MVP, skip the GCP layer entirely** and mirror Cascade's architecture instead — a router + queue + worker running locally (Docker Compose, same as Cascade), reachable from GitHub via a Cloudflare Tunnel instead of a cloud ingress service. The gRPC/cloud-engine design in `PROJECT.md` is not being built yet; treat it as a possible future phase once the local-only version works end-to-end for one user, not as the current target. If this changes, update this file and `README.md` in the same change.

## Why copy Cascade's shape instead of `PROJECT.md`'s

`PROJECT.md` was written before we had a concrete reference implementation to copy. Cascade already solves "webhook comes in → figure out which project/task it belongs to → run an agent → report back" for exactly this kind of pipeline, in the same language, and its author knew Node.js well. Rebuilding that shape from scratch (or building the gRPC/Pub/Sub version) is strictly more work for no MVP-stage benefit. SWARM's two product differences from Cascade are:

1. **PM provider = GitHub Projects**, not Trello/JIRA/Linear (Cascade explicitly has no GitHub Projects adapter — this is net-new).
2. **SCM = GitHub**, same as Cascade — copy this piece close to verbatim.

Everything else — router/queue/worker split, manifest-based provider registration, credential scoping, loop prevention — should be copied, not reinvented.

## Components (MVP)

```
GitHub (repo + Projects v2)
   │  webhooks (pull_request, pull_request_review, issue_comment, issues, check_suite, projects_v2_item)
   ▼
Cloudflare Tunnel (external, not our concern — just a public HTTPS URL pointed at the router)
   ▼
Router  (Hono HTTP server, local Docker container)
   — verifies webhook signatures
   — resolves which SWARM project the event belongs to
   — records a durable dispatch (Postgres, ADR-002) and publishes its BullMQ
     wake-up (PR review-lifecycle jobs are prioritized ahead of PM-board jobs,
     so a review never queues behind a planning or implementation run —
     `src/queue/producer.ts`'s `priorityFor`)
   ▼
Worker  (host process — NOT containerized, one job at a time or a small pool)
   — looks up the trigger handler for the event
   — provisions a Git worktree (see "Worktree lifecycle" below)
   — spawns `claude` or `antigravity` CLI with the worktree as CWD
   — validates structured agent hand-offs and performs deterministic SCM delivery
   — persists step progress, then posts results back to GitHub Projects

API server (Hono HTTP server + tRPC, host process)
   — exposes a `/health` check and mounts a tRPC API under `/trpc`
   — self-hosted, single-process model running locally on the host
   — binds to `127.0.0.1`; authorizes every request except `/health` and `ping` by a per-user session cookie (issue #281 task 2) — or, when local single-user mode is enabled (`SWARM_SINGLE_USER_MODE`, issue #298), by resolving a bootstrapped `localhost-admin` with no cookie at all — then scopes every project-keyed procedure to the caller's project membership (issue #281 task 4)
   — serves the built dashboard SPA (`dashboard/dist`) statically as a fallback when present (self-hosted mode)
```

Redis (for BullMQ) and Postgres (for project config, credentials at rest, and run history — same role it plays in Cascade) run in the same Docker Compose stack as the router. The **worker and the API server are the exceptions**: they run directly on the host rather than in containers — the worker because it provisions Git worktrees and spawns the `claude` / `antigravity` CLIs (which need the developer's own PATH, auth, and config), and the API server (scaffolded via Hono and tRPC, and serving the dashboard SPA) for local-first, single-process execution. They connect to Redis/Postgres over their published host ports (`REDIS_URL` / `DATABASE_URL` in `.env`). There is no separate "cloud" process for the MVP; router, worker, API server, Redis, and Postgres are all local.

**Worker connection modes (ADR-003 §1).** The worker has two additive ways to reach the session service. The default in-process host worker (`src/worker/index.ts`) calls it directly and holds `DATABASE_URL`/`REDIS_URL` — the single-user/same-machine path. A **remote** worker instead runs the transport client (`src/transport/connect-entry.ts`, `npm run dev:worker:connect`) and holds **only** `SWARM_WORKER_CREDENTIAL` + `SWARM_CONTROL_PLANE_URL`: it reaches the router's authenticated `/worker/*` endpoint over the Cloudflare tunnel (`POST /worker/session` handshake, then a `/worker/stream` WebSocket carrying heartbeats), reconnecting with exponential backoff. Both keep the same `worker_sessions` liveness lease fresh, so the eligibility gate treats a remote worker exactly like a local one. The transport carries a session handshake and heartbeats and — when `SWARM_DISPATCH_MODE=transport` (ADR-003 §2, issue #407) — the split-delivery back-channel: a `TaskAssignment` pushed cloud→worker and `TaskExecutionResult`/`StreamLog`/`TaskProgress` reported worker→cloud. Never source. Beyond the handshake and heartbeats, the remote worker now **executes** a pushed `TaskAssignment` DB-free (`src/transport/assignment-execution.ts` `runAssignmentDbFree`, ADR-003 §2): it reconstructs the `ProjectConfig` from the assignment's non-secret slice (`src/transport/db-free-project.ts`), runs source-carrying delivery under the operator's own token (`SWARM_OPERATOR_GH_TOKEN` → `src/integrations/scm/github/operator-delivery.ts`), and streams `ack → running → live logs → terminal result` back over the #406 back-channel — no `DATABASE_URL`/`REDIS_URL`, no source on the wire, live output streamed only (never written to `run_output_events`), and cancellation via the shutdown signal alone. Everything a DB-free worker cannot do itself reaches its backing resource through the router's delivery API instead (below), called with the worker's *own* credential (`src/transport/delivery-client.ts`), so no project credential and no database connection is ever needed on the worker: **Implementation**'s two board writes and **Respond-to-review**'s board-card lookup + two status-report moves go up as PM delivery calls under the project's PM credential, **Review**'s `submitReview` goes up as an SCM delivery call under the project's reviewer PAT, and two things whose backing store is the control plane's *database* go up too — Review's three **review-verdict ledger** calls (`src/pipeline/review-ledger.ts` → `src/transport/review-ledger-delivery.ts`), so the review-verdict cap (issue #235) and the re-review signal (issue #328) keep working rather than being skipped for want of a `DATABASE_URL`, and Respond-to-review's **follow-up Review** enqueue (`src/pipeline/follow-up-review.ts` → `src/transport/follow-up-review-delivery.ts`), which writes a dispatch row and queues a synthetic event so a pushed fix is re-reviewed (issue #241). A remote worker therefore runs five of the six phases today: `respond-to-ci`, `resolve-conflicts`, `implementation`, `review`, `respond-to-review`. The two board-driven ones get the delegate-less transport writer (`createWriteOnlyTransportPmProvider`): the two writes plus two narrow reads — `listBlockers` and `findWorkItemByUrlSuffix` — ride the transport, and every other board read refuses loudly rather than guessing, because the control plane already performed the reads the assignment was composed from. `listBlockers` is transported, not stubbed, precisely because nothing else gates dependencies — `findOpenBlockers` runs inside the Implementation phase, not in the dispatcher — so answering "no blockers" would build a task whose prerequisites are still open (issue #330). `findWorkItemByUrlSuffix` is the *narrow* form of the board read (one URL tail in, at most one card out), which is why `listWorkItems` keeps refusing: a worker has no business enumerating a board to answer a one-card question. Respond-to-review's fix commit, push and response comment stay on the operator token — that reply is the *implementer* answering the review, so routing it through a composite built for the reviewer persona would have the reviewer answering itself. (The same attribution now holds on the control-plane delivery path, where the reply *does* ride the transport: the `/pr-comment` frame names the implementer, so the router writes it under that persona rather than the reviewer's — issue #444.) (A dependency block on a *transport* run enters the same bounded recheck as an in-process one: the worker reports it as a `dependency` deferral carrying the still-open blockers, and the control plane rebuilds `DependencyBlockedError` from that frame so the token-free `recheck` budget and its terminal "must be done first" board message apply unchanged — issue #438.) The supported-phase gate still fails `planning` cleanly, whose much wider PM write/split surface stays on the local host worker. The control-plane sending side that builds and pushes assignments is still a later phase, so this path ships un-wired and test-exercised. See **Control-plane dispatch** below.

### Observability

All code logs through one shared logger (`src/lib/logger.ts`) — a deliberately tiny, dependency-free wrapper (no pino/winston) mirroring Cascade's `logger.info/warn/error/debug(message, context)` shape. It emits **structured JSON** (one `{level,time,msg,...context}` object per line) for machine parsing, or — for a human watching a terminal — a local-clock timestamp, a colored level tag, the bound `component` as a `[component]` prefix, and remaining context as `key=value` pairs (color only on a real TTY, never when `NO_COLOR` is set). Format follows `SWARM_LOG_FORMAT` (`json`|`pretty`) and auto-picks pretty on an interactive TTY, json when piped/containerized — **leave it unset** in `.env` rather than hardcoding either value: the router's own `docker-compose.yml` environment block already pins it to `json` for that container regardless of `.env`, so setting it in `.env` only ends up overriding the host worker's auto-detection (and silently losing pretty/color) without changing the router at all. `SWARM_LOG_LEVEL` (`debug|info|warn|error`, default `info`) sets the minimum emitted level. Because router and worker share a log stream, each entry point calls `configureLogger({ component })` at startup so every line it emits is tagged `component: "router"` / `"worker"` and stays attributable.

## Provider abstraction

Three integrations, each following the manifest/registry pattern from `ai/CODING_STANDARDS.md`:

### SCM: GitHub (`src/integrations/scm/github/`)

The integration itself lives under `src/integrations/scm/github/` — consistent with the PM provider (`src/integrations/pm/github-projects/`) and the module shape in `ai/CODING_STANDARDS.md` — but its internals are ported close to verbatim from Cascade's `src/github/*`, so match Cascade's file shapes (`scm-integration.ts`, `client.ts`, `personas.ts`) rather than reinventing them. Webhook ingress lives beside them in `webhook.ts`: it was Cascade's router adapter (`src/router/adapters/github.ts`), and issue #385 moved it under the provider it belongs to once ingress started running through the contract.

- **The contract + registration (issue #294).** Shared code programs against the provider-neutral `SCMProvider` (`src/scm/types.ts`), which `GitHubSCMIntegration` declares (`implements SCMProvider` *is* the conformance check — a runtime harness stays deferred until a second provider implements the whole contract rather than throwing for the half it hasn't built; see the Bitbucket section below). It composes the pre-existing neutral seams rather than duplicating them: it extends `ScmMergeProvider` (`src/scm/merge.ts`) and returns `ScmDeliveryProvider` (`src/scm/delivery.ts`), and its `deliveryProvider(project, persona)` is documented as *one* producer of a delivery provider, not the only one (the operator-token and transport-backed composites below are the others). Neutral homes for the shapes shared code reads — `ScmPersona`/`ScmPersonaIdentities`, `PullRequestDetails`, `CheckRunState`/`AggregateCheckStatus` — live in the same file, with GitHub-local aliases (`GitHubPersona`, `ConflictCandidatePullRequest`, `CheckSuiteStatus`) kept in the GitHub module so nothing had to be renamed at once. GitHub self-registers an `SCMProviderManifest` into `scmProviderRegistry` (`src/integrations/scm/{manifest,registry}.ts`) from `src/integrations/scm/github/index.ts`, loaded by the one canonical entrypoint alongside PM — a **shared instance**, not a `createProvider(project)` factory, because the integration is stateless and takes `project` per call.
- **Neutral ingress + triggers (issue #385).** Webhook ingress and the SCM-driven triggers now run entirely through the contract, which widened with the four methods the receiver needs: `readWebhookRequest` (which header names the event / carries the delivery id / carries the signature), `parseWebhookEvent` (raw body → normalized event), `verifyWebhookSignature`, and `isSwarmGeneratedEvent` (the comment drop gate). The normalized event is `ScmEvent` (`src/scm/events.ts`) — a Zod schema, because it is also the durable queue payload — whose `kind` is a neutral vocabulary (`pull-request`, `pull-request-review`, `work-item`, `work-item-comment`, `checks`) that each adapter maps its own event names onto. The manifest gained a `webhookRoute` (`/github/webhook` for GitHub, which GitHub Projects' `projects_v2_item` board webhook shares), and the receiver mounts one route per registered manifest instead of hardcoding a path.
- **Registry-resolved outbound call sites (issue #386).** The project-scoped mutations resolve their provider through the registry too, so no pipeline, worker, or router module constructs one: the lazy delivery-provider default in the five delivery-owning phases (`implementation`, `review`, `respond-to-review`, `respond-to-ci`, `resolve-conflicts`), the worker's `resolveScmDelivery` local delegate, its run-row PR-title read and its phase-failure/interrupted-job PR comments (`src/worker/consumer.ts`), the durable merge executor's default merge capability (`src/worker/merge-automation.ts`), and the router's server-side `buildScmDelivery` default (`src/router/worker-delivery.ts`). Two lookups, picked by what the caller holds: `requireSCMProvider(job.providerId)` where a durable job already names its provider (the interrupted-job comment), `requireProjectSCMProvider(project)` everywhere else. The latter deliberately implements no selection and no fallback — it asserts that exactly one provider is registered and throws otherwise, because `ProjectConfig` carries no provider discriminator; that throw is what forces project→provider selection to be designed alongside the second provider rather than resolving silently. Only the *source* of the provider changed, never when it is built: every default stays inside the phase's own `??`, so persona-credential resolution keeps happening inside the delivery try/catch and the `legacyMode` guard, injection precedence, merge outcomes, and retry policy are untouched. The durable merge executor resolves its default inside the attempt's own `try` rather than in a default parameter, so an unresolvable provider settles the claimed dispatch as `provider-error` like any other provider failure instead of throwing out of `processJob` and leaving the dispatch in flight. Still concrete, for Phase 2/2: the DB-free worker's operator-token delivery (`src/transport/assignment-execution.ts`), which needs the contract widened with an operator-credential delivery producer.
- Dual-persona tokens (`implementer`, `reviewer`) scoped via `AsyncLocalStorage` (`src/integrations/scm/github/client.ts`'s `withGitHubToken`), never passed as plain arguments. Both resolve behind the same `getPersonaToken`/`getPersonaTokenOrNull` seam (`src/config/provider.ts`) but from different sources (issue #396): the **implementer** is the worker operator's own token, a worker-local `SWARM_OPERATOR_GH_TOKEN` env var (`src/config/operator-token.ts`) that is never persisted, never in project config, and never sent over the transport — mirroring `SWARM_WORKER_CREDENTIAL`; the **reviewer** stays a project-scoped credential *reference* in the config's `credentials` block, resolved from Postgres (`src/db/repositories/credentialsRepository.ts`). Two distinct GitHub identities remain required for persona routing (`getPersonaForLogin`/`personaForEvent`), the Respond-to-review reviewer gate, the board's status-change drop gate, and the independent-reviewer invariant (PROJECT.md §5.3), while comment loop prevention keys on content markers (see below). (Same-host `SWARM_OPERATOR_GH_TOKEN` assumption today; federating it is a later phase.)
- GitHub's webhook module (`src/integrations/scm/github/webhook.ts`) parses `pull_request`, `pull_request_review`, `issue_comment`, `issues`, and `check_suite` into the neutral `ScmEvent` kinds; the receiver resolves the SWARM project from the event's repo and the worker dispatches with the right persona's credentials in scope. Raw event names, header names, payload paths, and the `sha256=` signature framing exist only here.
- Loop prevention on comment events by **SWARM-origin marker**, not author login (issue #443, exactly as described in `ai/CODING_STANDARDS.md`): `SCMProvider.isSwarmGeneratedEvent` reads the comment's own body off the normalized event (`commentBody`, populated for comment events only and for this gate only) and drops it when `isSwarmGeneratedBody` (`src/scm/swarm-origin.ts`) finds a hidden `<!-- swarm-… -->` marker or the `_Generated by SWARM…_` footer — so SWARM never reacts to its own ack/reply whichever account posted it, and the operator's *hand-written* comments from that same account still get through. Every SWARM comment body must therefore carry one of the two markers; both the delivery markers (`swarmMarker`) and the footer are built from that module's constants so producer and detector can't drift. The gate needs no credential and so has no failure mode. PR/review lifecycle routing between personas is handled by `getPersonaForLogin`, not by the drop gate.
- Pipeline code requests deterministic mutations through the provider-neutral `ScmDeliveryProvider` seam (`src/scm/delivery.ts`). Agents write Zod-validated semantic hand-offs and never commit, push, create PRs, submit reviews, or post comments. The GitHub adapter supplies persona-scoped implementations, durable delivery markers, existing-PR recovery, and safe expected-SHA pushes. Step progress is written beside the hand-off in the retained worktree so a retry resumes the failed delivery operation rather than repeating completed mutations.
- **Server-side SCM metadata delivery (ADR-004 §2, config-gated).** The metadata-only delivery calls — `submitReview` and `postComment` — can run on the router instead of the worker, so a federated worker never holds the per-project reviewer PAT. The router hosts a small authenticated delivery API (`src/router/worker-delivery.ts`: `POST /worker/delivery/review` + `/pr-comment`, mounted in `src/router/index.ts`) whose pure `handleSubmitReview`/`handlePostComment` authenticate the worker credential, confirm a routable enrollment in the target project, resolve the acting persona's credential **server-side** (`getPersonaToken`), and perform the GitHub write — the review lands as a genuine GitHub review, keeping the `pull_request_review` respond-to-review trigger working. **The `/pr-comment` frame carries the requesting persona** (`PostCommentDeliveryRequestSchema`): a Review's comment is the reviewer's, a Respond-to-review reply is the *implementer* answering that review, and a server left to infer it posted that reply under the reviewer being answered (issue #444). The field defaults to `reviewer`, so a client that sends none is unchanged and the wire stayed compatible without a protocol bump; `/review` carries no persona because only Review submits a verdict and it is always the reviewer's. The router resolves `implementer` through the same seam to its own `SWARM_OPERATOR_GH_TOKEN` — the same-host assumption that variable already documents (issue #396), so on a genuinely different-machine deployment the reply is authored by the *server* operator's account, which the federation gap ADR-004 §3/§4 (#397/#398) owns. A worker opts in with `SWARM_CONTROL_PLANE_URL` + `SWARM_WORKER_CREDENTIAL`: `resolveScmDelivery` (`src/worker/consumer.ts`) then hands the phase a transport-backed provider (`src/scm/transport-delivery.ts`) built for the phase's persona, which POSTs only the verdict + comment body + PR number (+ that persona) up the wire (never the repository tree) and delegates every source-carrying / attribution op (commit, push, create PR) to the operator's own in-process token. The frames are Zod schemas in `src/transport/protocol.ts`, and the wire mechanics (URL join, bearer header, protocol stamp, throw-on-non-2xx) live in one shared client, `src/transport/delivery-client.ts`; the server writes are marker-idempotent, so a retried transport call can't double-post. Unset (the local host worker, the default) keeps the in-process delivery path unchanged. A **DB-free** remote worker (ADR-003 §2) uses the same route for its Review phase, composing the transport provider over its operator-token provider instead of a DB-backed one, and four sibling routes front a **database** rather than a credential for it — same worker-credential auth and enrollment check: `POST /worker/delivery/review-ledger/prior|mark|abandon` over the `review_verdicts` table, and `POST /worker/delivery/follow-up-review`, which performs the dispatch-row write + queue enqueue a `fixed` Respond-to-review response owes its new commit (issue #241). That last one stays a *call the phase makes* rather than a fact reported in its terminal result, so a failed enqueue still defers inside deterministic delivery and the resumed retry re-schedules; the scheduler's deterministic dispatch identity absorbs the retry.
- **Server-side PM metadata delivery (ADR-004 §2, the independent Phase 2/2 half).** The same split applies to the two metadata-only **PM** board writes — `moveWorkItem` and `addComment` — so a federated worker never holds the per-project PM credential either. The same delivery API gains two sibling routes (`POST /worker/delivery/pm/move` + `/pm/comment`) whose pure `handleMoveWorkItem`/`handleAddPmComment` run the identical worker-credential auth + active-enrollment authorization, then resolve the PM credential **server-side** by building the concrete provider (`createGitHubProjectsProvider(project)`) and calling `moveWorkItem`/`addComment`. Only the canonical `PmStatusKey` (`src/pm/pipeline.ts`) or the comment body crosses the wire — never a board option ID (the adapter resolves it server-side, RULES.md §2) and never the repository tree. A worker in control-plane mode gets its `pm` from `resolvePmDelivery` (`src/worker/consumer.ts`), a transport-backed `PMProvider` composite (`src/pm/transport-delivery.ts`) whose two writes POST to the control plane and whose every read + other write delegates to the in-process provider, so the full `PMProvider` surface the phases (planning / implementation / respond-to-review) expect is preserved. Unset keeps today's in-process `createGitHubProjectsProvider(project)` path byte-for-byte. A **DB-free** remote worker has no in-process provider to delegate to, so it uses the same module's delegate-less variant (`createWriteOnlyTransportPmProvider`): identical writes, plus two transported **reads** — `POST /worker/delivery/pm/blockers`, so Implementation's dependency gate still gates (issue #330), and `POST /worker/delivery/pm/find-item`, which resolves the one card whose backing URL ends with a given suffix so Respond-to-review can still report In progress / In review — and every other read refusing rather than guessing. The card lookup is a `PMProvider` method (`findWorkItemByUrlSuffix`), not a URL match at the call site: widening the interface (RULES.md §2) is what lets the server answer with one card instead of proxying a whole board, and keeps the pipeline free of any provider-specific URL shape. The remaining PM **reads** (`getWorkItem`/`listWorkItems`/`findComment`/discovery) stay worker-side on the DB-holding worker and have no server-side route; the out-of-band failure/interrupted-run board comments run on that worker's `processJob`, not on a remote worker, so they need no routing here. Both delivery halves have now landed, so **ADR-004 §2 is built** — and so is its §3, in two phases: the Review trigger's ownership gate now keys on work-item origin (`isSwarmManagedPullRequest`, issue #397) and comment loop prevention on SWARM-origin markers (`isSwarmGeneratedBody`, issue #443), so neither reads a persona login and auto-review fires on the federated path.
- **Worker→PR attribution on the run row (ADR-004 §4, issues #398 + #446).** The control plane keeps a durable `(work item, phase, worker, user, PR url)` record so it can say which worker/user produced a given PR or review even if the token model later changes — all of it on the existing `runs` row (`src/db/schema/runs.ts`) rather than a parallel table, written through that row's normal lifecycle. Two nullable columns join `worker_id`/`worker_fencing_token`: **`worker_user_id`** (→ `users.id`, `ON DELETE SET NULL`), written at dispatch from the owner the gate already resolved (`DispatchSelection.ownerUserId`, `src/worker/eligibility-gate.ts`) in all three run-row entry points (`createRun` plus both `resetRunToRunning` paths), and **`produced_pr_url`**, written at settle from the phase result (`PhaseRunResult.prUrl` → `CompleteRunInput.producedPrUrl`). Both ends are the control plane's to record because a DB-free worker (ADR-004 §2) cannot write them itself: the produced PR travels home on the terminal result frame as an optional `TaskExecutionResult.prUrl` (`src/transport/protocol.ts`), emitted by `succeededResult` (`src/transport/assignment-execution.ts`) and mapped back into the shared settle path by `adaptResultToPhaseRun` (`src/router/dispatcher.ts`) — optional, so it needs no protocol-version bump and an older worker simply omits it. The user id is denormalized rather than joined through `workers.owner_user_id` so removing a worker (which nulls `worker_id`) cannot erase the attribution, and `produced_pr_url` is deliberately *not* cleared on a retry: the PR is a real external artifact that outlives the attempt. Nullable throughout — an unfederated / single-user run records no worker at all, and only a PR-producing phase (Implementation) reports a PR; a produced *review* needs no column, since `review_verdicts` plus the run's `pr_number`/`review_verdict`/`review_ordinal` already identify it. Phase 2/2 (issue #446) surfaces the record on the run detail view: `runs.getById` (`src/api/routers/runs.ts`) resolves the recorded ids into display labels with the same `getWorker` + `getUserById` pair `assembleDashboardWorker` uses — naming each safe field explicitly, and only *after* `assertProjectAccess`, so a caller who may not see the run triggers no identity read — and returns them as an additive `attribution` object (`{ workerId, workerName, userId, userDisplayName }`) on the existing payload, no new procedure. The page shows **Worker** / **Worker owner** in its Execution Environment grid and links `produced_pr_url` as **PR opened by this run**, labelled apart from the `PR #n` a Review / Respond-to-review run acted on. Nullability carries through to the UI: a run with no recorded worker renders the same neutral `—` the other optional fields use (never a raw UUID, never a fabricated owner), a historical row with `worker_id` but no `worker_user_id` attributes through the worker row's current `owner_user_id`, and a deleted worker/user or a failed lookup degrades to the recorded id rather than erroring the page. So **ADR-004 §4 is built**. The Runs *table* and the Queue view stay unattributed by design (a fixed-width layout change, and a waiting dispatch has no bound worker yet).
- Merging an approved PR goes through the provider-neutral `ScmMergeProvider` seam (`src/scm/merge.ts`, issue #253; direct-merge-only per issue #292): a single `mergePullRequest(project, prNumber, approvedHeadSha)` capability returning a terminal `MergePullRequestOutcome` — `merged`, `not-ready`, `not-eligible`, `policy-blocked`, `unsupported`, or `provider-error` — never a thrown error, so a refusal can't retroactively fail an already-completed Review. Pipeline code never merges: after an eligible Review approval the worker persists a **durable merge dispatch** (`src/worker/merge-automation.ts`, see "Durable dispatch state machine" below) whose executor invokes this capability. GitHub is the first implementation: every attempt re-reads the PR's current state, verifies the approved head SHA and approval still hold, and performs the **direct** REST merge (`pulls.merge` via `src/integrations/scm/github/client.ts`'s `mergePullRequestDirect`) under the project's implementer PAT, pinned to the approved head so a concurrent push produces GitHub's non-merged stale-head response rather than merging unreviewed code. GitHub's native auto-merge is deliberately never requested (issue #292): it is unavailable on many private repositories, has no portable equivalent in other SCMs, and its error text (`Auto merge is not allowed for this repository`) once bypassed merge automation entirely. GitHub-specific classification (which REST error means what — a merge-queue requirement is `unsupported`, 405/409 are `not-ready`, 403 is `policy-blocked`) stays inside the adapter. A future Bitbucket/GitLab adapter implements the same interface against its native direct PR/MR merge API and outcome mapping, with no dispatch or worker changes.

### SCM: Bitbucket (`src/integrations/scm/bitbucket/`) — registered, not selectable (issue #296)

The second SCM provider, built out over four ordered phases. Bitbucket **Cloud** only (`https://api.bitbucket.org/2.0`); Server / Data Center is out of scope. It mirrors the GitHub folder's file shapes (`client.ts`, `credentials.ts`, `personas.ts`, `scm-integration.ts`, `index.ts`) rather than inventing a layout, and adds no npm dependency.

- **Phase 1/4 (landed): the credential-scoped foundation.** `client.ts` binds the **credential string** (not a client object — Bitbucket has no Octokit) to the async context via `AsyncLocalStorage` (`withBitbucketCredential`), builds each request over the global `fetch`, throws `BitbucketApiError` carrying a `status` that mirrors Octokit's `RequestError#status` (so phase 4's merge classifier reads it the same way), follows the `next` cursor in `paginateBitbucket` and refuses a cyclic one, and resolves an account login (`nickname`, falling back to `account_id`) for loop prevention. It is the only place that branches on the credential's *form*: a `username:app_password` pair goes out as HTTP Basic (the one form that can answer `GET /2.0/user`), anything else as a bearer token. `credentials.ts` resolves the implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN` and the reviewer from the project's existing provider-neutral `credentials.reviewer` reference — deliberately *not* by widening `src/config/provider.ts`, whose implementer branch returns the *GitHub* operator token. `project.repo` (`owner/repo`) doubles as Bitbucket's `workspace/repo_slug`, so no config-schema field was added. `personas.ts` caches both persona identities per project with the same 60s TTL, fails closed when either can't be resolved, and matches logins case-insensitively (a Bitbucket `nickname` has no canonical case) with no `[bot]`-suffix handling — that suffix is a GitHub App artifact.
- **Registered but unreachable.** `BitbucketSCMIntegration implements SCMProvider`, and every method the later phases own **throws a message naming the method and its phase** rather than returning a misleading empty value. Its manifest registers from the same canonical entrypoint with `runtimeReady: false` (`src/integrations/scm/manifest.ts`), so the project-scoped lookup keeps resolving GitHub and the receiver mounts no `/bitbucket/webhook` route — registration changed no existing behavior. See `ai/RULES.md` §2 for why that flag is not provider selection.
- **Still to come:** webhook signature verification + event parsing (phase 2/4), pull-request/check reads (phase 3/4), comments + delivery + merge (phase 4/4). Even after all four, a Bitbucket project cannot run end to end — nothing selects a project's SCM provider, which needs project→provider selection plus a served ingress route in a separate follow-up.

### PM: GitHub Projects (`src/integrations/pm/github-projects/`) — net-new, no Cascade equivalent

GitHub Projects (v2) is GraphQL-only; there is no REST equivalent for reading/writing item fields. Shape the provider around:

- **Work item** = a Projects v2 item (usually backed by an Issue or PR in the repo).
- **Status** = the item's single-select "Status" custom field — moving a task through the pipeline (Backlog → Planning → In Progress → In Review → Done) means updating that field's option value via `updateProjectV2ItemFieldValue`.
- **Events** = the `projects_v2_item` webhook event (`created`, `edited`, `reordered`, `deleted`), filtered to status-field edits — this is the equivalent of Cascade's `pm:status-changed` trigger. It is **never** a repo-level event: GitHub delivers it on an **organization** webhook or to a **GitHub App** with the Projects permission (there is no plain user-account webhook). For SWARM's user-owned board the App route is effectively the only option — see `docs/github-projects-v2-api.md` §5.
- **Comments** = GitHub Projects items don't have their own comment thread; write agent output (e.g. Antigravity's plan) as a comment on the linked Issue/PR, not as a Projects-native comment.
- **Assignees** = the backing Issue/PR's assignees, read in the same round-trip as the item and mapped to the provider-neutral `WorkItemAssignee` (`handle`/`displayName`/`providerId`) on every `WorkItem` — GitHub's `login` vocabulary stops at the adapter. `assignees` is always present (`[]` when nobody is assigned), and the capability flag `PMProvider.supportsAssignees` lets a provider with no assignee concept opt out explicitly, exactly like `supportsDependencies`. SWARM resolves a handle to one of its own users through the identity-linking seam (below), never by pattern-matching a GitHub identity.

Implement it against the same `PMProvider`-shaped interface Cascade uses (`getWorkItem`, `moveWorkItem`, `addComment`, `listWorkItems`, …) so the router/trigger/dispatch code stays provider-agnostic — see Cascade's `src/pm/types.ts` for the exact interface to mirror.

## Pipeline phases

Per `PROJECT.md` §5, adapted to GitHub Projects as the board and GitHub as the sole SCM:

Each worker-spawned agent is scoped to one phase. A shared prompt guard forbids the manual
`solve-issue` skill, arbitrary subagents/skills, and later-phase work; only the worker owns
phase hand-offs, personas, and worktrees.

**Automation opt-in gate (issue #131).** The two board-driven phases below — the phases that *start*
SWARM working on a work item — only dispatch for an item carrying the project's
`pipeline.automationLabel` (default `swarm`). The check is provider-neutral: `resolveAutomationLabel`
/ `hasAutomationLabel` (`src/pm/automation-label.ts`) match the configured name against
`WorkItem.labels`, the canonical PM capability every adapter already populates from its own native
labels — no `PMProvider` method was widened, and a Trello/Jira/Linear adapter inherits the gate for
free. It is evaluated at the single dispatch choke point (`processJob`, `src/worker/consumer.ts`),
*before* the in-flight guard and `acquireProjectSlot`, so a skip costs no slot, no worktree, and no
tokens; because it lives there it is re-evaluated on every fresh webhook, delayed retry,
self-enqueued next phase, capacity promotion, reconciler republish, and manual "Retry now" —
removing the label therefore stops all later dispatches, but never terminates an agent already
running. A skip logs the missing label and settles the dispatch `completed` with outcome
`skipped-not-eligible` (a retried run row is finalized `failed` with the same reason rather than left
`deferred`). That outcome is deliberately named for eligibility in general, not for the label:
#339's worker-authorization gate lands at the same call site and settles through the same value with
its own reason. Split children Planning creates carry the configured label so SWARM's own siblings
aren't gated out of its pipeline. An explicitly empty `automationLabel` disables the gate. The label
is an automation opt-in, **never** an access-control mechanism — ADR-001's authorization layers are
separate and unaffected. The SCM continuation phases (3–5) are not gated yet (phase 2/2 of the same
work item).

1. **Planning** — item enters "Planning" status → worktree provisioned → the planning agent writes `proposed_plan.md` → plan posted as a comment on the linked Issue. On successful completion the item's backing issue is also labeled `planned` via `PMProvider.addLabel` (issue #384) — an idempotent, provider-visible marker (the label is auto-created if missing) that a run *finished* planning, applied on both the normal-agent and preplanned-split-child completion paths and independent of the `autoAdvance` Status move. By default the item stays in "Planning" (a human reviews the plan, then moves it to "ToDo" to greenlight Implementation); `pipeline.planning.autoAdvance` flips that to an automatic move. When `pipeline.planning.autoSplit` is on (default) and the agent judges the item too large for one PR, it also writes `proposed_split.json`: the original item is re-scoped into the smaller **first** task (`proposed_plan.md` is that task's plan) and the remaining work is spawned as sibling items via `PMProvider.createWorkItem`. Each sibling ends in **Planning**, is tagged `swarm:split-child` **and `planned`** (issue #426 — a split child is planned by construction, so the marker is accurate as soon as it holds the parent's plan; a prepared child's own Planning dispatch is then suppressed, and the `applyPlannedLabel` on any run that does reach it is idempotent), and gets a comment explaining the split. SWARM first creates its card in Backlog, publishes the child's complete plan as a normal, human-readable **Preplan** comment (issue #431 — GitHub does not render the hidden marker, so this is the copy an operator reviews; it carries its own `<!-- swarm-preplan-comment:… -->` provenance marker, which also keeps it out of the dependency gate's prose scan; a replayed delivery is short-circuited by the plan-delivery marker before any child is re-prepared, so no per-child duplicate check is needed), writes the parent-generated validated preplanned marker (`<!-- swarm-preplan:v1 … -->`, `src/pipeline/preplan.ts`) into its issue body, then moves it to Planning. Publishing before the marker write is deliberate: a failed publication leaves no marker, so the child stays in Backlog — with a split comment that claims no published preplan — and a later Planning move runs a normal agent, rather than being suppressed by a marker whose plan nobody can read. That ordering guarantees both the Planning-move event and any delayed card-creation event find a valid marker; the trigger suppresses the redundant Planning run while the marker remains valid and the item keeps its `swarm:split-child` label. The `planned` label is applied right after that marker-and-move preparation succeeds — not in the `createWorkItem` labels — so a child whose preparation failed is never labeled up front (issue #436); if marker embedding failed, the child stays in Backlog needing a full Planning agent run, while if the Planning move failed, its embedded marker remains valid, so it keeps its plan and `shouldSkipPreplanned` suppresses any later Planning dispatch — no agent is spent on it, but nothing applies `planned` either, and the card stays unlabeled unless an operator forces the fallback run (getting the card into Planning and invalidating the preplan via `swarm:replan` or removing `swarm:split-child`). That label write is best-effort like `addBlockedBy`, logged and swallowed so it can never abort the split mid-loop; nothing reads the label, so a swallowed failure costs only the marker's accuracy. A malformed/stale marker, `swarm:replan`, or removing the label falls back to normal Planning. This keeps splitting behind the provider-agnostic `PMProvider` (no GitHub Projects specifics leak into the phase). A split also **chains the phases as dependencies** (issue #330): the agent orders the titles by phase (`Phase 1/N …`), and for each spawned sibling the phase records a cumulative `blocked by` relationship on *every* preceding phase (phase 3 ← phases 1 and 2; phase 4 ← 1, 2, 3; …) — via `PMProvider.addBlockedBy` (behind `supportsDependencies`, so a provider that can't model dependencies degrades gracefully) *and* by naming those blockers in the sibling's split comment. The two guards mean a later phase is never startable before its predecessors land.
2. **Implementation** — item enters "ToDo" → **a dependency gate runs first** (issue #330): before the "In Progress" move, the worktree, or the agent, the phase asks the `PMProvider` for the item's still-open blockers (`listBlockers` — native `blocked by` relationships plus prerequisites named in the item's description or in a **human** comment; SWARM's own comments are excluded from that prose scan by `isSwarmGeneratedBody`, so a published plan saying "requires #N" never invents a blocker for the item it plans, issue #431) and, if any are unfinished, **defers** the run as a token-free `recheck` (no worktree, no agent → zero model tokens; re-checked every `SWARM_DEPENDENCY_RECHECK_MS` on its own budget, separate from the rate-limit budget, until the blocker closes or `SWARM_DEPENDENCY_MAX_WAIT_MS` is exhausted, at which point it settles `failed` with an "issue X must be done first" comment). This is what stops a later phase from being implemented before its predecessors land (the out-of-order build that produced the PR #326/#327 conflict). Otherwise → the phase moves it to "In Progress" to report the pickup → the agent implements/verifies and writes a semantic hand-off → SWARM validates the prepared tree, commits/pushes, opens or reuses the PR, and links it back to the item. Successful delivery moves the item to "In review" exactly when `pipeline.review.enabled` is on; otherwise it remains "In progress".
3. **Review** — PR opened / checks pass (independent of the Projects status report) → the reviewer agent writes a structured verdict and body → SWARM submits the formal review under the reviewer persona. A durable, restart-safe ledger (`review_verdicts`, one row per `(project, repository, PR, head SHA)`, issue #235) caps every PR at **three** submitted verdicts — an initial review plus at most two **re-reviews** (`REVIEW_VERDICT_CAP`, the single place the number is defined): the `pr-review` trigger reserves a slot before dispatching (reusing a same-head retry's existing slot rather than charging it again) and refuses one past the cap; the phase marks its reservation `submitted` once GitHub confirms the review (idempotently, so a crash between delivery and this write is repaired by a retry without a duplicate submission). **The re-review is scoped, not a fresh full pass (issue #328):** when the phase finds a prior `request-changes` verdict already submitted for this PR (`getPriorSubmittedReview`), it builds the re-review variant of the prompt (`buildReviewPrompt(..., isReReview=true)`), which tells the reviewer to verify *only* whether the previously requested changes were implemented correctly — approve when they were, otherwise request changes with a strong, specific fix instruction — and **not** to surface newly-noticed pre-existing issues the first review missed (the only admissible new findings are regressions the fix commits themselves introduced). This keeps each permitted re-review spent on confirming the fix rather than restarting the cycle over unrelated work. Only a submitted `approve` requests a merge (`pipeline.respondToReview.autoMerge`, issue #235) — the worker's Review success path persists one durable merge dispatch per approving run (`requestMergeAutomationIfEligible`, `src/worker/consumer.ts` → `src/worker/merge-automation.ts`, issue #292), and the dispatch's executor performs the direct PAT merge through the provider-neutral `ScmMergeProvider`, retrying transient `not-ready` outcomes on a bounded backoff (15s doubling to 5min, six retries). Every outcome lands on the Review run's `review_merge_*` columns; a terminal refusal (`not-eligible`, `policy-blocked`, `unsupported`, `provider-error`, `retry-exhausted`) is visible there and on the dispatch record but never fails the completed Review.
4. **Respond to review** — by default, the reviewer persona's `changes_requested` review → the implementer addresses the batch and writes a structured response → SWARM commits/pushes any fix and posts the response idempotently. `pipeline.respondToReview.skipOnMinors` defaults to true so approvals and comment-only reviews do not consume a separate agent run; set it false to respond to every reviewer-persona verdict. The trigger resolves the submitted review's ledger record (by review id, falling back to PR/head for the narrow webhook race before the Review phase has stored it) and, on the safety cap's **last permitted** `changes_requested` verdict, stops here instead of dispatching — that PR needs a human, and the outcome is recorded as `manual-intervention-required` rather than starting an unbounded further cycle; a lookup failure for a `changes_requested` event fails the same way (closed) rather than risk reopening the cycle on a persistence outage. Respond-to-review's own outcomes (`fixed`/`pushed-back`/`no-findings`) never request a merge themselves — addressing feedback isn't a fresh approval. Like Implementation, it reports progress on the board as a status *report*, not a trigger: the card moves to "In progress" while the implementer works and back to "In review" once it has responded (best-effort — a card it can't resolve or move is logged and skipped, never failing the response). Neither status starts a phase, so bouncing the card can't re-fire Review; only a new fix commit does.

**Reliable follow-up Review after a `fixed` push (issue #241).** A `fixed` outcome whose commit was actually pushed and differs from the reviewed head reliably enqueues exactly one follow-up Review for the new SHA — reusing the same Review trigger, aggregate-check routing (`decideAggregateCheckOutcome`), reviewer persona, PR/head dispatch dedup, and durable review-verdict ledger a real `checks` webhook would drive, via a synthetic `checks` `completed` event (`src/pipeline/follow-up-review.ts`) carrying the PR number/branch/repo and new head. Unlike `selfEnqueueNextPhase`'s best-effort PM hand-off, this is part of the phase's own deterministic delivery: it runs after the push/comment delivery steps and before the delivery-progress checkpoint (`DeliveryProgress.followUpEnqueued`) is saved, so a queueing failure raises `DeliveryDeferredError` (preserving the worktree for a resumed retry) instead of silently dropping the follow-up, and the enqueued job's id is a deterministic hash of `(project, PR, new head)` so a crash between a successful enqueue and that checkpoint write can't duplicate the job. `pushed-back`, `no-findings`, a failed/unpushed response, and an unchanged head (the pushed commit somehow matching what was reviewed) enqueue nothing. A follow-up Review that approves may still request the same approval-only merge described above; Respond-to-review itself still never requests it.
5. **Respond to CI** — a PR's check suite completes with a failing check → worktree on the PR's task branch → Claude Code (implementer persona) inspects the failing checks, fixes the build surgically and pushes (or reports no code change was warranted) — mirrors Cascade's `respond-to-ci` agent. A per-PR fix-attempt cap stops a never-sticking fix from looping (each fix commit is a new SHA, so it re-triggers CI).

### Trigger wiring (SWARM-53)

The phases are self-contained orchestrators; the trigger registry (`src/triggers/`) is what connects inbound events to them. `registerBuiltInTriggers` (`src/triggers/builtins.ts`) registers three handlers under `src/triggers/handlers/`:

- **`pm-status-changed`** — one handler for both PM-driven phases. On a `projects_v2_item` Status edit (or a card added), it re-reads the item authoritatively via the `PMProvider` (never trusting the webhook's Status value — `docs/github-projects-v2-api.md` §5) and, per `resolvePipelinePhaseForOptionId`, starts Planning (→ Planning) or Implementation (→ ToDo), or returns `null` for any other status — including "In progress", which Implementation itself moves an item *to* as a status report, not a trigger. The Board view's drag-and-drop actually fires a `reordered` action (no `changes.field_value` at all — a real delivery confirmed this), not `edited`, so the adapter accepts both; a Redis-backed dedup (`pm-status-dedup.ts`) stops the resulting harmless within-column reorders from re-dispatching the same phase.
- **`preplan-invalidated`** — starts fallback Planning for a split child whose card is already in Planning when an `issues` webhook reports a body edit, addition of `swarm:replan`, or removal of `swarm:split-child`. Those issue changes do not emit a Projects Status event. The handler lists Planning items through `PMProvider`, matches the event's backing-item URL, and re-evaluates the authoritative marker/labels before dispatching; a still-valid preplan remains a no-op.
- **`pr-review`** — the PR-lifecycle handler. Starts Review on a non-draft, **same-repo**, **SWARM-managed** PR opening or its checks passing, and routes a *failing* check suite to Respond-to-CI. A `review` disposition also reserves the durable review-verdict safety-cap slot (see Pipeline phases §3) after the dispatch dedup claim; `respond-to-ci` never consumes one. On a `checks` completion it re-queries *every* check on the head SHA (`SCMProvider.getAggregateCheckStatus`) rather than trusting the single event's own conclusion — a provider fires one event per workflow — and decides via `aggregate-check-decision.ts`: review if all complete and none failed, **respond-to-ci** if a check failed, or **defer** if a check is still running, scheduling a coalesced ~30s recheck (`scheduleCoalescedJob`) that re-queries fresh state (a `recheckAttempt` cap bounds the loop against a stale checks API). Fork PRs are dropped from the Review path (their head SHA is unreachable for the detached review checkout). A **work-item origin gate** (`isSwarmManagedPullRequest`, `src/triggers/swarm-managed-pr.ts`, issue #397) reviews only PRs SWARM manages, so a human- or third-party PR never burns a review: the PR's head branch must be exact `<branchPrefix><taskId>` (digits) **and** SWARM must hold an `implementation` run row for that work item in that project (status-agnostic — Implementation opens the PR from inside its own still-running process). It replaced an author-persona gate, which stopped carrying the signal once the implementer credential became the worker operator's own GitHub account (ADR-004 §3): a federated PR is authored by a plain user, and the control plane cannot even resolve another operator's identity. The gate is evaluated **once** for both entry events, inside the mergeability check that already fetches the PR — so it still runs *before* the `checks` path's heavier aggregate query, and that path no longer needs an author PR read at all. A failed run-history lookup degrades to the same bounded mergeability recheck as a failed PR fetch rather than dropping a legitimate review. The respond-to-ci dispatch reuses the same per-SHA dedup slot (review and respond-to-ci are mutually exclusive for a commit) and adds a per-PR fix-attempt cap (`respond-to-ci-attempts.ts`) so a fix that never makes CI green can't loop forever.
- **`resolve-conflicts`** — a side-car handler for merged pull requests. It lists open same-repository, SWARM-authored PRs targeting the advanced base, retries GitHub's asynchronous mergeability result with bounded coalesced jobs, and dispatches only confirmed conflicts. Redis dedup keys each attempt by PR/head/base state; the implementer phase merges the base normally and checks the remote head before pushing.
- **`pr-review-submitted`** — starts Respond-to-review on a `pull_request_review` `submitted` with `changes_requested`, authored by the *reviewer* persona (`getPersonaForLogin`). `pipeline.respondToReview.skipOnMinors: false` restores dispatch for approve/comment verdicts. Stops instead of dispatching on the safety cap's last permitted `changes_requested` verdict (see Pipeline phases §4).

A matched handler returns a `TriggerResult` naming the phase plus its resolved inputs; the worker's `processJob` (`src/worker/consumer.ts`) dispatches on that phase and calls the matching `runXPhase`, building the concrete GitHub Projects `PMProvider` (`src/integrations/pm/github-projects/provider.ts`) for the two board-driven phases. The review handler is guarded by a cross-process dedup claim (`src/triggers/review-dispatch-dedup.ts`, SWARM-62): a Redis `SET NX EX` keyed on `owner/repo:pr:headSha`, claimed before dispatch and left to expire by TTL (nothing releases it on failure in the MVP), so a PR that opens *and* then passes checks (or emits several check-suite successes) is reviewed once per commit rather than once per event. It fails closed — a claim it can't obtain (duplicate, or Redis down) skips the dispatch — and the respond-to-ci path shares that same slot before its own attempt cap runs.

`processJob` also self-enqueues the hand-off from Planning's `autoAdvance` to Implementation, rather than waiting on GitHub to echo that move back as a webhook (`selfEnqueueNextPhase`, `src/worker/consumer.ts`). The router's loop-prevention gate (`GitHubProjectsRouterAdapter.isSelfAuthored`) correctly drops *every* Projects status-change webhook authored by a SWARM persona — but Planning moves its own card to "ToDo" using the `implementer` persona, the very identity that gate checks against, so the direct webhook for that move is dropped every time by design. Left as webhook-only, the pipeline only ever advanced when some other, differently-attributed event for the same item happened to arrive later — unbounded, and observed live leaving an item in "ToDo" for hours with Implementation never dispatching. Instead, once a PM-driven phase's own move lands on a status that starts the next phase (`resolvePipelinePhaseForStatusKey`, `src/pm/pipeline.ts`), the worker enqueues a synthetic `github-projects` job for the same item directly onto the BullMQ queue (`enqueueJob`, no `deliveryId` — the same "synthetic/manual" carve-out `src/queue/producer.ts` already documents), which re-enters the normal trigger-match → authoritative-re-read → dedup path a real webhook would. Best-effort: a failure to self-enqueue is logged, not thrown, so it can't turn an already-succeeded phase into a failed job.

## Worktree lifecycle

Unchanged from `PROJECT.md` §4 — this part of the original spec is SWARM-specific and already correct:

- Main repo at `~/swarm/{project-name}/`, worktrees under `~/swarm/{project-name}/.swarm-workspaces/task-<id>/`.
- `git worktree add` per task; config/caches and the `cascade` sibling-checkout pointer (`.env`, root and nested package dependencies such as `node_modules` / `dashboard/node_modules`, `cascade`, build caches) grafted in via symlinks with **absolute** targets — a relative link would dangle at the worktree's `.swarm-workspaces/<name>/` depth (see `ai/RULES.md` §1).
- `git worktree remove --force` on completion.
- **Provision-time collision reclamation (issue #367).** When a phase provisions `task-<id>` and a checkout is already there, it runs the shared reclaim gate (`src/worktree/reclaim.ts`) before doing anything destructive. The gate applies one ordered, fail-closed safety check — a live worktree lease, a resumable deferred/failed run pinning the checkout, uncommitted changes, then unpushed local commits. Only a checkout that clears all four is *reclaimed*: the phase atomically holds the task lease across removing the stale checkout and re-provisioning a fresh one (releasing the lease on any failed provision), so two concurrent provisioners can't both remove it. A checkout protected by any check is left untouched and the run settles **terminally** as a `BlockedRecoveryError` — it is no longer treated as a transient `worktree-exists` deferral that retried against the same protected checkout forever — persisting `recovery.state = "blocked"` with the exact reason (`live-leased`, `resumable-owner`, `dirty`, `unpushed`) and posting an actionable message on the item/PR.
- **A lease is only honoured while it has a live owner (issue #427).** The lease key carries an opaque token, not an owner id, so a run that died — or completed — without releasing it left an orphan that wedged every later run for that task as `live-leased` until the 4h TTL expired, recoverable only by hand. The collision gate therefore checks *liveness in the database* before honouring a lease it could not claim (`src/worktree/lease-liveness.ts`): an owner is another `running` run (`hasLiveRunForTask` — the same query the reset path's `hasLiveOwner` resolver uses, so the two paths cannot drift), or another `leased`/`running` dispatch, for the same `(projectId, taskId)`. The asking attempt's own `runId` — threaded in through `ProvisionOptions.runId`, which `runAssignedPhase` passes to **every** phase and each phase forwards to `provision` — is excluded, since its run row is already `running` by the time it provisions, and a retry of a crashed run reuses that id so its own leftover lease reads as stale. With an owner, the run blocks as `live-leased` exactly as before. With none, the orphan lease is adopted by compare-and-set against the token actually observed (`takeOverWorktreeLease` — a provisioner that legitimately claimed it in between still wins) and the checkout behind it goes through the *same* ordered reclaim gate, so a dirty, unpushed, or resumable-pinned checkout is still retained and never force-removed. The token is read *before* liveness is evaluated, so a run that becomes the genuine owner after that check invalidates the compare-and-set instead of losing its checkout. Every uncertain outcome — no `runId`, a database or Redis error, a lost compare-and-set — reports "live" and blocks, so the fix only ever removes protection where the owner is provably gone. Liveness is deliberately not extended to `worker_sessions` heartbeats: a worker still writing after its run and dispatch have both been reaped as timed out has no database owner, and that window is accepted rather than closed because the reclaim gate behind this one still retains any dirty or unpushed checkout — only a provably clean, fully pushed one can be reclaimed there.
- Stale `task-<id>` worktrees left behind by interrupted runs are reclaimed by a retention sweep running periodically in the background of the worker process, or manually on-demand via `swarm worktrees prune`. The sweep preserves up to a configurable number of most-recently-active worktrees (defined by `worktreeRetention.maxWorktrees` in the project config, defaulting to 10), and runs the *same* reclaim gate on each prune candidate so it never removes a worktree that is leased (in-flight), pinned by a resumable deferred/failed run, has uncommitted changes (`git status`), or carries unpushed local commits.

## Harness (agent-CLI execution engine)

Once the worker has a provisioned worktree, it hands off to the harness (`src/harness/agent-cli.ts`, `runAgentCli`) to actually run the agent. The harness is deliberately narrow: it spawns `claude` or `antigravity` (Node's `child_process.spawn`, no subprocess library) with the worktree as CWD, streams stdout/stderr line-by-line (optional callbacks + `logger.debug`) while accumulating the full output, and resolves with `{ exitCode, signal, stdout, stderr, durationMs, timedOut }`. A non-zero exit is a normal outcome the caller inspects — only a spawn failure (e.g. the CLI isn't installed) throws. `timeoutMs` and an `AbortSignal` both kill the run (SIGTERM, escalating to SIGKILL). Prompt construction, persona/token selection, and the queue→worktree→harness→cleanup lifecycle live in the worker (SWARM-17), not here.

**Live output (issue #356).** Claude runs in print mode with `--output-format stream-json --verbose`, not `json`: the single-document format is buffered until the process exits, so a run's log stayed empty for its whole duration and got one event at termination. `src/harness/claude-stream.ts` decodes those NDJSON records incrementally into readable lines (assistant progress, `Tool started/completed/failed: <name>`, and a one-line rendering of a failed terminal `result` record) and forwards them through the same `onStdout` callback every CLI uses — tool inputs, tool results, and thinking are never rendered, and unparseable protocol lines are dropped rather than leaked. The terminal `result` record still supplies the run's final text, session id, and usage (`src/harness/usage.ts`), and its rendered error line is what failure classification reads, so a streamed 429 stays a deferred, resumable rate limit. The worker side (`src/worker/live-output.ts`) batches those lines into `run_output_events` every 100ms while the run is alive, flushes on every settle path, and — for Claude only — appends a "still running" heartbeat after 30s of silence so a working run is distinguishable from a hung one.

**Capability-aware target routing (issue #346).** A phase's agent config holds an *ordered* list of `targets` (`agents.<phase>.targets`, `src/config/schema.ts`). For an unfederated project, `selectTarget` (`src/worker/target-selection.ts`) walks that list against the local host's runnable-CLI discovery (`cli_quotas`); for a federated project, #339's gate walks the same policy across enrolled workers and binds the selected target to an authenticated worker execution claim. `agentOverrideFor` (`src/worker/consumer.ts`) feeds either selection's `cli`/`model`/`reasoning` into the unchanged four-tier model chain. A per-run pinned retry (`cliOverride`/`modelOverride`/`reasoningOverride`) bypasses fallback and is evaluated as one exact target.

**Model + reasoning mapping (issue #180).** The harness takes a *logical* `model` plus a normalized `reasoning` level and turns them into per-CLI launch args through `resolveModelLaunch` (`src/harness/models.ts`), the one place provider-specific reasoning semantics live: Claude gets `--model <alias> --effort <level>`, Codex gets `--model <id> -c model_reasoning_effort="<level>"`, and Antigravity — which has no reasoning flag — gets the reasoning folded back into the combined `agy models` variant string it passes to `--model` (e.g. logical `gemini-3.5-flash` + `high` → `"Gemini 3.5 Flash (High)"`). A pre-#180 config that stored the combined string directly is recognized and passed through verbatim, so it keeps launching that exact variant. Omitting reasoning preserves each CLI's own default (no flag for Claude/Codex; the model's default variant for Antigravity). `src/harness/models.ts` is the versioned capability catalog — logical models, their supported reasoning levels, and known defaults — cached in code, never discovered by invoking a model.

### Durable dispatch state machine (issue #284, ADR-002)

Every attempt to start or resume a pipeline phase is one row in the Postgres
`dispatches` table — the single source of truth for pending/in-flight
orchestration state (`docs/decisions/ADR-002-durable-dispatch-state-machine.md`).
BullMQ jobs are pure wake-ups carrying a `dispatchId`; the worker acts only
after atomically claiming the dispatch (`pending`/`retry-scheduled` → `leased`),
so a cancelled, completed, or superseded dispatch refuses every late delivery —
redelivery, delayed retry, slot release, or reconciliation. The lifecycle is
`pending → leased → running → completed/failed`, with `retry-scheduled` for
deferred attempts (the derived retry payload is persisted on the row *before*
any queue work, so a crash never loses retry intent) and `cancelled` for
user/operator cancellation. Wake-up job ids are deterministic per
(dispatch, wake sequence), so the reconciler's re-publish is a queue no-op when
the wake-up already exists. Project-capacity waits are `pending` dispatches with
wait reason `project-capacity`, woken by slot releases under the
continuation-priority policy — there is no separate Redis registry. A worker
startup + periodic reconciler (`src/dispatch/reconciler.ts`) reclaims expired
leases (failing the dispatch and its still-`running` run together), re-publishes
lost wake-ups, and — once, at startup — imports legacy shapes (Redis
pending-continuation entries, deferred runs with no active dispatch, and
pre-#292 `not-ready` merge-follow-up intent) as durable dispatches.
Merge automation is the one agent-less dispatch kind (issue #292): a
`merge-automation` payload (dedup key `merge:<reviewRunId>`, linked to the
approving Review run) skips triggers, worktrees, and project slots entirely —
`processJob` routes its claimed wake-up straight to
`processMergeAutomationDispatch`, which merges via the `ScmMergeProvider` and
settles the dispatch itself (`completed` with a `merge-*` outcome, `failed` on
a provider error, or `retry-scheduled` while transiently `not-ready`).

The dashboard deliberately exposes two complementary read models (issue #313):

- **Queue is dispatch-centric.** The Queue API/UI (`runs.queued`) reads every waiting
  dispatch from Postgres — state, wait reason, priority, and scheduled time — never a
  BullMQ snapshot. `swarm queue clear` cancels those canonical records first. A fresh
  dispatch with no `runId` is Queue-only because no persisted attempt exists yet.
- **Runs is run-centric.** The Runs list (`runs.list` / `listRunsFromDb`) reads persisted
  attempts by their normal lifecycle, but hides a `deferred` attempt linked to a pending
  or retry-scheduled dispatch to avoid displaying a duplicate row (issues #279/#316).
  Deferred attempts with no waiting dispatch remain visible in Runs as history and for operator recovery.

### Failure handling & rate-limit retries (issue #91)

A phase whose agent exits non-zero throws, and `processJob` turns that into a `phase-failed` `JobOutcome` rather than rethrowing — an agent run isn't idempotent, so a BullMQ retry storm is worse than surfacing the failure (the phase already logged the agent's stdout/stderr, and the `attempts: 3` default only ever fires for the infra throws that happen *before* the agent runs). The exceptions are transient failures: a **usage/session-limit** hit where the agent never did any work, an **aborted** run where the worker itself shuts down mid-phase, or a deterministic-delivery failure after the agent has already produced a valid checkpoint. Delivery deferrals preserve the worktree and expose the wrapped push/hook/API cause in the run rather than misreporting it as a worker shutdown.

`src/harness/agent-failure.ts` classifies a failed run (`classifyAgentFailure` → `rate-limit` | `capacity` | `timeout` | `aborted` | `stalled` | `error`). Harness timeout and abort take precedence; recognised quota/capacity banners then outrank a trailing response-stall marker, so a provider condition is never hidden by the generic terminal text. On a `rate-limit`, `capacity`, `aborted`, or genuinely-interrupted `timeout` error, `processJob` returns a `phase-deferred` outcome with a computed delay instead of `phase-failed`; the worker entrypoint (`src/worker/index.ts`) re-enqueues the job (delayed, fresh job id, `rateLimitRetryAttempt` bumped) via `enqueueDelayedRetry`, capped by retry budgets. The retry delay is floored above the review-dispatch-dedup TTL.

`capacity` is a transient **provider-capacity** signal, matched per CLI so one CLI's provider error isn't triggered by another merely quoting it: Codex's structured `error` / `turn.failed` events containing `selected model is at capacity` anywhere in captured output (or its textual terminal banner), and Claude/Claude Code's terminal `529 Overloaded` / `overloaded_error` banner (Anthropic's documented temporary-overload response — issue #229). It defers on a shorter capacity budget (`MAX_CAPACITY_RETRIES`, `MIN_RETRY_DELAY_MS` backoff) and retries **fresh, not resumed** — the provider rejected the request before the model did any work, so there is no partial reasoning or edit to continue. Only a bare status number never matches; human-readable provider banners use a conservative terminal-output window, so borrowed CI logs or reviewed code mentioning these numbers stay a plain `error`.

A retry **reuses the originating `runs` row** rather than inserting a second one (issues #136 and #146): the `phase-deferred` outcome carries the run's `runId`, the dispatch settle path (`settleDispatchRetry`, `src/worker/consumer.ts`) persists it in the derived retry payload on the dispatch record, and on the next claim `processJob` resets that same row to `running` (clearing `completedAt`/`error`/`nextRetryAt` and the outcome columns) instead of creating a new one. A fresh webhook that intentionally reruns a deferred or failed task/phase also claims and resets its latest terminal row, so automatic retries, manual retries, and user-triggered reruns all remain one logical dashboard run. A **manual "Retry now"** (the `runs.retryNow` tRPC mutation, offered for both `deferred` and `failed` runs) never flips the run row itself — the run turns `running` only when the worker actually claims the dispatch, so a failed enqueue can't strand a false `running` run (issue #284). It re-opens the run's active dispatch for an immediate attempt with `rateLimitRetryAttempt` reset to 0 (bypassing the automatic cap), folding any cli/model/reasoning overrides into the stored payload; a run with no active dispatch (terminally `failed`, or a legacy orphan) gets a fresh dispatch reconstructed from the row's persisted `jobPayload`. The conditional dispatch transition plus the one-active-dispatch-per-run unique index prevent concurrent automatic/manual retries from starting the same row twice. **"Reset & restart"** (the `runs.reset` mutation over `resetRun`, `src/dispatch/run-reset.ts`, issue #424) is the last-resort variant for a row "Retry now" cannot move: it additionally cancels the run's active dispatch, clears the Redis cancellation flag, tears down the checkout and its worktree lease (including a *stale* lease no live run owns), and clears the recovery record and captured session id before re-dispatching that same row from its stored `jobPayload` with a fresh agent session. Guards run before any mutation and the replacement dispatch is created last, so a partial reset leaves the run terminal-and-idle — the state a second reset retries from. `force` additionally permits resetting a `running` run, cancelling an already-claimed dispatch, and discarding dirty/unpushed work; it cannot stop an already-spawned agent process (only Terminate does). The dashboard surfaces it on the run-detail page beside "Retry now"/"Terminate" for a `failed` (incl. recovery-`blocked`) or `deferred` run (issue #428): a confirmation modal names each step, carries the default-off "discard uncommitted / unpushed work" opt-in that maps to `force`, and renders the mutation's per-step report — dispatch outcome, checkout removed/retained (+ reason), new dispatch id — so an operator can tell a reset that freed the checkout from one that restarted the run but kept protected work. `swarm run reset <runId> [--force]` (`src/cli/commands/run.ts`, issue #429) is the second surface over the same service, printing that same per-step report and exiting non-zero with the refusal message: like `swarm queue clear` / `swarm worktrees prune` it goes straight to Postgres + Redis, so a wedged run can be freed with the worker — and the API serving the dashboard — stopped.

PM retry dispatch intent is separate from Implementation branch reuse. Manual and automatic retries
carry `resumePmPhase` so an item already reporting "In progress" still re-enters its original phase,
while `implementationBranchProvisioned` is persisted only after successful task-worktree acquisition.
The retry uses the existing branch only when that explicit checkpoint is present; a run row by itself
never proves that provisioning happened.

### User-initiated termination (issue #166)

A **running** or **deferred** run can be terminated from the dashboard (the `runs.terminate` tRPC mutation). The API server and worker are separate processes, so termination never touches a PID: `terminate` records the intent in a durable, run-id-keyed Redis set and publishes a notification (`src/queue/cancellation.ts`). For a **running** run the worker aborts the agent via the per-run `AbortController` threaded into `runPhase` (the same SIGTERM→SIGKILL path shutdown uses), and settles the row as `failed` with a user-termination reason — `handlePhaseFailure` checks the cancellation set to tell a user termination apart from a worker-shutdown abort (which still defers). For a **deferred** run `terminate` atomically cancels the canonical dispatch record and flips the row `deferred → failed` together (`cancelDeferredRunInDb` — a cancelled dispatch refuses every future claim, so no retry, slot release, or reconciliation can resurrect the work; issue #284); if a concurrent automatic pickup wins that race, the transition loses, the run is now `running`, and the cancellation flag drives the worker to terminate it instead. Keying on the immutable run id (not the task id) means a later retry of the same task is never terminated by an old request, and `retryNow` clears the flag before re-running. The mutation is idempotent: an already-terminal run returns its settled state rather than erroring. Captured logs are preserved (the aborted agent's output is stored like any failed run); only the board "failed" comment is skipped, since an intentional stop isn't a stall to investigate.

**Worktree settlement when a termination settles (issue #361).** Once a terminated run has fully stopped, its checkout, worktree lease, and persisted recovery record are reconciled to one consistent outcome by `reconcileTerminatedWorktree` (`src/worktree/termination-cleanup.ts`), shared by both paths: the running-run path calls it from the worker's `finalizeFailedRun` after the agent exits (the phase deliberately *preserves* a cancelled run's worktree so this reconciler owns the decision), and the deferred path calls it from `runs.terminate` after the atomic `deferred → failed` claim succeeds (so it never touches a checkout while the run might still be active — a lost race leaves cleanup to the running-run path). An **explicit resumable session** is preserved (`recovery.state = "preserved"`): the checkout is kept and its live lease released, because the database recovery record — not a live lease — pins the checkout for retention (`hasResumableDeferredRun`) until a resume. With **no resumable session** a checkout is removed only once it is provably safe — not owned by a *different* live run, `isClean()`, and free of unpushed commits — and a session id never outlives the checkout it would have resumed. Otherwise the work is **retained** with a blocked reason (`dirty`, `unpushed`, or `live-leased`), recorded on the run without reopening the cancelled dispatch. It fails closed: any git-validation error surfaces as a blocked reason rather than a forced removal. A later fresh run may still encounter an older clean collision; automatic collision-time reclamation is a follow-up phase. A third caller, **"Reset & restart"** (`resetRun`, `src/dispatch/run-reset.ts`, issue #424), is the only one that passes the settlement's opt-in options: it supplies a `hasLiveOwner` resolver (`hasLiveRunForTask`, shared with the provision-time liveness check above — which additionally weighs executing dispatches, a stricter bar suited to an automatic gate than to a deliberate operator override), so a lease **no live run owns** is recognised as a stale marker and reclaimed instead of being reported `live-leased` forever, and — only when the operator forces the reset — `discardProtectedWork`, which discards a dirty/unpushed checkout with a loud warning and reports what was thrown away. Both are opt-in: without them (and without `force`) the settlement fails closed exactly as above, and a checkout a *different* live run genuinely holds stays `live-leased` even under `force`.

On a **terminal** `phase-failed` (such as `error`, `timeout`, or `stalled`), `processJob` also posts a failure comment on the backing Issue for the work-item-carrying phases (planning/implementation) via `reportPhaseFailureToBoard` → `pm.addComment`, so a human watching the board sees *why* the item stalled. For a recognised response stall, `src/worker/failure-diagnosis.ts` labels the task **likely scope exceeded** only when the captured run shows at least ten minutes and 1,000 non-terminal output bytes *and* the latest successful Planning artifact declares multiple independent concerns; missing metadata or a lookup error falls back to **provider stalled early**, and a harness timeout alone never claims task size. Quota/rate-limit, capacity, launch/authentication, worker-shutdown, and user-termination conditions take precedence. The serialised diagnosis is persisted beside the raw error and rendered on both the board and run detail; the comment is best-effort and skipped for intentional user termination.

## Single-user scope

No per-org config and no multi-tenant Firestore layer. One Postgres row per SWARM project, one set of GitHub credentials (per persona) per project. The API server is loopback-only (`127.0.0.1`) and, as of #281 task 2, gated by per-user session auth (below) rather than a shared secret; as of #281 task 4 each request is then scoped to the caller's project membership (below), so an authenticated user no longer sees every project. As of #281 task 5 a project may *opt in* to a `discoverable` visibility that layers a limited public-discovery view and a request/approve join flow on top of that strict members-only default (below), without wiring any execution/routing permission to visibility. Revisit the per-project credential model as remaining ADR-001 work (worker registration/routing) lands.

**Multi-user foundation (ADR-001, issue #281) — in progress.** The identity domain landed first: a `SwarmUser` Zod schema (`src/identity/schema.ts`), a `users` table (`src/db/schema/users.ts`), a provider-neutral identity read-model service (`src/identity/service.ts`), the installation-level `instanceAdmin` flag, and a `swarm users` operator CLI. A SWARM user is a person who signs in to this installation — **not** an SCM identity and **not** an implementer/reviewer GitHub credential.

**Session auth (task 2) is now live.** The shared `DASHBOARD_TOKEN` bearer guard is gone: a user gets a password via `swarm users set-password` (stored as a `scrypt` salt+hash in `users.password_hash`, never plaintext), signs in at `/login`, and receives an opaque session token — stored only as a SHA-256 in `user_sessions`, delivered as an HTTP-only, `SameSite=Strict` cookie (`Secure` off localhost), never in a response body or log. The tRPC context (`src/api/trpc.ts`) resolves the caller from that cookie (`src/identity/auth.ts` `resolveSession`); every procedure except `ping` is an `authedProcedure` that 401s without a session, and logout revokes it. Because every request now carries a cookie via `credentials: 'include'`, the API server fronts all routes with a credentialed CORS layer (`src/lib/cors.ts`, `CORS_ORIGIN`, default `http://localhost:5173`) so the documented separate-origin dev setup (SPA on Vite, API on `API_PORT`) can send it — inert for the recommended same-origin deploy, which never pre-flights.

**Local single-user mode (issues #298 & #373).** For a single-operator local install, `SWARM_SINGLE_USER_MODE=true` (`src/lib/env.ts`; disabled-by-default, only the literal `true` enables it, and set in `.env.docker.example`) swaps the cookie requirement for a zero-setup identity: `createApiApp` resolves the mode once per instance and, in `createContext`, lazily bootstraps and caches a passwordless reserved `localhost-admin` `instanceAdmin` (`ensureLocalAdminUser`, an atomic idempotent upsert on the existing `users.identifier` unique constraint — no schema, no migration) and supplies it as `ctx.user` even with no `swarm_session` cookie, so a project-scoped procedure runs against a real installation admin exactly as if signed in. The `resolveSession` path, `/auth/login`, `/auth/logout`, and session minting are untouched and remain in force whenever the flag is disabled; the single-user path never mints or reads a session. The dashboard `/login` route consults `auth.me` and, when an identity already resolves, redirects into the app rather than showing the form — so a direct visit to `/login` is skipped in single-user mode without any browser-visible mode flag.

The same flag also governs **dispatch (Phase 2/2, issue #373)**: the host process is the implicit local executor for *every* project. `gateDispatch` (`src/worker/consumer.ts`) short-circuits to its `undefined` no-selection result — the same one an unfederated project yields — *before* reading the roster (`listProjectDispatchCandidates`) or constructing the assignee provider, so `processJob` reuses the existing local path (`acquireProjectSlot`, capability-aware local target selection, a null worker identity) and never touches enrollment, sharing consent, assignee affinity, live sessions, worker fencing, or worker capacity even when worker/enrollment rows exist. It creates no synthetic workers, `worker_sessions`, or `worker_project_enrollments` rows, mutates no consent, and rotates no credential — the federated eligibility, fencing, affinity, and capacity behavior are fully preserved and simply restored the moment the flag is disabled.

**Project membership (task 3, layer 2) is the read model — data only, not yet enforced.** It adds a `ProjectMembership` Zod schema and per-project role (`projectAdmin | member | contributor`, ordered by privilege) with `canAdministerProject`/`canWriteProject`/`canReadProject` predicates (`src/identity/membership.ts`), a `project_members` table (`src/db/schema/projectMembers.ts`, unique per `(project, user)`, cascade-deleting with either its project or its user), a repository (`src/db/repositories/projectMembersRepository.ts`), a provider-neutral membership read-model service (`src/identity/membership-service.ts`, whose `listAccessibleProjectIds` resolves an installation admin to *all* project ids and any other user to their membership set), and a `swarm members` operator CLI to seed membership before the dashboard UI exists. Membership is created directly (repository/CLI/admin) or, as of task 5 (below), via an approved open-project join request. It is the read model that **project-scoped authorization (task 4, now live — below)** and **open-project policy (task 5, now live — below)** build on.

**Project-scoped authorization (task 4, layer 2) is now enforced.** `src/api/authz.ts` turns the membership read model into the API's enforcement layer — the second of ADR-001's three authorization layers (installation role → project membership → worker enrollment). Every project-keyed tRPC procedure (`routers/projects.ts`, `routers/runs.ts`, nested `routers/credentials.ts`) calls `assertProjectAccess(user, projectId, minRole)` or scopes a cross-project list through `filterAccessibleProjects` / `accessibleProjectScope`. An `instanceAdmin` bypasses every check (layer 1 override); a user with no membership cannot even learn a project exists (reads and mutations alike surface `NOT_FOUND`, never `FORBIDDEN`, so real project ids never leak); a member below the required role gets `FORBIDDEN`. The role → capability matrix, defined once in `authz.ts` and mapped from the `canReadProject`/`canWriteProject`/`canAdministerProject` predicates:

| Capability | Min role | Procedures |
| --- | --- | --- |
| Read a project, its runs, its (masked) credentials | `contributor` | `projects.getById`/`list`, `runs.list`/`queued`/`getById`/`getLogs`/`getOutput`, `credentials.list` |
| Drive a project's runs | `member` | `runs.retryNow`/`terminate`/`putBack` |
| Administer config, credentials, or delete the project | `projectAdmin` | `projects.update`/`delete`, `credentials.set`/`delete` |

Creating a project (`projects.create`) is open to any authenticated user, and the creator is written a `projectAdmin` membership row in the same call, so they can administer what they just made without an operator seeding membership first. Host-level procedures that are not keyed to a project (`ping`, `auth.me`, `settings.*`, `scm.verifyGithubToken`, `quota.*`) stay `authedProcedure` only — installation-admin gating of global settings is a separate, later concern, not project-scoped authorization.

**Open-project policy + join/request flow (task 5) — the final foundation slice.** Task 4's default is strictly members-only; task 5 adds an *opt-in* public face without loosening it. It keeps four permissions deliberately separate — **discovery ≠ joining ≠ worker registration ≠ task routing** — so public visibility never equates to execution permission (ADR-001 access model). A per-project `visibility` policy (`src/config/schema.ts` `ProjectVisibilitySchema`: `private` default | `discoverable`, a `text` column on `projects`) drives it:

- **Discover** — `projects.listDiscoverable` (any authenticated user) returns a **limited** read of `discoverable` projects the caller cannot already access: `id` + `name` only, projected in the query itself (`listDiscoverableProjectsFromDb`) so credentials/config/repo/run internals never even leave the DB. It excludes the caller's own projects; an `instanceAdmin` (who already sees everything) gets nothing new.
- **Join / request** — `projects.requestMembership(projectId)` files a **pending** membership request (`project_membership_requests` table, mirroring `project_members` with a `pending|approved|rejected` status and a *partial* unique index allowing one pending request per `(project, user)`). This resolves ADR-001 open question #1 in favour of **request/approve over immediate membership**: joining an open project grants no access on its own. A private/unknown project is `NOT_FOUND` (existence never leaks); an existing member or pending request is `CONFLICT`.
- **Approve / reject** — `projects.listMembershipRequests`/`approveMembershipRequest`/`rejectMembershipRequest` reuse `assertProjectAccess(user, projectId, 'projectAdmin')`, so only a `projectAdmin`/`instanceAdmin` acts on requests (a non-member gets `NOT_FOUND`, a lower-role member `FORBIDDEN`). Approval creates a `contributor` (**read-only**) `project_members` row atomically with resolving the request, and is idempotent w.r.t. an existing higher role.

Critically, visibility and membership remain separate from worker registration (#132) and task routing (#130): public visibility never grants execution permission. The highest role joining ever yields is `contributor`, which grants read and nothing more.

**Registered worker identity (#132 Phase 1).** Where a `SwarmUser` is *who* a person is and a `ProjectMembership` is *what* they may do on a project, a **worker** is *where* a user can execute — a locally operated execution environment they own (ADR-001's third identity layer). It adds a `Worker` Zod schema (owner user id, a safe machine `displayName`, and declared CLI `capabilities` reusing `AgentCliSchema` — `claude | antigravity | codex`; `src/identity/worker.ts`), a `workers` table (`src/db/schema/workers.ts`, FK to `users` `ON DELETE CASCADE`, unique per `(owner, displayName)`, unique credential hash), a repository (`src/db/repositories/workersRepository.ts`), a provider-neutral `worker-service` (`src/identity/worker-service.ts` — credential issue/hash primitives, `registerWorker` returning the raw credential **once**, `refreshWorkerCapabilities`, and the `resolveWorkerByCredential` auth seam), and a `swarm workers` operator CLI. The **worker credential** is distinct from an SCM PAT, stored only as a SHA-256, and returned raw once; a federated host supplies that raw value as `SWARM_WORKER_CREDENTIAL` so #339 can bind execution to its authenticated worker identity.

**Worker session leases (#336 Phase 2) — one live claim per worker, fenced.** On top of Phase 1's identity, a **worker session** is the single live claim on a registered worker's execution environment, so two daemons can never drive the same machine at once. It adds a `WorkerSession` Zod schema (`src/identity/worker-session.ts` — a per-worker monotonic **fencing token**, `lastHeartbeatAt`, a nullable `currentRunId`), `worker_sessions`, its atomic acquire/heartbeat/release repository, and the provider-neutral `worker-session-service`. A session expires after `SWARM_WORKER_HEARTBEAT_TTL_MS` (default 60s); re-acquisition bumps the fencing token and stale holders cannot heartbeat or attach work. The host worker now acquires and refreshes this lease from `SWARM_WORKER_CREDENTIAL`, and #339 atomically locks the session row to validate its id/token and reserve dispatch capacity before execution.

**Worker-project enrollment, sharing consent, and rosters (#337 Phase 3) — the routability seam + read models.** An enrollment links a worker to a project with `pending|active|suspended` status, allowed CLIs, an optional per-worker `concurrencyAllocation` (nullable; `null` = no per-worker sub-limit), and owner-controlled sharing consent. The provider-neutral service owns those writes and secret-free roster/owner views. Busy/capacity is derived from the worker's live session plus unexpired selected-worker claims on durable dispatches (with the older `currentRunId` pointer as a compatibility fallback), never client-supplied. `isRoutable(e) = e.status === 'active' && e.sharingConsent` is consumed by #339; revocation blocks future claims but never terminates running work.

**Worker connectivity roster (#133) — the dashboard's read-only aggregate.** On top of the same foundations, `listDashboardWorkers(projectScope)` (`src/identity/worker-enrollment-service.ts`) composes the one cross-project view the dashboard's **Workers** screen renders: machine display name, owner identity, declared CLI capabilities, `online`/`offline`, a nullable `lastSeenAt`, the run it is executing, and per-project enrollment/approval summaries. It adds no schema and no second liveness rule — `online` is `getLiveSessionForWorker` (so `SWARM_WORKER_HEARTBEAT_TTL_MS` stays the single TTL), and `lastSeenAt` comes from a new *retained*-session read (`getRetainedSession` → `getRetainedSessionForWorker`) that deliberately ignores liveness so an expired or gracefully released worker keeps its last heartbeat; a worker that never connected reports `null`. **Authorization is the caller's `accessibleProjectScope` verbatim**: `null` (an `instanceAdmin`) sees every registered worker including un-enrolled machines, and any other viewer sees only workers enrolled in their membership projects, with inaccessible enrollments stripped from the row. The current-run id is validated against run lifecycle exactly as `deriveWorkerRunState` does *and* filtered by project, so an in-flight run in an inaccessible project never leaks through a worker the viewer shares another project with. The tRPC `workers.list` query (`src/api/routers/workers.ts`) exposes it read-only, serializing `lastSeenAt` to ISO at the boundary; no machine path, credential, token, allowed-CLI constraint, consent/approval control, or routing affordance is on this surface.

**Assignee resolution + identity linking (#130 Phase 1) — the affinity lookup.** ADR-001's routing rules make assignment an *execution-affinity* rule: a work item assigned to a PM identity that maps to a SWARM user may run only on that user's eligible worker. **(1) A provider-neutral read of who an item is assigned to**: `WorkItemAssignee` + `WorkItem.assignees` + the `PMProvider.supportsAssignees` capability flag (`src/pm/types.ts`), populated by the GitHub Projects adapter from the backing Issue/PR (see "PM: GitHub Projects" above). Because `trigger.workItem` is already built from an authoritative `pm.getWorkItem()` (`src/triggers/handlers/pm-status.ts`), assignees flow to the trigger layer. **(2) A SWARM identity-linking seam**: a `UserIdentity` Zod schema (`src/identity/user-identity.ts` — a `(provider, handle)` pair owned by one `users` row), a `user_identities` table (`src/db/schema/userIdentities.ts`, FK to `users` `ON DELETE CASCADE`, **unique per `(provider, handle)`**), a repository (`src/db/repositories/userIdentitiesRepository.ts`), and the resolver `src/identity/assignee-resolver.ts` (`resolveUserForAssignee(assignee, provider)` / `resolveAssignedUser(workItem, provider)`), whose `provider` argument is the caller's `PMProvider.type` so the seam stays provider-agnostic. This answers ADR-001 open question 5 by construction: a handle maps to **at most one** SWARM user (the unique index), keys are normalized (trimmed + lowercased, so casing never splits a link), and an unlinked handle resolves to `undefined` rather than a guess. Links are seeded by an operator (`swarm identities link`) — automatic linking (OAuth / SCM account discovery) and a dashboard UI are deliberately out of scope. The worker eligibility gate consumes these links to enforce owner affinity before execution.

**Worker eligibility evaluation (#338, #130 Phase 2) — the pure half of the dispatch gate.** `evaluateWorkerEligibility` (`src/identity/worker-eligibility.ts`) folds ADR-001's routing prerequisites into one structured verdict: `{ eligible: true }` or `{ eligible: false, reason }`, where `IneligibilityReason` is `missing-enrollment` (no enrollment, or one not yet `active`) | `missing-consent` (consent never granted or revoked) | `worker-unavailable` (no live session, or — when the enrollment sets a `concurrencyAllocation` — that per-worker allocation fully used; a `null` allocation imposes no per-worker slot cap, leaving the worker bounded only by its `SWARM_WORKER_CONCURRENCY` and the project cap) | `missing-cli-capability`. Checks run in the ADR's order — active enrollment → sharing consent → connection/health → free capacity → declared CLI capability — and the **first** missing signal is returned, so a caller has one reason to show rather than a set; the first two checks are `isRoutable` split apart only so a revoked consent reads as `missing-consent`. It is **target-scoped, never target-choosing**: it judges exactly one candidate target from `agents.<phase>.targets` against that target's effective CLI (its own `cli`, else the phase's coded `DEFAULT_*_CLI` passed as `phaseDefaultCli`) and requires that CLI to be both a declared worker capability *and* allowed by the enrollment — it never reorders or falls back across targets, so Phase 3 can call it once per target and keep configured target priority across workers instead of collapsing back to a single model. The module is dependency-light and side-effect-free (like `src/pm/dependencies.ts`): the DB-backed signals arrive as a caller-resolved `WorkerAvailability` (`connected` from the fenced worker session, `activeRuns` from unexpired durable dispatch claims). The dispatch wiring, scheduler ordering, assignee affinity, and the scheduler-only `assignee-worker-unavailable` reason are Phase 3 (below).

**Federated dispatch gate (#339, #130 Phase 3) — the scheduler that consumes all three.** The gate (`src/worker/eligibility-gate.ts`) runs inside `processJob` **after** trigger resolution and **before** any worktree provisioning or agent invocation, on every phase and every (re)dispatch. When local single-user mode is enabled via `SWARM_SINGLE_USER_MODE=true`, this gate is completely bypassed; the worker routes the run directly to local execution using the host worker, skipping any registry, affinity, or eligibility checks. Otherwise, it reads the project's enrolled workers (`listProjectDispatchCandidates`, `src/identity/worker-enrollment-service.ts` — worker + enrollment + resolved availability in the deterministic **enrollment-creation order**, which is the documented "first free eligible worker" sequence), applies ADR-001's affinity rule, and judges each candidate with Phase 2's predicate. Selection is **target-priority-first, worker-order-second**: it walks `agents.<phase>.targets` in configured order and takes the first eligible worker for each, so a higher-priority Codex target wins whenever *some* enrolled worker can run Codex even if a Claude-only worker is free for a lower-priority Claude target — and it never silently falls back to `targets[0]`. A per-run "Retry now" override still pins exactly one target, which the gate evaluates rather than routes around; `src/worker/target-policy.ts` is the one place that reading of the policy lives, so the gate, local capability routing (#346), run creation, retry reset, and the phase invocation all agree on the chosen target.

Routing outcomes:

- **Unassigned item** (no assignees, or none linked to a SWARM user — ADR-001 open question 5) → the first free eligible project worker in that deterministic order.
- **Assigned item** whose assignee resolves to a SWARM user → *only* a worker owned by that user. There is **no cross-user fallback**: the work waits.
- **Nothing eligible** → a structured refusal, never a silent drop. `DispatchIneligibilityReason` is Phase 2's four reasons plus the scheduler-only `assignee-worker-unavailable`; the gate throws `WorkerIneligibleError`, and `handlePhaseFailure` treats it exactly like a dependency block — a **token-free** deferral (nothing was provisioned, no model spend) on the dependency gate's cadence with its own `workerEligibilityRecheckAttempt` budget and the dispatch wait reason `worker-eligibility`, settling `failed` with an actionable board comment (grant sharing consent, approve the enrollment, enroll a worker that can run the configured CLI) only once that budget is exhausted.

Because the gate sits on the common dispatch path it re-checks **before retries and later phases**: a consent revocation, enrollment suspension, health loss, or capability removal between attempts blocks the *next* dispatch, while a run already in flight is untouched. A selection becomes executable only when the dequeuing process authenticates as that exact worker and `claimWorkerForDispatch` locks its live fenced session, re-validates enrollment/consent/CLI, counts active unexpired claims, and persists the worker/session/fencing token on the dispatch (and worker/token on the run). A different host defers; simultaneous claims serialize on the session row and, when the enrollment sets one, cannot exceed its `concurrencyAllocation` (a `null` allocation adds no per-worker cap — the project's `maxConcurrentJobs` and the worker's `SWARM_WORKER_CONCURRENCY` still bound it); retries clear the claim, while terminal/expired dispatch states cease consuming capacity. A project with no enrollments remains unfederated and runs locally as before.

**Control-plane dispatch (ADR-003 §2, issue #407).** `SWARM_DISPATCH_MODE=transport` relocates the BullMQ consumer + this gate off the host worker and onto the **router** (`src/router/dispatcher.ts`), turning federation into true split delivery: the control plane decides *and* the worker executes on a different process (today, the same host; tomorrow, a remote one). It reuses `processJob` verbatim — the whole claim → trigger → automation gate → eligibility gate → `bindSelectedWorker` → run-row → durable settle → self-enqueue → merge-automation machine is shared. `processJob` takes a small `ProcessJobDeps` seam (`src/worker/consumer.ts`) whose defaults reproduce the in-process behavior; the transport path injects just three things: a **connectivity predicate** folded into the gate so only workers holding a live `/worker/stream` socket here are selectable (`isWorkerConnected`, `src/router/worker-connections.ts` — a DB-live-but-not-connected worker is skipped as `worker-unavailable`, so an assignee's offline worker still waits rather than routing elsewhere); a **bind identity** resolved from the *selected* worker's live session (the control plane claims the fenced slot on its behalf); and an **executePhase** that, instead of running the phase in-process, composes the system prompt + target branch server-side (`src/router/assignment-composition.ts`, reusing the pure `src/pipeline/prompts/*` builders), builds a `TaskAssignment` carrying the **non-secret** project-config slice (never a persona token — `src/transport/assignment.ts`), pushes it to the worker, and awaits the worker's `TaskExecutionResult` (correlated by `dispatchId` through `src/router/dispatch-results.ts`) to adapt back into the shared settle path. That adaptation rebuilds the classified failure a reported deferral stands for — `DeliveryDeferredError`, an `AgentRunError` carrying the reported kind, or, for a `dependency` frame, a `DependencyBlockedError` reconstructed from the blockers the worker reported (issue #438) — so each one lands on the same budget an in-process failure would. With no eligible/connected worker the dispatch stays durably `pending` via the same `WorkerIneligibleError` token-free deferral. The host worker, in the same mode, runs the transport-dispatch client (`src/worker/transport-client.ts`) instead of the BullMQ consumer, so the queue is consumed by exactly one side. A worker that drops before reporting is reclaimed by the dispatch-lease reconciler — no new mechanism. The **DB-less remote worker** this once listed as out of scope has since landed (issues #394, #417, #418 — see "Worker connection modes" above): it resolves no persona token and opens no database, running source delivery under the operator's own token and routing the credentialed metadata reads/writes, the review-verdict ledger, and the follow-up-Review enqueue through the delivery API. Still out of scope: over-the-wire secret delivery (unnecessary — the split keeps each project credential server-side instead), and the one phase the DB-free gate still refuses, `planning`.
