# Swarm — Agent Rules

System prompt and working conventions for AI agents in this repository — the **single source of truth**. Read this in full before writing code. `CLAUDE.md` at the repo root simply points here.

---

## 1. What this project is

**SWARM** is a Local-First, Federated Multi-Agent Framework that automates software engineering workflows: a stateless cloud orchestrator (webhooks, PM-board routing, gRPC control plane) paired with a local daemon (`swarm-cli`) that runs `claude` / `antigravity` CLIs inside isolated Git worktrees on the developer's own machine. Source code never crosses the network — the cloud only ever sees issue metadata, comments, and logs.

**Read `README.md` in full before writing code.** It is the short orientation and quick-start guide; detailed operations, configuration, pipeline, and status references are linked from it under `docs/`. `PROJECT.md` at the repo root is the original design document, **frozen as a historical baseline** (see its own header) — consult it for original design intent, never as the authority on current behavior. (Its `swarm-cloud/` and `swarm-cli/` layout was never built; the code lives under `src/` and `dashboard/`.)

**Keep `README.md` current.** If a change makes anything in `README.md` inaccurate — an architecture shift, a renamed component, a pipeline phase that changed, a status/roadmap item that moved — update `README.md` in the same change. Do not let it drift from the code; a stale README is worse than no README.

**SWARM is based on Cascade.** SWARM's task modelling, webhook ingestion, and CLI-runner patterns take structural inspiration from Cascade's implementation — consult it for architectural precedent whenever a pattern here is underspecified. Resolve it in this order:

1. `cascade` at the repo root — a symlink to the sibling checkout. This is the expected setup; if it's missing, create it with an **absolute** target: `ln -sfn "$(cd ../cascade && pwd -P)" cascade`. (Use an absolute target, not a relative `../cascade`: git worktrees under `.swarm-workspaces/<name>/` check out the same committed symlink two levels deeper, where a relative `../cascade` dangles. The per-worktree `node_modules` symlink is grafted at runtime with an absolute target for the same reason.)
2. If not symlinked, look for a sibling checkout directly at `../cascade`.
3. If neither exists locally, it's the open-source project at <https://github.com/mongrel-intelligence/cascade> — clone it or read it there.

### Project-management features must stay provider-agnostic

SWARM's *implemented* PM providers are **GitHub Projects**, **Linear** (`src/integrations/pm/linear/`, the six phases of #491, registered by #530 — see ai/ARCHITECTURE.md "PM: Linear"), **Jira** (`src/integrations/pm/jira/`, the six phases of #490, registered by #580 — see ai/ARCHITECTURE.md "PM: Jira"), and **Trello** (`src/integrations/pm/trello/`, the six phases of #492, registered by #588 — see ai/ARCHITECTURE.md "PM: Trello"). That is every value `PMType` / `PmProviderIdSchema` name (issue #297, widened exactly as `ScmType` named `bitbucket`/`gitlab` before either registered), so all four now resolve to a registered provider — but that is a fact about today's providers, not a licence to program against them. **Every feature that touches the project board must be built behind the provider-agnostic contract — `PMProvider` (`src/pm/types.ts`) outbound, `PMRouterAdapter` (`src/pm/router-adapter.ts`) inbound — never against GitHub Projects directly**, so a new connector drops in by implementing those interfaces alone — no pipeline, trigger, or phase code changes.

**What a second provider actually owes** (settled across issue #297's six phases, #495–#499, and widened since by #543, #639 and #686): fifteen `PMProvider` methods — `getWorkItem`, `listWorkItems`, `findWorkItemByUrlSuffix`, `findWorkItemForArtifact`, `findWorkItemByDescriptionMarker`, `moveWorkItem`, `addComment`, `findComment`, `createWorkItem`, `updateWorkItem`, `addLabel`, `listBlockers`, `listDependents`, `addBlockedBy`, `resolveItemRepository` — plus the two capability flags a provider without the concept opts out with (`supportsAssignees`, `supportsDependencies`) and the one *optional* method, `discover`, which is declared per provider on the manifest rather than required of everyone. Inbound is five `PMRouterAdapter` methods: `parseWebhook`, `resolveProject`, `isStatusChange`, `isSelfAuthored`, `synthesizeStateChange`. Both halves plus the manifest's own metadata are asserted for every *registered* manifest by `tests/unit/integrations/pm/pm-conformance.test.ts`, which also fails on a method whose source still carries a not-implemented sentinel — so, exactly as on the SCM side, a provider under construction registers **nothing** until no method is a stub (`ai/TESTING.md` "Provider conformance"). Linear is the provider that took that route: phases 1–4 of #491 built the whole contract with no manifest, and #530 registered it together with a fixture in that suite and **no exemption**. Jira took exactly the same route — phases 1–4 of #490 built both halves with nothing registered, and #580 landed `jira/index.ts` with its own fixture and, again, no exemption. So did Trello: phases 1–4 of #492 built both halves with nothing registered, and #588 landed `trello/index.ts` with its own fixture and no exemption — including for `supportsDependencies: false`, which is a *declared opt-out* the suite already accepts (it asserts the flag is a boolean and that `listBlockers`/`listDependents`/`addBlockedBy` carry no sentinel), not a stub needing one.

Concretely:

- **Program against the contract, not the concrete provider.** Pipeline phases, triggers, and the worker take a `PMProvider` (or have one injected — `ctx.pm` on a PM trigger context) and call only its interface methods. They must not import `createGitHubProjectsProvider` or reach into `src/integrations/pm/github-projects/`: since issue #297 every project-scoped call site resolves through `requireProjectPMProvider(project)` / `requireProjectPMAdapter(project)` (`src/integrations/pm/registry.ts`, re-exported from the `src/integrations/pm/index.ts` barrel), and no pipeline, worker, or router module constructs a provider.
  - Those two lookups are a **plain registry lookup on `project.pm.type`**, with none of the SCM side's `runtimeReady` flag: `project.pm.type` is the config discriminator, and a PM provider carries traffic the day it registers. The SCM side now selects the same way (`project.scm`, issue #478) but keeps the extra `runtimeReady` gate, because an SCM provider also needs a served ingress route before it can be chosen. Don't copy that gate here — and don't add its "exactly one runtime-ready provider" conformance assertion either.
- **A provider declares its own wiring on the manifest, as data.** `PMProviderManifest` (`src/integrations/pm/manifest.ts`) carries everything shared code needs to serve a provider without naming it: `createProvider(project)` (a *per-project* factory, unlike an SCM manifest's shared instance), `configSchema` — the provider's own board mapping, which is also its member of the `project.pm` discriminated union (`ProjectPmSchema`, issue #495), narrowed back to a concrete shape only by the provider itself; `routerAdapter`; `credentialRoles` — the `{ role, label, description?, envVarKey, optional?, inheritsSharedCredential? }` list a project supplies one *reference* per under `credentials.pm[<providerId>]` (one block **per provider id** since issue #631, the PM twin of #628's SCM move — the role names collide outright across the four registered providers, so a flat map let an incoming provider's credentials overwrite the outgoing provider's; resolution reads only the block for `project.pm.type`, never another provider's, so a retained block is stored and never read), resolved through `resolvePmCredential(project, role)` and validated against the registered manifests (issue #497), so a provider's credentials never get baked into the central config schema. (`inheritsSharedCredential` resolves the repo side's **per-provider** secret for the SCM provider the project runs on since issue #628, not a single shared reference.) **A PM provider authenticates with a credential it declares here — never with an SCM identity, and in particular never with the worker-local operator token** (`SWARM_OPERATOR_GH_TOKEN`, a source-control credential belonging to one machine): issue #537 moved GitHub Projects onto its own required `apiToken` role for every board read, write, and discovery call, so board access is a property of the *project* rather than of whichever host runs the code, and the dashboard's Project Management tab renders whatever roles a provider declares (each role's `label`/`description` is the provider's copy, which is why the UI names no provider); `webhookRoute` + `verifyWebhookSignature` — the receiver mounts one route per registered manifest and authenticates with the manifest's own verifier (issue #496), whose input (`PmWebhookVerification`: raw body, a header reader, `secret: string | null`, SWARM's own callback URL) is deliberately wider than the SCM triple so no planned provider forces it to change; `discovery` — the capabilities `PMProvider.discover` answers for the board-mapping screen, dispatched through the manifest so an undeclared one fails with a clear `NOT_IMPLEMENTED` instead of a raw call; and `blankPm` + the optional `blankPmDiscoveryBlocker` — that provider's own `project.pm` member with **no board selected**, plus the operator-facing reason it cannot be discovered against when it cannot (issue #641). The blank member exists because the credential and discovery APIs serve a provider a project is *not* persisted on, so a switch can be entered before it is saved: discovery runs against `{ ...project, pm: manifest.blankPm }`, which is only provider-agnostic because the member is *data on the manifest* — assembling it at the call site would be a `pm.type` branch in shared code. Jira is the one provider declaring the blocker (its `baseUrl` is the origin every REST call is addressed to *and* board identity in `swarm.config.json`), and the API returns that copy verbatim as a `PRECONDITION_FAILED` rather than failing on an opaque fetch. **Since issue #642 the switch is actually made there, not in `swarm.config.json`**: the Project Management tab holds it as a client-side draft that walks an explicit order (select provider → its declared credentials → discover containers/states → map the six canonical status keys → Save) and persists the whole new `pm` union member in one `projects.update` write, with `projects.update` itself refusing a `pm.type` change to an unregistered provider or one whose required credential references are absent. So a fifth provider is reachable by the switch the day it registers, provided it declares `blankPm` — and it must not assume it is the provider a project *starts* on, nor that its own credentials were entered before some other provider's. A route an SCM manifest already owns is legal and expected — GitHub delivers `projects_v2_item` to the same `/github/webhook` URL, so the receiver co-tenants that PM manifest onto the SCM route rather than mounting a second, shadowed handler; a route nothing else owns gets its own GET ping + POST pair, which is how Linear's `/linear/webhook` is served (issue #530). Credential roles are where a second provider states its *differences* as data rather than as a special case: Linear declares `apiKey` + `webhookSecret` and inherits **neither**, because its board is a separate system from the GitHub repo, and its webhook role is required rather than optional since its verifier fails closed on an absent secret. Jira states the same differences plus its own (issue #580): three roles — `email` + `apiToken`, the two halves of Jira Cloud's basic auth, and `webhookSecret` — all required, none inherited, even though its `sha256=<hex>` signature framing coincides with GitHub's, because the *secret* does not. Trello states three too (issue #588): `apiKey` + `token`, the two halves of the key/token pair it authenticates with, and `webhookSecret` — again all required, none inherited. Its third role is also where the *role name* and the credential diverge on purpose: the credential is Trello's per-integration **API secret** (`TRELLO_API_SECRET`), while `webhookSecret` is the receiver's own vocabulary — the one role it resolves into `PmWebhookVerification.secret` — so naming the role after the credential would reach the verifier as `null`.
- **`taskId` stays SCM-derived — the board provider does not name the task** (issue #498). A task id names the worktree (`task-<id>`), the branch, and the PR opened from it: all SCM artifacts. Deriving it from a board key (a Jira `PROJ-123`, a Trello card id) would rename directories and branches without buying portability. What *is* the provider's job is the card↔artifact link: it fills `WorkItem.taskRef` from its own linkage on the way out of a board read, and answers `findWorkItemForArtifact` for the reverse. Shared code reads those, never a URL pattern (see ai/ARCHITECTURE.md "Task identity").
- **Speak canonical status keys, not board option IDs.** Pipeline/phase/trigger code uses the canonical `PmStatusKey`s (`backlog`, `planning`, `todo`, `inProgress`, `inReview`, `done` — `src/pm/pipeline.ts`); translating those to a provider's opaque option IDs (GitHub's `SingleSelectOptionId`, a Jira transition, a Trello list) is the adapter's job and stays inside the provider. That runs both ways: `WorkItem.statusKey` carries the canonical key the provider resolved from its native status on every board read, so shared code resolves a pipeline phase with `resolvePipelinePhaseForStatusKey(workItem.statusKey)` rather than inverting the board mapping's own `statusOptions` itself.
- **Keep provider-specific shapes out of shared code.** No GitHub-issue-URL parsing, `projects_v2` payload assumptions, or GraphQL node IDs leaking into pipeline/trigger logic. When a piece of data is provider-specific, resolve it through a `PMProvider` method or the work item's generic fields (`id`, `url`, `status`, `statusKey`, `taskRef`), not by pattern-matching a GitHub shape. (Example: `src/triggers/handlers/pm-status.ts` takes the worktree's task id straight off `WorkItem.taskRef` — the SCM artifact reference the *provider* resolved from its own linkage — instead of regexing an issue number out of a GitHub-shaped `url`; and `src/pipeline/respond-to-review.ts` resolves its board card from SWARM's own durable `runs.work_item_id` link, injected control-plane side. See ai/ARCHITECTURE.md "Task identity" for both seams and for the one deliberate GitHub-shaped fallback that remains.) Inbound is the same: the durable queue envelope is `{ type: 'pm', providerId, event }` carrying a normalized, provider-neutral `PmEvent` (`src/pm/events.ts`), so raw webhook event names, payload paths, and board field ids stop at the adapter.
- **Loop prevention is a per-provider obligation.** `PMRouterAdapter.isSelfAuthored` answers "did SWARM itself cause this board change?" using an identity the *PM provider* can establish on its own. A provider MUST NOT borrow another category's identity model — and since issue #537 none does: GitHub Projects used to reach into `GitHubSCMIntegration`'s persona helpers (legitimate only while board writes ran on the implementer persona's token), and now resolves the identity of its **own** declared board credential (`resolveGitHubProjectsIdentity`, `src/integrations/pm/github-projects/credentials.ts`) — the account its writes are actually made by. Linear does the same for itself (issue #530): `LinearRouterAdapter.isSelfAuthored` compares the delivery's actor id against the identity of the provider's own declared API key (`resolveLinearActorId`, `src/integrations/pm/linear/identity.ts`), never a GitHub persona. Jira, which has no shared identity to borrow either, keys on its own API-token account since issue #579: `JiraRouterAdapter.isSelfAuthored` compares the delivery's Atlassian `accountId` against the one its declared token resolves to (`resolveJiraAccountId`, `src/integrations/pm/jira/identity.ts`). Fail **open** (return `false` and log) on any identity-resolution failure — a swallowed error must never silently drop a real human status change.
- **If the interface is too small for a feature, widen the interface** (add a method to `PMProvider` and implement it for every provider), rather than special-casing GitHub Projects at the call site. Mirror Cascade's `src/pm/types.ts` when deciding the method shape. Widening it is a two-file change by design: the conformance suite's `PM_CONTRACT_METHODS` list fails to compile until the new method is added to it, which is what stops a method from being declared and then quietly stubbed everywhere.

The same "don't build it speculatively" rule (`ai/CODING_STANDARDS.md`) still applies — a fifth provider waits for its own issue — but nothing you build for one provider may *assume* it's the only one.

### Source-control features must not hard-code GitHub

Same story on the SCM side: **SWARM runs on three source-control providers — GitHub, Bitbucket Cloud (since issue #618), and gitlab.com (since issue #619) — with each project routing to the one it names.** The SCM side now has the same two-part shape as the PM side: a provider-neutral contract, **`SCMProvider` (`src/scm/types.ts`)**, which `GitHubSCMIntegration` (`src/integrations/scm/github/scm-integration.ts`) declares and satisfies, plus an SCM manifest/registry (`src/integrations/scm/{manifest,registry}.ts`) that each provider self-registers into from the single canonical entrypoint (`src/integrations/entrypoint.ts`). The contract composes the two seams that already existed — it extends `ScmMergeProvider` (`src/scm/merge.ts`) and returns `ScmDeliveryProvider` (`src/scm/delivery.ts`) — rather than duplicating them, and `ScmPersona`/`ScmPersonaIdentities` are the neutral names for the implementer/reviewer role model (`GitHubPersona`/`PersonaIdentities` remain as GitHub-local aliases).

**A complete provider carries no traffic until it is declared ready — and both of the later two now have been.** `BitbucketSCMIntegration` (`src/integrations/scm/bitbucket/`, issue #296 phase 4/4) and `GitLabSCMIntegration` (`src/integrations/scm/gitlab/`, issue #295 phase 4/4) each satisfy the **whole** `SCMProvider` contract: a credential-scoped client, persona credential resolution (implementer from a worker-local `SWARM_OPERATOR_BITBUCKET_TOKEN` / `SWARM_OPERATOR_GITLAB_TOKEN`, reviewer from **that provider's own** `credentials.scm.<id>.reviewer` reference since issue #628 — the shared provider-neutral pair GitHub used to lend them is gone), persona identity/loop-prevention helpers, webhook ingress, the pull-request/CI-status reads, and the writes: idempotent comments, review verdicts, the delivery seam (commit identity, PR find/create, expected-SHA push, review submission, idempotent comment), and the direct merge with its own outcome classification. Neither stubs a method, and the multi-provider conformance suite (`tests/unit/integrations/scm/scm-conformance.test.ts`) asserts that for every registered manifest.

**Issues #618 and #619 supplied the last of the wiring** — the step that had no owner once #457 and #485 closed. Each manifest declares `runtimeReady: true` (`src/integrations/scm/manifest.ts`), which is the single switch both readers consult: the project-scoped lookup routes a project that sets `"scm": "bitbucket"` / `"scm": "gitlab"` there, and the receiver mounts `/bitbucket/webhook` and `/gitlab/webhook` from the same loop that mounts GitHub's — no receiver edit for either. Two shared, provider-agnostic pieces landed with #618 and are not Bitbucket's alone: the contract gained `listPullRequestsForCommit` (a `commit_status` payload names no pull request and neither does a GitLab **branch** pipeline, so ingress completes a `checks` event through a *neutral* method rather than calling `listBitbucketPullRequestsForCommit` or its GitLab twin — the widening rule below in action), and the registry's "zero or two-plus runtime-ready" throw became reachable in production. **That last one is a migration, and it is deliberate:** a project naming no `scm` no longer resolves the sole runtime-ready provider, so every project must now state its provider (`"scm": "github"` for existing ones, then `swarm config apply`). It is not defaulted to `github`, because a default would silently route a Bitbucket or GitLab project's operations onto GitHub — the exact failure `requireProjectSCMProvider` exists to prevent. **What #619 decided rather than deferred again:** GitLab authenticates a delivery with the operator-chosen secret echoed in `X-Gitlab-Token`, so serving its route means accepting *sender* authentication where GitHub's and Bitbucket's HMAC also covers the body bytes. That is judged acceptable — it is GitLab's own long-standing mechanism, it fails closed and compares in constant time, and an attacker able to tamper with or replay a delivery has already broken the TLS the secret itself travels under. GitLab 19.0's Standard-Webhooks signing tokens stay a recorded follow-up, but only half of what blocked them does: they still need `verifyWebhookSignature` widened for headers it never sees, while the per-provider secret reference they also needed landed with issue #628 — `credentials.scm.gitlab.webhookSecret` is now GitLab's alone, no longer shared with the same project's PM webhook.

**Register when the contract is satisfied, not when the folder appears.** The two providers arrived at the same place by different routes, and GitLab's is the one to copy. Bitbucket registered a `runtimeReady: false` manifest from its own phase 1, so its intermediate phases had a registered manifest full of stubs. GitLab deliberately registered **nothing** through phases 1–3 and landed `gitlab/index.ts` in phase 4/4 together with the last stub's removal: the conformance suite asserts that no *registered* provider stubs a contract method, and `ai/TESTING.md` frames that assertion as the gate on the third provider, so registering early would have forced an exemption that disabled the gate for the providers already passing it. Until that final phase nothing resolved `gitlab` by id — the only shared-surface change was `ScmType` / `ScmProviderIdSchema` gaining the value — and every test constructed the class directly. Do that for the fourth provider too.

**Inbound runs on the contract; so does every project-scoped outbound call site — the DB-free worker's included.** The inbound path migrated with issue #385: the receiver mounts one route per registered manifest (`webhookRoute`) and delegates header interpretation, signature verification, event parsing, and comment loop prevention to `SCMProvider`; the durable queue envelope carries a provider id plus a normalized, provider-neutral event (`ScmEvent`, `src/scm/events.ts`); and the worker resolves the provider once at its composition root and injects it into `TriggerContext.scm`, so every SCM-driven trigger handler programs against the contract. The project-scoped **outbound** call sites migrated with issue #386 — the delivery-provider default in the five delivery-owning phases, the worker's `resolveScmDelivery` local delegate, its PR-title read and its phase-failure/interrupted-job PR comments, the durable merge executor's default merge capability, and the router's server-side `buildScmDelivery` default all resolve through the registry, so no pipeline, worker, or router module constructs a provider. The **DB-free federated worker** joined with issue #462, which was the last one left: the contract carries `operatorDeliveryProvider(repo, credential)` — the provider-neutral name for a delivery provider authenticated as the worker operator's *own* account rather than a per-project persona (ADR-003 §2 / ADR-004 §3) — GitHub implements it over the same `operator-delivery.ts` body, and `src/transport/assignment-execution.ts` resolves it through `requireProjectSCMProvider` with the remote-worker entry (`src/transport/connect-entry.ts`) importing the integrations entrypoint so the registry is populated. Operator-credential *env resolution* deliberately stays outside the contract (`SWARM_OPERATOR_GH_TOKEN` → `resolveOperatorGitHubToken`, `src/lib/env.ts`): the credential is the operator's, not the project's, so no project config names it. **Still concrete, deliberately:** the dashboard's credential-validation API route (`src/api/routers/scm.ts`), which validates a pasted secret before any project exists to resolve a provider from — one `verify…` procedure per provider (GitHub's, plus Bitbucket's since issue #618 and GitLab's since #619) rather than one generalised over the registry, because every `SCMProvider` identity method takes a `ProjectConfig` the caller does not yet have — and **one** remaining GitHub-SCM reach in the GitHub Projects PM provider — its webhook verifier delegating to the GitHub SCM provider's HMAC check (`src/integrations/pm/github-projects/webhook.ts`, issue #496 — board and repo are literally the same webhook, one URL and one secret; since issue #497 that shared *secret* is stated as data rather than borrowed at the call site: the manifest's `webhookSecret` role carries `inheritsSharedCredential: 'webhookSecret'`, so the receiver resolves a PM credential and still gets the project's existing SCM webhook secret). It was three until issue #537: the provider's `GitHubSCMIntegration` field for persona-credential scoping and its router adapter's persona/loop-prevention helpers are **gone**, replaced by the provider's own declared `apiToken` role (`src/integrations/pm/github-projects/credentials.ts`) and the identity of that credential. What is left is the PM provider's, not shared pipeline code, but it is still a PM provider wired to one specific SCM provider, so a second SCM provider has to unpick it. (Reusing the GitHub module's Octokit client — `withGitHubToken`/`getScopedClient` — is not one of these reaches: the board and the repo speak the same API, and the credential bound to that client is the PM provider's own.)

**An SCM provider declares its own credential references (issue #628).** `SCMProviderManifest.credentialRoles` names *that provider's* conventional key for each of the two credentials the contract itself names — `SCM_CREDENTIAL_ROLES` = `reviewer` + `webhookSecret` (`src/scm/types.ts`) — and a project supplies one reference per `(provider, role)` under `credentials.scm[<providerId>]` (`src/config/scm-credentials.ts`, `src/config/schema.ts`). It is the #497 PM precedent with a **closed** role set: a PM provider's roles genuinely differ per provider, an SCM provider's never do, so only the reference name is per provider. Three rules bind a fourth provider. First, **declare your own keys, and share none with another provider** — `GITHUB_TOKEN_REVIEWER` / `BITBUCKET_TOKEN_REVIEWER` / `GITLAB_TOKEN_REVIEWER` and their `*_WEBHOOK_SECRET` siblings; the conformance suite fails a manifest that reuses a key, because storing one provider's secret would then overwrite another's. Second, **resolve through `resolveScmCredentialOrNull` / `requireScmCredential` (`src/config/provider.ts`) with your own provider id**, never a shared pair and never another provider's block: retained credentials for a provider the project is not running on are stored but never read, and a missing credential for the provider asked for throws naming the project, provider, role, and your conventional key. Presence is enforced there rather than in the config schema (which validates structure only), because `project.scm` is switchable from the dashboard and "selected, not yet configured" is a state one click creates. Third, since issue #632 wired the API and the dashboard onto the same shape, **name your credentials in your own vocabulary and let the server resolve the key**: the Source Control tab edits `credentials.scm[<the selected provider>]` through `(providerId, role)`-addressed procedures, so a fourth provider adds its `roleLabels` and descriptions to `getScmProviderCopy` (`dashboard/src/lib/credentials.ts` — a hand-kept catalogue because a browser bundle cannot read the registry) rather than reusing another provider's ("Reviewer PAT" is GitHub's word for a Bitbucket app password), and anything that *displays* a key shows the `referenceKey` the role resolves through, never the manifest's conventional `envVarKey`. See "Per-provider SCM credentials" in `ai/ARCHITECTURE.md`.

Resolve a provider through one of the two registry lookups (`src/integrations/scm/registry.ts`), never by constructing one:

- **`requireSCMProvider(id)`** when something already names the provider — a durable job's `providerId`, written by this process's own ingress. That is the event-accurate lookup: the comment lands on the provider the event came from.
- **`requireProjectSCMProvider(project)`** for a project-scoped operation with no event in hand. Real selection since issue #478, keyed on the **`ProjectConfig.scm` discriminator** (`src/config/schema.ts`) — the SCM twin of `pm.type`, validated at the config boundary rather than pattern-matched here (a repo-URL match was the alternative and lost: `repo` is a bare `owner/repo` with no host, so nothing in it tells two providers apart). It resolves the manifest `project.scm` names, which must be registered **and** runtime-ready; when the project names none, the sole runtime-ready manifest — a back-compat path that **stopped resolving with issue #618**, since all three providers are now ready, so every project states its provider. **Everything else throws, loudly and specifically, naming the project and what it asked for** — an unregistered id, a registered-but-not-runtime-ready id, and "selects nothing while zero or two-plus are runtime-ready" are three distinct messages, and the last one tells the operator to set `scm` and is now the migration notice for an unmigrated installation. **Never a fallback**: resolving a project's operations onto a provider it did not name is the exact failure this lookup exists to prevent, so don't "fix" one of those throws by picking another manifest.

- **Keep GitHub specifics inside `src/integrations/scm/github/`.** GraphQL node IDs, raw webhook event names, `check_suite`/`pull_request_review` payload shapes, header names, the `sha256=` signature framing, `gh` CLI invocations, and GitHub REST/GraphQL calls live there — `webhook.ts` owns the ingress half — not in router, queue, pipeline, trigger, or worker code, which speak in domain terms and take the provider as a dependency.
- **Name SCM features by the domain concept, not the GitHub vocabulary.** Prefer provider-neutral names — "pull request" / "review" / "check run" / "comment" / "default branch" — over GitHub-only wording, in identifiers, config keys, and log messages. (GitLab calls a PR a "merge request"; a provider-neutral `pullRequest`/`changeRequest` name at the seam saves a later rename.) Provider-specific vocabulary (`check_suite`, `projects_v2`, a `gh` subcommand) is fine *inside* the GitHub module, not in the shared surface.
- **When you'd reach for a GitHub client in shared code, add a seam instead.** If a pipeline/trigger needs an SCM operation the current code exposes only as a raw GitHub call, widen `SCMProvider` with a provider-neutral method and implement it in the GitHub adapter (the same "widen the interface, don't special-case" move as the PM rule) — rather than importing the GitHub client at the call site. Keep provider-native shapes (Octokit types, GraphQL node IDs, webhook payloads, `sha256=` framing) out of the contract's public types.
- **New per-provider code goes under `src/integrations/scm/<provider>/`**, mirroring the existing `github/`, `bitbucket/`, and `gitlab/` folders and the `pm/<provider>/` layout, so the directory structure already anticipates the fourth provider.

Don't write GitHub assumptions into places another provider would then have to unpick — two other providers now actually exercise them. **A Bitbucket project runs end to end as of issue #618** and **a GitLab project as of issue #619**: each states its `scm`, its deliveries arrive on a served `/bitbucket/webhook` or `/gitlab/webhook`, and the same phases a GitHub project drives run against Bitbucket Cloud or gitlab.com. A fourth provider gets there the same way — the whole contract first, registered only once nothing is stubbed, then its own `runtimeReady: true` plus a served ingress route decided in one issue rather than smuggled in elsewhere. Neither of the two reachable providers is unlimited: Bitbucket reports no mergeability at all, and GitLab is gitlab**.com** only, with no subgroup paths (see their sections in `ai/ARCHITECTURE.md`).

## 6. Workflow expectations

- Verify before claiming done — run the relevant lints/type-checks/tests; if something couldn't be run, say so plainly.
- Small, reviewable changes over sweeping rewrites.
- When the SWARM protocol, architecture, or lifecycle is unclear, check **`ai/ARCHITECTURE.md` and `docs/decisions/` (the ADRs) first** — they describe what is actually built — then the matching `docs/*.md` reference. Do not guess message shapes, task types, or pipeline phases. Consult `PROJECT.md` only for *original design intent*: it is a frozen historical baseline (see its own header) and diverges from the implementation in places, so it is never the authority on current behavior.
- **Recovering a missed Respond-to-review dispatch:** do this only with explicit user authorization and only after verifying the exact submitted reviewer-persona review, PR branch, review ID, and reviewed head SHA. Prefer redelivering the original GitHub `pull_request_review` webhook (`submitted`) through GitHub. If the local `gh` token lacks the required `admin:repo_hook` scope, enqueue one synthetic `github` job carrying the same normalized event fields (`workItemId`, `actorLogin`, `prBranch`, `reviewState`, `reviewId`, and `headSha` from the review's `commit_id`) — omit the old delivery ID so BullMQ does not deduplicate it. Never fabricate a review or replay an event when a Respond-to-review run for that PR is already queued/running; verify the new run is dispatched afterward.
- **Don't assume a new agent-CLI harness has identical flag semantics to `claude`'s, even when a flag name matches.** Two CLIs can expose the same-named flag with different parsing behavior: `claude`'s `-p`/`--print` is a bare boolean (its position among other flags doesn't matter — the prompt is a separate positional argument), while Antigravity's `agy -p`/`--print`/`--prompt` is a *value* flag whose value is the prompt itself — a flag landing between `-p` and the prompt gets swallowed as the prompt instead of the real task, and the CLI still exits 0 having done nothing (confirmed live on a failed Implementation run; see the `SUBCOMMAND_ARGS`/`PRINT_FLAG` comment in `src/harness/agent-cli.ts`). The *process model* can differ too: `agy --print` runs the agent from its own scratch dir (`~/.gemini/antigravity-cli/scratch`), **not** the `cwd` SWARM spawns it with — so, unlike `claude`/`codex`, it can't see the task worktree by inheriting `cwd`. The harness therefore passes `--add-dir <worktree>` for Antigravity, and the phase prompt names the worktree's absolute path so all edits and hand-off files land where SWARM's delivery validation looks (issue #226; see the `addDirArgs` comment in `src/harness/agent-cli.ts`). Verify a new harness's actual argument-parsing behavior against its own `--help` and a real invocation — never infer it from Claude's shape.
- **`agy` does have structured output, and it is not Claude's** (issue #465 — earlier code and docs claimed it had none, which was true of 1.1.3 and stopped being true by 1.1.10). `agy --output-format text|json|stream-json` exists; SWARM asks for `stream-json` and reads normalized usage, the resumable `conversation_id`, and a terminal `status` from it. The matching flag name is where the resemblance ends: agy's records are `{"event":"init"|"step_update"|"result",…}`, it streams **deltas** (`text_delta`) rather than whole text blocks, it needs no `--verbose` (that is claude's requirement alone), and a *failed* run puts its detail in `result.error` while leaving `response` and `conversation_id` empty. Those shapes are modelled in `src/harness/antigravity-stream.ts` and were verified live, not inferred — which is exactly the standing rule above. Two consequences worth keeping in mind: the flag goes **before** `-p` (never between `-p` and the prompt), and it is passed only when `src/harness/antigravity-capabilities.ts` sees it declared in `agy --help`, so a worker on an older binary keeps the plain-text path instead of being handed an unknown flag.
- **`agy` also answers its own read-only slash commands in print mode** (1.1.11+, issue #670), which is the only reason the CLI Quotas page can show Antigravity a live allowance at all. `agy --output-format json -p "/quota"` (`/usage` is an alias) and `-p "/credits"` are answered from the CLI's own state — no agent turn, no tokens — and print a structured `command` block (`{"command":{"name":"usage","data":{"groups":[…]}}}`) alongside the ordinary print-mode envelope; the shapes are modelled in `src/harness/antigravity-quota.ts` and read by `queryAntigravityQuota` (`src/harness/quota-discovery.ts`). Both constraints above are load-bearing here and are what that code is shaped around: `--output-format` goes before `-p` with the slash command immediately after it, and which path a worker takes is decided by **observed capability**. A binary whose `--help` doesn't declare `--output-format` is never probed at all, while a newer build that answers without a `command` block can cost one probe before the worker records that it cannot serve print-mode commands and keeps the run-derived fallback thereafter. A probe that reports a command error or cannot run surfaces its detail to the operator. Note also that `remaining_fraction` is **remaining** while `QuotaWindow.usedPercent` is used, and that Antigravity reports two independent limit groups (Gemini, and Claude/GPT), each with its own weekly and 5-hour window — four windows that move independently, none of which may be collapsed into the others.
